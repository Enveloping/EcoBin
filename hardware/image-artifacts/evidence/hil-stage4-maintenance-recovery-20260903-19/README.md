上述真实流程共同覆盖。

通过 Windows 当前枚举的 CH340 串口 `COM8`，在已登录的普通 `orangepi` 账号下执行只读核验，
取得以下现场事实：

- 设备 Python 为 `3.11.2`；业务、通信代理和更新器当前链接分别指向
  `hardware-runtime-20260903-19`、`communication-20260903-19` 和 `updater-20260903-19`；
- 设备中的两份代理程序、两份状态存储实现、本机接口实现、助手预检和四个 systemd 单元的
  SHA-256 均与构建 v19 的受控源码一致；
- 正式运行目标、业务程序、蜂窝服务、远程支持、永久通信代理和设备更新器均在运行；出厂目标、
  热点、网页、DNS 和出厂测试服务均已停止；
- 通信代理以 `ecobin-communication`、更新器以 `ecobin-updater` 独立低权限身份运行，均无 Linux
  能力，启用了 `NoNewPrivileges`、私有设备、私有网络和严格只读系统保护；两个进程以及现有
  业务、蜂窝和远程支持服务从启动后均为 0 次自动重启；
- 通信代理明确保持 OneNet 所有权关闭，更新器没有第四阶段启用参数，业务环境没有第四阶段
  作业闸门参数，特权助手的变更能力仍固定关闭；
- 普通登录账号不属于任何设备本机接口组；连接通信、更新器、业务激活助手或 MCU 烧录助手的
  四个 Unix Socket 均被内核以 `EACCES` 拒绝，root 专用更新控制命令也明确返回
  `ROOT_REQUIRED`；
- 本启动助手预检以真实更新器身份返回 `PASS`，两个特权助手 Socket 正常监听，但没有任何助手
  执行实例；业务、通信代理、更新器和助手预检自正式运行以来均没有错误级日志；
- 接入服务第一次收到“后端仍在处理”的可重试结果，自动重试一次后成功安装并验证正式凭据；
  这不是残留失败。系统仅保留基础镜像的控制台字体和无可扫描硬盘的 SMART 自检两个无关失败
  单元，不影响 TF 卡、串口或 EcoBin 服务。

当前 `ecobin-hardware.service` 仍是旧业务程序并以 root 运行；未来业务程序低权限预检单元没有
在本轮主动执行。因而，真实投递和清运证明的是“v19 新增永久层与现有业务兼容”，不能替代未来
以 `ecobin-business` 身份运行后的完整投递、清运、UART、双摄像头和 COS 回归。

## 已知问题与剩余边界

本次冷启动中，Air780E 蜂窝链路很快获得地址和默认路由，但其 DNS 在约 10 分钟内无法解析后台
地址；服务期间明确显示蜂窝 DNS 不可用。系统随后自主恢复，可信校时完成，蜂窝状态连续四次
采样均为就绪，之后接入、封存、投递和清运正常完成。该现象不推翻本次功能通过结论，但必须作为
冷启动蜂窝 DNS 收敛较慢的可靠性问题保留，不能把本轮成功等同于长期运营商网络资格。

v19 至此通过“第四阶段默认关闭基础”的指定单卡真机验收。以下能力仍未启用或未验收：通信代理
接管 OneNet、设备更新器下载和执行远程业务包、更新期间停止新业务、业务数据库备份与回滚、
MCU 更新状态机及真实烧录、故障和断电注入、灰度发布控制面，以及未来业务程序低权限切换。
正式发布签名和量产信任策略也是独立门禁。因此本证据不能用于宣称远程更新已经可用或正式量产
已经放行。
