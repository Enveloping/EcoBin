# 第四阶段受控门禁与 MCU 维护交接基础证据

> 日期：2026-09-03  
> 结论：仓库实现和无硬件动作验证通过；生产启用、真实 UART 交接、MCU 烧录与断电恢复尚未验收  
> 代码边界：本证据与实现位于同一提交；它们完成于 v17 镜像构建之后，未进入 v17

## 1. 本轮完成了什么

永久设备更新器新增了三个仅允许 root 通过本机 Unix Socket 调用的操作：

1. 查询门禁、维护锁、未完成作业和物理动作的实际状态；
2. 携带唯一操作编号、现场证据 SHA-256 摘要和预期管理状态序号，受控激活第四阶段作业门；
3. 携带同样强度的操作身份和证据，立即施加只会收紧的人工安全锁。

更新器基础数据库版本仍为 3，新增表是旧版可忽略的兼容附加层。附加层单独持久化本次候选
启用周期是“需要激活”还是“已经激活”。候选关闭、旧版程序留下基础关闭状态、通用门禁迁移、
遗留任务收敛和上一周期激活命令重放都不能把该事实变成“已经激活”。只有 root 专用激活操作
可以在同一个 SQLite 事务内保存证据、更新激活事实并打开门。

业务程序本机控制层新增了可注入、默认关闭的 MCU 维护交接协议：只读观察、进入安全维护并
交出 UART、烧录后收回 UART 并验证。证据由控制器根据 MCU 维护状态查询、基础自检查询、
固件身份和 UART 所有权自行计算摘要，并绑定更新编号、交接编号、期望固件身份与助手烧录
回执。生产默认构造仍不注册这些操作。

第三阶段维护安装器的永久层卸载路径也补上了事实门禁。恢复旧业务服务前必须证明更新器库仍是
精确版本 3 + 附加层版本 1 的从未启用状态，且控制操作、所有状态的许可与物理动作、旧证据
隔离记录、维护锁和人工锁全部为空。在线预检通过后，安装器先关闭特权入口和更新器，再用新
快照复核；第二次通过前不会删除永久代码或恢复旧服务。每个 systemd 单元的启动意图会在调用
前持久化，只有日志能证明更新器从未尝试启动且数据库及全部 SQLite 边车文件均不存在时，
安装早期中断才允许按“尚未建库”清理。

维护安装器随后完成了安装与卸载事务的断电恢复收口。每个可产生副作用的步骤先持久化意图，
再执行文件发布、系统用户/目录创建、服务启动或删除；全局启动围栏和逐服务卸载围栏阻止
systemd 在中断窗口绕过恢复方向。固定原子临时文件、定位标记、记录目录和围栏均校验 root
所有权、精确权限、大小及内容归属。没有定位标记的孤立操作可按唯一记录恢复，多个操作、其他
载荷、未知目录项或不安全元数据一律拒绝。服务一旦可能启动，未完成审计的安装只能用同一载荷
向前收敛；完整审计后已经开始删除的卸载只能幂等续跑，不能重新执行已经删除配置对应的系统
命令。预检查和模拟执行均以整棵测试根文件树快照证明零写入。

## 2. 关键安全反例

自动化测试和独立复核覆盖了以下容易误开门的场景：

- 从未凭证激活时，先把受保护锁改写成普通失败原因，再请求通用开启；
- 已激活后关闭候选再开启，试图复用历史激活记录；
- 旧版版本 3 数据库遗留未开始许可或活动作业，收敛后自动恢复；
- 旧版更新器不认识附加表，只在基础表写回关闭状态，随后再前向启动；
- 重放上一启用周期完全相同的激活命令，试图用历史回执冒充当前成功；
- 激活已经更新基础门状态、但写证据或激活标记时注入失败；
- MCU 查询失败却携带成功字段、未知状态码、安全保留位、范围外重量或错误 UART 所有权；
- 相同交接正在执行时重复触发，以及服务停止与交接端口调用并发。
- 更新器库缺失、损坏、权限不符、基础表或索引漂移、附加层不完整以及出现未知未来扩展；
- 当前候选虽已重新关闭，但数据库留有历史激活操作、终态许可、已确认动作或任一维护/人工锁；
- 第一次卸载检查通过后，在停止入口期间才提交激活，以及激活只存在于尚未合并的 WAL 中；
- 更新器已经启动并写入安全事实后，后续安装步骤失败而进入自动回退。
- 原子记录或定位标记写到一半断电、定位标记尚未发布、留下空操作目录或多个孤立操作；
- `systemd-sysusers` 或 `systemd-tmpfiles` 只完成部分安全副作用后断电，以及部分状态被外部改成
  冲突身份或夹入未知目录内容；
- 服务启动围栏已经释放但首个服务尚未启动、某个服务启动失败、卸载围栏创建或删除中断；
- 卸载已删除系统用户/目录配置后断电、卸载受阻后由新进程重试、终态记录已落盘但定位标记
  尚未清理；
- 维护目录权限漂移、超大或外来临时文件、过期 MCU 当前启动事实，以及回滚后旧业务服务未恢复。

上述场景均保持失败关闭。未开始的遗留许可在新周期只可查询或弃置，`mayStart` 为 false；已经
实际开始的作业仍可按原身份完成安全收敛，但收敛后回到“需要激活并锁定”，不会接受新业务。

## 4. 旧版可读与永久层卸载边界

验证从 Git 当前父提交直接归档真实旧版 `hardware/updater_store.py`，没有用新代码模拟旧行为：

1. 新代码以默认关闭模式创建基础版本 3 与附加表；
2. 真实旧代码成功打开同一数据库并写入默认关闭姿态；
3. 新代码再以前向候选模式打开时，识别旧版写入的基础关闭事实；
4. 最终状态为“需要激活、门已锁定、等待凭证”，而不是沿用旧激活。

结果：

```text
LEGACY_V3_READ=PASS
FORWARD_REENABLE_LOCK=PASS
```

这只证明尚未真实启用第四阶段时，旧版默认关闭程序仍可读取数据库。产生第四阶段活动作业、
维护锁或物理动作事实以后，不允许回退到不理解这些语义的旧程序。

“旧版能打开数据库”和“可以卸载永久设备管理层”不是同一结论。当前卸载门禁进一步要求库中
连历史控制操作、已结束许可和已确认动作都不存在；设备曾经受控激活后，即使后来再次关闭
候选并恢复默认锁定投影，也不能恢复旧服务。数据库在线时先检查包含 WAL 的一致快照，关闭
写入口后再检查一次；测试确认两次检查之间新提交的激活事实会保留永久代码和维护 marker，
不会启动旧业务。

## 5. 当前香橙派 COM3 影子验收

通过 COM3 把同一份源码压缩包按 19 段传到当前 v13 香橙派，设备先核对压缩包 SHA-256，再以
普通 `orangepi` 用户在其家目录的全新临时目录运行。测试未停止或修改生产服务，未打开业务
数据库、OneNet、UART、摄像头或特权助手，也未重启设备。

现场事实：

```text
uid=1000
Python 3.11.2
result=PASS
communication schemaVersion=2, lifecycleRuns=2
communication onenetOwnership=DISABLED
communication remoteUpdateRouting=DISABLED
updater schemaVersion=3, lifecycleRuns=2
updater candidateActivationState=REQUIRED
updater jobGateMode=DISABLED, jobGateState=LOCKED
updater privilegedHelperMutationEnabled=false
START_BUSINESS_UPDATE=FEATURE_DISABLED
START_MCU_UPDATE=FEATURE_DISABLED
CANCEL_UPDATE=FEATURE_DISABLED
RENEW_DOWNLOAD_AUTHORIZATION=FEATURE_DISABLED
两份数据库权限=0600，SQLite integrity_check=ok
```

测试结束后，设备和电脑上的影子源码、状态库、Socket 与传输文件均已删除。当前串口登录用户
没有非交互 sudo，因此没有在这台已运行设备上切换 root 候选参数或执行激活；真实 UID 0/非
root 权限隔离由 Linux 自动化测试覆盖，生产设备仍保持原来的默认关闭服务。

## 6. 尚未完成，不能据此开放

- 本轮代码尚未进入新的签名运行时或整机镜像，v17 不包含它；
- 当前业务 `main.py` 和 systemd 尚未接入永久门禁或 MCU 交接端口；
- 人工安全锁和维护锁的带证据释放操作尚未实现；
- 永久更新器尚无 MCU 更新持久状态机、目标/回滚固件槽和断电恢复编排；
- 业务激活助手与 MCU 烧录助手的变更操作仍固定返回“功能未启用”；
- OneNet 连接仍由旧业务程序持有，通信代理不接收远程更新命令；
- v17 仍未写卡、完整回读或冷启动，当前 v13 也未做整机暖重启；
- 尚未完成低权限投递、清运、照片、COS、真实 UART 交接、目标烧录、失败回滚和断电故障注入。

因此本证据只允许继续下一段默认关闭的实现，不允许把生产参数改为启用，也不表示香橙派业务
程序远程更新已经可以使用。
