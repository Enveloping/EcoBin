# v8 运行目标成员自动恢复证据（2026-08-30）

## 结论

指定单卡本次冷启动暴露并关闭了一个首次启动竞态：`ecobin-runtime.target`（正式运行
目标）已经是 `active`，但目标启动期间因瞬时门禁失败而被 systemd 跳过的
`ecobin-hardware.service` 不会被旧协调器再次启动，导致 Air780E 的 RNDIS 网卡、地址、
默认路由和蜂窝上行均正常，OneNet/MQTT 仍长期离线。

提交 `fbc6c471` 修改首次启动协调器：首次仍只启动运行目标；运行目标已经 active 后，
每轮显式核对硬件网关和独立远程维护代理，只补启动 inactive 成员，不重复启动正常成员。
完整设备侧回归为 `994 passed, 46 skipped, 5 subtests passed`。

## 故障事实

- 香橙派本轮于 `2026-08-30T02:31Z` 左右启动。
- 运行门禁于 `02:31:22Z` 首次失败，`02:31:55Z` 重试通过。
- 硬件服务于 `02:32:02Z` 再次执行门禁时被 `exec-condition` 跳过；主进程从未启动，
  `NRestarts=0`。
- `ecobin-runtime.target` 同时进入 active，旧协调器随后因目标 active 而跳过整个启动动作。
- Air780E 仍被识别为 USB `19d1:0001`；RNDIS 接口 carrier 为 1，取得
  `192.168.10.2/24`，默认路由为 `192.168.10.1`，存在双向收发流量。
- root 权限重新采集的系统准备、验收报告、蜂窝上行、可信时间、注册、交接、封存和封存
  清理事实全部有效，证明恢复时门禁已经开放。

现场先手动启动硬件服务恢复业务。服务于 `03:04:24Z` 进入 active，完成 UART 自检、MQTT
订阅和运行快照上报；后端于 `03:04:24.152Z` 收敛为 ONLINE，并接受边缘事件 12962、
12963。该动作只恢复当前连接，不作为永久修复证据。

## 修复与现场验证

4. 后端于 `03:10:56.630Z` 收敛为 ONLINE，并将事件 12964、12965 作为可信运行快照；
5. 最新可信序列为 1686，新增隔离消息为 0，设备业务占用为 0。

验证结束时，首次启动协调器、运行目标、硬件网关和远程维护代理全部 active；硬件网关
