# v33 业务程序更新恢复加固镜像证据

## 结论

2026-09-08 已从提交 `1b89b7451c7aee413be219371415ef55ea63a3a4` 构建 v33
无秘密候选镜像和受控单卡 HIL（硬件在环测试）镜像。该版本把 v32 真机发现并修复的两项问题
固化进可重复镜像：

- 通信代理或设备更新器单独重启时，不再由 systemd 反向停止正在运行的业务程序；
- 成功、已回滚、已延期和已拒绝的更新会安全清理下载与解压临时目录，更新器重启后会补做中断
  的清理；失败且设备保持安全锁的任务继续保留诊断材料。

修复进入镜像前已在 v32 真机完成分别重启、整机重启、更新后真实投递和真实清运复核。v33
候选和 HIL 镜像随后通过磁盘布局、文件系统、源码一致性、正式验签公钥、私有 COS 下载边界、
最低权限及永久程序边界审计。生产后端厂家验收认可列表已在保留 v31、v32 的同时追加 v33，
业务程序远程下发总开关继续为关闭。

2026-09-08 又对 HIL 镜像做了只读 ARM64 用户空间虚拟验证：直接运行镜像内已经安装的
Python、通信代理、设备更新器和出厂业务桥接程序，并使用临时数据库验证更新制品清理及更新器
重启补偿。相关检查全部通过，且验证后的镜像摘要未改变。

v33 尚未写入 TF 卡，因此不能把上述构建、离线审计和用户空间虚拟验证等同于 v33 自身的
引导程序与内核冷启动、热点验收、投递、清运或远程更新真机通过。

## 只读 ARM64 用户空间虚拟验证

验证机没有 Allwinner H618（香橙派 Zero 3 所用芯片）的完整虚拟主板。QEMU 当前公开支持的
[Orange Pi 机型](https://www.qemu.org/docs/master/system/arm/orangepi.html)是使用 H3 芯片和
32 位 Cortex-A7 处理器的 Orange Pi PC；QEMU 的
[Arm 开发板说明](https://www.qemu.org/docs/master/system/target-arm.html)也明确指出，为未支持
开发板构建的镜像通常不能直接在其他虚拟开发板上启动。因此本轮没有把 v33 原始镜像伪装成
另一块主板，也没有把这种结果表述为整机启动通过。

本轮采用 QEMU 用户态 ARM64 指令模拟：以 `ro,noload,nodev,nosuid` 只读方式挂载 HIL 镜像
的 ext4 根分区，再由无网络、只读容器直接执行镜像内文件。测试写入只允许落到单独的临时目录，
镜像和工作区源码均不是执行时的可写数据源。结果如下：

- 镜像内 `/usr/bin/python3.11` 实际执行成功，版本为 Python 3.11.2；
- 镜像内永久更新器的协调器、下载器、状态库和入口模块导入通过；
- 镜像内永久通信代理的代理进程、路由和状态库模块导入通过；
- 洁净镜像首次启动前尚未生成 `/opt/ecobin/business/current`，按设计改由镜像内固定的
  `hardware-runtime-20260907-33` 出厂业务桥接环境完成导入，结果通过；
- 使用镜像内更新器及临时 SQLite 数据库，验证最终成功任务只清理自己的下载树，且无关文件
  保留；
- 正在执行的任务和“失败后锁定设备”的任务均拒绝清理，诊断材料保留；
- 下载文件存在硬链接时拒绝清理，避免越界删除；
- 人为令第一次暂存目录清理失败后，新建协调器模拟更新器重启，能够再次发现同一最终任务并
  完成补偿清理，任务的“已拒绝”最终状态不被篡改；
- 两轮虚拟验证退出后均无容器、挂载点或 loop 映射残留，重新核对 HIL 镜像 SHA-256 仍为
  `289f1b45a32cb90d09183b22a4bd30103cd9c749f3b36d8756dabb686c4c914c`。

该方法能够证明镜像里实际装入的 ARM64 程序可解释执行、关键模块及 SQLite 状态持久化可用，并
覆盖 v33 新增的清理与重启补偿逻辑。它不能模拟 U-Boot、H618 厂商内核、真实 systemd 启动
时序、GPIO、UART、摄像头、MCU、蜂窝网络、DNS、OneNet 或 COS，也不能证明断电恢复和真实
投递、清运。因此下方真机门禁保持不变。
