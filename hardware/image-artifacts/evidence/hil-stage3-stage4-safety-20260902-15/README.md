平台为 `linux/arm64`，再次运行正式输入校验后才开始组装。源码、载荷、基础镜像、构建器身份及
产物验证规则均未放宽；仅跳过了对同一已存在镜像的非确定性远端查询。

## v13 在线影子测试（不计入真机门禁）

由于指定 TF 卡当时仍装在运行中的设备内，2026-09-02 通过 COM3 调试控制台，在当前 v13
设备上补做了一次不需要 root 的在线影子测试。测试没有覆盖或切换
`/opt/ecobin/hardware/current`，而是把提交 `8fc355016605e615afb252fcb37a0c60dbed1d41`
中的通信代理、更新器及其本机接口/存储代码复制到普通用户专用目录。最终复核归档为 `35107`
字节，SHA-256 为
`0303a99238551d278fe9bdf77e31d9c80fee6374a90e888fb85aabea50418af1`；设备端先校验完整摘要，
再解包运行 [`stage3_shadow_probe.py`](../../../tools/stage3_shadow_probe.py)。结构化执行结果见
[`shadow-probe-result.json`](shadow-probe-result.json)。

影子进程以 `orangepi` 普通用户（UID 1000）和设备自带 Python 3.11.2 运行，所有数据库和
Unix Socket 都位于 `/home/orangepi` 下的专用测试目录。结果如下：

- 通信代理数据库初始化为 schema 2；同一探针进程内连续两轮重新实例化、启动和停止均返回
  健康，并产生两个不同的运行实例身份；OneNet 所有权和远程更新路由均保持关闭；
- 更新器数据库初始化为 schema 3；同一探针进程内连续两轮重新实例化、启动和停止均返回
  健康，第四阶段候选、业务程序更新、MCU 固件更新和特权助手变更能力均保持关闭；
- `START_BUSINESS_UPDATE`、`START_MCU_UPDATE`、`CANCEL_UPDATE` 和
  `RENEW_DOWNLOAD_AUTHORIZATION` 四种更新请求全部返回 `FEATURE_DISABLED`；
- 两个私有数据库权限均为 `0600`，测试后 SQLite 完整性检查均返回 `ok`；临时进程和
  Socket 均已退出或移除；
- 另以 Python 优化模式执行负例，探针在创建测试目录前即拒绝运行，避免优化参数跳过检查；
- 探针外部的 COM3 只读检查确认，现有 `ecobin-hardware.service` 测试前后均为 PID 1721、
  `active/running`、重启计数 0；
  `/opt/ecobin/communication/current` 与 `/opt/ecobin/updater/current` 仍不存在，设备镜像
  身份仍是 `0.1.0-single-card.20260831.13`。

这份证据只证明两项永久组件的纯 Python 代码能在目标 ARM64/Python 3.11 环境中初始化、
通过本机接口响应、保持危险能力关闭，并在同一探针进程内完成第二轮生命周期。测试没有把
组件作为独立 OS 进程或 systemd 服务启动，且两者使用同一个普通用户；它也没有接触真实
OneNet、UART、摄像头、业务数据库、设备凭据或特权助手，因此不能
证明三个最终低权限身份、对端身份校验、systemd 沙箱、真实硬件权限或 v15 冷启动正确，不能
用于关闭下述真机门禁。
