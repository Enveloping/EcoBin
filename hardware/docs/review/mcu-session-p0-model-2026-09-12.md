## 1. 本轮核查确认的旧实现缺口

1. `uart_link.py` 新对象的发送序号从 0 开始，但 `main.py` 保留原 Pi 启动身份；
   `_ack_matches()` 只比对双方启动身份、传输序号和消息类型。因此 Pi 单独重启、MCU 未重启时，
   旧 ACK（确认回复）可能匹配新命令。**不能把本轮模型通过说成此生产缺口已修复。**
2. `UartLink._send_and_wait_ack()` 默认最多发送三次；当前命令还不带目标 MCU 启动编号。
   新握手不能沿用这个自动重发器。
3. 当前 Registry 要求 HELLO 启动编号非零，并明确未包含 `targetMcuBootId`；
   不能只改 Python 就声称支持新启动语义。
4. 正常关键事件经 `main.py` → `EdgeStore.receive_mcu_frame()` 提交 SQLite 后才 ACK，这一机制可复用。
   但旧快照收集对不属于当前查询的分段存在直接 ACK 后丢弃的例外；新协议须区分可丢查询响应、
   分片接收确认和完整结果保存确认。
5. 旧收件唯一键包含 Pi 接收代次，允许同一 MCU 编号在不同接收代次出现不同内容；
   旧 `edge_boot.py` 也会在核实 MCU 是否重启前中止旧工作。新路径必须改这两个假设，保留固定帧旧路径的显式版本边界。

## 2. 启动绑定：保留 Pi 分配，不增加 MCU Flash 或随机正式编号

`probeId` 是“本次只读询问的编号”，不是 MCU 启动编号。候选步骤：

1. Pi 在 SQLite 事务中消耗一个从未使用过的 `probeId`，提交成功后才允许尝试发送一次询问。
   写入失败、结果未知、回复超时或 Pi 重启，下一次都使用新询问编号；不重发原询问。
2. MCU 未绑定时，RAM 保存本次询问编号，回复启动编号 0；已经绑定则只回复原启动编号，不覆盖它。
3. Pi 只接受当前仍在等待的询问回复。看到 0，先持久消耗一个新的非零正式 `mcuBootId`，
   再尝试发送一次引用该 `probeId` 的绑定请求。重复的 0 回复不重复分配。
4. MCU 仅在自身仍为 0、RAM 中保存的待绑定询问精确匹配时接收绑定；成功后清理待绑定询问。
   MCU 重启清空这些 RAM 状态，因此“询问已回复、绑定到达前重启”会拒绝孤立旧绑定。
5. 绑定是否收到不明时，Pi 发新的只读询问核对；不是重新下发旧绑定。
   如果 MCU 继续运行，读回原非零编号；如果仍为 0，消耗新编号开始新的绑定尝试。

Pi 单独重启只丢弃旧的握手等待状态，持久分配器不回退；不会为仍在运行的 MCU 换号。
绑定只建立关联，不关闭原业务、不清空结果、不释放永久账本，也不自动开门。
重复看到 0 不代表已证明发生了多次业务数据丢失；原业务如何归档仍由后续恢复模块按事实裁定。

### 前提与反例

必须满足：

- 单一串口所有者；校验后的完整请求不被底层复制或重新交付。可以丢失、延迟，缓冲可以跨端点重启保留。
- Pi 的询问/绑定请求各最多尝试写入一次，不交给通用可靠重发队列；发生部分写入也不补发整帧。
- Pi 持久分配状态不回退、不清空，不从过期备份恢复后继续使用原会话；计数耗尽明确失败，不回绕。
- MCU 未绑定时不受理业务动作；业务命令在语义校验后仍必须核对目标启动身份。

这是适用于计划中直连 UART 的候选传输约束，**不是声称现用发送器已满足**。
接入 P3 时要用真实串口适配器/伪串口测试证明这些约束，并检查解析器不会重复交付同一请求。
若以后换成会重放报文的桥接链路，本模型不能直接沿用；需要重新设计新鲜度依据。

保留了一个故意失败前提的反例：复制并重放整对旧询问和旧绑定，RAM 归零的 MCU 确实可能再次接收旧编号。
因此不是“任意重放也绝对安全”，更不能只写“清空串口就安全”。模型不依赖清空缓冲或猜测等待几秒。

另一个必须分开的事实：旧 MCU 回复已生成，MCU 随即重启，而回复这时才到 Pi，
Pi 仍可能暂时观察到旧编号。任何有限次握手都不能证明回复到达瞬间 MCU 没有再次重启。
解决方式是每条动作带 `targetMcuBootId`：MCU 为 0 或编号不符时直接拒绝，绝不执行旧开门。

### 有界枚举结果

枚举最多 3 个询问、2 次 MCU 重启、1 次 Pi 重启，以及请求/回复的丢失、任意延迟和乱序；
甚至允许比直连 FIFO 串口更强的乱序，但不复制完整请求。
共探索 **7,716 个状态**，其中 **2,514 个包含成功绑定历史**，未出现：

- 在另一 MCU 启动中消费前一启动的待绑定询问；
- 同一已使用正式 MCU 编号在第二次启动重新绑定。

枚举器的 MCU 实际启动次数只用于测试断言，**不传给模型 MCU，也不是新增 MCU 随机数或硬件输入**。
枚举使用不可回退计数器抽象 Pi 持久化；下面的 SQLite 强退是另一组测试，不能合称真实串口端到端枚举。

## 3. 命令编号与拒旧规则

候选有序身份是 `(targetMcuBootId, commandSequence)`；原 `mcuCommandUid` 和内容摘要仍保留、不可变。
Pi 后续必须持久保存它们之间的一一映射，不得给同一原命令换序号/UID 再当新动作。
模型不替代这一真实 EdgeStore 映射，也不把模型内的示例 UID 当合法线上 UUID。

MCU 在 RAM 中保存已处理最高序号和最近一份受理/拒绝详情：

| 收到的命令 | 模型结果 |
|---|---|
| 自身编号为 0，或目标启动编号不符 | 拒绝，不动作，不消耗当前启动的命令序号 |
| 序号为 0 或超出 32 位范围 | 拒绝，不回绕 |
| 等于最近序号且 UID/摘要相同 | 返回原受理或拒绝结果，不再动作 |
| 等于最近序号但 UID/摘要不同 | 身份冲突，拒绝 |
| 小于等于水位，但详情已不在缓存 | 明确“旧详情不可取”，不动作，不说“从未执行” |
| 大于水位 | 允许跳过未发送的预留号；先固定本命令受理/拒绝决定，再按该决定动作；较小序号永久退休 |

跳号是为了允许“编号已预留、还没进入可能发送阶段就退出”的无副作用空洞，不要求补发旧开门填号。
**它不是跳过未知业务的方法**：原命令已登记为可能下发（`ARMED`）且结果不明时，
Pi 仍保留占用、查询原工作，不能根据水位或查不到详情直接释放/归档。
正常副作用命令保持单个在途；故意再次清运开锁是同一操作中的新动作编号，不能当成旧请求重试。

业务前置条件拒绝也消耗该命令序号；之后条件变好，重复原命令仍返回原拒绝，不突然执行。
只缓存最新详情不是永久保留全部拒绝原因；历史证据由 Pi 负责保存。
结果清理不能重置命令水位。序号耗尽不擅自改启动编号或重启正在工作的 MCU。

新命令确认必须精确引用目标启动、命令序号、UID、内容摘要；传输序号只负责传输关联。
这才能消除“Pi 重启后旧 ACK 匹配新内容”，不能只依赖当前 `_ack_matches()` 的四项键。

## 4. 完整结果与保存确认

模型完整结果身份为 `(mcuBootId, resultSequence, workUid, resultDigest)`，原结果正文冻结。
同一启动/结果序号的不同工作或不同内容始终冲突，不因 Pi 新建接收代次而重新接纳。

结果集合模型先检查精确身份、分段序号、完整数量、完整字节数和整体 SHA-256；
重复同段同内容可接收，缺段、串入另一份结果、同段不同内容或总摘要错误均不能产出完整结果。
当前模型边界是最多 4 段、合计 1024 字节，**仅为有限模型边界，不是已冻结线上布局或已证明 MCU 内存够用**。
模型正文是完整性测试用字节，不验证重量、照片等业务必需字段；正式载荷仍需 Registry/Schema 语义校验。

Pi 取得完整合法结果后，在一个 SQLite 事务里保存原结果和待上报项，提交后才产生“完整结果已保存”确认。
MCU 仅收到精确身份的该确认后释放结果正文；普通传输 ACK、单个分段 ACK 和空确认不能替代。
确认迟到不能清理下一份结果；确认重复可回复已交接，但不影响当前工作。
MCU 释放正文不等于 Pi 立即接单，清运仍须等待后端对新袋/新基准的实际应用确认。

使用隔离 SQLite（WAL + `synchronous=FULL`）和真实子进程 `os._exit(17)` 验证：

- 编号事务提交前退出：未返回编号、未允许发送，可重新预留未使用号；提交后退出：该号已消耗，重开后不复用。
- 结果事务提交前退出：结果和待上报都不存在；提交后、保存确认前退出：两者都存在，重开后补交同一确认。
- 上报待办写入触发真实 SQLite 错误：整个事务回滚，没有半份保存事实，MCU 继续持有结果。
- 重复保存相同结果只保留一个待上报项；同身份不同内容保持冲突，不覆盖原结果。

这证明模型的本地数据库事务/进程退出边界，不替代 TF 卡物理掉电、真实 EdgeStore 迁移、云端去重或资金测试。
没有在模型中建立订单、钱包或自动提现，也没有实现未确认的“异常归档后迟到完整结果”资金取舍。

## 5. 兼容性判定和下一批机器契约入口

新方案改变启动编号分配、动作目标身份、确认匹配及结果释放语义；现有规范 UART 1.0 不能静默承载。
**需要主版本升级，下一版按原生 UART 2.0 设计**；这与旧固定帧文档名称中的 v2 不是同一协议。
本轮没有修改 `registryVersion` 或发布新版本，P1 才从唯一机器来源生成编码及校验。

字段预算建议（仅身份部分，不是已冻结完整消息长度）：

| 职责 | 身份字段与编码预算 |
|---|---|
| 新鲜只读询问 | `probeId: u64`，8 字节；版本、能力等继续按契约补齐 |
| 启动绑定请求 | `probeId: u64 + proposedMcuBootId: u64`，16 字节 |
| 原命令身份 | 现有 UID 16 + 摘要 32，加目标启动 8 + 有序编号 4，共 60 字节 |
| 命令决定回复 | 上述精确身份 60，加决定 1 / 原因 2，至少 63 字节 |
| 完整结果保存确认 | 启动 8 + 结果序号 4 + 工作 UID 16 + 总摘要 32，共 60 字节 |

启动/询问计数上限沿用可精确表达的 53 位正整数范围，有序命令为 32 位正整数；
不复用帧头会回绕的 `txSequence` 作为这些持久身份。

当前生成布局有 39 类消息，最大载荷允许 242 字节；现有 `CONFIG_PORT_BLOCK` 为 190，
`STATE_SNAPSHOT_BEGIN` 已为 229，只剩 13 字节。不能把所有新增结果身份机械附到每一帧；
必须完成逐消息字段表和集合布局，再重新计算生成物与 MCU RAM/栈/队列。
P0 的身份子项已取得条件性模型证据，但整个 P0 尚未完成，不能跳过载荷预算直接宣称 P1 已就绪。

   新身份、单次发送策略、完整结果确认、查询与关键结果的区别；同步新门事实/称重方式。
2. `hardware/uart_link.py` 与新会话协调逻辑：独立的单次握手发送路径、精确决定回复、目标启动检查；
