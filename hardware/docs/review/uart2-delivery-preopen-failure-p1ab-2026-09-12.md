# P1AB：首次开门前称重失败的本地最终交接

日期：2026-09-12。继续已授权计划，只使用实际 MCU C、模拟硬件边界、Python3.11 和临时
SQLite；未连接设备、操作 GPIO/HMI、部署或烧录。P3 仍未整体完成。

## 行为和业务效果

香橙派发起投递准备后，MCU 首次称重满 5 秒仍没有足够的新鲜合法样本，会保留原测量失败
记录。MCU 不开门，也不把缺值当成 0 克。即使香橙派长时间没有保存成功，原业务仍在进行，
不会丢掉记录或自动重新测量。

香橙派把这份过程记录按原业务、步骤、配置、启动编号、事件编号和原文摘要提交 SQLite，
再发送精确保存确认。MCU 核对成功后，现在会形成不可变的 `WORK_RESULT` 最终结果：

- `finishReason=FAILED`：本次失败，不冒充正常投递完成。
- `deliveryRoundCount=0`：没有执行第一轮开门；本路径也不生成机械动作记录。
- 首重 `UNAVAILABLE`：真实尝试过但不可用，保留测量编号、原始时间、样本数量和失败原因。
- 末重 `NOT_TAKEN`：尚未采集，不能拿前一笔业务的末重、轮数或重量下降异常填入。
- 不声称物理关门已确认；保存延迟不刷新实际失败时间。

结果沿既有 Pi 交接通道，同一事务保存原文及待分类任务后，才发送最终结果保存确认。
确认丢失或 Pi 重启只查询/确认原结果，不重新开门或采样。MCU 交出结果不等于 Pi 放行业务：
**本批始终保留 Pi 原业务占用，任务仍为 `PENDING_CLASSIFICATION`，没有云端或资金效果。**
向后端选择正常/系统异常/重启丢失三类结果、故障恢复及恢复接单仍由后续 P4/P5 实施。
这不是已部署“手动异常隔离”的替代入口，也不是所有失败已能自动恢复。

清运的开锁前称重失败仍交由清运执行模块处理，不会被投递执行器误组装为最终投递结果。
有合法均值或中位数的首重继续原首次授权流程，不被本路径误判为失败。

## 代码范围

- `hardware_mcu/USER/mcu_delivery_execution.c/.h`：首次失败的最终组装；只使用本次准备对象，
  不依赖上一笔执行器残留轮次；检查当前业务身份、阶段、时间、测量退休和精确交接。
- `mcu_opening_gate.c/.h`：把既有初始数据精确保存核对提取为共同接口；接口本身也要求
  原过程槽已释放。它只证明保存，不证明可用重量、动作许可或安全门位。
- `hardware/tests/test_mcu_delivery_preopen_failure.py`：实际 C / Pi / SQLite 联合测试。
- Registry 仍为 `2.0.0-rc.14`，schema25 不变；无新消息或迁移，无生成物手改。
  正常 main/HMI 仍未接入新协议，旧运行制品保持冻结。

## 既有 Windows SQLite 强杀恢复异常

P1AA 的 1546 / `SQLITE_IOERR_TRUNCATE` 尚未修复；P1V 已经独立重复复现。
按 diagnose 技能继续，当前排序及可证伪预测为：

1. 强杀后映射释放滞后：应捕获映射占用相关底层错误，控制延迟应改变复现概率。
2. 外部进程临时占用：应出现共享/访问冲突证据；未关闭安全软件或假定其是原因。
3. SQLite Windows 文件处理：去掉业务表的最小 SQLite 程序仍可复现。
4. 应用连接生命周期竞争：仅应用场景复现，最小 SQLite 路径不复现。

本批仅补测试诊断：`hardware/tests/sqlite_failure_evidence.py` 在恢复失败的异常处理内、
进程退出/失败连接回收前，复制合成测试库 DB/WAL/SHM，保存复制前后尺寸、副本 SHA-256、
SQLite/Python 版本及错误码。文件缺失、复制/目录/清单写失败都留显式记录，不覆盖原异常。
副本是**错误之后的顺序观察**，不是原子快照，也不是错误之前的数据库；尺寸不变不能证明
没有同时发生同长度写入。取证不重开原库、不触发 checkpoint、不重试、不降级日志模式。

新增 5 项确定性诊断测试覆盖完整副本/原文件不变、缺失 WAL、目录/复制/清单写失败；
连同强杀恢复和目标链接的组合为 **7 passed / 4.34 秒**。合成错误只验证取证工具，
不冒充真实 1546 的复现，更不代表根因已确定或修复。

本批沿原 pytest 入口、每次启动独立进程重复原强杀恢复测试 **100 次，全部通过**。
没有重试同一次失败、跳过、改生产连接或降级 WAL；未发生真实错误，因而本批没有新的
真实失败三文件归档或底层 Windows 错误日志。不能用 100 次通过覆盖 P1V/P1AA 的失败证据。
后续若再次复现，测试会在原异常退出前把副本放在该次临时目录的 `failure-evidence/`，
并在原异常链打印清单；仍需核对底层错误，不能把顺序副本当成恢复成功证明。
