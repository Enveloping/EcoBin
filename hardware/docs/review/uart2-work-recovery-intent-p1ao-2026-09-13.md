# P1AO：原完整结果优先与持久恢复意图

日期：2026-09-13。承接 [P1AN 真实启动证据](uart2-boot-observation-p1an-2026-09-13.md) 和
[P1AM 受限恢复关门许可](uart2-recovery-close-permit-p1am-2026-09-13.md)。
这是批准计划 P4 的本地增量，不是整套异常恢复完成，也不是上线记录。

## 本批结果与业务边界

新增 `hardware/work_recovery.py`，由调用方提供原作业许可、原 START 指令和当前启动观察。
香橙派先核对原业务占用，再在一个业务 SQLite 写事务中检查已经保存的完整结果：

- 原完整 `WORK_RESULT` 存在且身份、正文、摘要和待分类任务一致时，返回原结果处理入口。
  MCU 后来重启不推翻它；完整的 `FAILED` 结果也属于完整结果，不能重新归类成重启丢数据。
- 没有完整结果，但本次有效握手证明 MCU 已进入更晚的启动周期时，保存唯一的本地恢复意图，
  即“这笔原业务需要继续核对”的持久记录，并冻结当时已保存的相关指令与过程原文。
- Pi 单独重启、无回复、观察过期、仅看到零启动号，或仍为原 MCU 周期，不生成上述记录。
  未尝试发送的 START 与明确被拒绝的 START 单独返回，不冒充用户已经投递或机械已经动作。

**没有完整结果包，不等于必要业务数据已经丢失。** 例如首重、末重和结束选择可能已经逐条
保存到香橙派，只是 MCU 在交付最终结果包之前重启。因此本批记录使用中性原因
`MCU_RESTART_RESULT_UNAVAILABLE`（单片机重启、完整结果暂缺），并明确
`dataLossClassified=false`（尚未判定必要数据丢失）。不能直接把它改名为 P1AM 所需的
`MCU_RESTART_DATA_LOSS`，再据此取得关门许可或提交问题归档。

本批评估器不写串口、不调用永久更新器、不发布云端事件、不创建订单、不改变余额或提现，
也不清除原业务占用。下一笔业务仍受原有占用和永久账本限制；这是候选尚未接完的状态，
不是决定这些场景最终都需要人工解锁。清运的原人员、袋预留等上下文保持原样，不伪造新的
人工关门确认。此前已被真实证据确认的首轮动作仍为 `CONFIRMED`，不会为了恢复改回未知。

## 存储与串行裁定

业务数据库由 schema29 前向增加到 **schema30**；永久账本仍为 schema3。

`native_work_recovery_intent` 保存稳定恢复编号、原作业/START、新启动周期及有界的证据核心。
每个“作业 + 新启动周期”最多一条；同周期重试复用原记录，之后再重启另加历史，不覆盖前条。
`native_work_recovery_fact` 按稳定序号逐条保存原始字节及其保存回执关系，支持游标分页。
证据核心记录原许可、原 START、首次动作绑定、第一份有效启动原文、事实数量和整体摘要。
不把全部事实拼成一个无界 JSON 字段，也不保存可用于发送动作的临时令牌。

复制范围是原业务、原 MCU 周期的已知原生指令及观察、重量、执行器、投递选择、清运意图和
清运完成确认主记录。照片及其他业务上下文仍在原存储中，不宣称此处复制了“全部设备数据”。
有冲突的过程记录不能被重新认可；原冲突记录仍留在原库，评估报错并保留占用。
复制前调用原有保管校验器，核对原摘要、身份、冲突与精确回执，再计算新快照摘要；不能把
损坏原文重新哈希后当成可信证据。缺失的末重不会补为零，也不会凭开锁通断推断门位。

评估与 `save_native_mcu_result` 共享业务库的写事务串行边界：

1. 完整结果先保存：评估返回原完整结果，不新建恢复意图。
2. 恢复意图先保存、尚未问题归档：之后保存的合法完整结果在下次评估中优先；原意图仍保留
   “当时尚无完整结果”的历史，不覆盖或删除。
3. 两个连接并发评估：同一业务和启动周期只提交一份不可变意图。
4. 写意图、写事实或提交失败：整份新意图回滚；原指令、结果和占用不被清除。

查完整结果时同时检查投影字段和正文中的原业务/START 身份，防止损坏的 `work_uid` 投影
把已保存结果藏起来。存在正文矛盾、身份冲突或缺少原待分类任务时明确报错，不转成“没有结果”。
当前完整结果入口只接受 `PENDING_CLASSIFICATION`，后续分类状态的幂等衔接仍须接入。

创建意图前后均复核当前新鲜启动观察，事务中观察过期则回滚；历史数据库记录本身不证明
MCU 现在在线。提交后读取历史意图不要求设备在线，但会重查证据核心、原 START、首次动作
绑定、启动见证和冻结事实摘要。Pi 重启时也检查缺失事实与孤立行。这里证明的是指定存储
完整性边界，不宣称可以发现两张表同时被删除等任意破坏。

迁移仍保留原业务、启动、指令和结果；旧 schema29 不补造历史恢复意图。迁移 DDL 和版本
标记在原事务内提交，失败后原结构和数据保留。相应旧库测试同步到版本30；重建 schema18
的测试只补删两张候选表，原“没有任何原生表”的前置断言及恢复检查继续保留。

## 继续实施与发布限制

下一步仍需判断“必要业务数据是否缺失”，区分完整结果包暂缺与原首末重量/结束事实已经
保管完整，不能提前把后者归入零业务价值的数据丢失。实际问题归档与永久账本衔接还未实现；
P1AM 对原首轮动作仍未知的受限许可也尚未覆盖原动作已确认、反复重启等全部恢复情形。

随后接新 `SAFE_CLOSE`（仅投递门的受限关门）的实际 C 执行、原始反馈交接及本地恢复条件。
清运继续保留原操作/人员/袋预留，需要本次恢复的新测量与人工确认，不套用投递门执行器。
正常 `main` 自动发现占用、恢复调度、分类、云端接收、HMI 和热点验收仍须接通。
已经问题归档后又收到完整结果的资金处理仍是批准计划中的待确认项；本批只覆盖归档前竞态。

UART 仍为 **2.0.0-rc.20 / CLEAN_INTERRUPTION_CUSTODY_NOT_RUNNABLE**。本批没有改 MCU C、
协议布局或生成物，也没有新固件及 ROM/RAM 结论。发布声明仍为 schema25；包括新
`work_recovery.py` 和此前 `mcu_action_evidence.py` 在内的业务模块清单、永久层配套、后端认可
须在 P7 成对对齐，不能直接导出或远程推送当前候选。本批未部署、烧录、修改 HMI、
连接真实 UART/GPIO、操作设备或写云端数据；复用本机现有工具环境，没有重新下载依赖。
