| MCU firmware version | `1.0.0-hil.3` |
| MCU/Edge capability bitmap | `0x300` |
| 投口数 | `1` |
| MCU boot ID | `8837901547942448` |
| 配置版本 | `23` |

本次只打开 `CONFIG_STAGING_COMMIT` 与 `STATE_SNAPSHOT_SEGMENTS` 两个能力位。生产入口
仍要求完整 `0x1fff`；`ECOBIN_UART_HIL_REQUIRED_CAPABILITIES=0x300` 只能用于明确的
HIL 环境。

## 执行命令

```text
python3 /root/ecobin-hil-f11/tools/uart_hil_probe.py \
  --port /dev/ttyS5 \
  --port-count 1 \
  --required-capabilities 0x300 \
  --apply-sample-configuration \
  --repeat-sample-configuration \
  --config-version 23 \
  --query-state
```

命令退出码为 `0`，总耗时约 3.3 秒。

## 通过证据

- HELLO 握手成功；协议版本、设备身份、固件版本、投口数和能力位均被严格解析。
- `CONFIG_BEGIN -> CONFIG_DEVICE -> CONFIG_PORT -> CONFIG_COMMIT` 全部收到
  `ACCEPTED`。
- `CONFIG_APPLY_RESULT` 为 `APPLIED`、`faultCode=NONE`；配置版本、content SHA-256
  与 MCU payload SHA-256 和下发值一致，事件序号为 `1`。
- 原样重放同一配置时，BEGIN/DEVICE/PORT 返回 `ACCEPTED`，COMMIT 返回
  `DUPLICATE_ACCEPTED`；重放的结果仍使用事件序号 `1`，没有产生第二次配置结果。
- `QUERY_STATE` 的 BEGIN/PORT/END 三段齐全，快照 SHA-256 校验通过；applied 配置版本
  和两个摘要与配置结果一致，staging 已失效并清零。
- `pendingCriticalEventCount=0` 时，oldest/latest 的 boot ID 与 event sequence 四个字段
  均为 `0`，通过生成协议运行时的严格语义校验。
- 本次成功运行没有触发 UART 重试。

## 联调中发现并修复的问题

1. MCU 最初直接使用 STM32 硬件 UID 的前 8 字节作为 `mcuBootId`，可能超过冻结的
   `1..9007199254740991`。现已把线级 ID 归一化到该范围。
2. 初版 SHA-256 transform 在 512 字节启动栈上分配 `uint32_t words[64]`，覆盖相邻
   快照状态，导致空关键事件队列仍出现随机 latest sequence。现已改为 16-word rolling
   schedule，并把 STM32 启动栈提升到 2 KiB。
3. 生成的 Python 解码器此前未检查空队列的 oldest/latest 字段。现已补充 Registry
   语义检查，非法快照会直接抛出协议错误。

## 尚未关闭的边界

- 未在 MCU 实际 ARMCC/Keil 工具链中单独编译并运行生成的 C 黄金程序，也没有保存
  `hil.3` 的 Build Output/map 作为证据；F-10 因此仍保持 `blocked`。
- 当前 `mcuBootId` 是硬件 UID 派生的固定设备身份，同一 MCU 重启后保持不变。香橙派
  SQLite v3 因此在每次成功 HELLO 后建立本地 `mcu_receive_generation`，允许新代际
  安全复用 MCU 事件序号；该补偿不修改 UART 字段或 MCU 固件。
- 配置、危险命令去重、关键事件队列和作业状态仍是挥发实现，未验证掉电恢复、容量、
  擦写寿命或满队列安全行为。
- 尚未实现或验证完整 `0x1fff` 能力、六投口、投递/清运/称重/红外/烟雾/门控制状态机
  以及 ACK 丢失、断电、强杀和线路故障注入。
- HELLO 报告 `stm32f103rct6`，仓库 Keil target 名称仍含 `STM32F103C8`；实际板卡、
  scatter/flash/RAM 配置需在完整 H-03 前核对。
