# P1BP：原开门已确认后的独立恢复关门

日期：2026-09-13，接续 [P1BO 新关门反馈确认](uart2-recovery-close-confirmation-p1bo-2026-09-13.md)。
继续原计划 P4，不是完整恢复接单或真机验收。

## 已补齐的实际分支

香橙派已确认 MCU 重启，并把未取得最终结果包的投递归档后，原开门可能已经有可靠的实际输出确认。
先前 Pi 准备入口和永久关门许可都只接受原动作尚未确认，导致“证据更完整反而不能准备关门”。
本批接通这一分支，同时保留已有未确认原动作的第一次受限关门路径。

现在原动作满足两种情况之一，可继续核对独立新关门许可：

- 原动作仍为 `ARMED`，即已允许发送但效果尚未核对；保留原未知状态，不改为成功。
- 原动作已经以 `MCU_IDENTITY_BOUND_FACT`（与原单片机命令身份绑定的事实）确认 `EXECUTED`
  （原控制执行），并与本地固定原回执、摘要以及完整原受理/首重/输出证据一致。

永久服务只核对自己的许可与账本；真实 MCU 输出和原业务证据由香橙派核对，永久服务不伪装成传感器。
固定帧确认、尚未发送的取消、人工隔离和其他不符合这一原生执行证据的结果不混入本入口。
`FAILED_SAFE` 原动作的恢复仍待对应异常证据路径接入，不能伪装为本批已验证的正常控制执行，
也不把本批未覆盖路径定为必须人工处理。

原确认完成于新关门准备之前、永久准备/最终授权期间或最后一次前置检查时，均不需要降级或改写原确认。
永久已提交但本地还留待确认记录是合法丢回复状态；核对同一原证据后可以继续关门，
本地原待办仍由原动作核对器完成，不要求两个数据库在同一事务提交。

## 权限、证据和事务边界

- `native_delivery_recovery_close.py` 增加 `check_source_ledger`，复用原命令执行证据重建，
  不仅检查“已确认”标记，也核对固定原文、保存回执、原许可和真实输出。
- `EdgeStore.validate_native_recovery_close_source` 在独立 SQLite 事务内完整核对绑定、占用和源证据。
  准备阶段同样在原准备事务内核对；不跨永久层本地接口调用持有数据库事务。
- 发送前先完成外部前置检查，再查询当前原永久账本，最后在同一业务库快照核对证据及不可延长的期限。
  原动作的账本序号在确认时不变，不需要新建恢复身份或修改原序号。
- 永久层只扩大原生且已确认执行的这一种源状态；新关门仍只限原投递门、仍需独立准备和最终授权，
  原人工停机、真正维护接管、其他未确认动作、原许可与完整命令摘要检查均保留。
- 更新在等待原业务结束的 `DRAINING` 阶段仍允许本次受限关门，不转移更新占有权。
  永久层重启后不能重新授予已经授权的旧发送；未授权的同一仍存活业务调用可继续核对原准备。

## 不改变的业务结果

原开门执行事实不等于完整投递结果。问题原因仍为“单片机重启，未取得最终结果包”，
保留全部已有重量等记录；归档后迟到结果只作证据，不重建正常结算订单、余额或自动提现。
本批不改当前袋、皮重、后续业务状态，不重放开门。
即使原开门和新关门都确认，原业务占用与永久许可仍保持，不能跳过当前检查直接恢复接单。

## 测试与独立审查

使用 TDD 技能，先通过实际 C + 两份真实 SQLite 的用例复现已确认原动作被拒绝，再实现允许分支。
用户本轮授权子代理并行后，子代理独立补永久 API 测试及只读审查，主代理统一审查、修正和集成运行。
没有把永久 API 中的合成确认回执冒充真实 MCU 成功事实；实际输出正向链路由 Pi/C 联测覆盖。

测试和审查进一步复现并修复：

1. 已确认后删掉原输出，仅凭确认包摘要仍能准备/发送；改为重建原始受理、首重和输出证据。
2. 最后一次前置回调在发送声明提交后使原证据缺失，旧顺序仍会写串口；改为回调后统一快照核对。
3. 回调期间原账本变为不符合入口的确认，旧查询结果仍被使用；以及正常确认因此被错误拒绝。
   查询移至回调后，两类测试均通过。
