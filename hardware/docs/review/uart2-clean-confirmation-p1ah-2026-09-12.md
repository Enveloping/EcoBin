# P1AH：清运人工确认、最终结果与可靠保存

日期：2026-09-12。承接 [P1AG](uart2-clean-intent-p1ag-2026-09-12.md)，按已授权计划继续本地实现。
本批没有 SSH、真实串口、GPIO、HMI 修改、烧录、部署、云端调用或真实业务数据库操作。
测试使用实际 C 核心、本地模拟硬件/时间边界及真实 SQLite，不等于真机验收。

## 本批完成的业务行为

清运人员先发起完成请求，MCU（单片机）按原配置取得独立末次重量。香橙派保存完成请求和
该次重量后，MCU 才接受“确认当前重量，且已人工关门/安装完成”的新确认。确认绑定原清运
操作、原开始命令、当前动作步骤和本次测量身份；不能把旧按钮、旧重量、通断电或 PB5 当作确认。

例如已经称得 123 克，又请求开锁继续整理，则旧候选失效，但旧原文不删除。下一次完成重新
测得 456 克后，只能确认这次新测量；即使提交旧测量身份和新的步骤号也会被拒绝。

人工确认先成为独立、不可改写的过程记录。香橙派把原文与原业务关系在一个 SQLite 事务中
提交后，才发送 `PROCESS_EVENT_SAVED`（精确保存回执）。MCU 收到这份确认记录自己的正确
回执后，才从原首末测量组装 `WORK_RESULT`（最终结果）；不是收到重量回执就自动确认关门。

最终结果仍需另外可靠保存和确认。香橙派保存结果时只创建一个待分类任务，保留原业务占用，
不直接上云、释放设备或应用新袋/皮重，也不增加余额或触发提现。清运人员确认完成与后端
业务事实应用不是同一个时间点；后续编排仍需接通。

- 稳定均值、5 秒中位数、明确不可用沿用既有测量规则，不处理硬件准度。
- 无可用末重时，允许记录人工关门事实，但重量仍是 `UNAVAILABLE`（明确不可用），保留超时
  原因、采样数量、耗时和测量身份；字段内的零占位不能当作有效零重量。
- 已明确中断的末测量保持 `INTERRUPTED`（中断）及其采样信息，人工确认后生成 `FAILED`
  （失败）结果，同时保留关门确认，不把中断改成称重超时或正常完成。自动清运中断检测尚未接通。
- 已冻结的人工事实不会因回执晚到、后来超时或进入更新停止而被改写。没有人工确认之前，
  过期/更新停止仍拒绝确认；这不是对异常情况下恢复接单的证明。
- 香橙派单独重启只查询原记录、补保存回执；不会重开锁、重称重、刷新确认时间或再次要求按键。
  MCU 真实重启则新启动编号隔离旧确认，保存过的本地证据继续保留，不据此伪造新 MCU 的完成结果。

## 契约与实现

唯一消息来源 `contracts/uart/uart-registry.yaml` 更新为 **2.0.0-rc.19** /
`CLEAN_CONFIRMATION_CUSTODY_NOT_RUNNABLE`，仍标记 MCU 待评审、不可运行发布。

`CLEAN_COMPLETION_CONFIRMED`（消息 62）由 59 字节扩展为 **83 字节**：补入原开始命令 UUID
和配置版本，保留启动/事件编号、时间、清运操作、投口、步骤、最终测量 UUID、锁供电、线圈
健康、关门事实来源以及人工确认。确认必须为真、锁必须断电、事实来源必须是清运人员确认。
线圈健康仍上报 UNKNOWN（未知），不以输出值推断线圈或物理门位。

消息加入独立过程保管类型，不加入称重或动作类型。查询仍为原业务范围的 97 字节请求，
去掉临时查询号后保存 89 字节范围；过程摘要覆盖消息类型、长度和全部原文，保存回执 45 字节。
引用原 START 的完整命令摘要和编号，而不是临时查询编号或最近解锁命令。

- 生成器补齐 C/Java 布尔常量约束以及此消息的组合条件；此前通用布尔分支只检查 0/1，
  未检查 `const: true`。参考解析器、生成 Python、独立头文件 C、共享校验 C 和 Java 同步验证。
- MCU `McuCleanExecution_Confirm` 是尚未接真实屏幕的前台显式确认入口。核对当前操作/配置/
  步骤/候选、精确保存的末重、最新通断电两条记录、逻辑 CLOSE、原期限与更新状态；准入回调
  后再次读取输出快照和时间。拒绝可能留下事件编号空档，但不会推进动作步骤或形成完成事实。
- 实际过程槽仅允许确认紧随同原业务/配置/步骤的已保存末重，且测量身份和先后次序一致。
  回执必须匹配启动、事件编号、类型及原文摘要；旧重量回执、坏摘要或旧启动不能释放确认。
- `poll_confirmed` 只在原确认精确保存后冻结结果，保留确认发生时间与原首末测量，不重新采样。
  `WORK_RESULT` 使用独立的结果编号和保存回执，不挪用过程事件的编号空间。
- SQLite 从 **schema26 保留数据迁移到 schema27**，新增 `native_clean_confirmation`，单独保管
  人工事实并引用同一步骤已保存的完成请求和末重事件号。原文/回执读取时重新核对，不靠冗余
  索引列替代原文。它不写测量表，不创建最终结果任务，也不释放业务占用。
- 一次启动中的同一清运操作只接受一份人工完成事实；不同内容/范围/编号或与既有称重、动作、
  投递选择、清运意图撞号时，保留原文和冲突证据，后续不能返回保存回执。跨类型双向顺序均检查。
  缺少已保存的完成请求/末重、原范围不符或记录损坏时，同样不确认。

## 测试过程与证据

采用 TDD（先验证失败场景、再补实现）逐段推进；注入只发生在串口写入、硬件/时间、数据库
失败和显式 MCU 重启等边界，不手改 C 业务阶段伪造完成。

- 15 项新增契约测试：完整字段/长度/摘要/回执和非法身份、步骤、配置、人工确认及供电来源。
  初次失败揭示缺少新字段，随后三项真实 C 守卫失败揭示布尔常量及组合条件缺口，均已修正。
- 38 项真实 C/Pi 执行与交接测试：显式确认、重复/旧候选、未保存末重、再次开锁、期限/更新/
  准入期间状态改变、编号耗尽、可用及不可用结果、中断结果、晚到回执、MCU 真实重启和新候选。
  其中 16 项在确认/最终结果两段、可用/不可用两类测量下分别注入写异常、短写、报文丢失及
  回复丢失，然后关闭/重开 SQLite。发送回执前用独立连接验证原文已提交，最终仅一个待分类任务。
  另有真实客户端提交失败测试，确认不发送，MCU 继续保留人工事实与业务阶段。
- 中断末测量测试最初为 **1 失败 / 16 通过**：人工确认已保存，但正常完成原因与中断重量的
  契约组合不合法，结果构造拒绝，业务停在 RUNNING。改为失败原因后 **17 通过**，没有放宽
  契约或把中断重量改成可用。继续补充测试后该文件 **38 通过，7.36 秒**。
- 9 项实际 C 过程槽测试：原候选先保存、完整范围、步骤/配置/原命令/测量身份及事件/时间
  先后关系，坏回执和新启动隔离；**9 通过，0.52 秒**。
- 37 项真实 SQLite 测试：独立保管、重启/幂等、四类跨类型冲突双向顺序、前置证据缺失/
  不匹配、不可用重量不改写、schema26 原子升级/失败回滚、冲突键持久隔离、损坏记录/前置
  依赖、不允许嵌套事务、提交失败、提交前后进程退出；**37 通过，2.43 秒**。
- 同步旧迁移测试的版本预期和删除新表的旧库构造；尤其 schema22 的既有测试曾保留更高
  版本，仅重复补表而不是真正从 22 升级，现明确构造并断言 max(version)=22 后再测试迁移。
  初轮相关四文件为 9 失败 / 53 通过，修正旧库构造与当前版本预期后五文件 **77 通过，5.87 秒**。
  未放宽保留原数据、拒绝冲突或失败回滚的生产检查。
- 上述新增 **99 项**及旧迁移/结果交接的相关组合最终 **176 通过，18.45 秒**。
- 完整契约验证 **25 通过 / 0 notes**：**66 消息、55 完整守卫、49 帧、1477 流轨迹、15 摘要
  样例、104 生成物**；含 Java21、独立头文件 C 和共享实现 C，生成物无漂移。
