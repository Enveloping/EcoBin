# P1AC：关门输出前的投递动作中断与失败交接

日期：2026-09-12。继续既定计划，仅实际 C / 模拟硬件边界 / Python3.11 / 合成 SQLite。
未连接设备、触发真实串口/GPIO、修改 HMI、部署或烧录。P3/P4 仍未整体完成。

## 解决的具体场景

香橙派下发的首次开门指令被 MCU 受理后，若 MCU 尚未发出 OPEN 就已到执行期限，或
更新停止在 OPEN 前、OPEN 后、自动 CLOSE 前的换向等待期间中断本轮，MCU 现在除了保留
原 OPEN 输出/拒绝事实，还会保留一份明确的中断记录。已经发出的 OPEN 不被抹掉，未发出的
CLOSE 不会补成成功。现场防夹 PB5 仍只暂停关门，不会触发本中断路径。

连续投递第二轮中断同样适用：记录仍关联原会话/首次授权根及导致本轮的已保存 CONTINUE，
不伪造香橙派新命令。上一轮已经出现的重量下降异常保留；没有本轮末重，就明确未采集，
不能用上一轮值冒充。本机已保存的上一轮过程重量仍可供后续分类/排查使用。

香橙派精确保存原输出记录和中断记录后，MCU 才冻结 FAILED 最终结果：

- 保留整个会话原首重、原 START 和原配置。
- `deliveryRoundCount` 只计实际已发出 OPEN 的轮次：第一轮 OPEN 前中断为 0，第二轮
  OPEN 前为 1，第二轮 OPEN 后为 2；不是物理到位或完整关门轮数证明。
- 末重 `NOT_TAKEN`，不补零值、旧值或物理关门确认；完成时间使用真实中断时间，保存延迟不刷新。
- 两份数据任一未保存、确认摘要错误或保存身份已被回收，均不能提前形成该失败结果。

最终结果继续走现有 Pi 原文 + 待分类任务的同事务交接。Pi 重启和确认丢失只查询/确认原数据，
不重放动作；**Pi 原业务占用保持，任务仍为 PENDING_CLASSIFICATION，不上云、不产生资金。**
MCU 交出数据不等于故障已恢复、更新停止已解除或可以接新订单。永久账本效果核对、分类与
新的恢复关门检查仍由后续实现，不以本批失败收尾代替。

## 契约与实现

- 唯一 Registry：`2.0.0-rc.15 / DELIVERY_ABORT_CUSTODY_NOT_RUNNABLE`。
- 新 `DELIVERY_CYCLE_ABORTED`，消息 99，正文 61 字节/整帧 75 字节，需精确数据保存确认。
  字段包含启动/全局事件/原始时间、原授权命令/会话/投口/轮次、中断原因、OPEN 是否已发出、
  本地继续选择原因编号。OPEN 是否已发出是逻辑输出事实，不是门已物理打开。
- 原因区分 `CYCLE_START_REJECTED`、`OPEN_DEADLINE_EXPIRED`、`UPDATE_STOPPED`。
  前两种不能同时声称 OPEN 已发出；首轮原因编号必须为 0，后续轮次必须非零且早于本事件。
  Python/C/Java 同步校验，错误正文即使 CRC 正确也不能进入消费者。
- 原有独立 OPEN/CLOSE 双记录预留不增加空间：CLOSE 位置在正常时保存 CLOSE，在本轮中断时
  保存中断，两者互斥。没有取消已发布 OPEN 或把已用的编号额度还给其他生产者。
- 动作记录池新增只读 `MemberSaved`：精确检查启动、预留身份、成员、消息类型及保存状态；
  缺失/待填/未保存/已回收都返回否，不把“查询不到”当成“保存成功”。
- Pi 通用动作交接直接保存新原文，现有 schema25 的 64 字节上限足够，无新迁移/清库。
  此次没有改变 OneNet 模型、后端认可清单、永久动作账本或正常 main 接线。
