## 现场发现

### F32-01：显式重启永久服务会连带停止业务程序

状态：**已修复并热部署到当前 v32 测试卡；待递增镜像固化。**

复现条件和事实：

1. 更新 `76047cf0-96cc-4c95-8375-ea022598bbfc` 已安装 `0.3.0-rc.3`，正在执行 30 分钟健康
   观察；
2. 显式执行 `systemctl restart ecobin-communication-proxy.service`；
3. 通信代理约 3 秒后重新连接 OneNet，但可替换业务服务的主进程编号从 `34381` 变为 `0`，
   服务成为 `inactive`；
4. 更新器正确发现目标业务不可用，以 `BUSINESS_RUNTIME_NOT_READY` 进入回滚；
5. 2026-09-07T03:28:29.058Z 回滚完成，终态为 `ROLLED_BACK / COMPLETE`，业务准入重新开放，
   无待协调状态。

直接原因是 `hardware/ecobin-business.service` 和
`hardware/ecobin-business-updatable-candidate.service` 都用 `Requires=` 强依赖通信代理和更新器。
显式重启永久服务包含停止阶段，systemd 因强依赖同时停掉业务服务；已经处于 active 的
`ecobin-business-runtime.target` 不会因此重新提交业务启动任务。更新器在观察期把真实的业务
停止当成健康失败并自动回滚，这一回滚决定本身是正确的。

该行为与架构设计中的既定要求不一致：已经取得作业许可并开始的投递或清运，应能在通信代理或
更新器短暂重启期间完成。它也会使本来健康的业务发布在永久服务人工重启时被回滚。

后续修复不能只延长更新观察宽限。需要同时检查两个业务单元与通信代理、更新器之间的 systemd
依赖传播，候选方向是把“保证一起启动”和“任一永久服务停止时必须杀掉业务”拆开，例如保留
启动顺序与目标级拉起，但改用不会反向传播停止的依赖。采用任何具体指令前，必须验证以下边界：

- 冷启动时通信代理和更新器仍会被启动，业务拿不到作业许可时继续失败关闭；
- 通信代理短暂不可用时，业务事件按原事件编号保留并重试；
- 更新器短暂不可用时，不允许开始新作业，但已经开始的作业不被杀死；
- 在没有进行更新时，分别重启两个永久服务，业务进程和活动作业保持；
- 在业务发布观察期分别重启两个永久服务，观察起点和目标版本保持，恢复后继续观察；
- 真正的目标业务崩溃仍会触发自动回滚，不能被永久服务重启宽限掩盖。

2026-09-07 修复时，将两个业务单元对永久通信代理和永久更新器的关系从 systemd `Requires=`
改为 `Wants=`，中文含义是“启动业务时一并尝试拉起永久服务，但永久服务单独停止或重启时不再
反向杀掉已经运行的业务”。原有 `After=` 启动顺序、运行时切换门、MCU 安全门和厂家登记强依赖
均保留。

修复直接热部署到当前香橙派后，分别重启通信代理和更新器，业务主进程编号始终保持 `56459`；
整机重启后业务主进程编号变为新的 `1857`，再次分别重启两项永久服务后仍保持 `1857`。两轮中
业务版本均为 `0.3.0-rc.3`，作业门禁开放且没有活动更新。该结果证明 systemd 停止传播已经
解除。

更新后的真实投递会话打开期间又重启了通信代理，业务主进程在重启前后均为 `1857`；该投递最终
形成第 80 号 `DELIVERY_COMPLETE`（投递完成）事件，并于设备时间
`2026-09-07T05:04:38` 得到平台确认。当前使用模拟 MCU（微控制器），开门动作会立即返回，所以
人工执行重启前永久作业许可已经正常释放；这条事实证明投递会话和完成上报没有被通信代理重启
打断，但不能冒充“物理动作仍在执行”的时序证据。

清运也存在同一测试限制：模拟 MCU 在开始清运后很短时间内自动完成最终确认，现场人员无法稳定
把流程停在中间。为验证此次修复真正涉及的永久边界，随后以日常业务账号通过同一个本机控制接口
创建并开始一条 `CLEAN`（清运）许可，但不派发 UART 串口命令、不驱动门锁和称重。在许可保持
期间，更新器进程从 `1727` 重启为 `14780`，业务主进程前后均为 `1753`；重启后的更新器仍保存
一条活动许可，并按设计进入“等待活动作业协调”的关闭状态。测试最后将该许可记为取消且没有
物理动作，活动许可恢复为 0，作业门重新开放。整机就绪审计随后再次通过，业务版本仍为
`0.3.0-rc.3`，两个更新临时目录为空，域名解析和磁盘余量正常。

因此，systemd 停止传播和永久许可跨更新器重启的产品边界均已在真机通过；真实 UART 物理动作
进行中的同一组合场景，仍受模拟 MCU 自动完成能力限制。以后换用可控制停留时间的 MCU 时可以
补测，但当前记录不会把这次无硬件动作的确定性许可测试写成真实门锁中途测试。

### F32-02：顶层“等待下载”不能表示真实字节进度

状态：**功能正常，诊断展示仍可改进。**

更新请求刚送达后，顶层任务较长时间显示 `RECEIVED / WAIT_FOR_DOWNLOAD`。读取细分下载事实和
临时文件后确认下载器已经工作：`download_state=DOWNLOADING`，文件从 15,728,640 字节连续增长
到 53,755,880 字节，尝试次数为 1 且无错误。下载完成后顶层状态进入验签。

因此本轮没有重发命令或修改下载代码。后续若希望运维人员不把正常蜂窝下载误认为卡死，可在
只读状态输出中加入细分下载状态和当前字节数；不能通过缩短超时或重复下发来掩盖展示缺口。

### F32-03：旧生产诊断脚本可能读到历史软件事实

状态：**诊断方法已修正，产品代码不受影响。**

旧的 `query-production-v31-software-fact.sh` 对软件事实使用 `LIMIT 1`，但没有按管理状态序号或
事实主键倒序，因此一度显示历史管理序号 47。新增本地诊断脚本
`query-production-v32-software-facts.sh` 后，按 `management_state_sequence DESC` 读取，确认后端
最新事实为管理序号 14、业务版本 `0.3.0-rc.3`、进程运行、完全兼容且允许业务。

后续应把排序规则合并回可复用的生产查询工具，避免继续复制按版本命名的临时脚本。本次没有
修改后端事实计算或数据库记录。

### F32-04：特权助手首次连接产生系统性“结果未知”记录

状态：**动作最终成功，原因和降噪方式尚未处理。**

停止桥接业务、创建数据库快照、安装、激活和启动目标等多种动作均出现前两次
`PRIVILEGED_ACTION_RESULT_UNKNOWN`、随后一次 `SUCCEEDED` 的模式。未知记录在数毫秒内形成，
对应 socket 激活助手尚未稳定接收请求的窗口；最终受围栏保护的动作均成功，更新状态中的临时
错误也被清除。

当前证据没有表明同一物理副作用被重复执行，不能据此修改幂等或围栏规则。后续应定向测量 socket
激活与客户端连接时序，判断能否在派发新动作编号前完成有界连接重试，同时继续保留“助手可能已
执行但回执丢失”时的未知终态和实际状态协调。

### F32-05：终态更新没有完整清理下载和解压目录

状态：**已修复并热部署到当前 v32 测试卡；严格就绪审计已恢复通过，待递增镜像固化。**

第二次正常更新已于 2026-09-07T04:07:03.064Z 达到 `SUCCEEDED / COMPLETE`，三个运行服务、
数据库和后端软件事实均正常，但随后执行 v32 独立就绪审计得到：
`business update directory is not empty`。

只读核对显示：

- 两次远程更新的 `business-packages/<updateUid>/` 均保留完整 53,755,880 字节归档和 64 字节
  签名，下载缓存合计 107,524,176 字节；
- 第一次自动回滚任务的 `staging/<updateUid>/` 仍保留解压结果，暂存根合计 274,273,092 字节；
- 第二次成功任务的解压暂存目录已清理，说明成功路径已有 `package_stager.cleanup()`；
- 当前协调器成功路径没有清理远程下载目录，回滚完成路径也没有对下载目录和解压暂存目录执行
  对称清理；
- 就绪审计明确要求 `/var/lib/ecobin/updater/business-packages` 和
  `/var/lib/ecobin/updater/staging` 在没有活动更新时为空。

该问题不会使当前 `0.3.0-rc.3` 停止运行，但会让每次更新或回滚持续占用存储，并使严格更新
就绪门禁无法恢复。当前未手工删除目录，以保留复现证据并避免把人工清理误写成产品修复。

后续修复至少需要：为成功、回滚和安全取消定义同一套终态清理职责；区分仍在下载的活动目录与
可删除的终态目录；在更新器重启后根据持久任务终态重试未完成清理；清理失败只记录可诊断事实，
不能篡改已经形成的安装或回滚终态；增加成功、回滚、取消、清理中断后重启和符号链接/越界路径
负例测试。修复后真机必须证明两个目录为空且完整 v32 就绪审计恢复为 `PASS`。

2026-09-07 已按上述边界实现：更新日志只列出允许清理临时制品的成功、已回滚、已延期和已拒绝
终态；`FAILED_LOCKED`（失败且设备保持安全锁）继续保留材料供人工协调。下载器在删除前再次确认
任务终态、固定父目录、真实目录、非符号链接和文件单链接；协调器在成功或回滚形成终态后立即
清理，并在更新器重启时扫描历史终态补做中断的清理。清理忙时有界等待；路径或磁盘错误不改写
安装/回滚终态，也不让更新器线程退出，而是在下次更新器重启时重试并继续由严格审计暴露。

新更新器首次启动后自动删除了现场保留的约 382 MB 历史下载和解压目录。随后两次更新器重启、
一次整机重启及最终复核均确认 `business-packages` 和 `staging` 为空；完整
`v32-device-remote-readiness` 审计恢复为 `PASS`。
