# P1AM：原动作未知时的受限恢复关门许可

日期：2026-09-13。范围：原生 UART 2.0 候选的永久更新器、业务侧本地接口、隔离真实 SQLite
及发布目录依赖验证。没有连接设备、操作真实串口/GPIO/HMI、烧录、部署或修改真实数据库。
P3/P4 尚未整体完成，自动恢复接单尚未接通。

前置增量：[P1AL：清运再次开锁核对](uart2-clean-reopen-reconciliation-p1al-2026-09-13.md)。

## 业务含义与当前边界

原投递开门动作已获得发送许可，但执行结果仍未知时，原永久账本会阻止其他动作。这条
限制必须保留；不能先调用既有人工隔离接口，把它解释成“系统已经确认安全”，再绕过限制关门。

本批增加一个独立入口：香橙派业务进程提交已保存、已核对的 MCU 重启丢数据证据摘要、原开门
和新关门的完整串口命令、原业务许可及动作身份。永久更新器核对这些关系后，将新关门的
准备记录与恢复证据在同一永久库事务保存；后续最终授权也只允许这一个新关门动作。

永久层核对的条件包括：

- 原动作确为本次投递的 `AUTHORIZE_DELIVERY_FIRST_OPEN`，许可仍活动，原动作仍为
  `ARMED`（已允许发送、结果尚未确认），不是旧固定帧动作或已经人工隔离的业务。
- 原动作号、完整动作摘要、永久序列、许可/业务/平台命令身份完全一致。原 UART 命令正文
  的摘要重新按原动作键计算，不能只凭调用方另传的一段原文。
- 请求原因明确为 `MCU_RESTART_DATA_LOSS`，即业务方已判断 MCU 重启且必要数据丢失；
  通信超时不能冒充这个原因。新启动编号必须大于原启动编号，但两个数字本身不是重启证明。
- 新命令确为 `SAFE_CLOSE`，只限原投递门；解码完整载荷并重算摘要，业务/启动/投口及命令号
  不匹配即拒绝。不能扩大成全部投递门，更不适用于没有自动关门能力的清运门。
- 普通开门、其他未核对动作和新业务不因此放行。人工停机、真正硬件维护接管依然阻断。
  更新若只在 `DRAINING`（等待当前业务收尾）阶段，则允许原业务的受限关门，不解除更新占有权。

准备和查询都不授予机械执行权限。仍须经过原 `ARM_PHYSICAL_ACTION` 最终授权，以及业务方
保存发送声明后的单次串口写入。重复 ARM 的相同、仍存活调用可以获得幂等回复，不代表能再写
一次串口；单次写入仍由业务库发送声明约束。恢复动作在相同调用重试时也重新核对人工停机，
不能拿停机前的授权回复越过新停机状态。

**永久更新器不直接查询 MCU，也不独立证明重启、数据丢失或门的位置。** 新业务协调器仍须
在请求前核对真实启动信息、原完整结果是否已保存、当前配置/安全状态和持久恢复意图。本批
没有接入该协调器、原生 `SAFE_CLOSE` 执行或真实反馈，不会自行启动自动关门或恢复接单。

## 原动作、恢复动作、业务完成分开

原开门行不改成成功、未执行或安全失败，也不追加 `UNKNOWN_EFFECT_QUARANTINED` 人工隔离结果。
新恢复关门使用独立动作号及 `native:recovery-close:<恢复号>` 稳定键；证据包含新旧命令原文。
即使新关门收到输出确认，原动作未知事实仍未被解决，原许可和业务占用继续保留，不创建
订单、余额、自动提现、袋关系或云端完成事件。

测试中给新关门提交一份合成的永久输出回执，只用于验证“两项动作不互相代替”：新动作
可确认，原动作仍未知，业务不能据此完成。该用例不是实际 MCU 反馈或门已关闭的证明。
后续须接实际反馈、自动问题归档及独立恢复完成记录，再按既定条件恢复接单。

当前入口覆盖“原首开动作未确认后的第一次受限恢复关门”。原动作已确认后的数据丢失、
后续本地投递轮次、同启动期间中断、未授权准备在业务进程重启后如何退休、恢复关门期间再次
MCU 重启等仍须继续接入；当前拒绝或保留占用不是把这些场景定成必须人工处理。

## 持久化与本地接口

- `updater_store.py`：在首次成功准备的事务中惰性创建 `native_recovery_close`，将原始恢复
  身份、完整命令原文和摘要，与新 `physical_action_ledger` 准备行一起提交。失败不留半行，
  不消耗另一永久动作序列。正常/default-off 启动不会预先新建此扩展表。
- 原永久 schema **3**、业务 schema **28** 不变。扩展采用固定 DDL 校验，读回再次核对全部
  不可变关系和动作原文；表/行缺失、实际动作种类或摘要被修改时拒绝运行/授权，不退回普通动作。
  当前每个原动作最多登记这一条恢复准备，后续多次恢复/准备退休尚需接入对应策略。
- 新增 `PREPARE_NATIVE_RECOVERY_CLOSE` 和 `GET_NATIVE_RECOVERY_CLOSE` 本地操作。字段集合由
  `job_safety.py` 统一声明，更新器只给原业务进程身份开放；default-off 不注册这些业务操作。
- `PermanentJobSafety` 发送固定原身份，检查准备结果，再查询永久记录逐字段核对；记录冲突
  或旧永久服务不支持时保持拒绝，不降级成普通开门许可。
- 永久库只保存本次发送令牌的摘要，不把明文令牌存入恢复证据。业务进程重启产生的新令牌
  不能接管原准备/已授权动作；只查原记录。更新器单独重启后，仍存活的业务准备调用可以用
  同一令牌核对原 PREPARED，但已经 ARMED 的旧运行实例不能重新取得发送授权。

UART Registry 仍为 **2.0.0-rc.20 / CLEAN_INTERRUPTION_CUSTODY_NOT_RUNNABLE**，未改线协议、
生成物、OneNet 或 MCU C。本批不产生新固件及 ROM/RAM 报告，不把历史核心探针当本批构建。

## 安装目录边界

新增核对复用 `job_safety.py` 的动作摘要和 `uart2_protocol.py` 的契约解码。这两个文件原先
只有业务目录清单；直接导入会使独立永久更新器启动失败。按失败测试补入
`DEVICE_UPDATER_FILES`，安装的是永久层自己的受控副本，不从可替换业务目录动态加载。

隔离子进程使用 `-I`，只复制永久清单文件，验证三个模块实际来自临时永久目录，并创建
默认关闭的更新器；其门禁仍 LOCKED，不启用新业务或更新。此测试不代替 Linux 文件属主/权限
和真实安装验收。本次仅补新依赖清单，没有制作包/镜像或部署；业务清单 schema25 冻结与
其他候选模块打包、后端版本认可、永久层升级和成对发布仍需在 P7 完成。
