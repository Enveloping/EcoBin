## 2. 新消息及业务含义

机器偏移/枚举以 [Registry](../../../contracts/uart/uart-registry.yaml) 和
[生成布局](../../../contracts/uart/generated/uart-layout.json)为准。

| 消息 | 谁在什么情况下使用 | payload / 整帧字节 |
|---|---|---:|
| `COMMAND_DECISION` 0x0B | MCU 回显原命令完整身份，报告首次受理或拒绝；受理不等于机械完成 | 71 / 85 |
| `QUERY_COMMAND` 0x0C | Pi 没收到决定时，按原命令身份查询；不重新启动动作 | 68 / 82 |
| `COMMAND_QUERY_RESULT` 0x0D | MCU 回显查询编号、原命令身份、当前启动及已处理最大序号 | 83 / 97 |
| `RESULT_SAVED` 0x0E | 未来 Pi 在完整结果与待上报记录同事务提交后，确认保存这一份结果 | 60 / 74 |
| `RESULT_SAVED_REPLY` 0x0F | 未来 MCU 报告释放、已释放、查不到、身份冲突或启动不匹配 | 69 / 83 |

命令身份含原 UUID、原内容摘要、目标 MCU 启动编号和命令序号；查询/回显携带原摘要，
不能按查询消息号重算成另一条命令摘要。查询使用独立编号，不消耗或推进动作序号。
这 5 条消息都不要求通用帧 ACK；通用 ACK 不替代决定或完整结果保存确认。

例如 Pi 查询序号 7：MCU 已处理最大序号 10、只保存序号 10 的详细决定时，回答
`OLD_DETAILS_UNAVAILABLE`（旧详情不可取），不能回答 `NOT_SEEN`（尚未见到）。
Pi 不能据此认定开门从未执行、释放原占用。只有查询序号大于当前最大序号时才允许
`NOT_SEEN`，但这也不单独授权清理可能在途的动作或再次开门。

校验固定以下关系：

- `BOOT_MISMATCH` 当且仅当当前启动与目标不同；当前未分配的 0 只用于明确不匹配。
- `REJECTED` 必须有非空错误码，其他决定必须为 `NONE`；主动决定不能使用 `NOT_SEEN`。
- 只缓存最新决定，受理/拒绝/身份冲突的查询回复必须与最大序号对应；旧详情和未见过不能互换。
- 未绑定 MCU 的最大命令序号必须为 0。
- 结果保存身份为启动编号、结果序号、业务 UUID、完整结果 SHA-256；不能仅按业务号或传输序号释放。
- 保存回复的当前启动必须与结果启动一致，否则只能报告 `BOOT_MISMATCH`。

9 条新引导/会话消息均在 CRC 检查后、流回调前校验长度、范围、枚举、非零 UUID
及字段关系。Python 符号和数字枚举走相同规则。跨语言轨迹覆盖所有 16 个合法决定/查询/
保存回复状态组合，以及重算 CRC 后仍然非法的内容。

## 3. MCU 会话模块：已编译但未接主程序

新增 `hardware_mcu/USER/mcu_session.c/.h`。它没有 GPIO、Flash、计时、串口、堆分配或
结果正文，只有单一前台调用者管理的 RAM 状态。明确包含 contracts 中的候选头文件，
不会因头文件搜索顺序误用 `USER/uar/` 冻结版本。当前 Keil 工程/主程序没有纳入该模块。

- 初始化只清空本模块；停止输出仍是主程序/执行器的责任，不能把这里的初始化当成关门。
- 未绑定时只接受最新有效询问对应的绑定；已有编号不能重绑。重启清空询问和启动身份。
- 合法新命令先缓存决定，再向调用者返回 `execute_once=1`；调用者据此派发一次动作。
- 非法输入不仅返回失败，还清掉回复缓冲中的执行标志，避免复用缓冲时遗留上次的 `1`；
  用例先复现遗留标志再修复。其他回复字段只在返回成功时可用，输入/输出缓冲不能重叠。
- 已受理命令的重复消息只回原决定，即使当前业务前置已变为 BUSY，也不重新决定或动作。
- 业务拒绝同样消耗序号；同序号 UUID/摘要冲突拒绝。未发送的预留号可跳过，较小号永远退休。
- 查询只读；序号到 `UINT32_MAX` 后不能回绕成新动作。其他启动的旧命令不改变当前序号。
- 调用方必须先验证完整 payload、命令摘要和无副作用的业务前置。模块不是旧 39 条消息的
  解码器，也不实现通用 UART 发送/重试；现在不能直接放进运行入口使用。

9 个 C 场景验证：RAM 绑定、丢回复后的重复命令、只读查询、拒绝/身份冲突、序号空洞及
耗尽、重启前后旧命令、非法身份不消耗状态、询问替换、所有决定分支符合生成回复契约。
桌面 `sizeof`：会话状态 88 字节、一次决定 80 字节；桌面/ARMCC 同时编译检查上限
96/80 字节。ARMCC 5.06 update 5 build 528 / Cortex-M3 / C99 / O2 对模块和测试源
编译均无错误/警告；本模块未链接对象 Code 500 字节（包含 6 字节内嵌数据）。
这不包含库函数、串口解析器、业务/结果槽和调用栈，**不是整机 ROM/RAM/栈预算或目标板运行证明**。

## 4. 已修复的长输入丢帧问题

复现使用 40 条各 30 字节的合法 `BOOT_PROBE_REPLY`，总长 1,200 字节、固定时间 0：

| 一次读取块大小 | 修复前丢失序号 |
|---:|---|
| 30 / 480 / 511 | 无 |
| 512 | 18（前次留下半帧，再追加 512 字节也会超限） |
| 513 | 1、18 |
| 1200 | 1～23，只剩最后 17 条 |

排除计时与内容校验原因：时间固定不前进，同一组帧小块输入全部合法；丢帧只随读取边界变化。
根因是先追加全部输入并裁掉缓冲前部，之后才解析；C 虽逐字节入队，也在全部入队后才解析。

现在按实际剩余容量追加并立即排空完整帧，再读下一段。单帧最多 256 字节，排空后只可能
留下短于一帧的候选或单个 magic 前缀，因此 512 字节队列总有后续空间；不需要扩容或
裁掉可解析的合法帧。Python/Java 返回列表随本次实际帧数增长，不宣称整个调用内存常量；
C 回调消费当前帧，视图仅在回调期间有效，不允许重入。

三语言共同验证超过 512 字节合法连续帧、已有半帧后再读 512 字节、长数据混入 CRC 正确
但内容非法的帧、尾部半帧保留及 100 ms 超时、超时后恢复。原 CRC/噪声/方向/ACK/内容
拒绝轨迹仍通过。噪声可增量丢弃，不再仅因批量读取大而记录 `BUFFER_OVERFLOW`。
修复只在候选工具及生成物中，冻结旧运行模块原样保留。

## 6. 下一个独立切片与未关闭边界

继续完整结果契约与真实 SQLite 交接，不需要先改 HMI：

1. 已核对旧 `DELIVERY_SELECTION`（56 字节）和 `CLEAN_COMPLETION_CONFIRMED`（59 字节）
   都只引用此前测量；不能把它们单独当作可恢复的完整结果。新集合要自含首末测量、测量来源
   身份和结束确认，明确缺失事实；Pi 保存的袋/价格/照片 URL 不回塞 MCU。
2. 先在 Registry 定义有界结果正文、组成/摘要/原业务查询和相应资源预算，再实现冻结槽及
   三语言集合验证。P0 模型的 4 片/1,024 字节只是模型参数，不能复制成已确定线上协议。
3. 真实 `EdgeStore` 应提供一个窄的保存完整结果接口，在同一 `BEGIN IMMEDIATE` 事务中
   保存不可变原结果及 `event_outbox` 记录；`COMMIT` 返回之后才能提供保存确认身份。
   以 `(mcuBootId, resultSequence)` 跨 Pi 接收代次去重，同身份异内容拒绝；不复用旧的
   仅按 `event_uid` 去重，也不复制进带接收代次的旧 UART inbox。
4. 现有多个公共存储方法各自开启/提交事务，不能相互嵌套；复用 `_insert_event(conn, …)`
   等事务内部操作。永久更新器账本是另一个存储，不假设跨库原子提交，也不让保存接口释放
   接单占用或决定资金效果。

真实一次性发送、Pi 编号永久不回退、P0 的请求不复制前提仍待接线与演练。本批不证明完整
旧询问/绑定对被主动复制时也安全。完整结果/状态/门事实/称重语义迁移及 P3～P7 未完成。
