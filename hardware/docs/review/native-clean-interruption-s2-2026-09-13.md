# 原生清运中断：失败收口与袋状态锁

日期：2026-09-13。依据[精简实施计划](../../../docs/planning/mcu-edge-simplified-implementation-plan-2026-09-13.md)
和[D15清运中断决定](../../../docs/architecture/mcu-edge-simplified-recovery-discussion-2026-09-13.md#已确认-d15清运中断后人工确认当前袋必要时重新换袋称重)。
本批只修改本地候选、文档和测试；未连接设备、未部署后端、未烧录MCU/HMI、未操作真实门或袋。

## 已接通的第一片

当原清运START（开始命令）已经可能写给MCU，而Pi确认MCU出现了更大的真实启动号时，Pi仍先检查完整最终结果。
完整结果已可靠保存则走正常清运；没有完整结果才把原开始命令冻结为
`FAILED / MCU_RESTART_FINAL_RESULT_UNAVAILABLE`（失败：MCU重启且未取得最终结果）。
后台既有命令观察规则会把它投影为 `RECOVERY_REQUIRED`（需要人工处理），不会生成正常清运记录或重量。

Pi复用原控制失败的永久许可收尾：同一清运、同一START、同一失败摘要核对成功后，永久许可记为失败，再只释放原本地工作槽。
这不是 `EDGE_RESTARTED`（Pi重启），也不会触发旧的Pi重启清运动作恢复或错误释放袋预留。

当清运因控制通信超时失败时，也执行同一个袋状态保护。失败凭据与
`port_1_clean_restart_interlock=true`（1号投口清运中断锁）在同一SQLite事务写入；中断锁写入失败会把命令失败、事件和槽位变化整体回滚。
此后即使现场人员按独立入口解除了UART通信故障，新投递和新清运仍返回
`CLEAN_BAG_CONFIRMATION_REQUIRED`，不会把系统记录的旧袋和旧皮重直接用于物理状态不明的投口。

## 本片没有做的事

- 不根据首重、末重、按钮或动作记录重建原清运成功结果；
- 不清除后台原清运的预留新袋，不更新当前袋或皮重；
- 不把MCU重启冒充Pi重启，也不调用旧 `RESUME_CLEAN_OPERATION`；
- 不因偶然恢复通信或正常设备事实自动解除袋状态锁；
- 不把现有厂家初始袋基准接口用于普通清运袋。

下一片由人工扫描并确认实际袋：仍为原袋时核对原有效皮重后收口；已经换袋时先记录真实袋并建立独立空袋基准，
可信皮重完成后再解除投口锁。该入口尚未实现，所以当前候选在发生清运中断后会安全停接单，而不会自行恢复。
