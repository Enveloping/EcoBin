## 谁处理、依据什么、修改什么

后台可靠消息工作器收到 `DELIVERY_ISSUE_ARCHIVED` 后，经平台设备事实处理器调用
`NativeDeliveryIssueService`。先锁定永久设备资产，再核对原投递、原云命令及原命令摘要、
投口、冻结配置、原始 MCU START 和正向重启回复；不根据设备此刻的业务或袋子替换原关联。
原 START 中的价格、继续等待、防负重阈值及自动关门时间还须与原云命令一致。

同一 MySQL 事务内：

1. 写入唯一投递问题记录，原因固定 `MCU_RESTART_FINAL_RESULT_UNAVAILABLE`
   （单片机重启，未取得最终结果包），业务价值固定 `NONE`。
2. 只将原投递会话转为 `DEVICE_ABORTED`，记录结束原因，不补造正常物理成功结果。
3. 只删除仍属于原投递的后台占位；如果已有后续业务占位，不修改它。
4. 经既有可靠任务公开端口完成原 `START_DELIVERY_SESSION` 任务，并创建独立事件处理确认。
   任一步失败，问题、会话变化、占位删除及该事务中的确认/任务效果一起回滚。

若后台已经有正常物理结果、订单或另一种终态，拒绝用新问题覆盖它；相同归档重复到达只确认原记录。
归档不调用 recycling 的正常订单写入端口，没有钱包、提现、当前袋、皮重或机械控制写入路径。
数据库保留真实数据；“后台逻辑业务已结束”不代表香橙派已关门或可接单。

例如投递 A 的问题上报延迟，而设备已进入后续清运：该消息仍只归档 A，不能删除清运占位。
后续机械恢复仍由香橙派的新关门许可、实际反馈和检查决定，不能用后台确认代替。

## 原证据与迟到完整结果

`DELIVERY_ISSUE_EVIDENCE_APPENDED` 现在也已注册到可靠消息工作器及平台事实处理器。
先核对原设备、问题、投递、云命令和归档摘要，再追加不可变分片。

- 每个问题/证据类型/序号/片号唯一。片数、完整长度和整份摘要固定；重复不覆盖，冲突拒绝。
- 分片提前于归档消息到达时保留在可靠接收流程中等待重试，不误判为另一个正常投递。
  不凭片段自行创建归档或释放业务。
- 最后一片到达后才按片号读取全部原字节，验证无缺片、总长度和 SHA-256；采用 JDBC 流式读取，
  既不截断大上下文，也不把全部历史分片装入一个大数组。
- 原上下文和过程事实的“完整证据”标记表示原字节已到齐且摘要一致，不表示其所有传感器观测均可信、
  重量准确、机械到位或具备业务价值。过程事实序号不能超过归档声明的已有事实数。
- 完整最终包另按生成的 UART 正文校验器校验全字段、取值组合和原结果摘要，
  再匹配原 MCU 启动、投递、命令/序号、投口和配置版本；不是只看消息编号或首末重量。
- 校验通过只添加 `FINAL_RESULT` 证据完成标记。保留原归档，不重新完成正常订单，
  不覆盖当前袋/皮重或后续业务占位；坏包、错误身份和不同内容不能替换原关联。

当前没有新问题查询 API 或客服页面，不能把数据库保存完成描述为用户已经能在网页查看。
Pi 的问题确认与恢复状态连接、进度展示和主循环仍需后续实现。
