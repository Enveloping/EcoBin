# P1BQ：未授权恢复关门准备的持久退役

日期：2026-09-13，接续 [P1BP 已确认原动作后的独立关门](uart2-recovery-confirmed-source-p1bp-2026-09-13.md)。
继续原计划 P4；不是恢复接单完成，也不代表取消后已能创建下一代关门。

## 为什么需要独立退役

香橙派可能已保存新关门的命令和许可准备，却在获得最终发送授权前重启。
原调用的内存令牌不恢复，旧取消接口又要求该令牌，因此不能直接复用旧接口退休这份准备。
本批增加专用退役通道，不放宽旧取消、旧未发送终止或人工问题隔离的权限。

这里“退役”只表示旧准备不会再取得执行资格；不是推杆停止、门已经关闭或业务处理完毕。
香橙派先保存撤回发送意图，永久层再根据自己的账本证明它从未授权这条命令：

1. 香橙派在同一业务库事务中核对原问题、原命令/许可及当前原业务占用，保存稳定退役证据。
   已登记可能发送、已有受理/输出或冲突输出的命令不能这样退役。
2. 退役意图与发送登记共用立即事务：退役先提交则发送登记拒绝，发送登记先提交则退役拒绝。
   这不是仅靠某次普通查询避免竞争；既有运行实例也不能越过持久退役意图继续发送。
3. 专用 `RETIRE_NATIVE_RECOVERY_CLOSE`（退役原恢复关门准备）核对完整原恢复身份、原文、
   原动作回执及独立退役证据摘要。永久记录若仍为 `PREPARED / PREPARED_ONLY`，
   则原子确认 `NOT_EXECUTED / PREPARED_NOT_ARMED`，即从未取得发送授权。
4. 若永久层尚未登记这份准备，在同一事务注册原身份并直接形成上述不可执行结论。
   内部随机令牌仅保存摘要，不向调用方提供执行资格；迟到的旧准备请求也不能再次授权。
5. 若永久层已经 `ARMED`，即已经授权发送，退役必须失败；香橙派没有写串口也不能据此把它记成未执行。
   已保存意图只撤回后续发送，不代替该动作的原状态核对。
6. 永久请求、回复或本地最后提交丢失时，待办按同一原身份、回执及证据继续核对。
   待办扫描只消费已保存的退役意图，不抢先取消本进程刚创建、仍有效的新准备。

## 历史及业务边界

- 新增动作的退役不修改原开门的状态、确认或人工隔离结论，不调用门禁重开，也不结束原许可。
- 纯退役不要求机械门禁当前开放。人工停机、等待维护、原动作后来已确认失败等情况下，
  可以撤回尚未授权的新准备；这些事实本身不被清除，不因此允许其他动作或恢复接单。
- 原生新关门的准备/最终授权仍保留原执行门禁。纯取消的身份核对与执行资格检查分开，
  不把“允许取消”变成“允许通电”。
- 已完成退役的精确历史核对不要求当前仍占用原业务；首次退役和未完成待办仍须原占用。
  测试显式模拟后续业务释放，不把该测试当作完整准入已实现。
- 投递问题原因仍为“单片机重启，未取得最终结果包”，不重建正常结果、不恢复结算、余额或提现。
  不改当前袋、皮重、后续业务和清运恢复规则。

## 实现范围

业务 SQLite **37→38**：新增 `native_recovery_close_retirement`，持久保存完整撤回意图、摘要及
待确认/已退役状态。升级保留原准备，不自动创建退役；事务失败回滚。启动重新核对原证据，
摘要损坏、重算摘要后的篡改、撤回记录与发送登记矛盾均拒绝。

`native_delivery_recovery_close.py` 增加退役协调器，`edge_store.py` 提供原子意图与发送互斥、
待办和确认核对；未增加业务源码依赖。业务包、运行包和永久包均验证隔离目录运行。

永久库 schema **3** 不变，复用已有未授权取消的账本状态；首次无记录时的身份登记与确认同存同无。
`job_safety.py` 定义精确字段并验证原返回及原绑定，`updater_agent.py` 只向候选业务身份开放新操作，
默认关闭。主机接口测试适配器同步此操作，旧接口和旧权限保持不变。
