# 原生 UART 2 业务命令完整校验 P1H

日期：2026-09-12，承接 [P1G 控制报文入口](uart2-control-wire-p1g-2026-09-12.md)。仍只本地实现，未操作设备。

## 效果及范围

接收入口现在对 Registry 中 COMMAND 类的全部 9 条消息校验完整正文：固定长度、非零 UUID、
目标启动/命令序号、参数范围、枚举和 SHA-256 摘要。CRC 正确但内容非法也不能交给业务执行器。
合法报文仍不意味着允许动作；当前 C 控制入口没有执行这些业务消息，也不伪造受理或消耗序号。

范围由 Registry 的消息类别确定，不另维护第二份命令列表。新声明 commandPayloadValidation=
ALL_COMMAND_CATEGORY_MESSAGES，版本递增为 `2.0.0-rc.6` / `COMMAND_GUARDS_NOT_RUNNABLE`。
9 条原有布局/消息号/ACK 标志没有改变；真实动作仍遵守只发一次及原命令查询，不能启用通用 ACK 重试。
QUERY_STATE、SAFE_CLOSE、配置和其他事件不因此宣称已完成完整校验/执行；后续分批处理。

摘要继续使用既有 v2 定义：领域前缀、消息号、语义长度、目标启动/序号和业务字段。
UUID 不在内容摘要内，由命令身份单独比较；摘要不是认证或授权。C 流式 SHA 不复制整段正文到栈。
所有偏移、范围和枚举从机器契约生成，旧三个运行制品不变，OneNet 未改，schema20 不变。

## 先失败后修复的证据

- 新测试首先复现 C、参考解析器和生成 Python 在 CRC 正确但命令摘要错误时仍接受整帧。
- 扩大为“重新计算正确摘要，但 UUID/参数非法”时，又复现生成 Python 放过全零命令 UUID；
  已修复生成器，C、参考和生成 Python 一致拒绝，不只针对某条样本打补丁。
- 新增 182 条共享流轨迹：全部9条命令合法例、错误摘要、正文改动、长短正文、
  零 UUID、低于下限/超过上限、未知枚举、合法最大值及 uint64 超界。
  非法字段例仍带正确内容摘要，确保不是只依赖摘要失败偶然挡住；非法帧后合法帧仍可继续解析。
- 定向7项通过；实际C动态库直接执行生成帧验证器。契约验证24项通过、0 notes：
  Python3.11 / Java21 / C11 同过31帧、566流轨迹、4摘要向量；103个生成文件一致。
- ARMCC5 / Cortex-M3 / C99 / O2 控制入口编译无错误警告，新增校验后独立对象 Code9440字节
  （含数据262）、RO309。不是完整链接结果，不拿它证明原512字节栈足够；main/Keil仍未接新入口。
- 扩大回归604 passed、34 skipped、1616 subtests passed（83.35秒），Windows跳过项不代表Linux/真机。
  旧协议/生产模式、永久账本、数据保留及发布门禁不放宽。
