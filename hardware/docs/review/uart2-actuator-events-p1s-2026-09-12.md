## 本批完成内容

三类 MCU 上报消息现在都必须先通过完整内容校验，才能进入接收方的消息处理入口：

| 消息 | 表达的事实 | 本批边界 |
|---|---|---|
| `DELIVERY_DOOR_COMMAND_RESULT` | 原投递命令的推杆输出结果 | 不证明机械到位，不自行推进投递 |
| `SAFE_CLOSE_RESULT` | 原安全关门命令的输出结果 | 只能报告 CLOSE，不把结果当作新的关门授权 |
| `CLEAN_LOCK_POWER_CHANGED` | 原清运命令对应的锁供电状态 | 通电/断电不等于清运门已开/已关 |

例如，MCU 上报“输出已发出”，却同时携带“输出被拒绝”的故障码，或者缺少原命令编号，
即使串口 CRC 正确，接收方也会拒绝这条报文，不把它交给业务消费者。
这只是报文自身的合法性检查：不会因此新建订单、增加余额、自动提现，也不等于查询到了
当前业务、已写入 SQLite、可以释放 MCU 原记录或允许设备接下一单。
报文被拒绝之后如何按原命令查询/补交，由后续可靠交接与业务执行器处理，本批没有实现这些恢复行为。

完整校验从 41 条扩展为 **44 条**，消息总数仍为 59。三条消息的编号、字段布局、线长未改变。
新增独立 `actuatorEventMessages` 集合，不混入六类测量事件集合。

### 统一检查的规则

- 固定长度、每个整数的上下限、枚举、非零原命令/业务编号、启动编号和事件序号。
  64 位字段必须遵循现有安全整数上限，不能只检查非零。
- `command=NONE` 与 `outputStatus=NOT_DISPATCHED` 只适用于状态快照，不得作为动作结果。
- `OUTPUT_REJECTED` 必须带输出拒绝或硬件联调未合格的故障码；
  已发出、被后续命令取代、合并到已有关闭动作这三种结果必须使用 `faultCode=NONE`。
- “合并到已有关闭动作”只能是 CLOSE，不能把 OPEN 报文标成合并关闭；安全关门结果也只能是 CLOSE。
- `physicalDoorStateBasis` 恒为 `NOT_OBSERVABLE`，即这些输出结果本身不证明机械门位置。
  不改变用户共识：业务逻辑门状态仍取最近有效 PB6/PB7 方向，实际输出电平另行表达。
- 清运锁 UNKNOWN（未知）仍是合法的未知观察，既不篡改为正常，也不单凭报文校验触发故障处理。
  本批不新增供电状态与部件健康枚举之间未经确认的推断规则。

Python 参考实现与生成实现共用 `contracts/tools/actuator_event_contract.py` 的语义规则；
C/Java 由同一 Registry 枚举和字段生成固定边界检查。符号枚举与合法数值枚举编码一致。
旧三份运行制品继续按摘要冻结，不使用 `--include-hardware-mcu`。

## 为什么可靠交接仍是下一步

原本准备继续接动作结果保留，检查现有实现后发现它不能直接复用：

1. 当前过程记录槽仅支持六类测量消息，SQLite 过程保存回执关联的也是测量表，要求真实测量编号。
   不能给机械结果伪造一个测量编号来绕过这个限制。本批新增测试确认三类动作消息不能走该交接入口。
2. 现有过程范围按原开始命令、业务、投口、消息类型、步骤和配置定位；
   同一投递轮的 OPEN/CLOSE、同一次清运锁的通电/断电需要区分，不能只用这个范围覆盖保存。
   还需明确原 START 与实际导致动作的命令、自动动作和安全关门各自如何关联。
3. 清运锁一旦通电，定时断电不能等香橙派确认保存。只有一个未确认事件槽时，
   不能覆盖通电记录，也不能为保留记录而延长通电。后续需要在动作前预留足够的有界记录容量，
   并设计按子事件查询、原文摘要及精确保存确认；队列容量耗尽时也必须保留断电能力。

因此本批没有扩大现有 `PROCESS_EVENT_SAVED` 的支持范围、修改数据库或接机械命令处理器。
新增串口流用例仅证明通电和断电两条报文均能被解析保留在接收结果中，
**不证明 MCU 已有多记录存储、香橙派已落盘或掉电后可恢复这些记录**。
后续接通可靠交接后，再实现保留原期限的单次执行、100 毫秒双输出清零换向等待、
自动关门、清运锁定时断电与真实再次开锁请求，不能把本批视为这些功能已完成。
