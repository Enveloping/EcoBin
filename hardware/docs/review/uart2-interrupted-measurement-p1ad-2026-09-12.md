# P1AD：被业务中断的测量与精确数据交接

日期：2026-09-12。继续既定计划，使用真实 C 核心、模拟硬件边界、Python 3.11 和合成 SQLite。
未连接设备、操作串口/GPIO、修改 HMI、部署或烧录。不是可运行整机固件，P3/P4/P5 未完成。

## 这批解决什么

为“关门已经下发，随后业务中断”的后续实现先补齐数据表达。原来只有正常测量、称重超时和
未采集，不能准确表达“已经开始、只取得部分样本，但被业务打断”。现在增加独立中断终态。

例如开始测量后 300 毫秒已经收到一个有效样本，下一次读数仍在等待，此时前台调用中断接口：

- 保留原测量编号、配置/校准版本、已采样 1 次、实际耗时 300 毫秒。
- 标记 `INTERRUPTED / MEASUREMENT_INTERRUPTED`，即业务中断，不谎报称重硬件超时。
- 没有有效业务重量；数字 0 只是无效字段的占位，不表示测得 0 克。
- 不再发起本次测量的新请求，迟到的旧请求回复不能补入这份已冻结的结果。
- 若已取得稳定均值，或 5 秒截止已经到期，先保留原正常终态（均值、中位数或无数据），
  不能用较晚的中断覆盖已经确定的事实，也不延长窗口。

时间使用前台实际观察时间，不倒填为较早的中断服务程序时间。调用者仍须先按顺序处理已经
捕获且能够明确归属的串口回复；本地取消请求编号不能证明物理 RS485 线路已无迟到回复。

## 单片机和香橙派各做什么

实际 C 工作准备层将中断结果生成原业务下的过程事件，并在设备事实查询中显示独立中断状态。
香橙派将原报文和业务关联在一个 SQLite 事务中保存，提交后才发送精确保存确认。

投递首重中断时，MCU 等这份原记录保存后生成 FAILED（失败）结果，开门轮数为 0、末重未采集。
投递关门后测量中断时，若原关门控制上下文仍满足既有检查，MCU 等原中断记录保存后生成失败
结果，保留原首重、本轮末重的中断身份及真实时间。不会进入继续投递选择或重新称重。

最终原文与一个 `PENDING_CLASSIFICATION`（等待业务分类）任务仍同事务保存，MCU 只释放数据槽。
**Pi 原业务占用保持，不上报后端、不增加余额、不触发提现、不凭数据交接恢复接单。**
称重中断不是传感器硬件故障，未扩大 FAULT_OBSERVED 的硬件故障允许范围。

## 契约和代码

- Registry：`2.0.0-rc.16 / MEASUREMENT_INTERRUPT_NOT_RUNNABLE`，schema25 不变。
- 新增结果测量种类 10、查询观察状态 7、原因码 1031。无新消息号，报文长度不变。
- Python/C/Java 强制中断种类与原因成对；最终结果含中断测量时只能是 FAILED/CANCELLED，
  不能标成正常投递结束、窗口正常结束或正常清运完成。错误正文即使重算摘要也不能接受。
- `WeightMeasurement_Interrupt` 保留已完成事实；`McuWeightRun_Interrupt` 限定原测量编号、
  单调时间及未退休对象，不清除读数计数器。所有新入口纳入 ARMCC 核心链接保留探针。
- `McuDeviceFacts`、工作准备层和投递首/末失败组装接入中断种类；现有保存接口不变。
- 共 65 消息 / 51 完整守卫，46 黄金帧 / 1346 流轨迹 / 11 摘要样例 / 104 生成物。
  新增独立中断黄金帧与 28 条共享语义轨迹。
