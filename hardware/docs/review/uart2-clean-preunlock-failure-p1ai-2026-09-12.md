# P1AI：清运解锁前称重失败的结果交接

日期：2026-09-12。承接 [P1AH](uart2-clean-confirmation-p1ah-2026-09-12.md)，继续已授权实施计划。
本批只修改本地候选 C 核心并增加真实 C/Pi/SQLite 测试，没有 SSH、真实串口、GPIO、HMI 修改、
烧录、部署、云端调用或真实业务库操作。既有其他改动保留；未下载依赖、未重建 Linux 虚拟环境。

## 实际实现

香橙派发起清运后，MCU（单片机）只先测清运前重量，首次解锁另需授权。若前置测量已明确
无可用结果或被中断，本批不再让 MCU 仅停在“正在收尾”而没有最终结果：

1. MCU 先保留原测量失败记录，包括测量身份、采样数量、耗时、原配置和实际故障原因。
2. 香橙派保存这份原文与原清运/开始命令的关系，数据库提交后才回传精确保存回执。
3. MCU 核对回执确实对应原始首重后，从当前清运原记录冻结 `FAILED`（失败）最终结果。
   动作步骤为 0、末重为 `NOT_TAKEN`（未采集），没有人工关门确认；不执行解锁、推杆或新测量。
4. 香橙派另行保存最终结果，仅创建一个待分类结果任务，原业务占用不提前释放。可靠保存结果
   不等于后端已应用业务，也不代表设备已经恢复接单；分类/后端处理与释放仍需后续接线。

例如清运前只取得 1 条或 4 条读数，5 秒结束仍不足以形成有效重量，则记录真实采样数量和
`WEIGHT_TIMEOUT`（称重超时）。重量字段为无效占位，不能当成测得 0 克。若测量明确中断，
则保存 `INTERRUPTED` / `MEASUREMENT_INTERRUPTED`（中断及其原因）和中断时的真实耗时，
不改成超时。自动清运中断检测仍未接通，本批测试调用的是已有显式测量中断入口。

只有首重确实可用时才继续等待首次解锁授权；稳定均值和 5 秒中位数不会误走失败分支。
首次称重失败后，即使迟到解锁命令到达或重复收到原开始命令，也不会解锁或重新称重。

## 边界与实现位置

- `hardware_mcu/USER/mcu_clean_execution.c` 新增私有 `poll_initial_failure`，由原清运前台轮询
  调用。它仅处理原清运、首重已经完成且不可用/中断、采集已经退休、原测量精确保存的场景。
  检查启动、业务身份、原配置、阶段、原测量身份和真实时钟，不能把空过程槽当作保存证明。
- 汇总不使用上一场清运的动作序号、末重、人工确认或解锁授权。上一单成功后的下一单首重失败
  也只包含新首重、0 动作步骤和未采集末重。旧结果原文在 Pi 继续保留。
- 保存回执晚到、原业务窗口已过期或后来进入更新停止，不改写已经发生的测量失败时间和原因。
  这只是历史结果交接，不授权动作或恢复接单。错误或未来的轮询时间不能提前冻结结果。
- 最终结果使用独立结果编号，不再额外消耗关键过程事件编号；原失败测量已经合法保存时，
  后续关键事件编号用尽仍不阻止构造该份失败结果。本批不声称解决所有编号耗尽恢复。
- 清运所有者不替投递收尾；投递所有者也不替清运收尾。职责互斥继续由原业务类型约束。
- PB5 和推杆实际输出不是人工清运门位证明。本批没有换袋或解锁发生，不能自动生成“清运员
  已关门”的事实。定时器刷新已有输出与业务发起新动作是两回事。

本批无新报文、字段或数据库表：Registry 仍为 **2.0.0-rc.19** /
`CLEAN_CONFIRMATION_CUSTODY_NOT_RUNNABLE`，SQLite **schema27** 不变。仍不可部署/烧录。
Pi 复用已经实现的原过程/最终结果可靠保存模块，未修改生产 SQLite 设置或增加自动重试。

## 验证证据

采用 TDD（先建立失败测试，再补实现），通过真实 C 动态库的正式入口和实际 SQLite 观察行为：

- 第一条测试确认原实现即使首重已精确保存，仍停在 RUNNING（进行中），没有失败结果；加入
  清运首重失败收尾后通过。第二条中断测量测试先失败，再增加明确中断终态处理后两条通过。
- 首条测试中曾把定时器刷新原 00 输出的底层写次数当成新机械动作，导致一次测试断言失败。
  现直接在结果发布前后比较输出写次数，并核对没有锁通电、投递输出或动作事件；没有为通过
  测试去修改原定时器行为。
- 新文件 `hardware/tests/test_mcu_clean_preunlock_failure.py` 最终 **36 通过，4.29 秒**：无结果、
  中断、1/4 样本不足、正常均值/中位数、错摘要/类型/无回执/空槽、未来/倒退轮询时间、延迟
  保存与更新、跨业务隔离、上一单数据不串单、迟到解锁/重复开始拒绝重放、事件编号边界。
- 其中 **16 项**使用真实 Pi 过程与最终结果客户端，在不可用/中断两种测量、过程/最终结果
  两段交接中分别注入写异常、短写、报文丢失及回复丢失，关闭/重开 SQLite 后只查询原数据。
  每次发送保存回执前均用独立连接检查原文已经提交，最终只有一个待分类任务，原占用保持。
- 另有真实客户端数据库提交失败：不发送保存回执，MCU 保留失败首重和原业务，不构造最终
  结果、不动作。已有 SQLite 故障与冲突策略未放宽。
- 清运各阶段、投递前置失败/中断/收尾、业务准备、结果构造和首次动作核对的相关组合
