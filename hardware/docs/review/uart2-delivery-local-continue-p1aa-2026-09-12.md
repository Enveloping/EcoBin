# P1AA：原会话内连续投递与本地动作证据

日期：2026-09-12。按已授权计划继续本地实现；未 SSH、操作真实串口/GPIO/HMI、部署或烧录。
测试使用实际 MCU C 代码、模拟硬件边界及临时 SQLite。P3 仍未整体完成。

## 实际行为与边界

- 用户在本轮选择窗口内按“继续”，MCU 保存绑定本轮重量的唯一选择；Pi 查询原文并提交
  SQLite 后精确确认。MCU 再核对原业务、原配置、当前逻辑 CLOSE、更新停止、锁供电及
  外部本地安全检查，预留 OPEN/CLOSE 两条记录和两个全局编号，然后只启动一次下一轮。
- 不重新扫码、不重新取得服务器授权、不按普通满溢拦截同一用户。首次 Pi 授权仍保留，
  但本地继续不调用 Pi 命令受理、不生成新 Pi 命令 UUID、不伪造永久账本中的新动作。
  这遵循主设计 5.2 中“MCU 本地动作单独标明来源，账本只覆盖经 Pi 许可下发指令”的边界。
- 选择窗口限制按键接受时间，不是保存回执的期限。已接受 CONTINUE 遇回执丢失/Pi 重启，
  在同一 MCU/业务下仍保留原选择；保存恢复后重新核对本地条件再继续，不刷新选择时间，
  也不套用早已结束的首次开门授权期限。窗口过后才按的新按钮仍不能覆盖既有超时选择。
- 下一轮仍经过 100 ms 双输出断开、OPEN、原配置自动关闭计时及再次 100 ms 断开。
  自动 CLOSE 不等 Pi 保存动作记录；PB5 不影响开门，关门时暂停输出，解除后自动继续。
  这是逻辑门目标/施加输出，不是物理到位检测。
- 每轮 CLOSE 后按冻结机械等待建立新的称重阶段，使用原 250 ms / 5 点 / 100 g / 5 s
  规则。首重始终是整个会话第一次测量；轮次前重取上一轮已保存重量。任一轮下降达到
  原配置阈值就锁存异常标志，之后重量增加不清除；不改成按整场净重倒推。
- 最后 END/选择超时沿用既有最终交接；后续轮次中位数仍为可用数据，无值仍保留明确
  FAILED 和缺值，而非 0 克或旧值。结果记录真实轮数，Pi 业务占用不在中间交接时释放。
- 空间/编号不足时不启动半套动作、不遗失旧记录；空间恢复后可核对并继续。
  更新停止、外部检查拒绝、配置冲突、轮数耗尽等保留占用，不冒充正常结束；完整异常恢复
  尚待接线。普通确认只证明数据保存，单独不能绕过上述本地状态机检查。

## 契约和存储

唯一 Registry 推进为 `2.0.0-rc.14 / DELIVERY_LOCAL_CONTINUE_NOT_RUNNABLE`。
新增 `DELIVERY_LOCAL_DOOR_RESULT`（消息 98），64 字节正文、78 字节完整帧：

- 消息类型本身标明 MCU 本地来源；`mcuCommandUid` 是原首次开门授权根，不表示 Pi 又下发命令。
- `selectionEventSequence` 引用上一轮已保存 CONTINUE，也是本轮本地动作身份。
  OPEN/CLOSE 共享原因编号和新轮次，但分别有自己的全局事件编号和真实输出时间。
- 起因编号必须非零且小于本事件编号，轮次至少 2；完整输出矩阵、UUID、时间和保留枚举
  由 Python/C/Java 校验。实际状态机证明跨记录的会话/选择/轮次关系；Pi 原文保存不假称
  已与实际永久动作账本完成核对。

C 动作记录池从每条 60 扩为 64 字节，仍为八条有界记录。公共前缀偏移有编译期断言。
Pi schema25 在一个事务中扩展同一表的长度约束，原行、原创建时间、回执、冲突、业务占用
和报告任务均保留。复制/换表/版本号一起提交，错误或进程退出可回滚；包声明同步为 25。
未知额外索引/触发器拒绝自动换表，不擅自删除。旧候选/旧后台兼容范围不因此自动放行。
