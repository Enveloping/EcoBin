# P1AG：清运按钮意图、再次开锁与独立末重

日期：2026-09-12。承接 [P1AF 首次清运开锁](uart2-clean-first-unlock-p1af-2026-09-12.md)。
这是本机原生候选增量，不是完整清运、可运行固件或真机验收。未连接设备、部署、烧录、改 HMI。

## 本批业务行为

MCU 接到属于当前清运的“再次开锁”或“完成”按钮请求后，先检查原业务、显示的上一步编号、
原配置和操作期限，以及最近一次锁通断记录已经被香橙派精确保存。满足条件才保留新的按钮
请求；它不是开锁命令、重量或清运完成结果，单独保存请求不产生资金或释放业务占用。

- “再次开锁”：香橙派保存请求后，须另发绑定该请求编号的新开锁命令。MCU 检查原 START
  清运命令、业务、请求种类/编号、脉冲配置和未过期的原清运期限，预留两份输出记录后才
  单次通电；定时独立断电。旧首次命令、旧请求或命令重发不能冒充一次新的开锁。
- “完成”：请求被精确保存后，MCU 启动独立的末次测量，不复用开锁前重量。有效采集目标
  仍为 250ms 一次，最近 5 个样本最大与最小相差不超过 100g 时取均值；5 秒仍不稳定且
  样本足够则取中位数；没有有效数据记录为 UNAVAILABLE（不可用），零值只是协议占位，
  不是测得零克。秤的准确度仍由人工处理，本批没有校准或自动修正重量。
- MCU 保留末重候选后处于 CLEAN_RESULT_CONFIRMATION（等待结果确认），业务仍为 RUNNING
  （进行中）。末重不是“人工已关闭清运门”的证据，也不会直接形成 WORK_RESULT（最终结果）。
- 例如末重已保存为 123g，此时再次请求开锁：旧候选失效，但原 123g 记录仍保留。下一次
  完成请求产生新的测量身份，例如得到 456g；只允许新候选参与未来的人工确认。
  旧末重未保存时不接受再次开锁，不覆盖尚未交出的数据。
- 完成后的另一次“完成”按钮不能被本 API 当作新的称重请求。本批尚未接人工关门/候选确认
  入口，不能用重复 FINISH 或锁断电代替它。

投递门仍按有效逻辑 CLOSE 目标判断，PB5 仅暂停关门，不单独判定故障或拒绝清运开锁。
锁通断仍只证明输出，线圈健康为 UNKNOWN（未知），不证明清运门开关位置。

## 协议、持久化与执行边界

Registry 推进到 **2.0.0-rc.18 / CLEAN_INTENT_CUSTODY_NOT_RUNNABLE**，仍要求 MCU 评审，
不授权部署。消息总数 66 不变；54/55 两条清运请求由 39 字节扩展到 **63 字节**：
原关键事件身份、原 START 命令 UUID、清运 UUID、投口、共享动作序号及配置版本。
两个请求共用递增动作序号；完成请求的末重引用同一序号；再次开锁命令用新的真实命令 UUID。
请求中的命令号不是最近一次开锁命令号。

- 两个请求纳入完整校验、原业务范围查询和过程记录摘要/精确保存回执，不纳入测量枚举。
  Python/reference/C/Java 同源生成；54 完整守卫，49 黄金帧、1453 流轨迹、14 摘要样例，
  104 生成物。旧运行生成制品、OneNet 模型及后台版本认可均未放开。
- C 的单份过程记录槽保留原始正文和原 START 完整范围；确认须匹配启动号、事件号、类型
  和全文摘要。空槽、错误类型/步骤、错误业务或旧回执不能代替精确保存证明。
- `McuCleanExecution_Request` 接收画面实际对应的清运 UUID 和上一动作序号，不自动把延迟
  按钮重新贴成“当前画面”。调用方必须在前台串行调用，收到结果后再更新画面状态。
  新请求不允许动作序号回绕；事件编号用尽则拒绝，不补造编号。
- 再次开锁不受已经过去的首次 START 执行窗口约束，但新授权剩余时间只能缩短、不能延长
  原清运操作截止时间。新命令仍有独立受理去重和真实通断事件。
- Pi schema **25 → 26** 在原迁移事务内新增 `native_clean_intent`，不重写旧业务或测量数据。
  原文、完整范围、精确回执在同一事务提交后才可发送 SAVED（已可靠保存）。
  该表没有重量字段；同一启动/清运/动作序号不能同时对应两种按钮请求。
- 按钮请求与测量、输出和投递选择共用全局事件身份冲突检查。矛盾记录保留，后续读回/确认
  被拒绝，不能通过重新发送旧正文洗掉冲突。读取时重新核对原文和索引/回执字段。
- 香橙派重启或确认丢失时，以原完整范围查询并补确认原记录；不重开门，不重复已经完成的
  末次测量，不清理业务占用，不创建最终结果上报任务。
