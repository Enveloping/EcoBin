## 1. 本批接通的实际路径

香橙派既有 `EdgeStore.evaluate_native_work_recovery`（原业务恢复评估入口）发现已保存的
`WORK_RESULT`（MCU 最终结果）后，在同一个 SQLite 事务快照内核对原始证据。
原首末测量、配置命令与受理回复均从真实持久记录读取，不依赖内存中的最新重量或配置。
MCU 最终结果本来就允许表示明确的称重失败；“完整结果”不等于称重成功或正常订单。

具体流程：

1. 沿用原入口对工作许可、设备占用、START（开始命令）、最终结果原文与待分类任务的核对。
2. 由原 START、业务类型、投口、配置版本，以及最终结果中明确的轮次/清运动作号，构造
   唯一的过程查询范围。投递首重为第一轮、清运首重为动作0，末重取结果引用的具体阶段。
3. 查找该范围已提交的原过程记录，逐项比较首末测量的10个字段：取值种类、测量编号、
   MCU 启动编号、事件序号、重量、耗时、样本数、波动范围、校准版本及故障码。
   已保存的“裸重量行”不能替代该业务范围的保存凭据；上一轮也不能替代本轮。
4. 从同一 MCU 启动编号、原 START 之前最后一个已尝试提交且未明确拒绝的配置集出发，
   核对每个原配置命令及其真实受理回复。只剩缓存中的“已受理”标记不算完整证据。
   重建原配置集并核对摘要、投口启用状态及测量校准版本；不使用之后的新配置。
5. 有末重及满溢采样组时，核对原完整配置摘要、MCU 子集摘要、传感器种类、请求样本数、
   最少有效数和距离阈值。满溢开始时间不能早于该称重阶段开始，完成不能晚于最终结果。
   秤与超声波各自的实际完成时间保留，允许超声波晚于重量，不人为刷新重量时间。

例如：用户完成一轮投递，原末重为700克，结果也写700克，但结果把5个样本改成6个，
即使重新计算后摘要合法，也会被判为原证据矛盾。若只是缺少这轮的保存凭据，则保留
完整结果并指出缺少哪条原记录，不取别轮重量、不重新称重、不说整笔结果已经丢失。

## 2. 返回结果与不变的业务边界

外层仍返回 `COMPLETE_RESULT_AVAILABLE`（已存在完整最终结果），内层增加 `evidence`：

- `MATCHED`：本批所核对的原测量及配置证据一致。不是正常订单、测量成功、接单许可、
  人工关门证明、当前袋容量结论或资金处理授权。
- `WAITING_FOR_PROCESS_CUSTODY`：缺少原业务范围的过程保存凭据；返回准确范围、消息种类、
  测量编号与 MCU 启动/事件序号。即使裸测量还在，仍不能跳过原范围核对。
- `WAITING_FOR_CONFIGURATION_CUSTODY`：原配置集或其受理回复不足。不会使用后来配置补齐。
  若过程和配置都缺，优先显示缺过程，同时返回空配置；补齐后重新评估。
- 已有记录内部矛盾、摘要不合法或身份冲突时抛出校验错误。已持久保存的最终结果和
  待分类任务不删除、不改写，不转换为“没有结果”的重启恢复意图。

这些等待状态是本地评估结果，不是已经发出的查询、云端事件或人工处理任务。
本批没有新增 SQLite 表、消费完成标记或上报任务，没有串口发送、机械动作、重新测量、
占用释放、订单、余额或提现操作。原始字节依旧不可变；测试的直接数据库改写仅用于
构造校验失败反例，生产存储接口不允许覆盖原文。

配置核对证明的是“原始 MCU 子集内容与命令受理证据一致”，不是所有配置消费者已经
`APPLIED`（实际应用完成），也不替代完整云配置认证与全文摘要校验。
校准版本只作身份一致性核对，不判断秤的准度、不校准实物重量；250毫秒、5点、100克、
5秒中位数等既定采集规则未改变。

## 3. 实现与测试边界

- 新增 `hardware/native_result_evidence.py`，接入既有完整结果分支；不新增平行恢复入口。
- `NativeMcuConfiguration.from_parts` 从完整原配置字节重建不可变配置，拒绝混合应用/启动/
  版本、重复命令或乱序、错投口、改动内容以及畸形分块；逐块重新编码后必须逐字节一致。
- 将既有命令受理证据校验器公开为 `accepted_command_witness` 并共享，未另造仅信缓存的实现。
- 两类软件包源码清单均纳入新模块。真实 SQLite 数据由不继承仓库路径的 Python `-I`
  独立进程读取，实际执行完整结果核对；仅验证源码清单完整，不生成、签名或批准发布包。
- 复用 P1BB 超声波测试助手，只把原固定启动编号改为显式参数，默认42保持原测试含义。
  P1BB 文档中的旧文件摘要保留为当时的历史证据，不改写历史结果。

按已采用的 TDD（先让目标行为测试失败，再实现并复跑）推进；新增59项：
原结果/过程/配置41项、配置重建14项、两种包各投递/清运的独立进程测试4项。
使用真实 C 业务执行器、协议、配置受理和实际 SQLite；只模拟物理输入、时钟、串口连接
及非动作配置授权边界。不把模拟的其他配置消费者当作真机 APPLIED 证明。

关键反例包括：满溢摘要/阈值/数量或阶段时间错误；首末校准版本一起改错；结果元数据
与原测量不同；只剩裸测量、缺少范围凭据；只剩配置受理缓存、缺少原回复；错误轮次；
原业务结束后新配置被实际 C 受理，以及 MCU/Pi 重启后仍只读取旧业务的原配置。

测试先发现了新模块尚未进入两类包清单的问题：隔离进程4项均报缺模块；补齐清单后，
新旧共8项包内真实记录测试全部通过。未修改源码/发布版本不一致时禁止构建的门槛。
缺过程测试遵守实际外键约束：移除投递末重凭据时同时移除依赖它的结束选择测试记录，
恢复时先恢复末重再恢复原选择，没有关闭 SQLite 外键检查。
