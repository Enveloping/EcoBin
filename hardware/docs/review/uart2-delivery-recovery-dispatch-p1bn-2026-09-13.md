# P1BN：已归档投递到受限新关门的单次发送

日期：2026-09-13，接续 [P1BM 后台问题任务链](uart2-delivery-issue-reliable-chain-p1bm-2026-09-13.md)。
按已确认的投递取舍继续推进 P4；不是完整恢复接单或部署验收。

## 本批接通的路径

香橙派已通过正向启动证据确认 MCU 重启，并已将缺最终包的原投递可靠归档后，
新协调器 `NativeDeliveryRecoveryClose` 核对原业务占用、原开门绑定和永久动作账本，
为原投递门创建一份稳定的新 `SAFE_CLOSE`（独立投递门关门）命令。
不需要等服务器确认，也不要求服务器主动指挥关门。

本批连接现有 P1AM 受限永久许可与 P1AP 实际 C 关门执行器：

1. 原问题、原许可、原开门原文/摘要、永久动作序号、新关门完整原文、新动作/回执编号在
   业务数据库同一事务固定。此时尚未授权、尚未写串口。
2. 只有首次创建记录的运行实例保留本次发送令牌和不可延长的单调时钟截止点；重复准备只读取原记录。
3. 发出前重复校验当前前置条件、占用和期限，调用受限永久准备接口，再取得最终 ARM 授权。
4. 业务数据库提交“可能已发送”声明，再次复核期限和当前 MCU 启动身份，最多写一次串口。
5. 原命令受理回复可持久保存；无回复和香橙派重启只查询原命令，不能重新 ARM 或重放。
   实际 C 产生的关门输出记录沿既有动作交接器保存到 SQLite 后精确确认。

普通命令准备接口仍拒绝 SAFE_CLOSE，不把全部 CONTROL 类消息当作普通业务动作放行。
原开门不会重放、改成执行成功或人工隔离结论；问题原因仍为“单片机重启，未取得最终结果包”。
准备或发送期间收到原完整迟到包，也只补原问题证据，不恢复结算。

## 持久化和代码边界

- 业务 SQLite **35→36**：新增 `native_delivery_recovery_close`，将新关门命令和问题绑定同存同无。
  重开数据库时核对摘要、原问题/许可/启动/命令及完整原文；存在 SAFE_CLOSE 却缺绑定时拒绝初始化。
  35→36 不自动创建恢复许可，不改变原问题、原占用或已有确认。
- `native_delivery_recovery_close.py` 封装原问题到新关门的准备、受限授权和单次发送；
  `edge_store.py` 提供事务存储，并仅为这条专用路径支持 SAFE_CLOSE 的命令保管。
- 业务/运行时源码清单加入新模块，隔离安装目录可独立打开原数据库；永久层源码及接口不变。
- 本机接口测试适配器补入两条已有恢复许可操作，实际永久存储仍使用真实 SQLite 实现。
- 新协调器要求调用方提供会在条件不满足时抛错的实时前置检查；本批测试显式注入这项硬件边界，
  没有把空检查函数接到 main，也没有声称已经实现全机准入。
