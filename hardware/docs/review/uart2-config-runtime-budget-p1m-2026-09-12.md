# 原生 UART 2 配置运行核心与容量修正 P1M

日期：2026-09-12，承接 [P1L 称重配置](uart2-weight-config-p1l-2026-09-12.md)。本地候选，未部署、烧录或驱动设备。

## 配置切换核心

实际 C `McuConfiguration` 将完整集合与实际 `McuSession` 的命令接受/拒绝、
`McuWorkState` 的进行中业务/待保存结果连在一起。3 个固定存储区不超过1536字节：
现用配置、暂存候选、预检查草稿。前台单所有者，ISR不读这些配置，没有动态分配或Flash写入。

- 每条分段先完整校验，再检查原命令；旧命令、重复命令和身份冲突不改配置。
  新命令先缓存接受/拒绝，只有首次接受才改变存储区，不因丢回复再次执行。
- 只有全部分段及完整摘要正确、提交命令获接受时，整套候选才替换现用RAM配置；
  缺段、错误摘要或中途失败保留旧现用配置，不出现部分新、部分旧的配置。
- 进行中的投递/清运以及待保存结果会阻止配置；其他业务、采样、安全、升级条件须由
  所有者明确提供检查结果，不能把“没有投递记录”当成完整空闲证明。新业务还须检查配置暂存状态。
- 明确接受不同应用编号的新BEGIN可以替换暂存候选，不清业务、结果或现用配置。
  拒绝版本回退、同版本不同摘要、同应用编号改作另一版本；同版本同摘要的新应用可完整重新提交。
- Pi重新询问启动号不清配置；实际MCU重启丢失RAM配置，旧启动号命令不能重新应用。

`CopyActive`/`ReadWeightPolicy`表示此组件拥有的现用RAM配置，不表示硬件消费者已经接好。
**配置报文尚未接到控制入口，所有实际消费者/main尚未接通，所以不发APPLIED事件，也不发布伪造的
设备已应用版本。** 用户无需操作；后续继续接实际消费者、采集和业务，再同步云端配置。

11项实际C测试覆盖完整切换、旧配置保留、命令缓存、业务/结果互斥、外部前提、版本/应用冲突、
替换暂存候选与旧分段隔离、摘要失败、Pi重连和MCU重启；ARMCC编译通过。
其中业务占用通过既有已受理业务API构造，并非宣称正常投递/清运的串口执行器已接好。

## 找到并修正的程序空间问题

新增**只做链接、不执行、不可烧录**的核心容量探针，使用实际ARMCC5/armlink、STM32F103C8的
64KB Flash和20KB RAM边界，保留新核心公开入口及一组明确的前台状态对象。
它没有向量表、启动/硬件驱动或完整业务状态机，不是生产固件，也不证明完整栈预算。

第一次合并链接失败：完整报文校验函数以头文件内联形式重复进入多个模块，64KB空间不足，
仍有0x360字节的节无法放入。此前逐个对象编译通过不能证明整体装得下。

修正生成器：ARMCC5默认共享同一份完整校验函数，新增生成的
`contracts/uart/generated/c/ecobin_uart_protocol.c`，目标构建必须且只需编译链接一次。
主机可显式定义`ECOBIN_UART_SHARED_PAYLOAD_VALIDATOR=1`采用相同链接方式；
独立头文件用法仍可用于主机测试。两种方式使用同一生成函数正文，没有删规则、减少CRC/SHA校验或增加协议回退。

- 修正后同一核心探针最初ROM21240字节；补齐下述两个5秒入口后为 **21192字节**，RW+ZI **3840字节**，通过64KB/20KB容量边界。
  尚需加入剩余业务/真实驱动/启动和核算中断、回调、库函数的完整栈；不能将余量直接宣称为可烧录证明。
- 配置运行对象 Code由9574降至660字节；共享校验的代码计入公共对象，不是被删除。
- 实际C配置运行测试与控制入口/SQLite交接测试使用共享方式；最终31帧、730流轨迹、
  4摘要向量分别在独立头文件和共享方式执行。
- 契约25项通过、0 notes；104个生成文件一致。Registry仍rc.8、配置摘要v2、schema20。
- 配置运行核心加入后的扩大回归为671 passed、34 skipped、1616 subtests passed（117.04秒）；
  共享校验/容量修正后最终扩大回归 **672 passed、34 skipped、1616 subtests passed（111.11秒）**。
  Windows跳过项不代表Linux或真机已验证；`git diff --check`通过，仅既有CRLF提示。

旧3个运行制品保持冻结。OneNet/后端仍旧配置字段/摘要，候选发布门禁仍不放行；未修改HMI、云端或真实设备。

## 后续入口核对

继续检查时发现`SAMPLE_FULLNESS`和`MEASURE_BASELINE`仍接受旧6000ms期限。先由三端测试复现，
再将两个原生命令同步为const5000；它们不再绕过设备/投口统一的5秒策略。固定值检查取代原范围检查后，
自动生成轨迹从734变为730；不是跳过校验，两种C方式及Java/Python均重新通过。
最终扩大回归再次通过：672 passed、34 skipped、1616 subtests passed（108.77秒）；104生成文件检查一致。

下一实施点不能忽略：尚未接线的`WORK_PREOPEN_WEIGHT_READY`等过程消息仍使用旧`measurementResult`
（含UNSTABLE/末四点均值）结构。须按新取值类型和完整测量证据改造，不能把中位数硬填成稳定均值，
也不能因为最终`WORK_RESULT`已正确就认定所有过程消息已统一。随后连接配置报文/实际消费者、
真实采集归属、业务状态机和Pi持久交接/恢复，再做云端配置版本与存储的显式同步。
