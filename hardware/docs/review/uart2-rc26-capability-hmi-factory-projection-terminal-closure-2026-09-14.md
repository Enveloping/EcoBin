# UART rc.26能力、串口屏批次、工厂投影与终态失败收口

日期：2026-09-14。状态：本地跨端候选；未部署、未烧录，尚未通过真实串口屏、RS485、
门机构、清运机构或断电硬件在环（HIL）验收。

当前候选为UART `2.0.0-rc.26`、OneNet `2.4.0`、EdgeStore schema 40、数据库V83，
UART注册表共73种消息。发布状态仍为`MCU_REVIEW_REQUIRED`和
`SIMPLIFIED_BUSINESS_INTEGRATION_NOT_RELEASED`，本记录不能替代现场发布门槛。

## 1. MCU身份和能力是实际事实

`DEVICE_IDENTITY_REPLY`现在必须返回MCU当前启动编号、当前启动下已经消费的最高命令序号和
真实能力位。香橙派及业务发布校验要求能力位覆盖`0x8100`，不再根据固件版本、协议模式或
配置猜测MCU能力。能力缺失、未知或不满足要求时拒绝进入正常业务；身份查询本身不驱动机构、
不称重，也不创建业务。

工厂到生产入口仍只移交准确匹配的启动编号、结果序号和工作编号高水位。它不移交用户、资金、
业务所有权，也不允许生产入口重放工厂动作。

## 2. 串口屏的唯一软件可信边界

项目负责人确认：系统信任“写出指令即串口屏显示”，否则现有硬件无法对任何串口屏页面、数值
或二维码提供更强保证。这里的“写出”有且只有一个可检查的定义：**一条完整、未截断的高层
显示指令，或属于同一页面更新的完整指令组，已经通过一次队列头发布原子写入UART3软件发送
队列，即视为串口屏已经显示。**

系统不等待USART发送完成位，不要求串口屏返回应用确认，也不读取屏幕当前页面或控件内容。
真实屏幕观察只用于发现接线、组件名称、文本容量或HMI工程视觉兼容问题，不改变协议成功定义。

当前实现同时满足以下约束：

- `page0`、`page4`、`page8`切页，以及`page6/page7`的切页和一次性控件初始化，分别作为完整
  批次全有或全无地进入FIFO（先入先出）发送队列；
- 实时倒计时和重量也按完整批次入队；只有批次成功后才推进显示时间和已显示样本序号；
- 队列空间不足时发布零字节，不推进页面阶段、控件状态或样本序号，下一主循环继续重试；
- 后来的页面或数值指令只能追加，不能清空、覆盖或撤销已经入队的二维码或其他显示指令；
- 二维码`DEVICE_ENTRY_URL_APPLY_RESULT=APPLIED`仍只表示完整
  `page0.qr0.txt="..."`指令已经原子入队，不表示取得了屏幕回执。

这次没有增加HMI业务状态、逐控件确认或读回协议；串口屏接收方向仍只承担现有按钮事件。

## 3. uart-v2原生工厂验收和热点公开事实

P7工厂验收现在强制使用`uart-v2 / 115200 / 单投口`原生入口。验收以当前MCU身份、配置应用、
设备事实、一次START、完整结果可靠保存和`RESULT_SAVED`确认作为证据，不再把历史固定帧
`F0/F1`、`DD/EF`流程冒充当前量产验收。

热点页面及最终硬件报告现在展示而不只展示“通过/失败”：

- 称重空载、加载、卸载样本及操作者填写的参考克数；
- 超声波距离、阈值、遮挡判断和采集状态，或历史数字红外事实；
- MCU固件身份、启动编号、最高命令序号和能力位；
- 投递关门控制已经下发，同时明确“没有独立门位反馈”，不把控制信号伪装成机械到位；
- 清运锁已断电、锁健康未知、清运员人工确认门扇关闭等真实依据。

原生工厂动作的恢复仍只查询原命令和原结果；不能因为进程或设备重启构造替代START。固定帧
工厂模拟器仅保留为历史工具，不能作为rc.26量产P7通过来源。

## 4. 控制通信失败的跨端终结

香橙派确认原生投递START控制通信失败并上报
`FAILED / MCU_COMMUNICATION_UNAVAILABLE`后，后端在同一事务中把原投递会话终结为
`DEVICE_ABORTED`，保存准确错误原因，并且只释放仍属于该投递会话的占用。如果占用已经属于
后续业务，事务必须失败回滚，不能破坏新业务。

该投递终结不创建订单，不增加余额，不建立或触发提现。迟到的完整结果只可作为问题证据关联，
不能自动恢复结算，也不能覆盖当前袋、皮重或后续业务状态。仅通信超时仍不等于MCU重启，
也不自动套用重启归档结论。

清运不能照搬投递的直接释放规则：清运发生同类控制失败时结束为`ABORTED`，但已经进入换袋
风险范围的袋状态和人工恢复联锁继续保留，按既定“两袋人工确认与独立空袋皮重”规则恢复。
