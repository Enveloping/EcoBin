# 原生 UART 2 首次开门前置核对 P1R

日期：2026-09-12，承接 [P1Q 业务准备](uart2-work-preparation-p1q-2026-09-12.md)。
本批仅本地实现、测试，未连接设备、操作真实串口/GPIO、部署、烧录或修改 HMI。
Registry 仍为 2.0.0-rc.10 / PROCESS_EVENT_HANDOFF_NOT_RUNNABLE，SQLite schema22 不变。

## 本批做到哪里

新增 `hardware_mcu/USER/mcu_opening_gate.c/.h`，供后续业务执行器在首次开门前只读核对。
它读取实际 P1Q 保存的原始开始命令、原业务、首次测量、配置与过程交接记录，
不是重新建立一套模拟业务状态。没有动态分配、Flash 写入、串口发送或机械输出。

- 投递：香橙派取得并保存首次开门前重量及所需照片后，才应发首次开门授权。
  本模块核对当前 MCU 启动编号、原投递编号、原开始命令编号、投口、首次测量编号、
  等待授权阶段和原配置，返回这次授权最晚可开始执行的时间以及原自动关门参数。
- 清运：首次解锁核对原清运、原开始命令、投口、可用的首次解锁前重量及其精确保存确认。
  首次动作序号和恢复代数必须为 0，通电时长必须精确等于当前已应用配置中的清运锁通电时长。
  返回最晚开始时间、原清运截止时间和配置通电时长，不自行开启或延长电磁锁通电。
- **两者核对成功都不修改命令受理记录、业务阶段或事件序号，也不代表机械动作发生。**
  当前字节流入口依旧没有挂载这两条命令的执行器，仍不会伪造 ACCEPTED（已受理）回复。
  原业务保持等待阶段；只读核对不负责结束或放行后续业务，也不产生云端/资金任务。

## 关键规则

1. 完整报文先经过现有生成校验器检查长度、所有字段和命令摘要，之后才读取授权字段。
   非当前业务、不同启动、不同首次重量、不同父命令或投口均不能通过。
2. “过程槽现在空闲”不能替代“原始重量已被香橙派保存”。必须仍有同一启动、事件序号、
   原业务/步骤/配置范围及首次测量身份的已释放记录。
   数据还占用交接槽、槽被清空或证据不匹配都不能通过。
   精确保存确认只证明数据交接；不证明照片齐全，也不授予开门权限。
3. 稳定均值和 5 秒超时中位数都可作为有效前置重量；无可用数据即使占位重量字段是 0，
   也不能成为“测得 0 克”的开门依据。不处理称重准确度，不增加校准要求。
4. 核对时再次检查实际应用事实：当前启用投口、配置版本、完整内容摘要、MCU 子集摘要、
   校准版本及非暂存状态必须与原业务/测量一致。完整收到配置并不等于实际已应用。
5. 期限使用同一 MCU 64 位单调时钟。开始截止时间始终从原 START 首次受理时刻计算；
   香橙派给出的剩余时间从**该授权报文原始完整接收时刻**计算，两者取更早截止时间。
   清运还受原 START 时刻起算的操作窗口约束；不是从首次开锁重新开始计时。
   到达截止时刻即失效；时钟倒退、接收早于前置测量完成、64 位加法溢出均不能通过。
   例如 1020 毫秒收到剩余 500 毫秒的授权，截止就是 1520；到 1519 再核对仍是 1520，
   不能变成 2019。Pi 重连/重复绑定也不刷新原 START 时间。
6. 不接受旧命令序号，不能复用原 START 或最近保留命令的编号来伪装新授权。
   **这不是完整的动作去重器**：最终执行器必须先查询原会话，重复/旧命令返回原决定；
   本模块对非新命令返回的冲突码不能拿去覆盖旧的已受理/已拒绝决定。
   全历史编号唯一性与原始接收时间的可靠持有仍由外层命令账本/执行器负责。
7. 必须调用上层非修改式前置检查，处理尚未接入的实际安全、更新互斥、实际能力等条件；
   非法返回码按内部错误处理，不能当作放行。照片和香橙派授权账本应由香橙派在发送授权前核查，
   本模块不声称能够从 MCU 直接验证这些记录。PB5 底部防夹输入本身不被认定为开门故障。
8. 非零清运动作序号代表用户真实的再次开锁请求，恢复代数代表已续接的业务，
   不能走“首次解锁”分支。本批未实现对应请求生产者及恢复执行器，
   **不是取消清运过程中再次开锁的共识，也不是新增人工解锁政策。**

## 为什么尚未接机械输出

核对契约时确认了两项必须先接通的执行前提：

- `DELIVERY_DOOR_COMMAND_RESULT`（投递门输出结果）和 `CLEAN_LOCK_POWER_CHANGED`
  （清运锁供电变化）尚不在已完整守卫的 41 条消息中；现有过程交接槽只支持六类测量事件。
  不能在动作发生后才发现没有可靠的原始事件保留、查询及精确保存确认路径。
- 现有契约约定投递门输出在 100 毫秒双输出清零的换向间隔之后才可报告已发出。
  当前独立 DoorControl/ActuatorRuntime 设置目标后会立即更新输出，本批没有擅自去掉该规则，
  也没有假称已接通换向保护、自动关门及动作事件生产。

因此门槛通过只输出临时限值，不保存可重复使用的“许可”。后续执行器需要统一持有不可变的
原始报文接收时间，先处理原命令决定，再原子安排事件保留和单次受理/动作；
排队、换向等待和实际动作时仍必须遵守原期限，不能凭此前一次核对成功无限期延后执行。
实际整机配置消费者和更新/安全互斥也仍需接入，不能将当前测试的外部检查回调用于生产默认放行。

## 本地验证

遵循 `tdd` 技能，先加入投递前置交接测试，得到缺少入口的链接失败，再实现通过；
再加入清运首次解锁测试，确认原入口返回“不支持”后扩展实现。
后续边界回归均使用实际 C 会话/配置/业务/称重/过程槽与真实 SQLite 提交，
仅硬件输入输出和“其他消费者已完成应用”作为显式测试边界，没有用 Python 替代业务状态机。
每次核对前后还逐字节比较实际端点/准备对象，并检查测试 GPIO 写入计数未变。

- 首次开门核对 55 项，包含补充的非零 START 时刻、跨 32 位时钟边界及实际 MCU 上下文重置；
  加原准备阶段 37 项及 ARMCC 核心容量检查：**93 passed**（9.05 秒）。
- ARMCC5/armlink Cortex-M3 核心探针：Code29768、RO1488、RW40、ZI4640；
  ROM **31296**、RW+ZI **4680** 字节。新入口作为链接根保留，未因优化而消失。
  比 P1Q ROM 增加 1340 字节，不新增持久 RAM 所有者；局部变量仍需后续完整栈检查。
  `DO_NOT_FLASH` 探针只链接、不执行，不是包含启动、真实驱动、完整业务/中断的固件证明。
- 契约校验 **25 passed / 0 notes**；35 帧、1054 流轨迹、5 摘要跨 Python/Java/C 一致；
  **104** 个生成物与权威源一致。本批没有修改协议/生成物或旧三个冻结运行制品。
- 新 C 模块通过 Clang 静态分析，无诊断；`git diff --check` 通过（仅既有 CRLF 提示），
  新增文件另行检查无行尾空白。本批未更改 EdgeStore、主程序、Keil 工程或发布清单。
- 首轮扩大回归（当时本模块 49 项）：**884 passed、34 skipped、1620 subtests passed、1 failed**
  （175.53 秒）。失败仍是 P1Q 已记录的其他工作流 `DeviceAsset.listStatus` 未加入 OpenAPI required
  列表：`test_device_transport_and_runtime_presence_cannot_drift`。本批未修改设备列表接口、后端或放宽该测试。
  P1Q 曾出现的临时 SQLite 崩溃恢复 I/O 错误本轮未再现；不据此宣称已找到或修复其根因。
- 加入六项补充边界测试后的第二轮扩大回归，显式排除且仅排除上述接口声明测试：
  **889 passed、34 skipped、1 deselected、1620 subtests passed、1 failed**（176.91 秒）。
  失败是 `test_committed_edge_state_survives_forced_process_termination` 在强制结束子进程后，
  `EdgeStore._open_connection()` 执行 `PRAGMA journal_mode=WAL` 报 `sqlite3.OperationalError: disk I/O error`。
  这是 P1Q 已出现的偶发症状，本轮仍未解决，不能把第二轮记成全绿。
  冻结旧 UART、原适配层、发布清单与安装边界仍在回归中，未将跳过/排除项计为通过。
- 对该偶发问题按 `diagnose` 技能先界定反馈与复现范围：阅读真实子进程提交/强制结束/重新打开路径，
  然后以独立 pytest 进程连续运行原用例 **10 次，10 次通过**，每次均重新建立临时数据库。
  扩大集合可复现、独立运行未复现，不足以认定原因是硬件、Windows、SQLite 或测试顺序。
  本批不涉及存储实现变更，诊断止于记录复现范围，没有修改 EdgeStore、替换崩溃恢复用例、
  加入生产重试或跳过该测试；后续专项应捕获扩展 SQLite 错误码及失败当时的文件状态，再定位修复。
