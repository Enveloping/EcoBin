# S4：精简主链发布清单与隔离包保管验证

日期：2026-09-14。范围是把当前香橙派源码、签名运行包和后台包验证器对齐到同一份
可启动候选，并把发布隔离测试从已废弃的逐动作指令迁移到当前自主业务入口。二维码URL增量
已进一步把候选推进到rc.24。
本记录不代表已经部署、烧录或通过现场硬件验收。

## 发现的问题

清运中断人工袋确认完成后，源码数据库已经是 schema 40，但打包清单仍声明 schema 25。
构建入口会因此按设计拒绝真实源码，不能生成合法候选。递归检查当前本地模块依赖还发现：

- `main.py` 的恢复候选入口需要 `native_recovery_entry.py`；
- 该入口继续需要 `native_recovery_runtime.py`；
- `EdgeStore` 初始化及恢复关门隔离校验需要 `native_recovery_close_isolation.py`。

三者均不在当时的业务包或完整运行包清单中。仅从源码目录运行测试会借到工作区文件，不能
证明安装后的隔离包可启动。另有 24 项发布保管测试仍通过旧共享夹具发送
`AUTHORIZE_DELIVERY_FIRST_OPEN` 或 `UNLOCK_CLEAN_DOOR`；rc.23 正确返回“不支持消息”，
所以原失败是测试入口过期，不是应当重新开放逐动作控制。

## 本批处理

`RUNTIME_APP_FILES` 增加上述三个真实运行依赖，按既有排除规则派生的
`BUSINESS_APP_FILES` 同步增加；永久通信代理、设备更新器、密钥、厂家验收和特权 GPIO
模块仍保持原边界，没有被放入可替换业务包。发布 schema 改为 40，与
`EdgeStore.CURRENT_SCHEMA_VERSION` 一致。

后台 `BusinessReleasePackageVerifier` 同步采用完全相同的 63 个业务文件、schema 40 和
清单摘要。这样将来由运维人员提交签名包时，后台依据包内文件集合、schema 和摘要做同一套
校验；任一项不一致仍拒绝。同步认可只影响未来基于这份代码构建的包，不会自动部署代码，
也不会改变现有设备运行版本。

24 项隔离包保管测试改为：香橙派只发送
`START_DELIVERY_SESSION` 或 `START_CLEAN_OPERATION`，真实 C 代码自主执行后由香橙派查询、
保存和重开 SQLite。测试不再创建并不存在的逐动作许可。隔离重开后还核对：

- 原业务占用没有被提前释放；
- 原生命令清单没有新增机械动作；
- 问题归档后的迟到结果只补证据，不生成正常结算结果；
- 清运末重超时保持等待问题处理，不伪造成正常清运完成事件；
- 已保存结果、原配置和后台确认在独立发布目录中可原样读取。

这些验证只证明发布包对既有本地记录的保管边界。若业务发生控制通信失败、称重始终不可读
或已确认 MCU 重启，仍由前面已经确定的运行规则结束原业务或阻断新业务；本批不改变故障
分类、资金处理、袋状态或人工恢复规则。

## 旧夹具第一批迁移

第一批继续把测试依据从“Pi逐次批准机械动作”改为当前职责：Pi先取得并持久保存原业务许可和
唯一工作槽，只发送一次`START_DELIVERY_SESSION`或`START_CLEAN_OPERATION`；MCU随后按
本地按钮、定时器、PB5防夹和称重自主推进。旧命令若被直接发送，MCU会明确回复
`REJECTED / UNSUPPORTED_MESSAGE`，不会写GPIO。这样可以区分“旧入口已经退役”和“串口没有
回复”，也不会为了让旧测试通过而重新开放动作命令。

本批把投递开/关门时序、100毫秒换向死区、防夹暂停及解除续动、更新取消、清运锁脉冲、本地
重开和本地结束等核心MCU行为改到START自主测试。香橙派的工作恢复、投递问题归档、问题上报
和后台确认测试也改用同一自主流程：Pi可保存已经取得的首末重量，但最终结果包缺失时仍只归档
问题；已保存完整结果始终优先；归档后的迟到结果仍只补证。

迁移时发现一处实际完整性缺口：rc.23取消逐动作许可后，恢复入口原来只用旧动作绑定核对永久
许可；当前流程没有该绑定，若只比较业务编号，理论上可用另一份同业务许可冒领恢复。正常入口
本来已在取得工作槽时持久保存完整`job_safety`许可。本批让恢复入口在没有历史动作绑定时，改用
这份工作槽许可逐字段核对；许可编号、投口、业务类型、START身份或发送事实任一不符都拒绝，
不建立问题归档、不释放占用，也不改变是否接单。历史v1若确有旧动作绑定，继续按原绑定只读核对。

主代理合并运行当前MCU自主执行、Pi恢复/归档、冻结v1兼容、精简纵向业务及发布隔离保管共
**265项通过（67.28秒）**；其中恢复/归档四文件与v1兼容单独复核为**165项通过**。没有
`xfail`或跳过来隐去旧失败，也没有连接现场设备、部署、烧录或修改共享数据库。

## 旧夹具第二批迁移

第二批继续迁移投递开门前失败、关门后称重、继续/结束收尾、更新取消，以及清运解锁前称重
失败和清运中断。原117项围绕逐条过程保存回执的测试收敛为38项当前行为测试，保留：

- 首重无数据/不足五个样本时不动作、不补零，并在结果中保留实际样本数；
- 五个稳定样本取均值，5秒仍不稳定取中位数，末重不可读不复用首重；
- 投递开门、自动关门、100毫秒换向死区、PB5关门防夹和解除续动；
- 当前轮`CONTINUE`/`END`按钮、选择超时、陈旧按钮拒绝、连续投递最终轮重量；
- 更新或期限中断后停止输出，保留已经观察到的重量/轮次，最终结果不可变且不会恢复动作；
- 清运锁脉冲、本地重开、本地结束和中断阶段，不把PB5或未发生的人工确认伪造成完成。

香橙派的最终结果完成、结果证据和上报测试同步改用rc.23完整结果。当前v2正常结果只依赖原
START、原工作槽许可、配置和完整`WORK_RESULT`；删除独立按钮、测量过程或动作表后，正常
判断和报告保持相同。测试仍覆盖自洽重算摘要后的七类START身份篡改、许可替换、首末测量/
校准、结果索引及分类任务损坏、报告事务回滚、数据库重开幂等、照片快照冻结和非法价格。
投递末重失败由完整结果中的最近CLOSE控制事实形成异常报告；清运末重失败只保持本地失败，
不伪造正常清运完成或更新袋/皮重。

审查时还移除了现行上报测试对旧`native_result_execution`测试帮助函数的引用；连续投递和清运
重开均直接驱动当前MCU本地按钮。扩大合并回归第一次发现8项旧测试夹具未把原许可写入工作
槽，新的许可校验按设计拒绝；夹具随后对齐真实入口，没有放宽生产校验。最终合并当前MCU、
Pi恢复/归档、结果/上报、v1兼容和发布保管共**437项通过（107.46秒）**。

## 旧夹具第三批迁移

第三批把START准入、清运本地重开/结束按钮、旧二次确认和结果执行证明改到rc.23现行边界：

- START与已应用配置或投口不一致时拒绝且不动作；同一START可幂等查询，另一业务在忙碌时拒绝；
- 首重稳定或5秒中位数完成后，MCU自行开投递门或给清运锁脉冲；首重不可读时形成失败结果且
  不写门或锁输出；
- 清运重开与结束都是MCU本地按钮，不等待Pi保存按钮回执或再发确认；旧动作授权明确返回
  `REJECTED / UNSUPPORTED_MESSAGE`，不能产生GPIO效果；
- 完整`WORK_RESULT`自身携带原START身份、首末测量顺序、业务轮次和最终关门/锁断电控制事实；
  正常判断不再要求独立过程表、动作绑定或执行事件，但仍严格拒绝身份替换、摘要损坏、同身份
  异文冲突、结果索引损坏和缺失分类任务；相同结果重复保存保持幂等。

保留给邻近历史测试导入的帮助函数只用于逐步迁移，其中旧grant构造器只出现在“不支持消息”
边界测试中。主代理把本批MCU、清运按钮、结果执行/完成/证据/上报、冻结v1兼容和安全关门组合
复核为**200项通过（40.47秒）**，没有跳过或预期失败。扩大交叉回归另有201项通过，但旧
“业务内采样组过程交接”套件的17项仍使用旧编译夹具，已明确进入下一批迁移；不能把该问题
解释为应恢复逐动作命令。

## 旧夹具第四批迁移与历史兼容顺序

业务内采样组测试已改为把称重与可选满溢诊断分开。现行固定199字节`WORK_RESULT`只承载
业务身份、结束原因和首末称重，不为保留旧测试而增加满溢字段。MCU不等待任何过程保存回执就
能自主形成并持有结果；超声波的真实样本、中位数、无回声/有效样本不足降级、部分采样中断和
最新设备快照仍可独立查询，连续投递的新一轮也不能复用上一轮测量或满溢组。为了观察同一槽中
后续诊断而释放旧诊断邮箱的测试，明确发生在本地继续按钮已经生效之后，不构成业务授权。

同时拆除了现行恢复测试对旧清运动作账本测试的夹具依赖。中立`AutonomousRecoveryWire`只服务
一次START后的当前本地流程，并显式禁止写出旧首开、旧清运解锁和`SAFE_CLOSE`机械命令；
`RecoveryWire`保留兼容名称，其他恢复/问题归档测试无需跨历史测试文件导入。主代理组合复核
当前恢复、问题归档、结果处理和本批采样组为**261项通过（61.99秒）**；采样组与MCU自主/
清运按钮另行复核为**44项通过（10.01秒）**。全部硬件测试仍可收集，共4475项。

历史动作/恢复关门的303项测试已完成依赖审计，后续固定顺序如下：

1. 旧首开和清运动作账本改为加载两份现有checkpoint-v1数据，只验证原字节读取、损坏拒绝、
   幂等和冷启动，不再让当前MCU执行废弃命令；
2. 增加历史恢复关门规范化输入，覆盖已准备、已授权但Edge认领未知、已确认有输出、已退休、
   已撤回、已隔离及历史继任记录；Edge是否认领不能从永久账本推导，另由后续Edge输入验证；
3. 恢复候选只处理这些既有记录：允许查询、确认、退休、撤回和隔离，始终拒绝接单且本次写出的
   `SAFE_CLOSE`为零；
4. 最后迁移九个共享恢复夹具的消费者，再退役“现在新建/发送恢复关门或新继任动作”的断言。

生产历史读取模块暂不能删除：已创建的v1报告仍走`reconcile_legacy`，旧卡数据库也可能留有待
收敛记录。正常主链没有调用主动恢复关门；保留模块只代表读旧记录和安全收敛，不代表恢复这套
控制方式。

## 旧夹具第五批：冻结动作与恢复历史输入

旧首开与旧清运动作核对的101项动态测试已替换为34项checkpoint-v1只读兼容测试。两份既有
JSON是历史提交`3178a994…`由真实旧C执行及旧报告生成器导出的原始表行；当前测试不再编译旧C
或向当前MCU发送旧命令。保留验证包括START/动作受理、OPEN/CLOSE或锁通断输出、首末称重、
清运完成按钮与人工关门事实、v1报告和`reconcile_legacy`；UUID、boot、投口、配置、摘要、原始/
保存载荷、回执和时序任一被破坏，都在冷启动或只读核对时拒绝且不自动修补。两动作文件自身
**34项通过**；与冻结v1及全部结果系列组合为**209项通过（42.42秒）**。

另增加18项永久账本恢复历史规范化输入测试。它不是旧SQLite逐字节导出，而是以历史协议和恢复
合同为来源、使用固定原始UART字节及当前公开UpdaterStore API重放的确定性输入。可表示七类永久
状态：已准备、已授权但Edge认领未知、已确认有输出、已退休、已撤回、已隔离、历史继任已准备。
永久账本本身没有Edge `write_claimed`事实，因此没有伪造“ARMED且确定未认领”或“已认领但效果
未知”变体；这个缺口明确保留给后续Edge历史输入。主代理将这18项与两份动作兼容及既有v1兼容
合并复核为**56项通过（6.97秒）**。

本批完成后，仍有恢复候选及其九个共享消费者约202项需要迁移；现有规范化永久输入只是解除
动态旧MCU依赖的第一层，不能替代Edge认领、已有输出和schema迁移测试。
