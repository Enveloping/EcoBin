## 已实现的业务含义

单片机完成投递前后或清运前后的某次称重时，过程消息现在能准确表达：

- 最近窗口满足条件后取得的稳定均值；
- 5 秒仍波动、但有足够合法新读数时取得的中位数；
- 真正没有可用重量或传感器故障，而不是伪装成测到了 0 克。

例如，实际 C 核心在 5 秒内取得 20 个交替的 -1000/+1000 克读数，过程消息保留
`TIMEOUT_MEDIAN / 0g / 20点 / 跨度2000g / 5000ms`，与最终结果使用同一测量对象。
纯波动中位数依共识可以继续业务，不改标为旧 UNSTABLE、末四点均值或稳定值。
这证明的是本地核心与序列化行为，不是实际称重模块能以 250ms 响应或准确度已合格。

香橙派新增的是本机过程证据存储：完整校验后的原始正文提交到 SQLite 后才返回 STORED；
完全相同的重复返回 DUPLICATE。不会创建云端事件或最终结果待上报任务，不释放业务占用，
不触发订单、钱包或提现，也不自动发送 ACK（接收确认）或授权机械动作。
后续业务所有者仍须核对原业务、启动编号、轮次/清运动作及有效授权，才能使用证据或发确认。

## 契约与 MCU

- Registry `2.0.0-rc.9 / PROCESS_MEASUREMENTS_NOT_RUNNABLE`；55 条消息，37 条有完整接收内容校验：
  16 条引导/会话、15 条带启动约束的下行、6 条过程称重。
- 六类为投递开门前/关门后、清运首次解锁前/最终称重、满溢采样和空袋基准测量。
  共同记录测量种类、整数克数、耗时、样本数、参与取值样本跨度、校准版本、故障细码和实际采用的配置版本。
- 均值和中位数至少 5 点、最多 32 点；均值跨度最多 100g，中位数耗时恰为 5000ms，成功不得带故障码。
  耗时不超过本启动运行时间；启动号、事件序号、测量 UUID、配置版本非零。
  失败种类的重量槽必须为零，但种类表示无可用值。NOT_TAKEN/MCU_RESET_LOST 是最终结果的缺失槽，
  不能冒充当前 MCU 实际完成的测量事件。故障细码只附加已有诊断，没有细码不把失败种类变为成功。
- BASELINE 的 `measurementUid` 仍为原任务编号，`weightMeasurementUid` 才是实际测量编号。
  满溢消息的距离/红外分量沿用原候选规则；新称重校验不代表那部分消费者或业务准入已实现。
- 保留未启用的旧 `STATE_SNAPSHOT_PORT` 测量结构及 v1 快照摘要，不拿它兼容/改名新的中位数。
  旧 OneNet/后端称重字段也未悄悄更改；配置摘要 v2、最终结果布局/摘要不变。
- 修正了开门前重量消息原来误写为“门命令输出”的说明；同时修正数字枚举输入与名称输入在满溢校验中的差异。

新增实际 C `mcu_process_measurement.h/.c`，只组装前四类业务测量事件：

- 原业务编号、启动命令编号和投口从已保留的 `McuWorkState` 取得，不接受调用方另塞一套业务身份。
- 使用现有 `McuResultMeasurement`，检查同启动、业务类型、实际测量阶段、步骤编号和生成的完整报文校验。
  清运/轮次过程字段仍为 u16；拒绝超范围，不把 65536 截成 0。此上限在业务所有者接线时仍需处理耗尽，不能回绕。
- 在推进阶段前组装一次，后续发送/恢复应保留原字节，不能重新生成事件或重新测量来冒充重传。
- 输出只写调用方暂存区；不会修改业务、完成结果槽、测量对象，不分配编号，不发串口、不动 GPIO。
  满溢/基准的实际 C 事件生产者、过程事件保留及精确确认仍未接入。

## Pi 存储与迁移

`EdgeStore` 和候选发布声明同步到 schema21。两个独立表保留终态过程原字节及冲突证据，
迁移不删除旧业务、结果、动作命令或启动分配记录。没有把过程数据塞进已有云端结果队列。

- 去重同时检查启动号+事件序号和实际测量 UUID；同一身份不同内容保留双方，不覆盖原值。
- 冲突保持锁定：后来重发原包、给冲突事件换 UUID、给冲突 UUID 换事件编号，均不能洗掉已有冲突。
  一包同时冲突两条原记录时两条都保留并标为不可正常读取；冲突证据可单独查看。
- 正常读取会重验正文、索引身份和存储 SHA；这里的 SHA 是本机完整性检查，不替代认证或业务授权。
- 禁止嵌套在另一个数据库事务内，避免在外层尚未提交时声称已保存；写失败、提交失败不返回成功。
- 返回值不含可以直接发给 MCU 的保存确认正文。当前记录不会自动关联/推进 `WorkManager`，
  因此不能以“已存证据”宣称首次开门前置条件或断点恢复已经闭合。

旧后端仍只接受原文件清单/schema18，候选发布继续被拒绝。schema21 不意味着已部署或允许覆盖旧卡。

## 验证证据

遵循测试先行：先复现旧过程格式无法表达中位数、错误内容可进解析出口，再补契约/校验；
实际 C 生产者和 SQLite 保存也先由缺失接口测试暴露，再实现、增加边界及恢复测试。

- 过程契约 5 项，实际 C 组装 20 项；同一组固定帧及异常流轨迹覆盖 C、Python 3.11 和 Java 21。
- 存储 23 项，涵盖真实 C→Pi 原字节、六种消息、重开/并发、身份冲突、坏正文/存储损坏、
  嵌套事务、写入/COMMIT 失败、插入前/后及提交后强制退出、v20→v21 中途退出回滚和旧数据保留。
- 旧 v18/v19 迁移演练随新 schema 补齐旧形状构造，仍在原 v19/v20 提交边界强制退出，未绕过旧恢复测试。
- 契约工具 **25 passed、0 notes**；**104** 个生成物一致，**31 帧 / 978 流轨迹 / 4 摘要**通过。
  C 的独立头文件和共享实现两种构建方式都运行同一套黄金样例；旧三个运行制品保持冻结。
- ARMCC5/armlink 将新增 C 生产者计入只链接探针：Code23488、RO1124、RW40、ZI3800；
  **ROM24652 字节，RW+ZI3840 字节**。探针不可执行/烧录，没有启动向量、完整驱动和业务状态机，
  也不证明完整中断/库调用栈预算；ARMCC 仍须且只能链接一份生成的 `ecobin_uart_protocol.c`。

扩大回归最终为 **720 passed、34 skipped、1616 subtests passed（127.53秒）**，覆盖契约、新旧
MCU核心/适配、实际C控制入口、Pi会话/结果/过程存储、进程退出恢复、动作许可/永久账本、
运行包/业务包/镜像安装与切换相关测试。Windows环境跳过不代表Linux或现场已验证。
迁移测试随后补强对真实持久命令记录的保留断言，定向再次通过。
`generate_contracts.py --check`确认104生成物一致，`git diff --check`通过，仅既有CRLF提示。

第一轮扩大回归暴露三处schema升级配套差异：候选发布声明仍20、旧v18/v19测试数据库构造未去掉
新v21表/版本行。已同步声明为21并修正旧形状构造，没有删除真实数据、跳过测试或降低恢复断言；
三项定向及上述最终扩大回归全部通过。
