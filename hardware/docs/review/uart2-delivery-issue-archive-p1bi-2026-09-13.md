# P1BI：投递重启问题裁定与迟到结果证据保管

日期：2026-09-13，接续 [P1BH 后台确认交接](uart2-native-confirmation-p1bh-2026-09-13.md)。
依据[用户明确确认的两项决定](../../../docs/architecture/delivery-restart-result-decisions-2026-09-13.md)，
落实原计划 P4/P5 的本机裁定与保管部分。这不是整套恢复、云端问题闭环或部署完成。

## 本批已实现

香橙派在原投递占用、原许可/开始命令、原设备/配置身份及真实新 MCU 启动握手都核对后，
可以通过 `NativeWorkRecovery.archive_delivery` 提交独立的问题型终态。
仅通信超时、Pi 单独重启、同 MCU 启动身份不触发归档；清运不能进入此接口。

- 原恢复意图仍是中间记录，不自动变成问题。归档前再次在 SQLite 写事务内检查完整最终包；
  完整包保存先提交就继续原结果处理，归档先提交就永久保持问题结论。
- 归档原因固定为“单片机重启，未取得最终结果包”，代码为 `MCU_RESTART_FINAL_RESULT_UNAVAILABLE`。
  不是“重量全部丢失”，也不计算一笔可结算的投递净重。
- 全部已知原始命令/回复、测量、动作、结束选择均按原字节和来源保存快照；
  同时保留原业务上下文、设备、许可、启动及配置关联。没有测量就不编造零重量。
- 每个原投递只有一个归档身份。重复调用取回原结论，不要求原业务继续占用当前槽位，
  因而后续业务进行中也能查询原问题。
- 迟到完整包先核对原投递、原命令及序号、原 MCU 启动、投口、配置及协议摘要。
  核对一致后，原完整包和问题证据关联在同一事务提交，提交后才给 MCU 精确保管回执。
- 重复原包复用关联；同编号冲突保存冲突原文，不覆盖第一包。不同结果编号的冲突也保留原文，
  不替换原可信关联。身份错误的格式合法包保留在原始保管表，但不关联为可信问题结果、不回成功保管回执。
- 归档后的结果不再进入正常结果待办列表。正常报告、恢复核对及旧完成入口均不能将原投递重新上报为
  `DELIVERY_COMPLETE`。袋、皮重、后续业务占用和永久许可不会因迟到包修改。

原最终包的保管待办仍存在，用于保留精确 UART 交接身份；有归档判决时从正常分类列表排除。
这不是把原始结果删除，也不是把迟到结果当作新的正常订单。

## 存储与失败恢复

业务 SQLite **32 → 33**，新增原归档、冻结过程快照、迟到结果关联三张表。
迁移只建立结构，不把已有中间意图批量归档；原数据和归档结论不回填成业务成功。
启动及查询重新校验原身份、快照摘要和迟到包完整性，损坏不提升为正常业务。

原结果保存与归档裁定共用 SQLite 写事务互斥；不存在“看见缺包后解除锁，随后直接写归档”的窗口。
恢复意图可先单独提交，但它没有结算或归档权限。归档提交失败后，后来保存的完整包仍可优先处理。
问题归档、问题证据关联、永久动作账本和后台处理不是跨库单事务，不能把本批当作全部收尾已完成。

  后续换袋状态保护、并发、写盘失败、真实子进程退出、迁移回滚及重启检出证据损坏。

  重启读原归档、追加迟到包、保持原结论，不依赖工作目录的源文件。
- 扩大回归 **383 项通过**（84.59 秒），覆盖上述问题、P1BH 确认、原报告、隔离包、
  EdgeStore、OneNet 编解码/接收、重启核对、原动作/结果执行及 MCU 投递执行。

  跳过项为 POSIX 文件所有权、硬链接、权限边界，在 Windows 不适用；不是零跳过全量测试。
- 完整机器契约：**25 通过、0 notes**；104 生成文件精确匹配，67 UART 消息，
  50 帧/1826 流轨迹/16 摘要向量经 Python、Java、C 校验。此次未新增云端事件或修改 UART。

所有测试使用临时数据库、宿主机 C 状态机和本地缓存依赖；未连接真实串口、驱动机械、SSH、
