## 本批实现的业务行为

例如香橙派已准备或发出投递开门指令，尚未取得受理回复，单片机随后重启：

1. 香橙派仍通过既有握手询问启动编号；看到 `0` 只表示需要提出一个新编号，不立即认定
   已完成绑定，也不允许旧指令退出等待通道。绑定回复丢失时，下一次只发新查询。
2. 本次查询对应的有效回复确认了一个本机分配的非零编号后，香橙派在一个业务库事务中
   保存该启动周期第一份完整回复正文、确认当前编号，并标记更早启动周期的指令不能再发送。
3. 旧指令保留原文、原发送声明、已有回复、冲突标记及原受理结果。如果原来结果未知，
   现在仍未知；不会被补成“未执行”“执行失败”或“已成功”。后续迟到的原受理事实仍可保存。
4. 新启动周期可以准备自己的配置/指令记录，不再被旧周期的受理等待记录永久堵住。
   这不授予任何机械动作权限：原永久动作账本仍阻止无关开门，业务占用仍保持，不接新单。

香橙派单独重启、查询超时、仅收到 `0`、过期回复、错误查询号、绑定失败以及外来未分配编号，
都不能触发上述旧指令标记。绑定回复说“已经绑定”的时候，记录的是 MCU 实际返回的编号，
不是香橙派刚提出的编号。再次确认相同启动编号不覆盖第一份证据，也不解除本周期未决指令。

旧进程内存中的启动观察即使还没过期，也不能让已被另一当前观察标记失效的旧指令进入最终
发送授权；发送器在调用永久授权前先检查该标记。发送声明提交时还会再次检查。

## 存储和接口边界

- 业务库从 schema **28** 前向升级到 **29**；永久库仍为 **3**。
- 新表 `native_mcu_boot_observation` 每个已确认启动编号仅一行，保存消息种类、查询号及
  完整不可变正文。不是每秒一行的轮询日志，也不是单片机 Flash 或随机启动号方案。
- `native_mcu_command.boot_retired` 只表示旧启动周期的指令退出当前发送/受理等待通道。
  它不是业务终态、物理完成或永久动作核销。唯一未决约束只计尚未退出通道的指令。
- `McuBootSession` 负责查询相关性、单次消费和时效；`save_native_boot_observation` 负责
  检查本机分配关系、原始正文及事务提交。后者不是独立的“新鲜度证明”接口。
- `get_native_boot_observation` 返回重新检查过的历史证据。新香橙派进程绝不因此获得
  “当前已连接”状态；仍须取得新握手。旧的数字型 `recognize_native_boot_id` 入口不创建
  证据、不标记旧指令退出通道，不能替代恢复判断。
- 启动重查会验证原文与投影一致；已标记旧周期的指令必须有更晚的有效启动证据支撑。
  删除该证据后重启会报错，不默默保留放宽后的通道状态。
- 旧 schema28 数据库升级不补造历史回复，不擅自改变未知结果。DDL、索引和版本标记
  仍在原迁移事务中提交；中途失败后保留原结构和原数据。

UART Registry 仍为 **2.0.0-rc.20 / CLEAN_INTERRUPTION_CUSTODY_NOT_RUNNABLE**，没有修改
线协议、生成物、MCU C 或正式 `main` 接线。不产生新的 MCU 固件及 ROM/RAM 报告。

  外来编号、第一份原文不覆盖、原占用保留、跨周期两个未知记录重启，以及永久账本拦截。

  **269 通过，42.47 秒**。

- 两个数据库拒写断点证明：保存异常后本次回复已消费，不能再用原回复进入已连接状态；
  新查询重新取得事实后才可保存。四项旧库升级路径含三个迁移拒写断点。
