### 1.1 单机隔离例外

同一 CVM 上的独立容器、网络和数据卷只能提供实例/运行时隔离，不能提供主机级物理
隔离，也不能消除单主机、单系统盘故障。原 H-02 的“物理隔离”若严格解释为独立主机
或托管实例，本计划无法满足。

原 H-02 隔离验收要求主审二选一并记录结论：

1. 接受“前期受控试验期同主机例外”，以独立容器、网络、卷和禁止新旧交叉连接作为
   当前验收边界，同时保留后续拆库触发条件；或
2. 不改变原验收口径，H-02 继续保持 `in-progress`，直到使用独立数据库主机/服务。

不得把同主机隔离写成已经实现主机级物理隔离。

例外”。H-02 当前以独立容器、网络、数据卷和禁止新旧交叉连接为隔离验收边界，同时

## 3. 单机目标拓扑

```text
Internet
   │
   ├── TCP 22：仅管理来源 IP
   └── TCP 443；TCP 80 只做 HTTPS 重定向
            │
            ▼
   ecobin-target-web / reverse proxy
            │ Docker private network
            ▼
      ecobin-target-backend:8080
            │ Docker internal DB network
            ▼
      ecobin-target-mysql84:3306
            │
            ▼
   ecobin-target-mysql84-data
```

固定隔离对象建议为：

| 对象 | 目标名称 |
|---|---|
| Compose project | `ecobin-target` |
| Web | `ecobin-target-web` |
| 后端 | `ecobin-target-backend` |
| MySQL | `ecobin-target-mysql84` |
| 数据卷 | `ecobin-target-mysql84-data` |
| Web/backend 网络 | `ecobin-target-app` |
| backend/MySQL 网络 | `ecobin-target-db`，设置为 `internal` |

最终运行态不得出现：

- `0.0.0.0:3306->3306`、`[::]:3306->3306`；
- `0.0.0.0:8080->8080`、`[::]:8080->8080`；
- 后端和 MySQL 使用 `network_mode: host`；
- 目标容器挂载仓库根 `.env`；
- Web 容器进入数据库网络；
- 旧应用连接目标库，或目标应用连接旧库。

没有可用域名和证书时，Web/API 保持不可从公网使用，不能用 HTTP 明文登录替代 HTTPS。

H-02 迁移期间若宿主机 Maven 作业必须访问数据库，只允许临时绑定
`127.0.0.1:13306`。迁移和权限验收结束后必须移除该映射并重新验证；不得把迁移端口
加入腾讯云安全组。

## 4. 凭证保管方案

### 4.1 责任分层

| 层级 | 位置 | 职责 |
|---|---|---|
| 当前长期原件 | 操作机 ACL 受限 `.ecobin` | 当前受控试验的人工保管源；仅当前用户与 `SYSTEM` 可访问 |
| 服务器运行副本 | `/etc/ecobin/secrets/` | 只供部署和指定容器读取 |
| 容器内 | `/run/secrets/<name>` | 只挂载该服务需要的最小秘密 |
| 下一版本加固 | 加密密码库及异机密码库密文副本 | 降低操作机失陷、损坏或丢失风险 |

“放在服务器上”是可行的，但服务器文件只是运行副本。2026-07-27，项目负责人明确
接受本前期受控试验把操作机 `.ecobin` 的受限明文作为长期原件，并接受操作机失陷、
损坏或丢失带来的保密性与可恢复性风险。该例外不允许把秘密写入 Git、聊天、日志、
工单或服务器普通目录。

### 4.2 下一版本：加密密码库

本版本不建立加密密码库。下一版本加固时，操作人应创建一个支持强加密的离线密码库：

- 主密码不得与 SSH、数据库或腾讯云密码相同；
- 密码库文件至少有两份，位于两台不同设备或一台设备加一个受控云盘；
- 云盘只保存已经加密的密码库文件，不保存明文导出；
- 主密码或恢复材料采用独立的离线保管方式；
- 每次生产密码轮换后先更新密码库，再验证第二份密文副本可以打开；
- 文档只记录条目名称和保管位置类别，不记录任何密码。

完成密码库主副本和异机密文副本开启验证后，才能把它们写成已建立；当前 CMS 加密
暂存包不等于用户密码库。后续需要自动轮换、多人审计或减少人工分发时，再将长期来源
迁移到腾讯云 SSM，并给 CVM 绑定最小权限实例角色。这些均不是当前 H-02 的完成前置。

### 4.3 服务器运行副本

建议目录布局：

```text
/etc/ecobin/
├── runtime.env                 # 仅非秘密配置，root:ecobin-deploy 0640
└── secrets/                   # 长期运行源，root:root 0700
    ├── mysql-root-password    # root:root 0600
    ├── db-app-password        # root:root 0600
    ├── db-backup-password     # root:root 0600
    └── ...                    # 后续真实渠道秘密按服务拆分
```

规则：

- 长期运行源保持 `root:root 0600`；启动前由 root 部署脚本把后端所需项复制到
  `/run/ecobin-secrets/backend/`，该目录位于 tmpfs；
- 后端镜像固定使用 `USER 10001:10001`；临时秘密为 `root:10001 0440`，容器只读
  挂载。部署验收必须用容器内 `id` 和只读探针证明非 root 进程能读、其他服务不能读；
- MySQL 使用 `MYSQL_ROOT_PASSWORD_FILE`；不得为了读取秘密让后端以 root 运行；
- Compose 使用 `secrets.file` 或等价只读挂载，不依赖无法验证的默认 UID/GID 行为；
- Spring Boot 优先使用 config tree 或文件读取，不把密码写进 Compose `environment`；
- 运行应用只得到 `ecobin_app`，不得得到 root、schema owner 或 backup 密码；
- schema owner 密码只在单次 V1～V10 作业内存在，完成后删除配置并锁定账号；
- trigger definer 从创建起锁定，不作为可登录运行身份；
- `docker compose config` 只用静默校验，不把完整展开结果保存到普通日志；
- 禁止在 shell 历史、命令参数、Git、镜像层、普通日志或工单中出现秘密值。
- 不把 `ubuntu` 加入 `docker` 组；Docker 操作继续经受控 `sudo`，因为 Docker 管理
  权限等价于主机 root 权限。

当前 `/opt/ecobin/EcoBin/.env` 的秘密完成迁移后必须全部轮换。轮换和新容器验证完成前
先保留该文件用于旧栈回退。删除前必须完成以下二选一：

1. 用仓库外 `root:root 0600` 的 legacy 运行配置替代旧 `.env`，注入轮换后的有效
   凭证，并执行一次旧栈离线启动/readiness 回退验证；或
2. 主审明确宣布旧栈回退窗口结束，改以 H-01 制品和备份恢复而非直接启动旧栈。

确认旧值失效和回退路径有效后，再经单独授权删除旧 `.env`，不能在计划阶段擅自处理。

## 5. 资源与容量边界

### 5.1 试验期初始预算

当前 3.3 GiB 内存只能运行一套活动栈。建议初始上限：

| 服务 | 内存上限 | 进程建议 |
|---|---:|---|
| MySQL | 1152 MiB | 初始 `innodb_buffer_pool_size` 约 512 MiB，后续按命中率调整 |
| backend | 1024 MiB | 初始 JVM `-Xms256m -Xmx640m` |
| web | 128 MiB | 只托管静态资源和反向代理 |
| OS/Docker/监控余量 | 至少约 1 GiB | 不分配给容器 |

Compose 必须使用实际对单机 Compose 生效的 `mem_limit`、`cpus` 和 `pids_limit`，
不能只写不会生效的集群声明。CPU 上限在一次轻量压测后确定，避免 2 核同时被构建、
MySQL 和 Java 用满。

生产服务器不执行 Maven/npm 全量构建；镜像在开发机或 CI 构建并固定 digest，服务器
只拉取/导入审核后的镜像。这样避免构建阶段与数据库竞争内存和磁盘。

### 5.2 Swap 和告警

实施阶段可增加 2 GiB 紧急 Swap，并设置较低 swappiness。Swap 只用于避免瞬时 OOM；
持续使用 Swap 代表需要降载或升配。

至少建立以下告警：

- CPU 连续 10 分钟超过 75%；
- 可用内存低于 600 MiB 或容器发生 OOM；
- Swap 持续有读写；
- 根分区使用率超过 70%，预测 7 天内超过 80%；
- MySQL 连接数、慢查询或锁等待持续增长；
- 容器 healthcheck 失败或反复重启；
- 最近一次异机备份超过 26 小时；
- 最近一次恢复演练超过 30 天。

出现任一情况时先停止增加真实流量。出现两周内多次 OOM、CPU/IO 长时高位、数据量
快速增长或业务开始要求低停机时，应启动独立数据库方案评估。

试验期先按监控做两级处理：

1. 只有内存/CPU容量不足、IO 和可用性要求仍低时，先把单机升到 4 vCPU / 8 GiB；
2. 出现数据库 IO 竞争、备份影响接口、需要故障转移或不再接受单机停机时，直接拆分
   数据库，不再只纵向升配。

本文所称“长时高位”按连续 15 分钟 CPU iowait 超过 20%或 MySQL 关键接口 p95
相对无备份基线恶化 20%以上处理；“快速增长”按 30 天预测触发第 9 节磁盘门处理。

## 9. 后续拆分数据库的触发条件

满足任一条件就建立独立数据库方案，而不是继续挤压单机：

- 业务不再接受单机故障造成整体停机；
- 数据恢复目标需要自动故障转移；
- 7 天内两次出现内存/OOM、Swap 持续使用或磁盘 IO 长时饱和；
- CPU 连续多日高峰超过 70%，降低应用并发后仍无法改善；
- 数据、binlog、备份增长使根盘预测 30 天内超过 70%；
- 备份/恢复任务明显影响在线接口；
- 需要数据库自动轮换、审计、跨可用区或更短 RPO；
- 真实资金超出受控小额试验边界，或业务不再接受本计划暂定 RPO/RTO；
- 开始承接规模化设备流量。

迁移到腾讯云数据库前仍需先验证 MySQL 8.4 可购状态、V1～V10、触发器 definer、
`SET_ANY_DEFINER`、列级 grants 和参数权限；托管服务限制不能靠放宽运行账号来绕过。
