# 香橙派业务程序发布与远程更新设计

> 状态：设计已确认，分阶段实施中；第一阶段已完成，第二阶段接收面已完成仓库实现，第三阶段永久层已在一台 v13 设备通过受控原位安装及在线低权限验收；第四阶段默认关闭的安全基础已进入 v19 并完成指定 TF 卡、冷启动、接入封存、投递、清运和低权限边界验收，v19 之后的当前仓库候选又完成了永久 MCU 更新编排、候选通信代理与低权限业务接线及自动化回归，但尚未生成新镜像或完成真实烧录、回滚和断电注入，生产远程更新仍未启用
> 初稿日期：2026-09-01
> 最近更新：2026-09-03
> 适用范围：后端、OneNet、香橙派永久设备管理层、香橙派业务程序、MCU 固件
> 实施约束：已实施范围以第 21.4 节记录为准；后续阶段仍须按顺序验证，不能因接收面存在而提前开放远程更新。

## 1. 文档目的

本文档记录香橙派业务程序远程更新方案的已确认决定、当前实现事实和尚待讨论事项，避免长时间跨轮次讨论时丢失上下文。

本文所说的“业务程序更新”只指香橙派业务运行时更新，不等同于：

- 出厂程序更新；
- 整机系统镜像重装；
- Debian、内核或引导程序更新；
- MCU 固件更新；
- 后端服务器部署。

MCU 固件更新已有独立实现，可以复用其发布、单机部署、进度证据和灰度控制思路，但不能把 MCU 烧录动作与香橙派程序安装动作合并成同一个执行器。

## 2. 决定状态说明

本文用以下标记区分内容成熟度：

- 已确认：用户已经明确同意，后续讨论默认以此为边界。
- 当前事实：仓库或设备镜像中已经存在的行为，不代表目标设计合理。
- 待确认：已经提出的设计建议，但用户尚未明确同意。
- 待讨论：尚未展开或尚未形成方案。

## 3. 软件生命周期边界

### 3.1 已确认：出厂程序

出厂程序只在设备生产、接入、硬件测试、验收和封存阶段使用。

设备完成出厂封存后：

- 出厂程序不再运行；
- 出厂网页和热点不再开放；
- 出厂凭证、验收实现和临时状态被删除；
- 出厂程序代码应当被删除或变得不可执行；
- 后续业务和维护不得依赖出厂程序目录。

### 3.2 已确认：业务程序

业务程序负责封存后的生产业务，包括：

- 投递和清运业务；
- 后端业务命令的验证、持久化和执行；
- 业务事件生成；
- COS 图片上传；
- 与 MCU 的业务通信；
- 业务配置和本地业务数据；
- 业务程序自身的就绪报告。

业务程序是可替换的软件发布包，不拥有永久系统服务、设备更新器或设备级密钥。

### 3.3 已确认：永久设备管理层

设备还需要一个不属于出厂程序、也不随业务程序一起替换的永久设备管理层。

它类似设备引导和救援基础设施，至少包括：

- 常驻设备通信代理；
- 同时管理业务程序和 MCU 固件更新的设备更新器；
- 断电恢复日志；
- 设备作业闸门和维护锁；
- 最小通信收发账本；
- 最小物理动作防重账本；
- 业务程序启动、健康检查和回滚能力；
- 签名信任根和发布包格式支持。

永久设备管理层应尽量小、稳定并独立版本化。第一阶段不通过普通业务程序更新流程更新它，也不实现管理层在线自更新；确实需要修改时使用受控新镜像，或以后另行设计并验收专用维护机制。

### 3.4 当前实现差距

当前实现尚未完全满足以上边界：

- ecobin-first-boot.service 仍从出厂程序目录长期运行；
- 封存清理会停止服务和删除部分凭证、状态，但不会删除整套出厂程序目录；
- OneNet MQTT 连接和命令接收目前位于业务进程；
- 仓库已有运行时构建、验签、版本目录切换和回滚原语，但当前镜像尚未形成常驻自动更新闭环；
- 当前运行时安装只允许新旧 EdgeStore 数据结构版本完全相同；
- 后端当前只有一套 COS 桶配置，图片和 MCU 制品通过权限及前缀区分，尚未配置本文要求的独立私有软件制品桶；
- MCU 灰度已经采用单机验证和逐批人工放行，但尚无本文为业务程序定义的观察窗口、阈值判断和自动暂停能力。

## 4. 总体目标结构

目标结构如下：

    后端
      |
      | OneNet 管理命令、业务命令和设备事件
      v
    常驻设备通信代理
      |-- 业务程序或 MCU 更新命令 --> 设备更新器
      |-- 其他业务命令 ----------> 本机接口 ----> 业务程序
      |<-- 更新进度 -------------- 设备更新器
      |<-- 业务事件 -------------- 本机接口 <---- 业务程序
                                                    |
                                                    | UART
                                                    v
                                                   MCU

关键原则：

- 一个 OneNet 设备身份只维持一个 MQTT 连接；
- 常驻设备通信代理是唯一 MQTT 连接持有者；
- 业务程序更新和 MCU 固件更新命令不依赖业务程序接收；
- 其他消息由通信代理原样交给业务程序解释；
- 通信代理不仅接收，也负责向 OneNet 发送；
- 设备更新器不依赖业务程序接收后续救援更新。

## 5. 软件发布包

### 5.1 已确认：发布包范围

业务发布包只包含：

- Python 业务代码；
- OneNet 业务消息处理；
- 后端、COS 和 MCU 业务逻辑；
- ARM64、Python 3.11 的锁定依赖；
- 离线 wheelhouse；
- 数据迁移内容；
- 启动入口；
- 业务健康检查入口；
- 发布清单和包内文件摘要。

业务发布包不包含：

- 出厂程序；
- 常驻通信代理；
- 设备更新器；
- systemd 永久服务定义；
- MCU 固件；
- 操作系统、内核或引导程序；
- 设备密钥、OneNet 密钥或 COS 长期凭证；
- 设备数据库、照片、日志和运行状态。

### 5.2 已确认：一个下载 URL

设备每次只下载一个 tar.gz 业务发布包。

构建阶段仍可产生：

    ecobin-hardware-{releaseId}.tar.gz
    ecobin-hardware-{releaseId}.tar.gz.sha256
    ecobin-hardware-{releaseId}.tar.gz.sig

但下发给设备的临时 URL 只指向 tar.gz。

后端发布记录保存：

- 安装包 SHA-256；
- Ed25519 签名；
- 签名密钥编号；
- 文件大小；
- 私有 COS 对象位置。

更新命令携带临时 URL、摘要、签名、签名密钥编号和文件大小。设备下载一个文件后验证整包摘要和签名。

### 5.3 已确认：发布包建议结构

    ecobin-hardware-{releaseId}/
    |-- app/
    |-- wheelhouse/
    |-- requirements-runtime.txt
    |-- requirements-offline.txt
    |-- migrations/
    |-- manifest.env
    |-- release.env
    |-- SHA256SUMS

不直接打包开发机创建好的 Python 虚拟环境。设备更新器使用 wheelhouse 在版本目录中离线创建独立虚拟环境。

### 5.4 安全验证

下载 URL 只是运输地址，不是信任依据。设备至少执行：

- URL 必须为允许环境中的 HTTPS 地址；
- 文件大小上限检查；
- SHA-256 整包摘要检查；
- Ed25519 整包签名验证；
- 签名密钥必须来自设备内置信任根；
- 安全解压，不允许路径越界、符号链接或特殊文件；
- 包内每个文件必须被 SHA256SUMS 精确覆盖；
- 发布清单与后端目标发布一致；
- 不得包含出厂程序、设备密钥或永久管理层代码。

任何验证失败都发生在旧业务程序仍可运行的阶段，不得停止旧业务。

## 6. 私有 COS 制品存储

### 6.1 已确认：独立私有桶

软件制品不放入当前“公有读、私有写”的图片桶。

应使用独立私有 COS 桶。香橙派不拥有桶级读取或写入权限，只取得一个对象的短期只读 URL。

香橙派业务程序和 MCU 固件可以共用一个私有软件制品桶，通过不同前缀隔离：

    edge-runtime/releases/
    mcu-firmware/releases/

### 6.2 已确认：基础位置配置，具体路径后端生成

后端配置只保存：

- COS 区域；
- 私有桶名称；
- 业务发布包基础前缀；
- 允许的 COS 环境信息。

创建发布草稿时，后端自动生成不可修改的对象路径，例如：

    edge-runtime/releases/{releaseId}/package.tar.gz
    edge-runtime/releases/{releaseId}/package.sig

网页和调用方不能自行提交任意 COS 对象路径。

临时 URL 在实际 OneNet 下发前生成，不提前永久保存。日志必须隐藏临时 URL 查询参数。

## 7. 软件发布身份

### 7.1 已确认：四种身份

每个业务软件发布同时具有：

| 字段 | 用途 |
|---|---|
| releaseId | 后端关系、命令引用和幂等身份 |
| versionName | 人类可读的语义化版本，例如 1.4.0 |
| releaseSequence | 后端按组件生成的单调递增序号 |
| packageSha256 | 精确标识安装包字节 |

其他追溯字段包括：

- component，固定为香橙派业务运行时；
- packageFormatVersion；
- Git 完整提交 SHA；
- Python 系列，当前固定 3.11；
- 构建时间和目标平台。

Git 提交不是发布身份。相同源码在依赖或构建环境变化后可能生成不同制品。

### 7.2 已确认：不可修改

发布提交校验后，所有影响安装和兼容性的字段冻结。

同一个 versionName 不允许对应两个不同摘要。修复或重新构建必须创建新版本，不能覆盖原 COS 对象。

设备安装后上报 releaseId、versionName、releaseSequence 和 packageSha256；后端只有确认这些值全部匹配才承认安装事实。

## 8. 软件发布记录生命周期

### 8.1 已确认状态

| 内部状态 | 页面显示 | 含义 |
|---|---|---|
| DRAFT | 草稿 | 正在填写或上传，不允许选择设备 |
| VERIFYING | 正在校验发布包 | 内容冻结，后端自动检查 |
| VERIFICATION_FAILED | 校验未通过 | 不允许下发，可重试同一制品校验 |
| AWAITING_APPROVAL | 等待批准 | 技术检查通过，等待管理员 |
| READY | 可以下发 | 可以被单机部署或灰度计划选择 |
| SUSPENDED | 已暂停下发 | 暂时禁止新增下发 |
| RETIRED | 已归档 | 永久停止新增下发，保留历史和回滚制品 |

READY 只表示有资格被选择，不会自动向任何设备发送命令。

AWAITING_APPROVAL 是防止校验完成后意外获得下发资格的显式确认点，不代表双人审批；首版允许同一名平台管理员创建并批准发布。

### 8.2 自动校验内容

自动校验至少覆盖：

- 私有 COS 对象存在；
- 文件大小、SHA-256 和签名一致；
- 发布清单身份与后端记录一致；
- ARM64、Python 3.11 和包格式受支持；
- 安全解压；
- 业务文件和离线依赖完整；
- 不包含出厂代码、设备密钥或永久管理层代码；
- 发布版本、序号和摘要没有冲突。

### 8.3 暂停和归档

暂停发布阻止新的设备命令和尚未发送的任务。已经进入设备安全执行阶段的更新不能被粗暴中断，仍需完成当前安装或恢复。

归档不影响已经安装该版本的设备，也不立即删除制品，因为历史调查和回滚仍可能需要。

## 9. OneNet 连接与消息边界

### 9.1 已确认：单设备单连接

OneNet 官方资料说明同一设备只允许一个连接。当前代码也使用设备名称作为 MQTT Client ID。

参考：

- https://iot.10086.cn/doc/iot_platform/book/device-connect%26manager/MQTT/mqtt-example.html
- https://iot.10086.cn/doc/iot_platform/book/devops%26monitor/device-debugger/introduce.html
- https://iot.10086.cn/doc/iot_platform/book/device-connect%26manager/MQTT/topic.html
- https://iot.10086.cn/doc/iot_platform/book/device-connect%26manager/thing-model/protocol/OneJSON/service.html

因此：

- 业务程序和更新程序不能使用同一设备身份分别连接 OneNet；
- 不采用双 MQTT 连接按主题分工；
- 不为了进程隔离创建两个 OneNet 设备身份；
- 不把业务程序更新迁移到 OneNet 自带 OTA 控制面。

### 9.2 已确认：通信代理职责

常驻设备通信代理负责：

- OneNet 鉴权、Token 更新、连接和重连；
- 订阅、发布和 QoS 处理；
- 特殊识别业务程序更新、MCU 固件更新和更新取消服务；
- 向设备更新器交付设备维护命令；
- 向业务程序原样转发其他服务请求；
- 从业务程序接收并发布业务事件；
- 从更新器接收更新进度和实际安装事实，并在业务程序停止期间继续上报；
- 将平台确认转交给业务程序；
- 保存最小的、与业务含义无关的通信防重账本。

通信代理不解释投递、清运、称重、照片或配置的业务字段。

### 9.3 已确认：业务程序职责

业务程序接收通信代理转发的原始 OneNet 服务标识符、请求内容、请求编号和接收时间。

业务程序负责：

- OneNet 业务投影解码；
- 完整业务字段验证；
- 命令幂等和冲突检查；
- 写入业务命令箱；
- 执行业务；
- 生成稳定业务事件编号；
- 维护完整业务状态。

业务程序完成验证并持久保存命令后，才向通信代理返回“已受理”；通信代理随后回复 OneNet。

业务程序不可用时，通信代理对普通业务服务明确回复“业务程序暂时不可用”，由后端可靠任务决定是否重试。通信代理不把物理操作命令无限期积压到未来执行。

### 9.4 本机接口

第一版采用 Unix Socket 作为本机进程间通信接口：

- 不开放 TCP 端口；
- 通过文件权限限制调用用户；
- 使用独立本机协议版本；
- 严格限制消息大小和响应时间；
- 业务程序不再读取 OneNet 设备密钥。

## 10. 更新受理、准备和设备空闲

### 10.1 已确认：更新命令不交给业务程序

更新命令由常驻通信代理验证基础信封并持久交给设备更新器。业务程序中不增加香橙派业务程序升级处理逻辑。

### 10.2 已确认：先准备，再停止新业务

收到更新命令后：

1. 设备持久保存更新请求；
2. 立即回复“已受理”；
3. 在旧业务继续运行期间下载发布包；
4. 校验摘要、签名和发布清单；
5. 创建候选版本环境；
6. 发布包完全准备好后才关闭新业务入口；
7. 等待当前业务和必要收尾完成；
8. 取得维护锁并切换版本。

下载失败、URL 过期或候选环境准备失败时，旧业务不受影响。

### 10.3 已确认：设备作业闸门

永久设备管理层保存独立作业闸门：

| 状态 | 含义 |
|---|---|
| OPEN | 接受新业务 |
| DRAINING | 不接受新业务，等待当前业务完成 |
| MAINTENANCE | 正在切换、检查或恢复程序 |
| LOCKED | 状态无法确认，禁止业务 |

业务程序每次开始新的物理作业前必须取得永久层颁发的作业许可。永久层设置 DRAINING 后，旧业务可以继续完成，但新业务无法与更新动作发生竞态。

### 10.4 等待超时

DRAINING 必须有截止时间。

如果设备长期无法进入空闲：

- 不停止旧程序；
- 取消本次激活；
- 重新把作业闸门设为 OPEN；
- 上报“设备长时间未进入空闲，本次更新已推迟”；
- 后端以后重新安排。

首版从作业闸门进入 DRAINING 起最多等待 30 分钟。超过 30 分钟仍不能证明设备空闲，就按上述规则推迟本轮更新并恢复接收新业务；以后可以根据真机数据调整新任务的默认值，但已经开始的任务继续使用创建时冻结的期限。

### 10.5 更新期间的业务消息

DRAINING 时仍转发所有普通业务消息，由业务程序和永久作业闸门共同决定是否允许：

- 开始新投递、开始新清运等新作业会被拒绝；
- 当前作业继续、结束和恢复消息放行；
- 照片授权和结果确认放行；
- 安全恢复和远程维护消息放行。

MAINTENANCE 时业务程序已经停止，通信代理对普通业务服务回复“设备正在更新，请稍后重试”，不积压现场物理命令。

## 11. 后端设备业务准入

### 11.1 已确认：状态分离

后端不能把资产生命周期直接改成“正在更新”。至少分别保存：

- 资产生命周期：正常、停用、退役；
- 联网状态：在线、离线、未知；
- 业务准入状态：接受、暂停、未知；
- 软件部署进度；
- 安全和硬件状态。

普通业务不需要理解全部更新阶段，只检查统一业务准入结果。

### 11.2 已确认：设备事实驱动

后端发送更新命令或收到 OneNet 传输确认时，不立即关闭业务。

设备完成发布包准备并在本地持久设置 DRAINING 后：

1. 本地立即拒绝新作业；
2. 通信代理上报当前更新阶段和业务准入；
3. 后端追加进度证据；
4. 后端把当前业务准入投影为暂停；
5. 后端业务入口在创建 OneNet 命令前拒绝新物理业务。

设备本地是最终安全边界，后端是提前拦截和页面展示边界。

### 11.3 建议的当前投影字段

    asset_id
    business_admission
    block_reason
    maintenance_type
    maintenance_owner_uid
    maintenance_stage
    device_state_sequence
    source_event_uid
    observed_at

后端不能因为状态超时自动恢复为接受业务。设备离线或更新状态未知时应失败关闭，等待设备重新上报。

### 11.4 阻止与允许

业务暂停时阻止：

- 新投递；
- 新清运；
- 新称重或其他物理作业；
- 与当前更新互斥的其他维护。

继续允许：

- 已有业务结果上报；
- 照片和事件确认；
- 查询设备和更新进度；
- 更新进度上报；
- 更新取消、远程维护和安全恢复。

- 基础兼容性确定不成立。

## 13. 新版本健康检查

### 13.1 已确认：三层健康检查

第一层由永久设备管理层独立检查：

- 当前版本链接指向目标目录；
- 安装标记、发布编号和摘要匹配；
- 实际系统服务启动自目标目录；
- 进程没有立即退出或连续重启；
- 新业务程序已连接常驻通信代理。

第二层由业务程序提供结构化就绪事实，再由永久层交叉验证：

- 配置可读取；
- 业务数据库可打开；
- 必要迁移完成；
- 本机通信协议已协商；
- MCU UART 完成只读握手；
- 必要本地设备能够初始化；
- 没有遗留活动物理作业。

第三层是短期试运行：

- 基础检查通过后进入 OBSERVING；
- 重新开放业务；
- 保留旧版本和更新前数据库快照；
- 观察崩溃循环、本机协议断开、数据库严重错误和新引入的 UART 错误；
- 观察期通过后才进入 SUCCEEDED。

首版观察时间为 30 分钟。观察期从三层基础检查全部通过后开始；以后可以根据真机数据调整新任务的默认值，但不能在当前版本已经出现异常后临时缩短观察期。

### 13.2 不单独触发回滚的外部问题

以下问题不能单独证明新业务版本有缺陷：

- 蜂窝网络暂时中断；
- OneNet 暂时不可达；
- 后端暂时没有响应；
- COS 暂时不可用；
- 观察期间没有真实业务。

OneNet 连接属于永久通信代理，不是候选业务程序健康判断的唯一依据。

## 14. 本地数据库备份与恢复

### 14.1 已确认：设备可恢复性优先

最终业务取舍是：

> 每次启动候选业务程序前备份本地业务数据库；新版本发生严重问题时，允许恢复到更新前快照。设备恢复优先于保留快照以后产生的少量本地业务增量。

这项决定明确取代“开放新业务后绝不恢复快照”的早期建议。

后端已经接收的业务事实不会因为设备数据库恢复而删除。少量缺失业务可以通过客服或运营核对补偿。

### 14.2 安全底线

可以接受最后一段业务数据丢失，但不能因为恢复数据库而重复执行：

- 开门或关门；
- 清运解锁；
- 称重；
- MCU 固件烧录；
- 其他现场物理动作。

### 14.3 永久安全账本

永久设备管理层保存不会随业务数据库恢复的最小账本。

通信收发账本保存：

- 业务命令编号和内容摘要；
- 是否已交给业务程序；
- 业务程序是否已经受理；
- 业务事件编号和内容摘要；
- 是否已发送或得到平台确认。

物理动作账本保存：

- 业务作业编号；
- 命令编号；
- 物理动作编号；
- 动作尚未执行、可能已执行或已确认完成。

业务程序执行物理动作前必须先在永久层登记。账本不解释业务金额和订单内容，只提供防重复安全事实。

### 14.4 更新前快照

每次切换前：

1. 关闭新业务入口；
2. 等当前业务完成；
3. 停止旧业务程序；
4. 完成 SQLite WAL 归并；
5. 使用 SQLite 一致性备份能力创建快照；
6. 保存当前发布、数据结构、文件摘要、安全账本序号和时间；
7. 执行完整性检查；
8. 快照有效后才迁移和启动候选版本。

不能在数据库仍写入时直接复制 SQLite 主文件。

### 14.5 故障恢复

候选版本失败后：

1. 关闭新业务入口；
2. 停止候选程序；
3. 保存故障数据库供诊断；
4. 恢复更新前快照；
5. 根据永久安全账本写入防重标记；
6. 切回旧程序；
7. 验证旧程序；
8. 上报恢复窗口和受影响编号；
9. 根据是否存在未核对物理动作决定是否开放业务。

如果存在“物理动作可能发生但结果未知”，程序可以恢复运行，但业务保持暂停，等待后端或客服核对。

回滚进度还应报告：

    databaseRestored
    snapshotCreatedAt
    lostDataWindowStartedAt
    lostDataWindowEndedAt
    reconciliationRequired
    affectedCommandUids
    affectedWorkUids

### 14.6 数据结构策略

当前实现要求新旧 EdgeStore 结构版本完全相同。第一版远程更新继续保留这一安全限制。

真正出现跨结构更新需求时，再引入：

- 数据格式主版本；
- 能读取的结构修订范围；
- 安装后结构修订；
- 最低回滚读取版本；
- 幂等迁移入口。

破坏性迁移应拆成扩展、迁移、收缩多个发布，不在第一版实现。

### 14.7 已确认：本机版本、快照和空间处理

业务程序更新执行期间最多同时保留：

- 当前正在运行的版本；
- 上一份已经验证、可用于回滚的稳定版本；
- 本次已经下载并校验的候选版本。

更新器同时保留一份本次更新前创建并通过完整性检查的业务数据库快照。更新成功并完成观察以后，候选版本成为当前版本，原当前版本成为上一稳定版本；更早且不再承担回滚职责的本机版本可以清理。MCU 更新同样必须保留目标固件和上一份已经验证的稳定固件。

下载或制作快照前，更新器先检查候选包、解包临时空间、数据库快照和安全余量是否都能容纳。空间不足时：

- 不关闭业务入口；
- 不删除当前版本、上一稳定版本或当前有效快照来强行腾空间；
- 只允许清理已确认不再使用的临时文件和旧候选；
- 清理后仍不足就拒绝本次更新，并上报“设备存储空间不足”。

具体安全余量由真机测得的包大小、解包峰值和 SQLite 快照峰值确定，属于部署检查参数，不改变上述保留边界。

## 15. 版本兼容关系声明

### 15.1 已确认：不建立三维版本矩阵

不维护“后端版本 × 香橙派版本 × MCU 固件版本”的组合白名单。

软件发布版本表示制品身份和先后；通信契约版本表示能否交换消息；能力标记表示是否提供某项可选功能。

### 15.2 已确认：分边界声明兼容关系

| 边界 | 契约内容 |
|---|---|
| 后端—通信代理 | OneNet 运输信封、维护服务路由、进度和设备状态运输 |
| 后端—设备更新器 | 业务程序与 MCU 更新命令、取消、授权续期、进度和实际安装事实；消息经通信代理运输 |
| 后端—业务程序 | 投递、清运、配置、照片和业务事件 |
| 通信代理—业务程序 | 本机消息转发和就绪协议 |
| 通信代理—设备更新器 | 本机维护命令和更新进度协议 |
| 设备更新器—业务程序 | 作业许可、维护前安全交接、业务版本健康检查和 MCU 烧录后验证 |
| 业务程序—MCU | UART 帧、按钮、称重、门控、固件更新前准备、实际固件身份和自检 |

### 15.3 已确认：发布声明

后端发布声明：

- 能发送的业务命令契约；
- 能接收的设备事件契约；
- 能发送的设备管理命令契约；
- 能接收的设备管理进度契约；
- 当前启用的业务能力。

业务程序发布声明：

- 能接收的后端命令契约；
- 实际发送的设备事件契约；
- 支持的本机通信协议；
- 支持的 UART 协议及修订；
- 提供和要求的业务能力。

MCU 固件发布声明：

- 主板型号和硬件修订；
- UART 协议及修订；
- 固件身份；
- MCU 实际能力。

通信代理发布声明：

- 后端管理契约；
- 本机业务通信协议；
- 本机更新器通信协议；
- 能识别的固定设备维护服务；

设备更新器发布声明：

- 能接收的设备维护命令契约；
- 能发送的更新进度和实际安装事实契约；
- 与通信代理和业务程序使用的本机协议；
- 业务发布包格式；
- MCU 固件包格式；
- 签名算法和可信密钥编号；
- 支持的业务程序与 MCU 更新能力。

### 15.4 已确认：基础兼容与可选能力分开

基础兼容决定设备能否开展核心业务。

可选能力只影响对应功能。例如不支持 MCU 远程升级不能推导出投递也不可用。

后端功能应声明所需能力，不直接写死某个 MCU 或香橙派软件版本。

## 16. 实际兼容性计算

### 16.1 已确认：计算原则

设备只上报：

- 实际安装了什么；
- 实际启动了什么；
- 实际协商出了什么。

设备不直接上报“我兼容”。后端根据不可修改发布声明和当前平台契约自行计算。

### 16.2 已确认：软件事实快照

由通信代理统一运输更新器和业务程序提供的当前事实：

- 通信代理版本、管理运输协议和本机协议；
- 更新器版本、设备维护协议、本机协议、支持的业务包与 MCU 包格式；
- 业务程序 releaseId、releaseSequence、versionName、packageSha256；
- 业务进程是否就绪；
- 实际协商的本机协议版本；
- MCU 固件版本和身份；
- UART 状态、主次版本和能力位图；
- 持久递增的管理状态序号；
- 可信观察时间。

设备不重复上报业务发布理论支持范围。后端根据 releaseId 和 packageSha256 查找已登记发布清单。

### 16.3 已确认：计算步骤

1. 验证 OneNet 设备身份、事件编号和状态序号；
2. 确认业务发布编号和摘要已经登记且完全匹配；
3. 判断后端与通信代理的管理运输契约，以及后端与更新器的设备维护契约；
4. 判断后端命令发送版本是否被业务程序接受；
5. 判断业务程序事件版本是否被后端接受；
6. 判断通信代理与业务程序、通信代理与更新器的实际本机协议；
7. 判断更新器与业务程序的作业许可、维护交接和健康检查协议；
8. 判断业务程序声明与 MCU 实际 UART 握手；
9. 根据实际能力计算基础业务和每项可选功能。

### 16.4 已确认：计算结果

| 结果 | 业务处理 |
|---|---|
| 完全兼容 | 正常开放 |
| 基础兼容，部分功能不可用 | 开放基础业务，隐藏对应功能 |
| 不兼容 | 关闭新业务 |
| 无法确认 | 关闭新的物理业务 |

页面必须展示具体中文原因，不能只显示“版本不兼容”或内部代号。

### 16.5 现有基础与缺口

现有 DEVICE_RUNTIME_SNAPSHOT 已经包含：

- 香橙派版本；
- MCU 固件版本和身份；
- UART 状态及版本；
- 协商能力位图；
- 可信事件序号和接收时间。

仍缺少：

- 精确业务 releaseId、releaseSequence 和 packageSha256；
- 永久通信代理版本；
- 永久更新器版本；
- 管理协议、设备维护协议和各本机协议版本；
- 业务程序是否完成本机协议协商；
- 与后端不可修改发布记录的明确关联；
- 独立的当前兼容性投影和原因集合。

## 17. 跨端升级顺序

### 17.1 已确认：默认采用兼容桥接顺序

后端、香橙派业务程序和 MCU 不做同时切换，也不把三端升级伪装成一个分布式事务。涉及三端契约演进时，默认顺序为：

1. 先部署后端兼容桥接版本。它必须继续接受当前设备事件，并能理解目标事件；在设备尚未证明支持新命令前，仍发送旧命令或不启用新能力；
2. 再更新香橙派业务程序。这个桥接版本必须同时支持设备当前 MCU 和目标 MCU，并能与当前永久通信代理协商；
3. 再更新 MCU 固件。MCU 仍使用独立的签名、灰度、烧录和自动回滚流程；
4. 后端收到该设备实际安装、启动和协议协商事实后，才按设备开启新契约或新能力；
5. 等受支持设备完成迁移和观察后，未来另一个发布才可以删除旧契约，不能在同一轮升级中提前删除。

如果某次变更只涉及一端，就不强迫另外两端产生空发布。以上是需要三端协同时的默认演进顺序。

### 17.2 已确认：顺序由中间状态是否兼容约束

默认顺序可以因具体变更而调整，但发布计划必须先证明每个中间组合都至少满足基础兼容。例如：

- 当前后端 + 当前业务程序 + 当前 MCU；
- 新后端 + 当前业务程序 + 当前 MCU；
- 新后端 + 新业务程序 + 当前 MCU；
- 新后端 + 新业务程序 + 新 MCU。

如果相邻两个组合之间没有兼容交集，必须先增加一个同时理解新旧协议的桥接发布，不能直接下发并期待三端“恰好同时成功”。

永久通信代理和更新器虽然不在本轮更新顺序中，仍参加兼容计算。目标业务发布如果要求更高的本机协议、包格式或签名能力，而设备永久层不支持，该设备必须在下载或停业务前被判定为不能安装。

### 17.3 已确认：升级一半时按实际能力运行

- 后端只按设备已经证明的协议和能力发送命令，不按计划目标版本猜测；
- 新能力按设备逐台开启，不以“这一批已经下发”作为开启依据；
- 处在桥接组合的设备可以继续基础业务，但尚未共同支持的可选功能保持隐藏或拒绝；
- 中间组合不兼容或事实不可确认时，后端和设备都关闭新的物理业务；
- 同一设备同一时间只允许一个会改变业务程序或 MCU 的维护动作。

### 17.4 已确认：回滚也必须满足兼容关系

- 后端兼容桥接版本必须覆盖整轮设备灰度和观察期，不能在设备尚未收敛时先撤掉旧协议；
- 香橙派回滚前要确认上一业务发布仍支持设备当前实际安装的 MCU；
- 如果 MCU 已经更新，而上一业务发布不支持它，应先把 MCU 恢复到上一稳定固件，或保持设备业务暂停，不能强行启动不兼容的旧业务程序；
- MCU 继续使用自身的目标重试和自动回滚机制，业务程序回滚不能冒充 MCU 已经回滚；
- 后端只根据新的实际安装事实恢复业务，不根据“已发出回滚命令”提前恢复。

## 18. 更新命令的幂等、超时、重试和取消

### 18.1 已确认：四层稳定身份

| 身份 | 含义 |
|---|---|
| releaseId | 一个不可修改的业务制品 |
| rolloutUid | 一次灰度计划 |
| deploymentUid | 灰度或单机发布中，某台设备安装目标发布的部署记录 |
| updateUid | 设备真正执行的一轮更新；是设备侧幂等根 |

OneNet 的消息编号、HTTP 请求编号和每次传输尝试编号只作传输诊断，不能替代 updateUid。

同一个 updateUid 的重复命令必须遵守：

- 目标 releaseId、packageSha256、文件大小、签名和包格式完全相同，只返回或继续原更新状态；
- 已经下载、校验、切换或到达终态的步骤不得重复执行；
- 任一不可修改字段不同，作为身份冲突拒绝，不能覆盖原记录；
- 已到达终态时只重报原终态，不重新安装；
- 设备重启后从永久更新账本恢复同一轮更新。

同一设备已经存在活动更新时，另一个 updateUid 不能自动取代它。后端等待原更新收敛，或者明确取消仍处于安全取消点的原更新后，再建立新的一轮。

### 18.2 已确认：临时 URL 不属于制品身份

后端可靠任务冻结私有 COS 对象位置、releaseId、packageSha256、签名和大小，不冻结带查询参数的临时 URL。

每次准备真实下发时，后端才为同一对象生成新的短期只读 URL，并携带递增的下载授权序号。设备只接受：

- 与原 updateUid 指向同一制品；
- 摘要、大小和签名完全不变；
- 授权序号比已经保存的授权更新。

URL 过期、下载超时或临时网络错误只表示本次下载授权不可用，不创建新发布，也不改变目标制品。设备保留原更新记录并上报需要新下载授权；后端对同一 updateUid 生成新 URL。旧业务程序在候选包完整准备好以前继续运行。

### 18.3 已确认：设备离线和重试

- 设备尚未接收命令就离线：部署保持等待，OneNet 在线事实恢复后唤醒原可靠任务；临时 URL 在真正重发前重新生成；
- 等待超过部署下发期限：本轮进入“已推迟”，不把设备或制品判为故障；以后重新安排时保留旧记录并建立新的 updateUid；
- 设备已经接收后离线：后端不猜测结果，等待设备重连后按 updateUid 和 stageSequence 重报；
- 下载、COS 或 OneNet 临时失败可以有界重试；签名、摘要、包格式、硬件或兼容性确定错误直接拒绝，不能无限重试；
- 同一进度事件重复到达时按 eventUid 去重；乱序到达时只接受更高的 stageSequence 更新当前投影，历史证据仍只追加保存。

首版对同一次临时失败最多重试 3 次。每次重试继续使用原 updateUid、制品身份和已保存进度；如果下载授权已经过期，先取得序号更高的新授权再重试，不能创建一个新的发布或偷偷改换制品。

### 18.4 已确认：不同阶段使用不同超时结果

| 超时位置 | 处理结果 |
|---|---|
| 设备接收前 | 推迟本轮，业务不受影响 |
| 下载或候选环境准备期间 | 停止本轮准备，旧业务继续运行 |
| 等待当前业务结束期间 | 取消本轮激活，把作业闸门恢复为接受新业务 |
| 旧程序已停止或数据库快照已经开始后 | 保持维护状态，继续恢复、核验或回滚；不能因后端等待超时就开放业务 |
| 后端长时间收不到进度且无法确认设备状态 | 显示状态无法确认，并关闭新的物理业务，直到设备重报权威事实 |

后端超时只改变后端对“是否还应等待”的判断，不能修改设备已经发生的安装事实。

首版单次发布包下载期限为 30 分钟。期限从设备实际开始本次下载尝试时计算；到期后终止该次网络请求，旧业务继续运行，并按临时失败规则重试或请求新的下载授权。下载超时不能删除已经完整校验的缓存，也不能进入版本切换。

### 18.5 已确认：取消只在安全点生效

取消是发送给永久更新器的受控意图，不交给业务程序处理。

- 在下载、校验、候选环境准备和等待当前业务结束期间，可以取消；
- 取消成功时删除或隔离未激活候选、释放本次维护意图，并把作业闸门恢复为 OPEN；
- 从停止旧业务、制作数据库快照或开始切换起，取消已经太晚，不能强杀更新器；
- 太晚的取消只记录并回复“当前已进入安全恢复阶段，不能取消”，设备继续完成目标核验或自动回滚；
- 观察期内要求恢复旧版本属于新的回滚操作，不伪装成取消；
- 同一个取消意图重复到达只返回第一次结果。

更新意图和取消意图都携带设备内持久递增的控制序号。设备在同一事务中比较序号和当前阶段，解决“更新与取消同时到达”的竞态。

暂停发布或暂停灰度只阻止尚未发送的设备任务，不能中断已经进入设备安全执行阶段的更新。

## 19. 灰度更新

### 19.1 已确认：先验证一台，再逐批人工放行

一个 READY 发布不能直接自动扩散到全部设备。标准流程为：

1. 创建灰度计划并冻结目标发布、目标设备范围、验证设备、分批规则、观察窗口和停止条件；
2. 平台管理员人工启动一台验证设备；
3. 验证设备更新成功后，人工核对设备健康、兼容性、真实业务或受控现场测试；
4. 平台管理员明确“确认推广”后，计划才允许产生第一批；
5. 每一批完成观察后，平台管理员再次人工“下发下一批”；
6. 最后一批观察通过后，计划才完成。

验证设备成功不会自动推广，每批观察通过也不会自动下发下一批。

验证阶段固定先使用一台设备。后续批次大小由平台管理员创建灰度计划时选择，首版默认每批 3 台；计划开始后，本轮已经冻结的分批规则不能为了改变结果而直接修改，如需改变范围或分批方式，应停止后另建计划或执行明确的计划调整动作并留下审计。

### 19.2 已确认：设备范围和资格

创建计划时保存目标设备快照及当时的选择原因。至少排除：

- 硬件型号或修订不匹配；
- 永久通信代理、更新器、本机协议或包格式不支持；
- 当前实际安装事实缺失、冲突或基础兼容性不成立；
- 设备处于失败锁定、其他维护或未收敛物理作业；
- 磁盘空间等确定不满足安全安装要求。

验证设备应覆盖目标设备中的真实硬件、当前业务版本和 MCU 组合，不能只使用与目标群体不同的开发模拟环境证明可推广。

设备临时离线、正在工作或 URL 过期时进入等待或推迟，不从目标集合中静默删除，也不临时换入另一台设备美化成功率。设备同一时间不能参加两个活动的业务程序灰度计划。

### 19.3 已确认：观察窗口

每批所有设备先到达明确终态；仍在运行、回滚、状态未知或失败锁定时，不开始下一批放行判断。对成功设备至少观察：

- 业务程序崩溃、反复重启和就绪状态；
- 本机通信协议断开；
- 数据库打开、迁移、写入和完整性错误；
- 新出现的 UART、MCU 或硬件交互错误；
- 设备业务准入和后端兼容性投影；
- 投递、清运、照片和其他受影响业务的错误率；
- 自动回滚、人工核对和客服异常。

“观察期间没有真实业务”本身不能证明新版本正常。验证批必须有受控测试；后续批可以结合自然业务，但页面要明确展示样本不足。

首版每台成功设备至少观察 30 分钟。观察窗口和停止条件在计划创建时冻结，不能在结果不好时直接缩短观察时间或调宽条件。任一设备发生第 19.4 节列出的严重事实就自动暂停，不使用批次成功率去掩盖单台自动回滚、失败锁定或安全异常。

### 19.4 已确认：自动停止条件

以下任一严重事实立即自动暂停灰度：

- 任一设备进入更新和回滚都无法恢复的失败锁定；
- 任一设备发生自动回滚或回滚核验失败；
- 新版本导致基础兼容性不成立或无法确认；
- 出现数据库损坏、重复物理动作、门控安全或数据一致性严重异常；
- 达到计划冻结的崩溃率、业务错误率、失败率或健康检查阈值。

设备离线、设备忙、一次 URL 过期或一次外部网络错误不能单独证明制品有缺陷，但会阻止该批满足完成和放行条件。

自动暂停后：

- 不再创建或发送下一台设备的更新命令；
- 已经进入设备执行阶段的更新继续安全收敛；
- 不自动对全批设备强制回滚；
- 页面展示触发事实、受影响设备和建议处置。

单机自动回滚是设备自救；全批恢复到旧发布是平台管理员另行发起的受控发布计划，两者不能混为一个状态。

### 19.5 已确认：人工暂停、恢复和放行

平台管理员可以暂停计划。恢复自动暂停、继续下一批、结束计划或发起全批恢复都必须再次确认目标发布、设备范围并填写原因，形成只追加审计。

人工恢复只表示允许继续调度，不会覆盖失败证据，也不会把未成功设备改成成功。

## 20. 发布权限、安全和制品保留

### 20.1 已确认：只允许平台管理员

只有当前有效的平台管理员可以：

- 创建、上传、提交校验、批准、暂停和归档业务发布；
- 创建单机部署或灰度计划；
- 启动验证设备、确认推广和下发下一批；
- 暂停、恢复、取消尚未进入安全执行阶段的部署；
- 发起人工回滚或处理失败锁定后的恢复。

租户管理员、机构工作人员、厂家操作员和设备本身都不能创建或批准发布。

首版不采用双人审批。同一个平台管理员可以创建并批准自己的发布，但“提交校验”和“批准可下发”仍是两个明确动作，保留 AWAITING_APPROVAL 状态，避免上传完成就自动获得下发资格。

批准、暂停、恢复、归档、扩大设备范围和回滚等高风险动作必须展示精确版本、摘要和设备数量，要求填写原因，并只追加记录操作者、时间、前后状态和结果。首版不要求平台管理员重新输入密码，继续依赖当前有效登录会话、明确的二次确认和只追加审计。

### 20.2 已确认：离线签名与单一信任根

业务发布使用独立的 Ed25519 发布密钥，不与 MCU 固件、整机镜像、设备身份或维护密钥复用。

- 私钥只存在于离线发布机或专用签名环境；
- 私钥不进入 Git、后端、数据库、COS、Web 浏览器或任何设备；
- 后端保存并校验签名、签名密钥编号和制品摘要；
- 香橙派永久更新器只保存只读验签公钥，并在安装前再次验签；
- signingKeyId 继续进入发布记录和命令，即使首版只有一把受信密钥。

首版使用独立的本地命令行工具完成构建后签名：工具在离线发布机上计算制品摘要、签署发布清单并输出不可修改的完整签名制品。平台管理员随后通过管理页面上传这个已经签名的制品，后端只负责生成对象路径、上传或接收、重新计算摘要、验证签名并保存发布记录。后端不生成签名，也永远不取得私钥。

当前阶段明确不设计密钥轮换、吊销或私钥泄露后的在线处置流程。如果将来发生这类需求，必须通过新的安全设计、受控镜像或现场维护处理，不能假设普通业务发布包有权替换永久信任根。

### 20.3 已确认：私有 COS 权限

软件制品桶保持私有读、私有写：

- 后端只获得配置前缀内创建对象、读取校验和生成短期授权所需的最小权限；
- 管理员页面不取得桶级密钥；如采用浏览器直传，只使用后端为自动生成的单一对象路径签发的短期写入授权；
- 香橙派只取得单一对象的短期只读 URL；
- 对象路径由后端生成，上传方不能指定任意 key；
- 已校验发布的对象禁止覆盖；重新构建必须创建新 releaseId 和新对象；
- 临时 URL 的查询参数不得写入数据库、审计或日志。

### 20.4 已确认：首版制品永久保留

首版不配置自动生命周期删除，也不提供普通 Web 删除发布制品的能力。

- READY、SUSPENDED 和 RETIRED 发布的对象都继续保留；
- 归档只表示不允许新的普通下发，不表示删除；
- 当前安装版本、上一稳定回滚版本、历史部署、事故调查和审计引用的制品必须可继续取得和验签；
- 数据库发布记录、COS 对象和离线签名材料应能相互核对。

以后如果存储规模需要清理，再单独设计“没有任何设备安装、不是任何设备回滚版本、没有活动计划或部署、没有事故保留要求”的删除资格和保留年限；本轮不预先实现。

### 20.5 已确认：永久通信代理和更新器暂不远程更新

首版把通信代理和更新器视为长期稳定的永久设备管理能力：

- 不放入业务发布包；
- 不通过业务程序更新流程修改自身；
- 不预留由业务包执行 root 脚本、覆盖 systemd 服务或替换信任根的旁路；
- 仍各自具有版本，并随设备事实上报，参加包格式和本机协议兼容计算；
- 业务发布要求永久层尚不支持的能力时，明确拒绝该发布，而不是顺带升级永久层。

“长期稳定”不等于代码永远不可能修改。操作系统、OneNet、安全要求或实现缺陷以后仍可能迫使它们升级；当前阶段只是不实现在线自更新。确有需要时，使用受控新镜像或另行设计并验收的设备管理层维护流程，不能临时借用业务发布包越过这一边界。

## 21. 从当前实现迁移到目标结构

### 21.1 当前实现事实

当前 `hardware/main.py` 在同一个普通硬件进程内同时组装：

- OneNet MQTT 鉴权、连接、订阅和发布；
- OneNet 服务请求解码、命令持久化和业务事件中继；
- 投递、清运、配置、照片和 UART 业务；
- MCU 固件更新执行器；
- 运行快照和当前连接状态投影。

`ecobin-hardware.service` 以一个 systemd 服务启动上述全部能力，当前业务发布清单也同时包含 `mqtt_client.py`、`command_processor.py`、`edge_store.py` 和 `mcu_firmware_updater.py`。这说明当前制品仍是“通信、业务和部分设备维护能力合包”，不能直接当成第 3 节确认的目标业务发布包。

现有独立 `ecobin-remote-support.service` 已经证明“永久代理独立进程、独立私有 SQLite、本机 Unix Socket、普通业务进程重启不影响代理”的结构可以在当前镜像和 systemd 环境中工作。业务程序通信代理和设备更新器应复用这种进程隔离经验，但不复用远程维护的业务状态或凭据。

### 21.2 已确认：目标进程关系

目标设备运行关系为：

    OneNet
      |
      v
    永久通信代理
      |-- 普通业务消息 --> 业务程序 --> UART、摄像头、投递、清运和照片
      `-- 设备维护消息 --> 设备更新器
                              |-- 业务程序更新 --> 作业闸门、快照、切换和回滚
                              `-- MCU 固件更新 --> 安全交接、烧录、验证和回滚

设备维护消息包括业务程序更新、MCU 固件更新、取消以及同一更新的下载授权续期。通信代理只负责把这些消息持久交给更新器，不依赖业务程序识别更新命令。

当前已经实现并验证的 MCU 目标重试、实际固件身份校验、自检和自动回滚状态机迁移到永久更新器，不重新设计其安全语义。业务程序继续独占正常 UART 业务，只参与两个明确阶段：烧录前通过正常 MCU 协议要求停止输出、证明设备安全并交出串口；烧录后重新连接 MCU，读取实际固件身份并执行自检。更新器取得维护锁并停止业务程序后，才调用按需运行的 MCU 烧录助手操作固定串口、BOOT0 和 NRST。目标和上一稳定固件都无法通过验证时，更新器保持 LOCKED，后端拒绝新的物理业务。

业务程序更新和 MCU 固件更新共用同一个永久维护锁，同一设备同一时间只能执行其中一个。

永久通信代理和设备更新器互不依赖业务程序存活：

- 业务程序损坏时，通信代理仍能收到新的业务程序更新命令；
- 业务程序停止时，更新器仍能完成切换、健康检查和回滚；
- 通信代理不读取业务 `edge.db`；
- 更新器不解释投递、清运、金额、照片等业务事实；
- 业务程序不读取 OneNet 设备密钥，也无权修改永久层代码或信任根。

### 21.3 已确认：迁移基本原则

迁移采用“先搭兼容桥、再切通信、后开放更新、最后删除旧路”的顺序。

永久通信代理和更新器不能由第一条普通业务更新命令安装，否则首次更新失败时设备会同时失去后续修复通道。当前验证设备应通过新的受控系统镜像安装永久层；以后已经在用的设备只能通过受控新镜像或既有独立远程维护通道完成一次性迁移，不能把永久层伪装成普通业务发布内容。

同一个 OneNet 设备身份在任何时刻只允许一个连接。通信切换时必须先停止当前直连进程，再启动通信代理；禁止以两个客户端同时在线作为过渡方案。

通信代理接管 OneNet 并且业务程序不再取得设备密钥后，当前“业务进程直接连接 OneNet”的版本不能再作为普通回滚版本。切换前必须先形成一个同时通过当前业务回归和本机代理接口验收的桥接业务发布；该发布是迁移后的最低回滚版本。

后端在迁移期显式区分：

- 尚未迁移、仍由业务进程直连 OneNet 的设备；
- 已经完成永久通信代理和更新器切换的设备。

旧设备在受控迁移窗口内继续按当前规则工作；新永久层事实只对明确完成切换的设备成为必需。设备一旦确认完成切换，永久层版本、协议或状态缺失就必须显示为无法确认并阻止新物理业务，不能自动退回旧判断。全部设备迁移并超过回滚保留期后删除该临时旧路径，不把它保留为长期双协议兼容层。

#### 第二阶段仓库实施记录（2026-09-02）

第二阶段新增“设备软件实际安装与运行状态上报”这一独立可靠事件，机器契约内部标识为
`DEVICE_SOFTWARE_STATE_REPORTED`。中文名称是产品和运维说明使用的名称；内部标识只用于
跨端契约、日志定位和开发诊断，不直接展示给普通用户、清运员或非开发人员。

该事件通过可信 OneNet 收件箱可靠接收，完整保存永久通信代理、设备更新器、当前业务发布、
进程就绪、三组实际协商协议以及 MCU/UART 实际状态。后端先追加不可变事实，再按设备内单调
序号更新当前兼容性和业务准入投影；重复事件保持幂等，旧序号不能覆盖新投影。V63 同时建立
不可变业务发布声明、设备管理架构代次和兼容性投影，共新增 4 张领域表，数据库基线由
V62 的 119 张领域表推进到 V63 的 123 张领域表。

这里的“实施”指仓库机器契约、迁移、后端、查询接口和页面已经形成同一候选版本，不表示
现场数据库或 OneNet 控制台已经自动升级。部署时仍须先按 H-02 手册把目标库从现场实际纪元
前向迁移到 V63，再导入并核对 15 服务 / 19 事件的候选物模型，最后才能激活依赖新事实的
后端；运行 JAR 不会自行执行迁移或修改 OneNet 控制台。

迁移与准入边界如下：

- 所有既有和新登记资产默认标记为 `LEGACY_DIRECT`，即“沿用原有业务程序直连 OneNet 的
  管理方式”。这类设备继续使用原有投递、清运和安全检查，不会因为尚未上报永久层新事实
  被暂停，也不会在页面上显示内部代次名称；
- 只有可信新事实才能把设备单向切换为 `PERMANENT_V1`，即“已经由永久通信代理和设备更新器
  管理”。切换后不能自动降回旧规则；永久层或实际安装事实缺失、业务暂停、兼容性不成立或
  无法确认时，后端一律停止创建新的物理业务；
- 小程序投递可用性预览、清运可用性预览，以及实际创建投递或清运的事务都读取同一业务准入
  结果。只有新架构设备明确处于“可接收新业务”时才允许创建；预览和创建不会出现页面显示
  暂停、后端却仍生成任务的分叉；
- 已经开始的投递或清运仍按原有事实收敛，设备软件状态变化不用于中断完成事件、业务确认或
  恢复处理。

Web 设备列表和详情只展示中文业务结论、可理解的原因、必要版本与上报时间。业务准入和软件
兼容性分开显示；旧设备显示“沿用现有业务检查”。内部原因码、发布编号、摘要、事件编号、
设备内序号和固件身份不作为普通页面文案。

这一阶段仍是只接收、计算、准入和展示：没有新增业务程序更新下行命令，没有部署或灰度
状态机，没有发布创建/修改接口，也没有可触发设备更新的页面按钮。业务发布声明表对运行
账号保持只读；真正的发布写入、审批、私有 COS 制品和远程下发仍属于第七、八阶段。

在第五阶段让第一台设备上报新版管理事实以前，必须通过受控、可审计的数据库前向迁移登记

并停止新业务；这项预登记只解决首次切换的兼容声明，不等于提前开放通用发布写接口。

#### 第三阶段仓库与现场实施记录（2026-09-02 至 2026-09-03）

第三阶段先形成了可制作受控镜像的仓库实现，随后又在当前 v13 设备上通过受控维护完成永久
原位安装和在线低权限验收。受控维护路径的在线退出条件已经满足；镜像路线当时也重建了包含
最终权限修复的 v17，但 v17 最终没有写卡、完整回读或断电冷启动，不能把两条路径的证据互相
替代。后续当前写卡候选已由包含第四阶段安全基础的 v19 取代。

受控镜像软件载荷升级为格式版本 2。新格式在原有业务运行时、接入、远程维护、出厂测试和
首次启动组件之外，新增永久通信代理与永久设备更新器两个独立、精确锁定的组件；两个按需
特权助手及其 systemd 单元随永久更新器组件进入同一签名载荷。新镜像只接受格式版本 2，
审计器仍可按冻结的历史文件清单读取格式版本 1 的既有候选，不能用当前新增文件重新解释旧锁。

镜像通过 systemd-sysusers 和 systemd-tmpfiles 建立 `ecobin-communication`、
`ecobin-business`、`ecobin-updater` 三个不可登录的低权限用户、三个本机接口组、三份私有
状态目录和固定 Socket 目录。通信代理、业务程序与更新器只能打开自己的数据库；永久服务
代码和运行时发布验签公钥由 root 安装为只读内容，OneNet 凭据仍只留在当前旧业务路径。

永久通信代理当前只保存自身实际启动事实，并提供健康和状态查询；它没有普通网络能力，
不读取 OneNet 凭据，也不路由远程更新。永久更新器同样只保存自身实际启动和第三阶段固定
姿态；业务程序更新、MCU 更新、取消和下载授权续期全部稳定返回“功能未启用”，永久作业
闸门明确报告尚未执行。两者由生产运行目标统一启动，但不依赖业务服务；单独重启业务服务
不会重启这两个永久进程。

三个主要本机接口共用严格的单请求 JSON 协议：限定 256 KiB、连接最多等待 1 秒、响应最多
等待 5 秒，同时校验 Socket 文件权限、内核提供的调用进程身份、逐 action 调用者白名单、
精确字段和协议主版本。这里的 action 是“一种固定本机操作”。即使调用者有权连接某个
Socket，也必须再次通过该操作自己的身份白名单。处理线程超过期限时只报告“结果暂时无法
确认”，后续有副作用的操作必须复用稳定业务身份查询或重试，不能假定后台动作已经停止。

业务运行时包已经带有只读业务本机接口适配器，但当前 `main.py` 不启动它。原因是当前业务
服务仍以迁移过渡的 root 身份直接连接 OneNet；在第五阶段切换到 `ecobin-business` 之前，
提前监听业务 Socket 会制造错误的“已经完成通信切换”事实。第三阶段权限预检改为让真正的
业务虚拟环境以 `ecobin-business` 身份运行：先后两次确认旧业务服务已停止，再逐项打开固定
UART、两台摄像头，写入并清理业务数据库目录、照片目录和业务 Socket 探针，并调用通信代理
与更新器健康接口。任何必要权限缺失都会指出具体资源并失败，不会退回 root 运行。

两个 root 特权助手是本机、按连接启动的固定原语，不是更新状态机，也没有远程消息入口：

- 业务激活助手只接受更新编号和发布编号，操作固定业务服务、固定发布目录、固定业务数据库
  快照和固定候选目录；复制时拒绝符号链接、硬链接和特殊文件，包内迁移脚本绝不以 root
  身份执行；
- MCU 烧录助手只接受更新编号以及“目标固件/回滚固件”二选一，读取固定本地槽，调用固定
  `/usr/bin/gpio`、`/usr/bin/stm32flash`、`/dev/ttyS5` 和已确认引脚，并在成功或失败后
  恢复且读回安全启动电平。

助手 Socket 使用只包含 `ecobin-updater` 的专用调用组，并继续核对内核提供的真实进程身份；
业务程序和通信代理即使可以访问各自的普通本机接口，也不能占用或调用 root 助手。固定原语
代码已经随镜像安装，但第三阶段在助手分发边界统一返回“功能未启用”，不会进入字段处理、
互斥锁或 root 处理函数；能力查询也明确报告变更能力关闭。原因是持久维护锁、异步动作状态和
物理动作防重账本属于第四阶段，不能先开放一个依赖尚不存在安全事实的半成品入口。

生产运行目标还会启动一次由真实 `ecobin-updater` 用户执行的本启动预检。它通过两个生产
Socket 分别请求健康状态，实际覆盖 Python 导入、systemd 沙箱、Socket 权限和内核身份校验；
预检 oneshot 服务只有在两个助手都确认“第三阶段变更关闭、无远程触发”时才保持成功状态，
封存健康检查要求该本启动状态存在，而不是只检查两个监听 Socket 看起来处于 active。数据库
回滚快照的 root 所有目录独立放在 `/var/lib/ecobin/privileged/business-snapshots`，不嵌套在会被
更新器服务接管所有权的 `StateDirectory` 中。

第四阶段启用任一助手变更 action 前还有三个代码硬门，不能只把功能开关改成 true：必须先
落地持久维护锁、快速受理的异步动作状态和同一稳定身份的完成回执；MCU 助手必须把 systemd
总运行上限调到严格覆盖最坏烧录与安全恢复时间，并提供不依赖主进程 `finally` 的固定引脚
恢复；业务数据库恢复必须使用可断电收敛的 root 事务标记及旧主库/WAL/SHM 保护，并把源文件
校验绑定到 `O_NOFOLLOW` 打开的同一文件描述符。

#### 第四阶段默认关闭的仓库候选实施记录（2026-09-02 至 2026-09-03）

第四阶段已经形成可供继续审计和真机验证的仓库候选。第三阶段受控维护路径的在线低权限条件
已经通过，但第四阶段自己的业务回归、MCU 更新迁移、断电恢复和真实动作门禁仍未满足，也
没有在生产启动路径中启用。永久更新器服务不携带第四阶段候选开关，业务程序默认使用不改变
现有行为的关闭适配器；更新器数据库初始及默认重启姿态均为“已禁用并锁定”。因此，仅安装
当前代码或重启服务，不能意外开放候选能力。

本机接口现在增加三个只允许 root 调用的受控操作：查询当前门禁与待核对事实、携带证据激活
第四阶段门禁，以及立即施加人工安全锁。激活请求必须同时携带唯一操作编号、已审核现场证据
的 SHA-256 摘要和调用者刚读取的管理状态序号；状态序号已经变化、存在活动作业、未核对物理
动作、维护锁或人工安全锁时都拒绝。人工锁只叠加在原有门禁和维护事实之上，不会把正在排空、
维护或恢复的原阶段改写丢失。当前尚未实现人工锁和维护锁的受控释放，所以这些操作只提供
“核对后首次启用”和“立即收紧”，不能用来绕过后续恢复流程。

“本次候选启用是否已经审核激活”作为独立持久事实保存为“需要激活”或“已经激活”。每次以
候选关闭方式启动，或者新程序发现较旧更新器曾把基础状态写回关闭，都会把该事实重置为
“需要激活”。只有上述 root 专用激活操作能在同一个 SQLite 事务内保存证据、改成“已经激活”
并打开新业务门；通用状态迁移、遗留作业收敛和重复许可均不能代替它。遗留的未开始许可在
新周期只可查询或弃置，不再显示为可以开始；已经实际开始的作业仍可按原身份完成收敛，但
完成后只回到“需要激活并锁定”，不会自动开放下一项业务。上一启用周期的激活命令即使内容
完全相同，也不会在新周期返回误导性的“当前已打开”。

这组事实使用基础格式版本 3 上的附加表，不提升基础 schema 版本。提交前已用真实上一版
`updater_store.py` 验证：默认关闭的旧更新器仍能读取带附加表的数据库；旧程序写回关闭姿态后，
新程序前向启动又会要求新凭证。这里的“能够读取”只服务于尚未启用候选时的软件回退，不表示
第四阶段一旦真实写入活动作业或维护事实后仍允许退回不理解这些安全语义的旧程序。

受控维护安装器对“卸载整个永久设备管理层并恢复旧业务服务”采用更窄的边界。它只接受精确
基础格式版本 3、精确附加层版本 1、候选关闭、激活仍为“需要审核”，并且从未留下控制操作、
任何状态的作业许可、任何状态的物理动作、旧证据隔离记录、维护锁或人工安全锁的数据库。
数据库缺失、不可读、权限或所有者不符、表/索引/约束发生变化、出现未知扩展，或者设备曾经
激活后又关闭候选，都会在停止任何服务前拒绝回退。正式执行时还会先关闭更新器和特权入口，
再用新的只读 SQLite 快照复核一次；第二次通过之前不删除永久代码，也不恢复旧业务服务。
安装器会在每个 `systemctl start` 前先持久化“准备启动哪个单元”的日志，只有该日志明确证明
更新器从未尝试启动，且主数据库、WAL、SHM 和回滚日志均不存在时，安装早期的断电恢复才可
按“尚未建库”清理。这个卸载门禁与“旧更新器可以只读/默认关闭地打开附加表”是两个不同
结论，后者不能替代前者。

维护安装本身也改为可由新进程继续的落盘事务。安装器在任何文件发布、系统用户或目录创建、
服务首次启动、卸载停止服务和删除文件之前，先把唯一操作编号及下一步意图写入 root 独占的
维护目录并同步到磁盘；全局启动围栏和逐服务卸载围栏阻止 systemd 在中断窗口自行拉起新层。
固定临时文件、定位标记、安装记录和围栏都校验所有者、权限、大小及内容归属，无法解释的
目录项、多个孤立操作、其他载荷留下的操作或损坏记录一律失败关闭。`systemd-sysusers` 和
`systemd-tmpfiles` 只在精确意图已经落盘、现有部分副作用仍是声明的安全子集、配置文件仍为
已认证内容时才允许幂等重放。服务启动边界一旦可能越过就只能用相同载荷向前收敛；已经通过
完整安装审计并进入卸载事务后则只能继续幂等卸载，不能因重启误走安装恢复或再次执行已删除
配置对应的系统命令。预检查和模拟执行只读取这些事实，不创建、修复或清理文件。

候选实现新增了两类不会随业务数据库回滚的永久事实：

- 通信代理私有数据库保存入站命令收件、交给业务程序受理、出站业务事件、发送尝试和平台
  确认。稳定命令编号或事件编号相同但内容摘要不同会被拒绝，网络发送结果和业务处理结果
  分开记录；
- 更新器私有数据库保存作业闸门、维护锁、作业许可、活动作业和物理动作回执。投递、清运、
  满溢检测及空桶基线都必须使用稳定身份申请并开始作业；同一作业最多只有一个结果尚未
  确认的物理动作，恢复业务数据库也不能生成第二次许可来重放同一动作。

业务进程候选接入点会在发送串口指令之前向永久更新器登记动作，并只把与动作身份绑定的
MCU 实际事实作为完成依据。例如，收到“门已经打开”的 MCU 事实只能确认本次开门动作，
不能仅因串口写入成功就宣称门已打开。不能读取永久更新器、身份或摘要不一致、存在未核对
动作、维护锁生效或恢复状态无法收敛时，新作业失败关闭；当前作业的收尾和恢复仍按冻结的
许可处理。进入排空状态后不再接受新作业，但既有作业的动作在登记和确认期间不会把排空
意图错误恢复为接受新业务。

原先“永久更新器已经批准动作，但批准响应在返回途中丢失”的歧义，已经由仓库候选中的
两阶段派发协议解决。业务程序先以稳定动作身份执行 `PREPARE`，中文含义是“登记待派发动作”，
此时永久记录处于 `PREPARED`，不授予串口写入。串口实现完成串口可用、MCU 就绪、截止时间、
帧内容等检查并取得 UART 独占写锁后，才在第一次写入字节前立即执行 `ARM`，中文含义是
“允许本次派发尝试写入”。只有 `ARM` 明确成功，当前调用才可以继续一次串口写入。

每次活跃派发尝试在 `PREPARE` 前生成一个仅属于该动作的高熵短期令牌；`PREPARE`、`ARM`
以及确定首字节尚未写入时的取消或终止都必须匹配同一个令牌。令牌明文只活在当前业务进程
的易失内存，更新器从 `PREPARED` 起只保存令牌摘要，业务数据库和日志都不保存明文。如果
`PREPARE` 的响应丢失，业务程序先按完整动作身份查询：能够证明动作仍为 `PREPARED` 时，
同一进程用原令牌把它安全结束；查询或结束结果仍不明确时，原令牌只为后续可靠重试保留，
重试只允许重新建立并结束这条从未写过串口的原记录，不能借机继续 `ARM`。如果 `ARM` 已经在
更新器数据库提交但本机响应丢失，业务程序则只在同一个 UART 写锁内用完全相同的令牌重试；
更新器把它识别为同一次派发，串口回调仍只放行一次写入。不能取得明确结果时不会生成新令牌
继续发送，业务进程重启后也不会重发原物理命令。

进程重启时发现的 `PREPARED` 记录不根据可回滚的业务数据库状态自动取消；新进程已经没有
原令牌，永久更新器会拒绝它接管、放行或取消旧动作。只有仍持有原令牌、并能直接证明首字节
尚未写出的原业务进程，才能使用受限取消。其余情况保持锁定，等待可信事实或人工处理。

本机接口为了避免永久线程阻塞设有处理时限；返回 `RESULT_UNKNOWN` 的中文含义是“回复等待
结束，但后台处理仍可能提交”，服务停止过程中返回的 `SERVICE_STOPPING` 也具有同样的不确定
边界，二者都不能当成确定拒绝。业务侧会用完全相同的动作身份、摘要和短期令牌立即重试一次；
若第二次仍不能确认，则统一视为“永久作业闸门暂不可确认”，让可靠命令或 MCU 事件继续保留
待重试。这样后台稍后提交的许可、动作或回执仍能通过幂等查询收敛，不会因为一次本机接口
超时或停止时序把已有硬件事实标成失败并丢弃。

当前固定帧 MCU 不能在 DD 投递结果或 EF 清运结果中回显业务动作编号，因此候选实现没有把
这些帧伪装成跨重启都可信的动作回执。业务程序只在同一个业务作业管理组件进程（代码组件
`WorkManager`）内短期保存“动作编号到派发令牌”的对应关系：DD/EF 到达并与当前活动作业
匹配时，使用该动作的原令牌向永久更新器确认；F0/F1 自检和称重查询则在同一次同步调用内用
原令牌确认。令牌明文不写入业务
`edge.db`，不进入稳定上下文或日志，永久更新器只保存其摘要。业务进程一旦重启便失去短期
令牌；如果永久动作此前尚未确认，后来到达的 DD/EF 不能据此伪造完成，动作继续保持“已经
允许派发但结果未确认”，作业闸门保持锁定并转人工核对。

`END_CLEAN_BEFORE_UNLOCK` 的中文含义是“在尚未解锁清运门时取消 MCU 内的清运工作状态”。
它不驱动电磁阀或其他执行器，重复执行仍是同一个停止意图，因此不建立物理动作记录，也不
经过上述 `PREPARE/ARM` 派发。清运解锁、开关门和其他可能产生现场效果的命令仍必须进入永久
物理动作账本，不能借用这一例外。业务程序会在发送这条控制命令前先持久化“禁止继续解锁”
意图；结束和解锁分别通过同一个业务数据库中的原子占位竞争，先提交的一方会使另一方条件
失败。云端接入线程在拍照期间收到结束命令时会先把它写入可靠命令收件箱；即使单线程命令
消费者还在处理称重事件、尚未调用结束方法，照片后的解锁占位事务也必须先检查这个匹配当前
清运工作和端口的待处理命令。结束命令已落盘就拒绝解锁占位，等当前事件处理返回后再由同一
消费者发送停止控制。只有不存在这项已接收事实且成功取得解锁占位，才允许进入物理动作的
`PREPARE`。因此较早的开始命令结果稍后到达时，只能用于核对开始动作。只有取消命令已经得到
ACK（单片机已受理）的事实才能结束永久作业许可；取消结果不明时继续保留作业和设备占用，
但两种情况都不得继续发送清运门解锁命令。
若结果不明期间又收到迟到的开始事实，仅允许完全相同的结束命令复用原 MCU 命令编号重试；
不同命令编号或不同原因仍按状态冲突拒绝，避免把新的停止意图混入旧命令。云端重复下发时，
设备只在命令收件箱仍为“结果未知”、活动清运槽仍绑定同一停止意图、原因、MCU 命令编号和
内容摘要全部一致时，才会在一个事务中把原命令重新排队；普通物理命令不能借此恢复入口重放。
如果待处理的结束命令已经明确超过首次执行期限，解锁占位事务会同时把该命令记为过期，再按
当前清运事实重新判断解锁；无法确认截止时间、身份不完整或内容摘要不匹配时仍由结束命令
优先并保持锁定，不能用时钟不确定性绕过已落盘的停止意图。

作业许可、业务终态和完成回执之间增加了断电恢复衔接。业务数据库写入成功、失败或取消
终态时，会在同一 SQLite 事务中冻结待提交给永久更新器的完成身份；若进程在事务提交后立刻
退出，重启后仍使用原身份补交，不会开放第二个作业。更新器或本机接口暂时不可用时，业务
命令和 MCU 事件保留为待重试；已知串口尚未发送的失败会把动作确认成“没有执行”并安全结束
作业，而串口已写入但没有取得结果的超时会保留为“物理结果未知”，锁住后续新业务等待核对。

永久动作完成 `ARM` 后，串口写入或刷新抛出异常也统一按“物理结果未知”处理，不能因为业务
程序没有拿到正常返回值就生成“确定失败”事实。此时开始命令进入恢复状态，原投递或清运继续
占用设备，后续新业务被拒绝。标准 UART 只能用携带原 MCU 命令身份的结果收敛；固定帧结果
不携带业务身份，因此还必须匹配当前进程保存的原派发令牌和永久更新器中的完整动作记录。
任一证明缺失、进程已经重启或永久记录暂时不可读时都保持恢复锁，不能猜测性完成或释放占位。

业务进程启动恢复也不能把仍绑定受保护活动作业的命令统一改成“设备重启导致失败”。命令收件、
活动作业编号、端口、永久许可摘要和本地动作回执全部一致时，投递、清运、满溢检测、空桶基线
以及清运中的恢复或结束命令只转入不可重放的恢复状态，不生成失败观察；原工作槽继续阻止新
业务。随后先核对永久动作确认和已冻结的业务终态，再由原 MCU 事实补齐事务。只有不具备这组
受保护绑定的旧式中断命令才沿用原重启失败规则，任何分支都不会自动重发物理命令。

标准 UART 的投递完成、清运完成、满溢检测完成和空桶基线完成都以“本次接收代次、MCU 启动
编号、MCU 事件序号”作为派生事实身份。完成事件、业务投影、活动工作上下文和 MCU 收件箱的
已处理标记在同一个 SQLite 事务提交；即使提交后立刻强杀、永久更新器暂时不可用并重放同一
MCU 事实，也只能得到原来的一个事件编号，不能生成第二条完成事实。

为缩小“许可取得后、真正写串口前已经超时”的窗口，候选会在等待许可、开始作业、拍照和
登记 `PREPARED` 后重新计算命令的绝对截止时间，并把换算后的单调时钟截止值传到真实串口
实现。串口实现在取得自身写锁后、第一次写入前再次检查；超时则不执行 `ARM`、不写入，并
由仍持有本次调用的进程以“首字节尚未写入”事实结束该动作。由于 `ARM` 本机调用本身也可能
等待或重试，回调在 `ARM` 返回后还会在同一个 UART 写锁内再次检查单调时钟截止值；已经过期
时使用原令牌终止刚放行但尚未写入的动作，终止结果不明则保持锁定，绝不返回适配器继续写。
清运解锁还会把设备启动本次清运时记录的本地单调时钟窗口作为第二个截止上限，与云端绝对
截止时间取更早者；即使设备墙上时钟不可用，也不能因绝对时间回退值而越过现场操作窗口。

固定帧投递必须区分两个时限：云命令的 `expiresAt` 只限制第一次写出 BB/AA，不能限制已经
开始的整场投递。由于固定帧不会下发 `deliveryAutoCloseMs`，用户还可以在 MCU 屏幕上继续
投递，设备无法从现有线路证明整场业务的有限截止点。第一次写出后冻结的单调时钟预计窗口
暂按“配置的自动关门时间 + 配置的继续选择等待时间与 30 秒两者中的较大值”计算；它只用于
把长期未收到 DD 的工作转入恢复锁，不能把命令、永久作业或计费事实冻结为失败；原业务
进程仍持有本次短期令牌时，唯一可归属的迟到 DD 继续按原会话正常完成，设备只在本地记录
“预计窗口已过”的诊断。由于该窗口本来就不是业务截止点，设备不能据此伪造后端人工复核
语义。业务进程重启后短期令牌消失，DD 又不携带会话身份，此时保持恢复锁并等待现场处理，
不能把任意迟到帧绑定到旧会话，也不能仅因预计窗口结束就开放下一次投递。

作业闸门暂时不可用且当前没有占用作业槽时，命令处理循环使用受控退避，不会形成持续占用
CPU 的快速重试。

MCU 烧录助手补上了独立于主处理函数异常退出的固定恢复程序、严格的 systemd 运行上限，
以及目标文件打开和校验的一致性保护。生产使用的第三阶段助手分发层仍然拒绝所有变更操作；
另行增加的第四阶段候选助手只在静态候选服务被显式启动后存在，并且每次动作都必须先由永久
更新器按更新编号、动作编号、助手种类、操作种类和完整载荷摘要消费一次授权，随后才可取得
全局变更锁并进入固定 root 原语。它不能接受调用者提供的路径、服务名、命令或 GPIO 参数。

业务程序本机接口增加了默认关闭的 MCU 维护交接协议。只有候选业务服务同时启用永久作业
闸门、MCU 交接和本机通信代理姿态时，才注册三个操作：只读观察当前 MCU 与串口事实、要求
MCU 进入安全维护状态并交出串口、烧录后收回串口并验证 MCU。当前 `main.py` 已把固定帧真实
UART 接到该端口，候选 systemd 单元也已按 `ecobin-business` 低权限身份接线；原生产单元仍
保持旧直连与关闭姿态，所以安装代码本身不会开放这些操作。

每份交接证据同时包含两类 MCU 查询和串口所有权。维护状态查询必须证明协议修订、固件版本、
8 字节非零固件身份、当前模式、状态码和完整安全位；运行态只接受模式 1、状态码 0、安全位
精确等于 `0x0F`，交出串口后的维护态只接受模式 2、状态码 0、安全位精确等于 `0x1F`。
基础自检查询还必须证明通信正常、称重与传感器字段有效、重量在硬件范围内、红外值是布尔值、
烟感为正常或告警这两种可解释健康状态。查询失败时不得同时携带成功字段，保留位或未知状态码
也一律拒绝，避免用“差不多安全”的证据进入烧录。

证据摘要由业务控制器按固定 JSON 结构自行计算，调用者不能上传一个摘要冒充现场事实。

特权助手的烧录回执摘要。完全相同的成功请求可以幂等返回；正在执行的同一请求不会再次碰
硬件；失败请求可用相同身份安全重试，但改变载荷会冲突。服务停止会先标记正在停止，并在
有界时间内等待当前交接端口调用退出，不能在硬件操作仍继续时假装本机接口已经停稳。

公钥验证签名、精确硬件型号、包摘要、镜像摘要和清单，再写入更新器私有的固定目标槽与回滚

或在这一阶段得到不健康、错误代次或格式错误的证据，只结束本轮更新并恢复业务，不交出串口、
不停止业务程序、不触碰 BOOT0/NRST，也不烧录固件。

通过前置检查后，更新器取得同一维护围栏，业务程序再次读取 F3/F1 现场事实，要求 MCU 进入
安全维护态并关闭自己的 UART；候选 root 助手随后停止固定业务服务，从更新器私有只读槽调用
固定烧录程序，并无论成功失败都恢复应用启动引脚。更新器再启动低权限业务程序，业务程序只
在永久账本精确匹配更新编号、交接编号、维护围栏、交接摘要、烧录回执摘要和期望固件身份时
重新打开 UART、读取实际 F3 身份并执行 F1 自检。目标最多尝试 3 次；目标始终不能验证时改烧
已签名且与更新前实际身份一致的回滚固件，回滚最多尝试 3 次。只有目标或回滚的实际身份与
自检均通过才能释放维护围栏；两者都不能证明时保持锁定，后续物理业务继续被拒绝。

重启与不确定结果按“先观察实际状态，再决定下一步”处理。特权动作在调用前先持久化并标记
正在派发；若进程在助手回复落盘前退出，重启会把结果记为未知，启动业务控制面并读取真实
MCU 身份，绝不直接重复烧录。停止业务或交出 UART 的回复未知也进入同一恢复路径；仅烧录后
只读验证的回复未知时，只重复读取和验证，不再次烧录。若观察到的身份既不是本次签名目标，
也不是签名回滚，设备保持锁定。排空阶段重启则只在同一更新编号、同一围栏、维护记录仍为
“尚未接触硬件”且遗留业务已经收敛时恢复排空状态；它不会借恢复动作开放新业务。业务服务
启动、候选助手和更新器客户端的超时按包含关系设置，外层不会先于仍在执行的内层助手超时。

候选通信代理、候选更新器、候选业务程序和两组候选 root 助手都是无 `[Install]` 段的静态
systemd 单元，量产启动目标不会自动启用它们。永久更新器的远程 `START_MCU_UPDATE` 仍固定
返回“功能未启用”，当前只提供本地 root 候选入口；业务程序历史烧录器在本机代理姿态下不会
实例化。当前代码通过 Windows 全量 `1809 passed, 101 skipped, 5 subtests passed`，并在只读

边界的综合离线审计；当前已验收并运行的 v19 仍不包含本段新增状态机。v21 尚未执行真实 MCU
目标升级、故意失败后的自动回滚、烧录期间断电、助手超时和整机重启验收，因此第四阶段仍未
达到进入第五阶段的条件，后端也不得下发远程 MCU 更新。

### 21.5 已确认：第一阶段只做进程内解耦

第一阶段不创建新 Unix Socket，不新增 systemd 服务，不拆分 SQLite，也不改变 OneNet 物模型。它只在当前进程中建立可替换边界，使以后从直连实现换成本机代理实现时不再改动业务逻辑。

建议的职责为：

| 组件 | 第一阶段职责 |
|---|---|
| DirectOneNetTransport | OneNet Token、连接、重连、订阅、QoS、原始消息收发和服务回复格式 |
| BusinessMessageHandler | 解码业务服务、完整字段校验、命令防重、写业务命令箱并形成受理结果 |
| BusinessOutboxRelay | 从业务事件发件箱读取事件、提交给通信端口并处理平台传输结果 |
| DeviceIdentity | 单独提供不可变设备名称，不再通过 MQTT 客户端对象取得 |
| CloudTransport | 定义可由当前直连实现和未来本机代理实现共同满足的稳定接口 |

入站接口只向业务层提供：

- 本次本机或传输交付编号；
- OneNet 请求编号；
- 服务标识；
- 有界原始参数；
- 可信接收时间。

业务层只有在完成业务解码、校验和持久化后，才返回“已受理、重复受理或已拒绝”、业务命令编号、稳定错误原因及需要回复 OneNet 的业务数据。

出站接口由业务层提供：

- 事件编号；
- 设备内事件顺序；
- 事件类型和投递类别；
- 完整业务载荷；
- 规范载荷摘要。

接口不得暴露 Paho 客户端、MQTT 消息编号、Topic 拼接规则或 OneNet 设备密钥。运行快照仍由业务程序根据本地、UART 和 MCU 事实构建，只通过抽象通信端口发送；通信代理以后只负责运输，不能替业务程序拼快照。

### 21.6 已确认：第一阶段文件和存储边界

- `mqtt_client.py` 只保留网络运输能力，不再写业务命令，也不解释投递、清运、配置、照片、封存或 MCU 更新字段；
- 新的业务消息处理器承接当前服务调用中的业务解码、封存准入、命令防重和持久化；
- 新的业务事件中继器读取 `event_outbox`，通信实现不得直接读取业务数据库；
- `WorkManager` 直接取得 `DeviceIdentity`，不再为了设备名依赖 MQTT 对象；
- `edge_boot.py` 负责 SQLite、UART、MCU 和本地安全恢复，连接的启动和停止由 `main.py` 组装层负责；
- `main.py` 是唯一选择当前直连实现或未来代理实现的组装点，其他业务代码不得判断具体通信实现。

第一阶段继续把下列事实保存在现有业务 `edge.db`：

- 业务命令箱和业务事件发件箱；
- 平台业务确认；
- 投递、清运、配置、照片和本地故障事实；
- MCU 固件更新状态。

当前 `mqtt_session_present`、`mqtt_last_rc` 和 `mqtt_msg_id` 是需要退出业务库的运输细节。第一阶段只把它们隔离在直连适配器内部，不立即迁移或删除；通信代理真正接管时再由代理私有数据库承接相应事实。未来通信代理和更新器都不得直接打开业务 `edge.db`。

### 21.7 已确认：第一阶段验收条件

- OneNet 服务、事件、Topic 和载荷字节语义不变；
- 命令仍然先完成业务持久化，再回复设备已受理；
- 命令重复、身份冲突、封存准入和临时 COS 授权行为不变；
- 业务事件编号、顺序、重试和平台业务确认行为不变；
- MQTT 连接、断线、重连、订阅和 QoS 测试继续由直连通信实现证明；
- 原先放在 MQTT 客户端测试中的业务服务测试迁移到业务消息处理器测试；
- 进程仍只有一个 OneNet 连接；
- 不修改后端、数据库迁移、OneNet 控制台和设备 systemd 单元。

### 21.8 已确认：最终本机接口拓扑和基本格式

完成进程拆分后，每个主要程序各自拥有一个 Unix Socket 服务端：

| 所有者 | 固定接口 | 主要调用方和用途 |
|---|---|---|
| 通信代理 | `/run/ecobin/communication/control.sock` | 业务程序提交业务事件和运行快照；更新器提交更新进度和实际安装事实；调用方查询连接状态 |
| 业务程序 | `/run/ecobin/business/control.sock` | 通信代理投递普通业务命令和平台运输结果；更新器请求维护前安全交接以及烧录后的 MCU 身份与自检结果 |
| 设备更新器 | `/run/ecobin/updater/control.sock` | 通信代理提交业务程序更新、MCU 固件更新、取消和授权续期；业务程序申请、完成或查询作业许可 |

首版采用短连接的 `AF_UNIX`、`SOCK_STREAM` 请求应答：一次连接只发送一个以换行结束、UTF-8 编码的 JSON 请求，收到一个 JSON 响应后关闭。单条消息上限为 256 KiB，接口不传输发布包、照片或其他二进制文件。

请求至少包含本机协议名称和主次版本、requestId、action 和 payload；响应复用同一个 requestId，并返回成功结果或稳定错误。requestId 只用于关联一次本机调用，不能承担业务防重。任何会修改状态的请求还必须携带稳定的业务命令编号、事件编号、updateUid 或作业许可编号以及内容摘要；超时重试必须复用这些身份。

每个 action 使用严格字段白名单，未知字段、未知 action、超限消息或不兼容的主版本直接拒绝。Socket 文件权限和 Linux `SO_PEERCRED` 调用方身份检查必须同时成立；知道路径但用户身份不匹配的进程不能调用。接口不暴露 OneNet 设备密钥、MQTT Topic、Paho 对象、任意系统命令或任意文件操作能力。

连接权限和操作权限是两层检查。一个用户因为需要查询状态而有权连接 Socket，不代表它能调用
该 Socket 上的所有 action；每个 action 还必须声明非空的精确调用用户集合，并且该集合只能
是 Socket 总调用者集合的子集。以后增加写操作时，通信代理提交更新命令、业务程序申请作业
许可、更新器提交安装事实等能力必须分别授权，不能把三个进程都放进同一份操作白名单。

### 21.9 已确认：OneNet 路由、本机超时和持久确认

通信代理只直接识别三类设备维护命令：

1. 开始业务程序更新；
2. 开始 MCU 固件更新；
3. 取消尚未进入不可中断阶段的更新。

同一更新的下载授权续期继续使用原开始命令和原 updateUid，只提高授权序号并替换临时下载授权。上述维护命令始终交给更新器；未知的维护命令明确拒绝，不能回退交给业务程序。其他投递、清运、配置、查询和确认等 OneNet 消息全部交给业务程序。

通信代理只检查运输信封、大小、基本 JSON、OneNet 请求编号和服务标识。兼容性、制品身份、URL、设备空闲、业务字段以及能否执行分别由更新器或业务程序判断。出站时，业务程序提交业务事件，更新器提交更新进度和实际安装事实，通信代理负责持久排队、构造 OneNet 运输消息、重试和确认；调用方不能自行指定原始 Topic 或取得设备密钥。

本机连接首版最多等待 1 秒，接收方完成校验、持久化并应答最多等待 5 秒。下载、安装、烧录、健康观察和现场业务都必须异步执行，不能占用一次本机请求等待完成。超时结果分为：

- 连接没有建立：接收程序不可用，请求没有被接收；
- 收到持久化确认：接收程序已经承担后续处理责任；
- 请求已经发出但响应丢失：受理结果暂时无法确认，调用方只能使用同一稳定身份重试或查询，不能生成新命令再次执行。

业务程序只有取得更新器明确返回的作业许可才可以开始新物理作业。拿不到许可时失败关闭；已经凭有效许可开始的作业可以在通信代理或更新器短暂重启期间完成。普通物理业务在业务程序不可连接时不排队等待以后自动执行。业务事件和更新进度则由发送方保留到通信代理明确确认持久化，超时后按原事件编号重试。

### 21.10 已确认：运行用户和普通权限

最终结构使用固定的低权限 Linux 用户：

| 用户 | 必要能力 | 明确不拥有 |
|---|---|---|
| `ecobin-communication` | OneNet 凭据、网络、通信代理数据库及三个本机接口所需权限 | UART、摄像头、业务数据库、更新目录和任意 systemd 管理权 |
| `ecobin-business` | 固定 MCU UART、摄像头、业务数据库、照片目录、COS 照片上传网络及本机接口 | OneNet 设备密钥、通信代理或更新器数据库、版本切换和 systemd 管理权 |
| `ecobin-updater` | 更新器数据库、下载缓存、只读验签公钥、私有 COS 单对象下载网络、作业闸门及特权助手调用权 | 业务数据库、OneNet 设备密钥、正常投递清运逻辑和任意 root 命令 |
| `ecobin-remote` | 继续沿用现有远程维护的独立权限边界 | 不与上述三个程序共享数据库、凭据或业务状态 |

当前 `ecobin-hardware.service` 以 root 运行只允许作为迁移过渡。在开放任何远程业务程序更新之前，桥接业务程序必须已经以 `ecobin-business` 运行，并在最终 systemd 隔离环境下通过投递、清运、UART、摄像头、照片、COS 和本机接口真机验证。

UART 和摄像头通过明确的设备组或 udev 规则授予业务程序，不向业务程序开放 `/dev/mem`、`/dev/gpiomem`、`CAP_SYS_RAWIO` 或其他宽泛特权。权限完整性不建立额外业务模型，只在镜像部署、最终 systemd 单元预检和真机验收时逐项检查；普通用户手工运行成功或使用 sudo 成功不能证明服务权限完整。缺少必要权限时报告具体资源并阻止相应动作，不能自动改回 root 运行。

### 21.11 已确认：两个按需特权助手

设备更新器通过两个彼此隔离、按需运行的 root 助手完成普通用户不能执行的固定操作。它们不是 OneNet 客户端，不接收业务命令，也不决定是否应该更新。

业务程序激活助手只允许：

- 停止、启动和查询固定的业务程序 systemd 服务；
- 在固定目录创建或恢复与本次 updateUid 绑定的业务数据库快照；
- 把已下载且校验通过的候选安装到固定发布目录；
- 原子切换当前版本，或切回上一稳定版本；
- 更新完成后清理本次临时文件和已经不再承担回滚职责的旧文件；
- 修正这些固定目录内约定的所有者和权限。

发布包中的数据迁移由候选业务程序以 `ecobin-business` 身份执行，助手不以 root 身份运行包内脚本。助手不得接受任意命令、任意路径、任意 systemd 单元，不得下载文件、访问网络、修改通信代理、更新器、系统用户、信任公钥或普通硬件业务事实。何时调用、是否继续、是否回滚和向后端上报什么，全部由更新器根据持久状态决定。

MCU 烧录助手只允许在更新器已经取得维护锁、没有活动作业、业务程序完成 MCU 安全准备并交出串口后执行：

- 使用固定 MCU 串口，当前生产配置为 `/dev/ttyS5`；
- 使用镜像中固定的 BOOT0、NRST 引脚和电平；
- 调用固定的 `/usr/bin/gpio` 与 `/usr/bin/stm32flash`；
- 烧录更新器已经校验的目标固件或上一稳定固件；
- 烧录结束或失败收尾时把引脚恢复到已验证的正常安全状态。

它不能接受任意串口、引脚、程序路径、命令参数或固件来源，也不能发送开门、称重等普通 MCU 业务命令。烧录后由更新器重启业务程序，业务程序读取 MCU 实际固件身份并执行自检；只有目标身份和自检都通过才算成功。失败时更新器要求助手烧录本地上一稳定固件并再次验证；目标和回滚都失败时保持维护锁定。设备断电后，只能依据更新器已经持久化的同一 updateUid 和安全阶段继续原烧录或回滚，不能把重启当成绕过安全准备的新授权。

### 21.12 已确认：三份数据库及一次性迁移

最终每个程序只打开自己的 SQLite 数据库：

| 数据库 | 主要事实 |
|---|---|
| `/var/lib/ecobin/business/edge.db` | 现有投递、清运、照片、配置、封存、普通命令、业务事件、业务确认和 MCU 正常通信事实 |
| `/var/lib/ecobin/communication/communication.db` | OneNet 连接、入站运输收件、出站发送队列、运输结果和通信防重事实 |
| `/var/lib/ecobin/updater/updater.db` | 业务程序与 MCU 更新、作业闸门和许可、维护锁、物理动作防重、实际安装版本、快照、回滚和更新进度 |

任何程序都不得直接打开另一个程序的数据库。业务程序恢复快照时只恢复业务 `edge.db`；通信代理和更新器数据库不得随业务版本回滚，否则运输确认、作业许可、更新进度和已经发生的物理动作事实会倒退。

一次性切换不拆表、不搬迁完整历史：现有 `edge.db` 作为业务数据库整体保留；旧 MQTT 字段和旧 MCU 更新表可以留作历史但不再由新组件读写。通信代理和更新器创建新数据库，只导入当前实际安装版本、上一份已验证 MCU 固件及其他继续安全运行所必需的当前事实。切换必须在没有活动业务和没有进行中 MCU 更新时执行；无法验证上一稳定 MCU 固件时，先禁用新的 MCU 更新，不能假定存在可回滚包。

原 `edge.db` 中尚未交付的业务事件由桥接业务程序按原事件编号提交给通信代理；通信代理持久化后才返回接管确认。迁移窗口发生重复传输时仍依靠稳定事件编号去重，不能通过删除旧业务发件箱来换取表面上的空队列。

## 22. 已确认的安全不变量

- 传输确认、设备受理、物理效果和后端业务结果是不同事实；
- 更新命令送达不能等同于更新成功；
- 设备目标版本不能等同于实际安装版本；
- 兼容性只依据实际安装、启动和协商事实，不依据计划目标；
- 本地作业闸门先关闭，后端随后依据设备事实关闭；
- 后端状态延迟时，本地仍拒绝不安全动作；
- 后端状态未知时不能自动推断设备已恢复；
- 业务程序损坏不能切断下一次更新通知和更新进度发送；
- 下载 URL 只负责运输，摘要和签名才决定制品身份与可信性；
- 暂停计划和后端超时不能强行中断设备已经开始的安全恢复；
- 数据库恢复不能使已执行物理命令再次执行；
- 任何不可读或不可确认的关键安全事实都失败关闭；
- 页面不直接暴露只对开发者有意义的内部代码。

## 23. 延期项和尚待讨论

### 23.1 已明确延期，不纳入首版

- 签名密钥轮换、多公钥过渡、吊销和私钥泄露后的远程恢复；
- 永久通信代理和更新器自身的在线更新；
- 自动删除或按年限清理 COS 历史制品；
- 业务数据库的破坏性跨结构迁移；
- 灰度自动推广和无人值守全批回滚。

这些项目被延期不代表相应风险不存在。首版仍保留 signingKeyId、永久层版本、包格式版本和不可变发布身份，避免未来完全没有演进依据。
