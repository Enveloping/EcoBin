# 投递审核金额阈值与 Web 配置中心（V54）

状态：已冻结，作为 V54 前向迁移和实现依据。

## 1. 本次目标

V54 在 V53 的投递自动审核和提现规则上补充两个边界：

1. 机构可为自动审核设置“单笔投递结算金额上限”；
2. Web 管理端把投递审核规则和提现规则归入统一的“配置管理”导航。

本次不改变设备、OneNet、香橙派、MCU 或微信支付协议，也不回溯处理 V54 之前已经创建的投递订单。

## 2. 投递金额如何决定是否自动审核

投递规则仍有 `ALL_MANUAL`、立即自动审核、24 小时后自动审核和 48 小时后自动审核四种模式。

- `ALL_MANUAL` 不保存自动审核金额上限，所有新订单等待人工审核；
- 三种自动模式必须保存非负的金额上限，允许配置为 `0.00` 元；
- 新订单的原始结算金额小于或等于上限时，才可能登记自动审核任务；
- 新订单的原始结算金额大于上限时，正常保留为待审核订单，不登记自动审核任务，也不记为设备、用户或系统异常；
- 金额条件只是自动审核的附加条件。原始计算不可靠、负重量、负金额或存在用户/系统异常时，仍按 V53 规则转人工处理。

例：机构设置上限 `10.00` 元。结算金额为 `10.00` 元的正常订单可按所选时间自动审核；`10.01` 元的订单等待人工审核。上限为 `0.00` 元时，零金额正常订单仍可自动审核，任何正金额订单等待人工审核。

## 3. 为什么必须保存两份金额事实

规则版本保存 `automatic_review_max_amount_cent`，表示机构发布规则时选择的金额上限。订单创建时再把该值固化到 `automatic_review_max_amount_cent_snapshot`。

后续机构发布新规则不会改变旧订单。可靠任务执行时只读取订单快照，并再次核对原始结算金额没有超过快照上限；这既防止异步执行期间规则漂移，也防止遗漏任务登记入口后错误放行。

订单继续通过 V53 的复合外键引用原始规则版本；金额上限快照不加入该外键。原因是 `ALL_MANUAL` 的上限按业务定义必须为 `NULL`，而 MySQL 会在复合外键任一列为 `NULL` 时跳过整条引用校验。保留原外键可以确保人工审核订单也始终引用真实存在且审核模式一致的规则版本。

V54 不给历史自动规则猜测金额上限。迁移开始前如发现已有自动模式规则或对应自动模式订单，会在任何表结构修改前失败，要求管理员先明确处理，避免静默改变既有业务语义。当前已核对的线上规则均为 `ALL_MANUAL`，可以安全迁移。

## 4. 提现上限不新增字段

现有 `hard_limit_cent` / `hardLimitYuan` 继续表示“单次最大提现金额”，同时约束手动提现和自动提现。手动最高金额、自动最高金额都必须小于或等于它，系统仍保留单次不超过 `200.00` 元的数据库硬约束。

Web 文案由“提现硬上限”改为“单次最大提现金额”。本次不增加另一个含义重复的提现字段。

## 5. Web 配置管理边界

主导航增加“配置管理”，首期只有两个子页面：

- `投递与审核规则`：路径 `/configurations/delivery`；
- `提现规则`：路径 `/configurations/withdrawal`。

旧路径 `/delivery-configuration` 保留兼容跳转，并完整保留查询参数。机构编辑弹窗中的重复投递规则页签退出；资金总览页中的提现规则卡片和发布弹窗退出。

小程序渠道配置、单台设备配置、设备运行快照全局策略和远程支持不迁入这个配置中心，因为它们分别属于平台渠道、设备资产或运行治理，不是机构日常业务规则。

## 6. 权限

- 投递规则沿用 `delivery.configuration.manage`；
- 提现规则拥有 `withdrawal.read` 或 `withdrawal.configuration.manage` 时可查看；
- 只有租户工作人员拥有 `withdrawal.configuration.manage` 时可发布提现规则；
- 平台管理员只读查看提现规则，不能代机构发布。

旧订单、旧提现单和既有待审核状态都不会因发布新配置自动变化。
