# 设备出厂接入进度与封存响应设计

> 决策日期：2026-08-31
> 适用范围：香橙派出厂热点网页、首次启动协调器、正式硬件服务、平台 Web 设备详情
> 目标：让验收员只看必要操作，让排障人员能准确知道流程停在哪个事实节点，同时不把诊断投影升级为业务权威。

## 1. 两个观察面

出厂接入有两个互补观察面：

- **设备局域网页**：手机连接香橙派出厂热点后使用。它只展示设备本机已经可靠观察到的事实，并提供“本机硬件检查”和“结束出厂模式”两个操作入口。
- **平台设备详情**：平台管理员使用。它展示后端数据库中的厂家袋码、云端自动验收、平台确认的验收结果、封存授权和完成事件；主视图提供通俗问题说明及处置方向，稳定机器代码只进入折叠技术诊断。

局域网页不直接访问后端，也不根据“等待时间较长”推断云端失败。平台网页不把可靠任务 `DONE` 推断成设备已经封存；只有后端收到并保存 `FACTORY_SEAL_COMPLETED`，封存状态才是 `SEALED`。

## 2. 局域网页九节点链

网页固定从左到右展示九个节点；只有进度链可横向滚动，页面主体保持移动端单列布局。

| 节点 | 谁在什么情况下推进 | 依据的事实 | 失败是否阻止后续 |
| --- | --- | --- | --- |
| 1. 启动准备与热点 | 首次启动协调器在系统和磁盘准备后启动热点 | `systemPrepared`、`factoryPortalReady` | 是 |
| 2. 本机硬件检查 | 验收员按网页指示逐项操作 | 本机检查状态、检查项和有效报告 | 是 |
| 3. 蜂窝联网与校时 | 本机硬件检查通过后由设备自动执行 | 蜂窝通信模块配置、上行链路、可信时间 | 是 |
| 4. 自注册与正式凭证 | 联网和时间可信后由设备自动执行 | 注册阶段、正式凭证、K1 清理 | 是；可重试错误保持自动推进 |
| 5. 正式服务与 OneNet | 注册完成并安全交接 UART 后自动执行 | 正式服务、UART、MQTT 及 5 秒心跳 | 是；心跳过期显示状态未知 |
| 6. 厂家扫码与初始袋码 | 厂家小程序扫描设备和各投口袋码 | 设备收到当前 P8 请求 | 是 |
| 7. 云端自动验收 | 后端发起请求，设备自动执行 | 存储、配置、设备控制板、摄像头、照片上传、检查结果保存和平台确认 | 是 |
| 8. 云端判定与封存授权 | 后端判定并可靠下发授权 | 设备已确认的证据送达事实和当前代次授权 | 是 |
| 9. 结束出厂模式 | 授权到达后由验收员单向确认 | 本机封存事实和清理状态 | 不可逆 |

设备本机不知道后端厂家袋码的精确 `N/M` 数量，因此局域网页不伪造数量。当前代次 P8 请求能够到达设备，表示后端已经满足袋码前置条件，节点 6 才记为完成。相同地，设备不会直接读取后端 `PASSED`；只有当前代次 `AUTHORIZE_FACTORY_SEAL` 已被设备验证并保存后，节点 8 才显示云端判定与授权完成。

## 3. 设备侧进度投影

首次启动协调器生成 `/run/ecobin/factory-portal/flow.json`。该文件是可丢失、可重建、无密钥的诊断投影，不参与业务门禁。它只从以下白名单来源聚合：

- P7：`/run/ecobin/factory-portal/acceptance.json`；
- 蜂窝：`/run/ecobin/cellular-uplink/status.json`；
- 注册：`/run/ecobin/enrollment/progress.json`；
- 正式运行、UART、MQTT 和 P8：`/run/ecobin/hardware/factory-progress.json`；
- P8 请求及证据可靠发送：只读查询 `/var/lib/ecobin/hardware/edge.db`；
- 当前代次封存授权和单向封存：`FactorySealController` 的公开状态。

注册和正式运行投影均采用严格字段白名单、原子替换和 `0600` 权限，不写入硬件 SN、UID、URL、请求正文、凭证或原始异常文本。局域网页得到的总投影只包含固定节点、固定状态、固定详细码和固定错误码。任何来源缺失、格式错误或正式运行心跳超过 15 秒，都显示 `UNKNOWN`，不能沿用旧值假装健康。

P8 细分阶段为：收到请求、持久化存储检查、配置检查、MCU/传感器检查、双摄拍照、COS 上传读回、证据持久化、证据可靠落盘、OneNet 接收和后端业务确认。失败时保留最后阶段及固定错误码，验收员可以判断问题发生在本地拍照、COS、OneNet 传输还是后端确认之前或之后。`platform_accepted_at` 只表示 OneNet 已接收上行；只有本地可靠发件箱记录 `confirmed_at`/`CONFIRMED`，才表示后端已通过确认命令完成业务确认。

## 4. 平台侧一致性快照

平台新增：

```text
GET /api/v1/web/platform/device-assets/{hardwareSn}/factory-progress
```

接口需要平台 `device.read` 权限，使用数据库 `REPEATABLE_READ` 只读事务并返回 `Cache-Control: no-store`。一次响应同时读取：

- 厂家袋码期望数、已登记数和修订号；
- 当前验收代次、权威状态和失败原因；
- 当前资产 `acceptance_evidence_sha256` 精确绑定的**权威证据**；
- 最近收到但不一定权威的**最新历史证据**；
- P8 请求和封存授权可靠任务的状态、最近尝试、外部请求号和脱敏诊断；
- 当前验收代次的封存授权及完成时间。

“已登记袋码”严格复用机器验收的资格谓词：只统计历史资格袋码，或由厂家小程序安装且操作员、标签和未释放占用均完整的袋码；平台创建的占位行不计入。P8 任务也必须同时匹配资产当前的袋码修订号和袋码集合摘要，旧修订任务只保留在历史记录中，不能推进当前进度。

平台设备详情以六个云端节点展示：初始袋码、发起云端验收、平台验收结果、封存授权、本地确认、封存完成。页面可见时每 5 秒无重叠轮询；抽屉关闭、页面隐藏或达到 `SEALED` 后停止自动轮询。`ACKNOWLEDGED` 只表示设备已接受授权，仍必须显示“等待设备设置页面人工确认”，不能显示为完成。

可靠任务已经创建不等于指令已经发出：没有外部尝试时显示“系统正在安排发送”，物联网平台明确受理后显示“已受理，等待设备确认”，设备离线或临时失败则分别显示等待恢复和自动重试。正常等待厂家扫码属于黄色人工待办，不显示为红色故障。若整体进度已经变为 `BLOCKED`，页面必须先展示阻断并停止指导后续操作；即使此前已经收到 `ACKNOWLEDGED`，也不能继续提示操作员封存。

## 5. 最终封存响应的时序

结束出厂模式是不可逆操作，顺序固定如下：

1. 浏览器生成并保留一个 UUID v4 作为本次确认标识；网络结果不明确时复用同一个标识重试。
2. root 封存控制器验证 P7、当前代次授权和本地资格，先 fsync 单向封存标记，并把本地授权记录写为 `SEALING`。
3. 控制器进入内存态 `SEALED_RESPONSE_PENDING`，暂不停止热点和网页服务。
4. HTTP 返回成功；浏览器先显示全屏成功结果，并等待两次绘制帧。
5. 浏览器发送尽力而为的 `ACK_FACTORY_SEAL_PRESENTED`。收到后设备至少再保留 0.5 秒传输余量，并在后续协调周期停止出厂服务、清理材料、应用正式防火墙并可靠上报完成事件。
6. 浏览器没有回执时，展示等待以 5 秒为硬上限；到期后在后续协调周期自动清理，不能因手机断线永久保留出厂入口。

POST 成功但响应丢失时，下一次状态轮询看到 `SEALED_RESPONSE_PENDING` 也会显示相同成功页。进程或设备在封存事实落盘后重启时，不恢复这段展示等待，而是只沿封存方向继续清理，绝不重新开放出厂模式。

## 6. 移动端和文案边界

- 支持的重点宽度为 320、360、375、390、412 和 430 px；按钮最小点击高度 44 px。
- 首屏只保留当前步骤、当前必要操作、通俗问题说明和可执行处置，不展示规划代号、状态枚举、错误码、请求号或内部记录编号。
- 稳定错误码、原始阶段码、请求号、记录编号和校验值只进入默认折叠的“技术诊断（报修时使用）”；发生问题时也不自动展开，未知新码必须显示固定中文兜底，不能原样回显。
- 页面统一把 P7 表述为“本机硬件检查”、P8 表述为“云端自动验收”、MCU 表述为“设备控制板”、OneNet/MQTT 表述为“云端设备连接”、COS 表述为“云端照片存储”、K1 表述为“一次性注册材料”。机器契约和历史数据中的稳定名称保持不变。
- 进度链保持从左到右，当前节点变化时自动居中；尊重系统“减少动态效果”设置。
- 自动变化仅在节点、状态、详细码或错误码实际变化时向读屏软件播报对应的中文说明，不播报原始机器代码；最终成功页使用模态语义并隔离背景焦点。
- 状态读取、本机硬件检查操作和最终封存请求均有有限超时；封存结果不明确时保留并复用同一确认标识，先核实状态，不能生成新标识重复封存。
- 不加载外部字体、脚本或分析服务，手机也不通过出厂热点转发互联网流量。
- 模拟来源只按既定边界作为证据元数据和一次性提示，不改变接入流程节点或后端判定路径。

## 7. 验证与发布要求

本次代码回归包括设备进度生产者、九节点聚合、安全文件、封存掉电恢复、浏览器展示回执、AP 单向门禁、运行时安装清单以及既有硬件业务；完整硬件结果为 `1052 passed, 46 skipped, 5 subtests passed`。后端设备模块、平台进度投影、Web 类型检查、生产构建和 OpenAPI 生成检查也已通过。平台进度查询依赖 V62 的可靠任务查询索引，新后端启动前必须先将目标数据库迁移并验证到 V62；运行 JAR 本身不携带迁移。

这些变更进入下一版镜像后，仍需用空白卡实际走一轮本机硬件检查、自动注册、厂家绑袋、云端自动验收、封存响应和冷启动复核。代码回归不替代单卡现场验证，也不改变独立的真实硬件资格与正式量产信任门禁。
