# 设备接入、配置恢复、投递与清运一致性审查

> 审查日期：2026-08-10
> 状态：审查、软件修复及独立 MySQL 8.4 集成验证完成
> 范围：永久设备资产接入、机器验收、机构初始化、配置应用、自动激活、投递准入、投递完成、清运准入和清运完成
> 不在本次范围：清运结束/恢复流程重设计、历史数据清理、MCU 屏幕状态机、终态称重失败建异常订单的独立需求

## 1. 审查结论

设备接入的永久资产模型、自动机器验收和清运完成时的原子换袋主链已经基本成立。
本次发现的问题集中在一个共同原因：部分查询仍把“厂家最初安装的袋”“投口现在安装的袋”
和“当前重量/容量记录所属的袋”当成同一代事实。

设备完成一次清运后，厂家袋会成为历史事实，新袋才是当前事实。如果代码只检查“有一条
有效重量基准”或“有一条容量状态”，却没有检查这些记录是否属于当前袋，就可能出现两类
相反错误：

- 把正常换袋后的设备误判为资料不完整，导致配置或自动激活不能收敛；
- 把旧袋的重量基准或满溢状态误用于新袋，错误允许投递或错误计算容量。

因此，本次修复不再针对某个设备 SN 增加特例，而是统一建立并检查“当前袋代际”。

后续复审又发现配置恢复存在同一种“把不同阶段当成同一状态”的问题：命令尚未送达、
设备已经落盘但等待结果、设备明确应用失败，是三种不同事实。它们不能都通过“唤醒原任务”
处理。本次同时把配置恢复收口为：只有明确的下发前阻断可以唤醒原任务；应用一旦
`FAILED`，排障后必须发布更高版本。

## 2. 初级开发者需要先理解的四类事实

| 事实 | 表/字段示例 | 含义 | 清运后是否变化 |
|---|---|---|---|
| 厂家安装事实 | `dev_factory_installed_bag` | 设备出厂时装过哪只袋，用于首次初始化和追溯 | 不变化，永远是历史事实 |
| 当前占用事实 | `rec_bag_current_occupancy.bag_id` | 此刻投口上实际绑定哪只袋 | 变化，换袋时指向新袋 |
| 当前容量代际 | `rec_port_capacity_state.current_bag_id` | 当前容量/满溢投影是为哪只袋保存的 | 变化，换袋时指向新袋 |
| 当前重量基准 | `rec_port_weight_baseline.bag_id` | 当前有效皮重属于哪只袋 | 变化；新皮重无效时也必须明确失效 |

正常状态必须满足以下不变量：

```text
rec_bag_current_occupancy.bag_id
  = rec_port_capacity_state.current_bag_id
  = rec_port_weight_baseline.bag_id（当 baseline_state = VALID 时）
```

这里的“代际”不是新表或复杂版本号，只是用现有 `bag_id` 判断几条当前记录是否都在描述
同一只袋。

## 3. 三条主流程的当前判断逻辑

### 3.1 设备接入

1. 平台创建设备资产时，`TargetDeviceApplication` 写入永久资产。设备尚未分配租户和机构，
   机器验收为 `PENDING`，生命周期为 `NORMAL`，OneNet 在线状态为 `UNKNOWN`；厂家袋的
   皮重准备状态为待处理。
2. OneNet 上报设备在线后，`AutomaticDeviceAcceptanceChallengeService` 在设备未验收、
   生命周期正常且没有正在执行的挑战时，自动下发机器验收请求。
3. 香橙派上报的验收证据必须证明配置能落盘、MCU 能通信、传感器能自检、摄像头能拍摄、
   图片能上传和读取、设备入口 URL 已保存等功能事实。`mcuSimulated` 和
   `camerasSimulated` 只作诊断，不参与通过/失败判断。
4. 验收通过后，平台才能永久分配一次租户；租户随后永久分配一次机构。
5. 分配机构的事务会建立运行时、投口、厂家袋、当前占用、容量状态和初始基准等机构事实，
   然后触发配置及自动激活收敛。机构不需要人工确认或开启经营资格。

首次初始化可以要求厂家袋仍是当前袋；设备完成过清运后，后续配置更新只能接受当前换入袋，
不能再次要求厂家袋占用投口。

### 3.2 投递

投递有两个准入入口，必须使用同一套规则：

- 小程序读取设备/投口选项时，给用户显示能否投递及阻断原因；
- 用户真正点击投递时，后端在事务和行锁内重新读取当前事实，防止查询后状态已变化。

两处都应检查：永久归属、验收和生命周期、租户/机构启用、OneNet 明确在线、最新配置版本
及摘要一致、整机/投口没有其他作业、机构投递规则有效、投口当前袋存在，以及下列当前袋
专属条件：

- 只有容量记录属于当前袋且状态明确为 `FULL` 时，返回 `PORT_FULL` 并阻止新投递；
- `WEIGHT_ONLY`（只用重量）和 `INFRARED_OR_WEIGHT`（红外或重量）模式要求当前袋有
  `VALID` 的重量基准，且基准记录的 `bag_id` 等于当前袋；
- `INFRARED_ONLY`（只用红外）不因为缺少重量基准而统一阻止投递；
- 旧袋的 `FULL`、旧袋基准、缺失满溢上报都不能冒充当前袋事实。

投递已经完成并上报结果后，即使发现容量代际不一致，也应先保住真实订单和原始证据；不能
因为后置容量投影异常而丢单。异常情况下应跳过错误容量计算并记录可观察的技术异常。

### 3.3 清运

清运是修复满袋和基准问题的业务，所以准入规则与投递不同：当前袋已满、当前重量基准无效，
都不能反过来阻止清运。

开始清运时，后端冻结当前旧袋、可信旧基准（如果确实属于旧袋）、预留的新袋、规则和命令
载荷。香橙派收到命令后再按现场实时状态判断传感器、门控和本地锁，后端不能使用较早的
运行快照替代现场判断。

清运完成事务会核对旧袋仍是当前占用、新袋仍被本操作预留，然后同时：

- 创建清运记录和异常记录；
- 取下旧袋、安装新袋；
- 为新袋建立有效基准，或在最终称重失败时建立明确的无效基准；
- 把容量状态切换到新袋，并初始化为 `NOT_FULL`；
- 结束操作、释放占用并登记可靠确认。

这一段原子换袋主链目前是审查中最完整的部分，后续修复不得破坏它。

## 4. 已确认问题与影响

| 编号 | 等级 | 已确认问题 | 可能出现的实际结果 | 计划状态 |
|---|---|---|---|---|
| G-01 | P0 | 投递选项和开始事务没有真正使用当前袋 `FULL` 作为阻断条件 | 已满设备仍能开始下一场投递 | 已修复，定向回归通过 |
| G-02 | P0 | 重量参与模式没有要求有效基准属于当前袋 | 使用旧袋皮重计算新袋容量，或在无基准时仍开门 | 已修复，定向回归通过 |
| G-03 | P1 | 清运开始只看基准为 `VALID`，未核对基准袋等于当前旧袋 | 旧袋 A 的皮重被当成当前袋 B 的可信皮重，并进入清运命令和结果计算 | 已修复，定向回归通过 |
| G-04 | P1 | 清运最新配置查询把运行快照 `safety_status='SAFE'` 当成配置应用条件 | 旧诊断快照会阻止清运，且与投递准入口径不一致 | 已修复，定向回归通过 |
| G-05 | P1 | 配置应用事实与自动激活在同一事务中强耦合 | 激活数据异常会回滚真实的 `APPLIED`，设备一直显示 `EDGE_SAVED` | 已修复，定向回归通过 |
| G-06 | P1 | 自动激活查询用内连接再按版本倒序，最新配置缺少应用记录时可能回退到旧版本 | 旧配置被误认为“最新可激活配置” | 已修复，定向回归通过 |
| G-07 | P1 | 投递完成容量查询未返回容量袋和基准袋，无法防止旧基准参与后置容量计算 | 订单能建成，但容量显示可能被旧袋基准污染 | 已修复，定向回归通过 |
| G-08 | P2 | 多条大 SQL 用内连接直接过滤不一致记录 | 真正的“袋代际不一致”被压成笼统的“资料不完整”，排查困难 | 已修复，定向回归通过 |
| G-09 | P2 | 自动激活调度器的候选条件与服务中的失败重试分支不一致 | 原修复把失败配置加入扫描，但没有证明真实状态转换和设备执行 | 复审推翻原结论，已改为失败后不重试 |
| G-10 | P1 | `EDGE_SAVED` 后失败会保留 `edge_persisted_at`，原重试却把应用改回 `PENDING` | 违反 `ck_dev_config_app_state_shape`，事务回滚并周期报错 | 已修复，删除失败回退和自动重试 |
| G-11 | P1 | 唤醒原任务复用原 `commandUid`，香橙派把配置命令识别为 `DUPLICATE` 且不重新分发 | 即使绕过数据库约束，也不会再次调用 MCU 或产生新证据 | 已修复，失败后必须发布新版本 |
| G-12 | P2 | `PORT_FULL`、`WEIGHT_BASELINE_MISSING` 未进入 OpenAPI、客户端类型和中文提示 | 后端能阻止投递，但客户端显示内部英文代码 | 已修复，机器契约和小程序同步 |
| G-13 | P2 | 当前占用袋与容量袋不一致时仍无条件返回旧袋百分比 | 页面可能显示旧袋 100%，同时按新袋条件判断是否允许投递 | 已修复，当前代际不完整时返回未知 |
| G-14 | P1 | 配置重同步读取把可变应用表与不可变版本表一起 `FOR UPDATE` | 最小权限运行账号不能更新版本表，MySQL 返回 1142，重同步接口变成 500 | 已修复，只锁应用行，再做无锁关联读取 |

另有“明确终态称重失败是否仍建立系统异常订单”的既有需求缺口。本次只记录，不与袋代际修复
混在一起，避免一次改动同时改变订单成立规则和容量投影规则。

## 5. 本次明确保留的正确边界

- 模拟 MCU/摄像头只作诊断；只要功能证据完整，自动机器验收仍可通过。
- OneNet 在线只由 `deviceOnline/deviceOffline` 生命周期事件决定，运行快照不推断在线。
- 厂家袋只用于首次初始化和历史追溯，不能在清运后重新绑定回厂家袋来修数据。
- 已开始的投递不因结束后得到 `FULL` 而丢单；`FULL` 只阻止下一场投递。
- 清运必须允许修复“满袋”或“重量基准无效”，不能复用投递准入策略一刀切。
- 清运完成的袋交换、基准、容量和操作结束继续保持同一事务。
- 本轮优先复用现有表和可靠任务，不为了修复判断逻辑增加新表。

## 6. 修复顺序和每项完成条件

### G-01：当前袋满溢准入

1. 先增加失败测试，分别证明选项查询和开始事务在“当前袋 `FULL`”时仍错误放行。
2. 让两处读取并使用同一语义：只有 `capacity.current_bag_id = occupancy.bag_id` 且
   `fullness_state = FULL` 才阻止。
3. 验证旧袋 `FULL`、当前袋 `NOT_FULL` 和无满溢上报不会误阻断。

### G-02：重量模式当前基准

1. 建立按满溢模式分类的纯判断：只用红外、只用重量、红外或重量。
2. 重量参与时要求 `VALID` 基准的袋、编号和重量都与当前事实自洽。
3. 查询展示和事务开始共用判断；事务内仍重新加锁读取。

### G-03：清运冻结旧基准

1. 查询同时返回容量当前袋和重量基准所属袋。
2. 只有两者都等于清运开始时锁定的旧袋，才冻结为 `TRUSTED`。
3. 不一致时标记为 `UNTRUSTED`，允许清运继续，不把旧皮重放入命令载荷，并留下异常证据。

### G-04：清运配置准入

1. 从“最新配置已应用”查询中移除运行快照安全状态条件。
2. 仍严格校验配置版本、边缘摘要、MCU 摘要及运行时应用版本。
3. 现场安全继续由香橙派收到命令后检查并以稳定错误码拒绝。

### G-05：配置应用与自动激活解耦

1. 配置证据成立时先独立提交 `APPLIED` 和可靠任务完成事实。
2. 自动激活作为后续可重试收敛执行；数据不一致不能回滚已经发生的设备应用事实。
3. 激活失败必须可查询、可重试并带具体原因，不能静默吞掉。

### G-06～G-08：防御性校验与诊断

1. 先选真正最新配置，再判断其应用/运行记录是否完整，禁止回退旧版本。
2. 投递完成发现代际不一致时保留订单，跳过错误容量投影并记录异常。
3. 查询尽量返回原始事实后由策略分类为 `MISSING`、`MISMATCH` 或 `VALID`，减少内连接把
   问题隐藏成“资料不完整”。
4. 为每种候选状态补测试，并确保诊断输出能指出缺少或矛盾的具体事实。

### G-09～G-14：配置失败恢复

1. `FAILED` 应用不再进入自动激活调度候选，也不能改回 `PENDING`；通用可靠任务恢复接口
   不接受 `ENSURE_DEVICE_CONFIGURATION`，避免绕过配置专用策略。
2. 同版本重同步只允许当前最高应用仍为 `PENDING`、`edge_persisted_at` 为空、原任务为
   `BLOCKED`，且原因属于明确下发前白名单。证据超时、确认超时和未知原因默认拒绝。
3. 故障排除后发布更高版本，由新版本创建新的 application、command 和 task；原失败事实
   保持可审计。原版本和摘要完全一致的迟到 `APPLIED` 仍可纠正事实，迟到
   `EDGE_SAVED` 不重新打开失败应用。
4. 重同步事务只对 `dev_config_application` 这一可变行加锁；随后无锁读取不可变
   `dev_config_version`。运行账号不需要获得超出职责的版本表更新权限。
5. 用真实 MySQL 和真实运行账号验证允许/拒绝分支、发布新版本、旧任务取消及最小权限锁。

## 7. 逐项解决结果

| 编号 | 实际修改 | 出现异常时是否阻止后续业务 |
|---|---|---|
| G-01 | 小程序查询和开始投递事务都读取当前袋满溢状态；事务入口重新加锁检查，避免用户看到可投后设备已变满 | 当前袋明确为 `FULL` 时阻止新投递；已经开始或已经完成的订单不回滚 |
| G-02 | 抽出当前袋代际判断；重量参与模式要求容量袋、容量基准编号/重量、基准记录和当前占用袋全部一致 | 只用重量、红外或重量模式缺少当前基准时阻止投递；只用红外不受影响 |
| G-03 | 清运开始同时读取容量当前袋和真实基准记录；只有基准确属当前旧袋时才冻结为可信皮重 | 旧基准不可信不会阻止清运，只是不参与命令和重量计算，并在完成阶段留下异常事实 |
| G-04 | 清运配置查询不再使用较早运行快照中的 `SAFE`；香橙派收到命令后检查现场安全 | 旧快照不再阻止清运；现场真实不安全仍由香橙派拒绝物理动作 |
| G-05 | 设备报告配置已应用后先提交 `APPLIED` 和可靠任务，再在提交后用独立事务推进自动激活 | 激活失败不会把真实 `APPLIED` 回滚成 `EDGE_SAVED`；失败原因写入服务端日志并由补偿扫描重试可恢复状态 |
| G-06 | 先选版本号最大的配置，再左连接它的应用记录；最新版本缺应用记录时明确报错，不准回退旧版本 | 阻止错误激活旧配置，不修改已经存在的配置事实 |
| G-07 | 投递完成读取容量所属袋及基准所属袋；代际不一致时仍保存订单、照片和原始证据，跳过容量投影并写 `CAPACITY_PROJECTION_SKIPPED` 系统异常 | 不丢真实订单，但不让旧基准污染当前容量显示 |
| G-08 | 自动激活以投口为主表左连接厂家袋、当前占用、容量和配置快照；逐项报告 `FACTORY_BAG`、`CURRENT_BAG_OCCUPANCY`、`CAPACITY_STATE` 等缺失事实，并检查两处当前袋是否一致 | 结构缺失或代际矛盾时停止本次激活，日志直接指出投口和事实名称；不会改回厂家袋 |
| G-09～G-11 | 删除 `FAILED → PENDING` 和自动失败扫描；只有命令明确未送达时才允许唤醒原任务，其他失败由平台发布更高版本 | 原失败应用和命令保持审计事实，不再触发数据库约束或设备重复命令；新版本使用新的应用、命令和可靠任务身份 |
| G-12 | OpenAPI 增加两个阻断码，重新生成 Web 类型并同步小程序类型和中文提示 | 用户看到可处理的中文原因，客户端类型与后端实际响应一致 |
| G-13 | 面向当前袋的投递、清运和设备业务快照只有在容量记录所属袋等于当前占用袋时返回百分比；百分比可能来自红外，不额外要求重量基准有效 | 旧袋容量事实不删除，但不会冒充当前袋状态；纯红外投口仍能显示当前袋的有效百分比 |
| G-14 | 重同步先单独锁定 `dev_config_application`，再无锁关联读取配置版本；不扩大数据库授权 | 运行账号保持最小权限，合法重同步不再因锁到只读版本表而返回 500 |

## 8. 回归测试矩阵

至少覆盖以下场景：

- 厂家袋从未换过，初始基准有效；
- 完成一次、两次清运后，当前袋和厂家袋不同；
- 当前占用袋与容量当前袋不一致；
- 当前占用袋与有效基准袋不一致；
- 当前袋 `FULL`、旧袋 `FULL`、当前袋 `NOT_FULL`；
- 三种满溢模式下基准为有效、无效、缺失和旧袋；
- 最新配置存在但应用记录缺失，旧配置应用完整；
- 配置已经 `APPLIED`，但激活数据暂时不一致；
- 投递完成时容量代际异常，订单仍成立但容量投影不被污染；
- 清运开始时旧基准不可信，清运仍可修复并正确切换到新袋。
- 配置 `EDGE_SAVED → FAILED` 后不再自动选择或改回 `PENDING`；
- 只有未送达的 `BLOCKED` 配置任务可同版本唤醒，证据超时必须发布新版本；
- `FAILED` 后迟到的精确 `APPLIED` 可纠正事实，迟到 `EDGE_SAVED` 不重新打开应用；
- 当前袋 B 与旧容量袋 A 不一致时，投递和清运页面不显示 A 的百分比。
- 最小权限运行账号可以锁配置应用并完成安全重同步，但不能借机获得修改不可变配置版本的权限。

MySQL 的外键、锁、事务和查询行为以 MySQL 8.x 集成测试为最终证据。本次使用从当前
V1～V46 迁移全新建立的独立 MySQL 8.4 数据库和最小权限运行账号执行；旧 V30 本地库因
已应用迁移校验和与当前仓库不同而没有被修复或冒充当前验证环境。
