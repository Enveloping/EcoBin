# 设备接入、配置恢复、投递与清运一致性审查

> 审查日期：2026-08-10
> 状态：G-01～G-15、R-01～R-07 已完成；生产数据库已升级到 V47，S-01～S-04 已部署验收并重新冻结；D-01～D-04 继续暂缓
>
> 后续说明（2026-08-13）：独立设备安装资料确实需要结构变化，当前代码因此新增 V48。本文后文“除非需要，否则不新增 V48”是本次一致性修复当时的约束，不再表示当前数据库纪元仍停在 V47。
> 范围：永久设备资产接入、机器验收、机构初始化、配置应用、自动激活、投递准入、投递完成、清运准入和清运完成
> 不在本次范围：清运结束/恢复流程重设计、历史数据清理、MCU 屏幕状态机、终态称重失败建异常订单的独立需求

## 1. 审查结论

设备接入的永久资产模型、自动机器验收和清运完成时的原子换袋主链已经基本成立。
本次发现的问题集中在一个共同原因：部分查询仍把“厂家最初安装的袋”“投口现在安装的袋”
和“当前重量/容量记录所属的袋”当成同一代事实。

设备完成一次清运后，厂家袋会成为历史事实，新袋才是当前事实。如果代码只检查“有一条
有效重量基准”或“有一条容量状态”，却没有检查这些记录是否属于当前袋，就可能出现两类
相反错误：

- 把正常换袋后的设备误判为资料不完整，导致配置或自动激活不能收敛；
- 把旧袋的重量基准或满溢状态误用于新袋，错误允许投递或错误计算容量。

因此，本次修复不再针对某个设备 SN 增加特例，而是统一建立并检查“当前袋代际”。

后续复审又发现配置恢复存在同一种“把不同阶段当成同一状态”的问题：命令尚未送达、
设备已经落盘但等待结果、设备明确应用失败，是三种不同事实。它们不能都通过“唤醒原任务”
处理。本次同时把配置恢复收口为：只有明确的下发前阻断可以唤醒原任务；应用一旦
`FAILED`，排障后必须发布更高版本。

## 2. 初级开发者需要先理解的四类事实

| 事实 | 表/字段示例 | 含义 | 清运后是否变化 |
|---|---|---|---|
| 厂家安装事实 | `dev_factory_installed_bag` | 设备出厂时装过哪只袋，用于首次初始化和追溯 | 不变化，永远是历史事实 |
| 当前占用事实 | `rec_bag_current_occupancy.bag_id` | 此刻投口上实际绑定哪只袋 | 变化，换袋时指向新袋 |
| 当前容量代际 | `rec_port_capacity_state.current_bag_id` | 当前容量/满溢投影是为哪只袋保存的 | 变化，换袋时指向新袋 |
| 当前重量基准 | `rec_port_weight_baseline.bag_id` | 当前有效皮重属于哪只袋 | 变化；新皮重无效时也必须明确失效 |

正常状态必须满足以下不变量：

```text
rec_bag_current_occupancy.bag_id
  = rec_port_capacity_state.current_bag_id
  = rec_port_weight_baseline.bag_id（当 baseline_state = VALID 时）
```

这里的“代际”不是新表或复杂版本号，只是用现有 `bag_id` 判断几条当前记录是否都在描述
同一只袋。

## 3. 三条主流程的当前判断逻辑

### 3.1 设备接入

1. 平台创建设备资产时，`TargetDeviceApplication` 写入永久资产。设备尚未分配租户和机构，
   机器验收为 `PENDING`，生命周期为 `NORMAL`，OneNet 在线状态为 `UNKNOWN`；厂家袋的
   皮重准备状态为待处理。
2. OneNet 上报设备在线后，`AutomaticDeviceAcceptanceChallengeService` 在设备未验收、
   生命周期正常且没有正在执行的挑战时，自动下发机器验收请求。
3. 香橙派上报的验收证据必须证明配置能落盘、MCU 能通信、传感器能自检、摄像头能拍摄、
   图片能上传和读取、设备入口 URL 已保存等功能事实。`mcuSimulated` 和
   `camerasSimulated` 只作诊断，不参与通过/失败判断。
4. 验收通过后，平台才能永久分配一次租户；租户随后永久分配一次机构。
5. 分配机构的事务会建立运行时、投口、厂家袋、当前占用、容量状态和初始基准等机构事实，
   然后触发配置及自动激活收敛。机构不需要人工确认或开启经营资格。

首次初始化可以要求厂家袋仍是当前袋；设备完成过清运后，后续配置更新只能接受当前换入袋，
不能再次要求厂家袋占用投口。

### 3.2 投递

投递有两个准入入口，必须使用同一套规则：

- 小程序读取设备/投口选项时，给用户显示能否投递及阻断原因；
- 用户真正点击投递时，后端在事务和行锁内重新读取当前事实，防止查询后状态已变化。

两处都应检查：永久归属、验收和生命周期、租户/机构启用、OneNet 明确在线、最新配置版本
及摘要一致、整机/投口没有其他作业、机构投递规则有效、投口当前袋存在，以及下列当前袋
专属条件：

- 只有容量记录属于当前袋且状态明确为 `FULL` 时，返回 `PORT_FULL` 并阻止新投递；
- `WEIGHT_ONLY`（只用重量）和 `INFRARED_OR_WEIGHT`（红外或重量）模式要求当前袋有
  `VALID` 的重量基准，且基准记录的 `bag_id` 等于当前袋；
- `INFRARED_ONLY`（只用红外）不因为缺少重量基准而统一阻止投递；
- 旧袋的 `FULL`、旧袋基准、缺失满溢上报都不能冒充当前袋事实。

投递已经完成并上报结果后，即使发现容量代际不一致，也应先保住真实订单和原始证据；不能
因为后置容量投影异常而丢单。异常情况下应跳过错误容量计算并记录可观察的技术异常。

### 3.3 清运

清运是修复满袋和基准问题的业务，所以准入规则与投递不同：当前袋已满、当前重量基准无效，
都不能反过来阻止清运。

开始清运时，后端冻结当前旧袋、可信旧基准（如果确实属于旧袋）、预留的新袋、规则和命令
载荷。香橙派收到命令后再按现场实时状态判断传感器、门控和本地锁，后端不能使用较早的
运行快照替代现场判断。

清运完成事务会核对旧袋仍是当前占用、新袋仍被本操作预留，然后同时：

- 创建清运记录和异常记录；
- 取下旧袋、安装新袋；
- 为新袋建立有效基准，或在最终称重失败时建立明确的无效基准；
- 把容量状态切换到新袋，并初始化为 `NOT_FULL`；
- 结束操作、释放占用并登记可靠确认。

这一段原子换袋主链目前是审查中最完整的部分，后续修复不得破坏它。

## 4. 已确认问题与影响

| 编号 | 等级 | 已确认问题 | 可能出现的实际结果 | 计划状态 |
|---|---|---|---|---|
| G-01 | P0 | 投递选项和开始事务没有真正使用当前袋 `FULL` 作为阻断条件 | 已满设备仍能开始下一场投递 | 已修复，定向回归通过 |
| G-02 | P0 | 重量参与模式没有要求有效基准属于当前袋 | 使用旧袋皮重计算新袋容量，或在无基准时仍开门 | 已修复，定向回归通过 |
| G-03 | P1 | 清运开始只看基准为 `VALID`，未核对基准袋等于当前旧袋 | 旧袋 A 的皮重被当成当前袋 B 的可信皮重，并进入清运命令和结果计算 | 已修复，定向回归通过 |

| G-12 | P2 | `PORT_FULL`、`WEIGHT_BASELINE_MISSING` 未进入 OpenAPI、客户端类型和中文提示 | 后端能阻止投递，但客户端显示内部英文代码 | 已修复，机器契约和小程序同步 |
| G-13 | P2 | 当前占用袋与容量袋不一致时仍无条件返回旧袋百分比 | 页面可能显示旧袋 100%，同时按新袋条件判断是否允许投递 | 已修复，当前代际不完整时返回未知 |
| G-14 | P1 | 配置重同步读取把可变应用表与不可变版本表一起 `FOR UPDATE` | 最小权限运行账号不能更新版本表，MySQL 返回 1142，重同步接口变成 500 | 已修复，只锁应用行，再做无锁关联读取 |
| G-15 | P1 | 配置未精确应用时设备查询按契约隐藏 `fullnessMode`，回收查询仍把该空展示值传给严格代际策略 | 用户扫码本应看到“配置尚未生效”，却因 `NullPointerException` 得到 500 | 已修复，展示查询保留配置阻断并跳过重量模式判断 |

另有“明确终态称重失败是否仍建立系统异常订单”的既有需求缺口。本次只记录，不与袋代际修复
混在一起，避免一次改动同时改变订单成立规则和容量投影规则。

## 5. 本次明确保留的正确边界

- 模拟 MCU/摄像头只作诊断；只要功能证据完整，自动机器验收仍可通过。
- OneNet 在线只由 `deviceOnline/deviceOffline` 生命周期事件决定，运行快照不推断在线。
- 厂家袋只用于首次初始化和历史追溯，不能在清运后重新绑定回厂家袋来修数据。
- 已开始的投递不因结束后得到 `FULL` 而丢单；`FULL` 只阻止下一场投递。
- 清运必须允许修复“满袋”或“重量基准无效”，不能复用投递准入策略一刀切。
- 清运完成的袋交换、基准、容量和操作结束继续保持同一事务。
- 本轮优先复用现有表和可靠任务，不为了修复判断逻辑增加新表。

## 6. 修复顺序和每项完成条件

### G-01：当前袋满溢准入

1. 先增加失败测试，分别证明选项查询和开始事务在“当前袋 `FULL`”时仍错误放行。
2. 让两处读取并使用同一语义：只有 `capacity.current_bag_id = occupancy.bag_id` 且
   `fullness_state = FULL` 才阻止。
3. 验证旧袋 `FULL`、当前袋 `NOT_FULL` 和无满溢上报不会误阻断。

### G-02：重量模式当前基准

1. 建立按满溢模式分类的纯判断：只用红外、只用重量、红外或重量。
2. 重量参与时要求 `VALID` 基准的袋、编号和重量都与当前事实自洽。
3. 查询展示和事务开始共用判断；事务内仍重新加锁读取。

### G-03：清运冻结旧基准

1. 查询同时返回容量当前袋和重量基准所属袋。
2. 只有两者都等于清运开始时锁定的旧袋，才冻结为 `TRUSTED`。
3. 不一致时标记为 `UNTRUSTED`，允许清运继续，不把旧皮重放入命令载荷，并留下异常证据。

### G-04：清运配置准入

1. 从“最新配置已应用”查询中移除运行快照安全状态条件。
2. 仍严格校验配置版本、边缘摘要、MCU 摘要及运行时应用版本。
3. 现场安全继续由香橙派收到命令后检查并以稳定错误码拒绝。

### G-05：配置应用与自动激活解耦

1. 配置证据成立时先独立提交 `APPLIED` 和可靠任务完成事实。
2. 自动激活作为后续可重试收敛执行；数据不一致不能回滚已经发生的设备应用事实。
3. 激活失败必须可查询、可重试并带具体原因，不能静默吞掉。

### G-06～G-08：防御性校验与诊断

1. 先选真正最新配置，再判断其应用/运行记录是否完整，禁止回退旧版本。
2. 投递完成发现代际不一致时保留订单，跳过错误容量投影并记录异常。
3. 查询尽量返回原始事实后由策略分类为 `MISSING`、`MISMATCH` 或 `VALID`，减少内连接把
   问题隐藏成“资料不完整”。
4. 为每种候选状态补测试，并确保诊断输出能指出缺少或矛盾的具体事实。

### G-09～G-15：配置失败恢复与未生效展示

1. `FAILED` 应用不再进入自动激活调度候选，也不能改回 `PENDING`；通用可靠任务恢复接口
   不接受 `ENSURE_DEVICE_CONFIGURATION`，避免绕过配置专用策略。
2. 同版本重同步只允许当前最高应用仍为 `PENDING`、`edge_persisted_at` 为空、原任务为
   `BLOCKED`，且原因属于明确下发前白名单。证据超时、确认超时和未知原因默认拒绝。
3. 故障排除后发布更高版本，由新版本创建新的 application、command 和 task；原失败事实
   保持可审计。原版本和摘要完全一致的迟到 `APPLIED` 仍可纠正事实，迟到
   `EDGE_SAVED` 不重新打开失败应用。
4. 重同步事务只对 `dev_config_application` 这一可变行加锁；随后无锁读取不可变
   `dev_config_version`。运行账号不需要获得超出职责的版本表更新权限。
5. 用真实 MySQL 和真实运行账号验证允许/拒绝分支、发布新版本、旧任务取消及最小权限锁。
6. 设备配置未精确应用时，`fullnessMode=null` 是“不可展示配置值”而不是数据错误；投递
   选项保留 `CONFIGURATION_NOT_APPLIED` 并跳过重量基准分类。真正开始投递仍使用严格策略，
   空模式继续被拒绝，不能借展示容错放宽物理动作准入。

## 7. 逐项解决结果

| 编号 | 实际修改 | 出现异常时是否阻止后续业务 |
|---|---|---|
| G-01 | 小程序查询和开始投递事务都读取当前袋满溢状态；事务入口重新加锁检查，避免用户看到可投后设备已变满 | 当前袋明确为 `FULL` 时阻止新投递；已经开始或已经完成的订单不回滚 |
| G-02 | 抽出当前袋代际判断；重量参与模式要求容量袋、容量基准编号/重量、基准记录和当前占用袋全部一致 | 只用重量、红外或重量模式缺少当前基准时阻止投递；只用红外不受影响 |
| G-03 | 清运开始同时读取容量当前袋和真实基准记录；只有基准确属当前旧袋时才冻结为可信皮重 | 旧基准不可信不会阻止清运，只是不参与命令和重量计算，并在完成阶段留下异常事实 |
| G-04 | 清运配置查询不再使用较早运行快照中的 `SAFE`；香橙派收到命令后检查现场安全 | 旧快照不再阻止清运；现场真实不安全仍由香橙派拒绝物理动作 |
| G-05 | 设备报告配置已应用后先提交 `APPLIED` 和可靠任务，再在提交后用独立事务推进自动激活 | 激活失败不会把真实 `APPLIED` 回滚成 `EDGE_SAVED`；失败原因写入服务端日志并由补偿扫描重试可恢复状态 |
| G-06 | 先选版本号最大的配置，再左连接它的应用记录；最新版本缺应用记录时明确报错，不准回退旧版本 | 阻止错误激活旧配置，不修改已经存在的配置事实 |
| G-07 | 投递完成读取容量所属袋及基准所属袋；代际不一致时仍保存订单、照片和原始证据，跳过容量投影并写 `CAPACITY_PROJECTION_SKIPPED` 系统异常 | 不丢真实订单，但不让旧基准污染当前容量显示 |
| G-08 | 自动激活以投口为主表左连接厂家袋、当前占用、容量和配置快照；逐项报告 `FACTORY_BAG`、`CURRENT_BAG_OCCUPANCY`、`CAPACITY_STATE` 等缺失事实，并检查两处当前袋是否一致 | 结构缺失或代际矛盾时停止本次激活，日志直接指出投口和事实名称；不会改回厂家袋 |

## 10. 2026-08-11 全流程状态机复审

### 10.1 本轮范围和结论

本轮只审查并记录，不修改业务代码。审查不是只沿着“成功一次”的演示路径走，而是逐项
核对以下问题：

- 谁在什么情况下创建业务意图；
- 后端依据哪些当前事实允许或拒绝；
- 香橙派和 MCU 的哪个证据代表“已保存”“可能开始物理动作”或“已经完成”；
- 每个中间状态由谁推进，失败或超时后由谁收口；
- 设备占用、袋占用、配置、重量基准和可靠任务是否一起释放或保留；
- 重复消息、迟到消息、换袋、离线、重启、禁用和并发请求是否会破坏当前事实。

结论如下：

1. 设备正常接入、正常投递、正常清运三条成功主链总体自洽，可以继续作为修复时不得破坏
   的基线。
2. 当前袋代际、配置冻结、投递完成建单、清运原子换袋和迟到满溢上报的保护逻辑没有发现
   新的代际错误。
3. 确认存在 3 个 P1 和 1 个 P2。P1 表示正常运维中可能让设备或整机业务永久卡住；P2
   表示不会破坏核心数据，但状态展示、错误契约或并发结果不符合设计。
4. 另有 4 类此前已经明确暂缓的异常恢复或真机验证缺口。本节单独标记，不能把“表里有
   预留状态、协议里有命令”误写成“端到端能力已经完成”。

### 10.2 三条流程的事实和状态

#### 10.2.1 设备接入

| 阶段 | 谁发起或上报 | 后端依据的权威事实 | 修改的记录或状态 | 是否阻止后续业务 |
|---|---|---|---|---|
| 平台创建设备 | 平台管理员 | 硬件 SN、公开码、OneNet 设备身份唯一 | 创建永久资产；验收为 `PENDING`，生命周期为 `NORMAL`，传输为 `UNKNOWN` | 未验收时阻止分配和业务 |
| 联网 | OneNet 北向生命周期事件 | `deviceOnline/deviceOffline`，不使用普通消息猜在线 | 更新 OneNet 传输状态；在线时触发自动验收挑战和待下发任务唤醒 | 只有明确 `ONLINE` 才允许新投递或清运 |
| 机器验收 | 后端下发挑战，香橙派上报证据 | 挑战身份、MCU/传感器/摄像头功能证据、照片上传回读、设备入口 URL 已保存 | 追加验收证据；失败为 `FAILED`，成功后资产变为永久 `PASSED` | `PASSED` 前不能分配；模拟标志只作诊断，不单独判失败 |
| 永久分配 | 平台分配租户，租户分配机构 | 设备 `NORMAL + PASSED`，目标租户/机构启用，原归属为空 | 永久写入 `tenant_id`、`organization_id`；机构分配时原子建立投口、厂家袋、当前占用和容量初始事实 | 分配完成前不能开展机构业务 |
| 配置应用 | 自动激活服务创建配置应用，香橙派上报进度 | 最新配置版本及两个摘要精确一致 | `PENDING → EDGE_SAVED → APPLIED`，或进入终态 `FAILED` | 最新配置未精确 `APPLIED` 时阻止投递和清运 |
| 首次皮重 | 配置应用后自动创建测量，香橙派向 MCU 取空袋重量并上报 | 当前袋仍是厂家预装袋、容量代际未变化、测量身份和配置一致 | 测量 `PENDING → COMPLETED/FAILED/STALE_IGNORED`；成功建立当前袋有效基准并把厂家袋皮重标为 `READY` | 重量参与模式没有当前有效基准时阻止投递；不阻止清运修复 |

设备接入的正常状态链是：

`创建资产 → 自动验收通过 → 永久分配 → 最新配置 APPLIED → 当前厂家袋皮重 READY → 联网即用`。

其中验收在平台创建设备后即可完成，不等待租户或机构分配；机构分配后不再要求机构人员
确认、启用或输入部署码。配置一旦进入 `FAILED`，原应用不重新打开，排除故障后发布更高
版本，形成新的 application、command 和 task。这个边界与 G-09～G-11 的冻结结论一致。

#### 10.2.2 投递

| 阶段 | 谁发起或上报 | 后端依据的权威事实 | 修改的记录或状态 | 是否阻止后续业务 |
|---|---|---|---|---|
| 查看投递选项 | 小程序用户扫码 | 用户机构、手机号、钱包资格、设备归属/验收/生命周期、OneNet 在线、最新配置、整机占用、当前袋、当前袋满溢和当前重量基准 | 只读，不创建会话 | 返回具体 blocker；不满足条件时不允许开始 |
| 开始投递 | 已登录且手机号已绑定的机构用户 | 在同一 `READ_COMMITTED` 事务中重新加锁检查上述事实，并冻结用户、价格、配置、投口和当前袋 | 原子创建 `AUTHORIZATION_QUEUED` 会话、整机 `DELIVERY` 占用、设备命令和可靠任务 | 任一步失败全部回滚，不留半套记录 |
| 边缘执行 | 香橙派收到命令 | 冻结配置仍为本机当前配置、本地没有工作、授权未过期、现场自检和安全事实成立 | SQLite 保存命令和唯一工作槽；写串口前上报 `ACCEPTED`，完整写出后上报兼容 `MCU_ACCEPTED` | 现场不安全应在物理动作前拒绝；不得自动重放开门命令 |
| 完成投递 | 香橙派上报唯一 `DELIVERY_COMPLETE` | session、command、资产、投口、冻结袋和配置一致；旧消息不得冒充当前作业 | 同一事务保存物理事实、创建一张订单和照片/异常，更新当前袋容量，结束 session，释放整机占用并创建业务确认意图 | 完成后的 `FULL` 只阻止下一场，不回滚本单 |

数据库设计出的投递状态链是：

`AUTHORIZATION_QUEUED → IN_PROGRESS → BUSINESS_CONFIRMED`。

能够证明从未开始物理动作时应进入 `PRE_OPEN_ENDED`；香橙派执行期重启按当前固定帧冻结
边界进入 `DEVICE_ABORTED`。`RESULT_PENDING_RECOVERY` 用于“设备可能已经开始，
但结果尚未可信收齐”。本轮实施后，证据超时和结果不确定已有生产写入者，
但专用的现场恢复与最终收口仍属于 D-01，不能视为已完成全部恢复能力。

数据库约束还允许 delivery session 使用 `PREPARED`，但当前生产开始事务会原子创建命令、
可靠任务和占用，并直接写入 `AUTHORIZATION_QUEUED`，没有任何运行时 writer 产生
`PREPARED`。它是无功能影响的死状态；如果后续不再设计两阶段云端准备，应在模型简化时
删除，而不是继续作为“兼容旧模型”保留。

同一次可达性核对还发现 `dev_device_command.physical_state=CREATED` 没有生产 writer：配置、
首次皮重、投递、清运和满溢采样命令都在与可靠任务同一事务中直接插入为 `QUEUED`。它与
delivery 的 `PREPARED` 属于同一批模型清理候选，不影响当前运行，但不应长期伪装成可达
状态。

#### 10.2.3 清运

| 阶段 | 谁发起或上报 | 后端依据的权威事实 | 修改的记录或状态 | 是否阻止后续业务 |
|---|---|---|---|---|
| 查看清运条件 | 清运员 | 人员身份、设备永久归属/验收/生命周期、OneNet 在线、最新配置、整机占用、投口和进行中的端口作业 | 只读，不预留袋 | 当前袋 `FULL`、当前基准无效或当前袋缺失不阻止清运，因为清运本身用于修复这些问题 |
| 开始清运 | 清运员扫描新袋码 | 事务内锁定清运规则、人员、资产、当前袋/基准、容量和新袋；新袋必须属于本机构且当前未被占用 | 原子创建 `PREPARED` 操作、预留 `CLEAN_RESERVED` 新袋、建立整机 `CLEAN` 占用、照片槽、设备命令和可靠任务 | 失败全部回滚；同袋不能被两次操作占用 |
| 边缘执行 | 香橙派收到命令 | 冻结配置、现场安全、本地唯一工作槽和授权有效期 | `ACCEPTED` 投影为 `EDGE_SAVED`；串口完整写出后的 `MCU_ACCEPTED` 投影为 `IN_PROGRESS` | 写串口前明确失败进入 `PRE_UNLOCK_ENDED` 并释放占用；可能已经解锁的失败进入 `RECOVERY_REQUIRED` |
| 完成清运 | 香橙派上报唯一 `CLEAN_COMPLETE` | 冻结旧袋事实仍成立，新袋仍由本操作预留，完成身份和配置一致 | 同一事务创建清运记录、取下旧袋、安装新袋、建立有效或无效新皮重、把容量切换到新袋并置为 `NOT_FULL`、完成操作和释放占用 | 新皮重无效时重量参与投递继续被阻止，但仍允许再次清运修复 |

清运正常链是：

`PREPARED → EDGE_SAVED → IN_PROGRESS → COMPLETED`。

能够证明尚未解锁时进入 `PRE_UNLOCK_ENDED`；物理动作可能已经开始但没有完成时进入
`RECOVERY_REQUIRED`；固定帧执行期重启进入 `ABORTED`，同时建立清运重启联锁。联锁阻止
投递，但不阻止下一次清运去修复现场，下一次可信清运完成后再清除联锁。

### 10.3 本轮确认仍然正确的边界

- 平台验收不依赖租户或机构分配；`mcu_simulated`、`cameras_simulated` 只记录诊断，功能
  证据完整时模拟设备仍可自动通过验收。
- 验收成功是永久事实；后续失败证据不能把 `PASSED` 降回失败。设备生命周期、租户或机构
  禁用只阻止创建新业务，不抹掉已经发生的验收、订单或清运事实。
- 厂家预装袋只用于首次建立皮重。完成清运后，当前投口绑定的新袋及其有效基准就是新的
  权威事实，配置滚动或自动激活不能重新要求厂家袋仍占用投口。
- 投递查询和开始事务都只把“当前占用袋自己的明确 `FULL`”作为满溢阻断；旧袋满溢、旧袋
  百分比和缺少上报不能冒充当前袋状态。
- 重量参与模式要求有效基准确属当前袋；只用红外的模式不因为重量基准无效而被误阻止。
- 清运有意允许当前袋已满、基准无效或当前袋缺失，以便现场通过换袋恢复；不能复用投递
  blocker 把修复入口一起关闭。
- 同一机构的清运开始事务会先锁同一个清运规则头，因此同机构两台设备扫描同一袋时会
  串行检查袋占用；跨机构扫描已有袋会按归属拒绝，并发登记同一个新袋码的唯一键竞争也
  已转换为 `CLEAN.BAG_UNAVAILABLE`。当前没有证据表明同一袋会被双重预留或泄漏通用错误。
- 投递开始冻结袋、价格和配置，清运开始冻结旧袋、新袋和配置。之后改价、发布新配置、
  禁用设备或机构，都只关闭新业务入口，已创建作业继续按冻结事实收敛。
- 投递完成和清运完成都先完成业务写入再释放整机占用；数据库事务失败时保留占用，避免
  新作业穿插并破坏原作业的冻结事实。
- OneNet 同一外部事件身份但内容不同会进入冲突隔离；相同内容重放按幂等处理，不会重复
  建单或重复换袋。
- 固定帧阶段 MCU 没有 ACK、CRC、作业身份和状态查询；因此 `MCU_ACCEPTED` 只表示完整
  串口字节已经写出，不表示门真的打开。当前代码没有把它误当成最终业务完成。

### 10.4 修复前新确认的问题

下表是 2026-08-11 复审当时的问题快照，用于保留缺陷前因。S-01～S-04 的
实施后状态以第 11 节为准。

| 编号 | 等级 | 问题 | 直接结果 | 当前是否已有自动出口 |
|---|---|---|---|---|
| S-01 | P1 | 首次皮重测量的可靠任务进入 `BLOCKED` 后，测量仍永久保持 `PENDING` | 自动激活一直认为“已有测量”，不创建新命令；厂家袋一直 `MEASURING`，重量模式永远不可投递 | 没有；只有迟到结果或明确 `EDGE_RESTARTED` 能偶然收口 |
| S-02 | P1 | 投递的 `REJECTED/PRE_START_FAILED` 命令证据只更新 command，没有投影到 delivery session | 已明确证明门没有开始动作，session 和整机 `DELIVERY` 占用仍不释放，设备永久显示忙 | 没有；清运已有同类投影器，投递没有 |
| S-03 | P1 | 物理开始可靠任务的阻断、授权过期和人工恢复策略没有与业务状态机对齐 | 找不到设备或永久拒绝后，过期器不处理 `BLOCKED`；人工恢复又可能下发已过期命令或唤醒一个边缘不会重跑的重复命令 | 仅 `PENDING + DEVICE_OFFLINE/DEVICE_PRESENCE_UNKNOWN` 有安全自动出口 |
| S-04 | P2 | 投递没有把 `ACCEPTED/MCU_ACCEPTED` 投影为 session 进度 | `IN_PROGRESS` 实际不可达；小程序一直显示“下发中”后直接完成，两个开始时间被完成接收时间代填 | 最终完成能收口，但过程状态和时间不真实 |

#### S-01：首次皮重可靠任务与测量状态脱节

正常情况下，自动激活先插入 `rec_port_baseline_measurement.status=PENDING`，再创建
`MEASURE_EMPTY_BAG_BASELINE` 命令和可靠任务。后续扫描只要看到该投口存在任意
`PENDING` 测量，就直接跳过，不会创建第二次测量。

问题场景例如：

1. 设备机构分配和配置应用都已完成；
2. 自动激活创建首次皮重命令；
3. OneNet 找不到设备身份、永久拒绝，或者自动提交重试耗尽；
4. `ops_reliable_task` 进入 `BLOCKED`，但没有任何服务把对应测量从 `PENDING` 改为失败；
5. 一分钟扫描器以后每次都看到“已有活动测量”并跳过。

这不是普通离线等待。普通 `OFFLINE` 会让任务保持待下发，设备重新在线后还能继续；这里是
可靠任务已经进入终态，而业务测量仍是假活动状态。通用人工恢复策略也没有允许
`MEASURE_EMPTY_BAG_BASELINE`。

修复不能只写一条随意的 `FAILED`。当前数据库约束要求“没有物理结果的失败”只能使用
`EDGE_RESTARTED`，而目标找不到并不是边缘重启。实施前必须先冻结两类恢复语义：

- 能证明 OneNet 从未接受命令时，可以在原 10 年有效期内审计后唤醒同一任务；
- 无法证明是否到达设备时，需增加明确的技术终态/重测代际，并规定旧结果迟到后记为
  `STALE_IGNORED`，不能污染新基准，也不能被当成数据库异常。

#### S-02：投递物理开始前失败不会释放占用

香橙派会在写串口前检查配置、端口、唯一工作槽、传感器和烟雾安全状态。若不满足，它会
上报 `REJECTED`；能够证明串口一个有效物理命令字节都没有写出时，会上报
`PRE_START_FAILED`。这两类证据都明确表示“本次门控不可能已经开始”。

后端目前把命令改为 `PRE_START_FAILED`，也会完成可靠任务的下发证明，但只为清运调用了
业务投影器。投递 session 仍是 `AUTHORIZATION_QUEUED`，与它精确匹配的
`dev_device_occupancy` 也仍存在。用户不能形成订单，下一位用户和清运员又都会看到设备忙。

正确方向是增加与清运同构、但使用投递术语的可信命令观察投影：

- `ACCEPTED` 只记录边缘已保存；
- `MCU_ACCEPTED` 才进入 `IN_PROGRESS`；
- 只有稳定白名单证明“物理动作未开始”时，进入 `PRE_OPEN_ENDED` 并原子释放精确占用；
- `FAILED/PHYSICAL_FAILED` 不能直接释放，因为门可能已经动作，必须保留给结果恢复流程。

#### S-03：可靠任务终态、授权有效期和恢复动作不一致

当前两个安全出口只处理：task 仍为 `PENDING`、没有租约、等待原因为
`DEVICE_OFFLINE` 或 `DEVICE_PRESENCE_UNKNOWN`。授权超过 60 秒后，投递会话进入
`PRE_OPEN_ENDED`；清运操作进入 `PRE_UNLOCK_ENDED`，并分别释放设备占用及清运袋预留。
这一分支是正确的。

以下分支没有对齐：

- `DEVICE_IDENTITY_UNRESOLVED` 或 `PERMANENT_TECHNICAL_FAILURE` 会先把 task 改成
  `BLOCKED`，因此授权过期扫描器永远选不到它；虽然 OneNet 根本没有接受命令，业务占用
  仍会长期保留。
- OneNet 已接受但没有可信设备证据时，task 最终成为 `DEVICE_EVIDENCE_TIMEOUT`。这时物理
  动作是否发生未知，不能像“明确未下发”一样直接释放；但投递和清运都没有由该事实进入
  明确恢复态的投影。
- 平台通用恢复白名单允许 `START_DELIVERY_SESSION` 和 `START_CLEAN_OPERATION`，却不检查
  原冻结 `expiresAt`、阻断原因和业务目标状态。超过有效期后恢复只会发送旧命令。
- 香橙派会先把 OneNet 服务调用保存到 SQLite 并回复受理，再由后台消费者校验封套有效期。
  已过期命令在 `validated=true` 之前就失败为本地 `COMMAND_EXPIRED`，当前不会生成可信
  `DEVICE_COMMAND_OBSERVED`。后端因此只会再次等到证据超时，不能依靠边缘拒绝事实自动
  结束原业务。
- 如果旧命令此前已经到过香橙派，相同 `commandUid` 会被识别为 `DUPLICATE`；为防止重复
  开门，物理开始命令不会再次分发，因此“恢复成功”也不会产生新的物理执行或新证据。

因此不能把“人工点击恢复 task”当成统一解决方案。需要按可信程度分流：

1. 明确未到 OneNet 且授权仍有效：允许唤醒原任务；
2. 明确未到 OneNet但授权已过期：结束业务意图并释放精确占用，让用户重新发起；
3. OneNet 已接受但缺证据：进入保守恢复状态，保留占用，等待迟到事实或走专用现场恢复；
4. 命令已经到边缘：不允许以相同或新命令身份盲目重放物理开始。

#### S-04：投递过程状态和时间不可达

数据库、小程序和查询服务都认识 `IN_PROGRESS`，但当前生产代码没有任何 writer 把
delivery session 更新到该状态。投递完成时，后端用本次收件时间同时补
`first_edge_accepted_at` 和 `first_physical_progress_at`，所以两个字段不能反映真实阶段。

它不会重复建单，也不会阻止最后完成，但会造成：

- 用户在门已经执行时仍看到 `START_QUEUED`；
- 运维无法区分“后端排队”“香橙派已保存”“串口已经写出”；
- 超时和异常恢复没有可靠的物理边界时间可用。

该问题应与 S-02 使用同一个投递命令观察投影器修复，避免再建立第二套状态解释。

### 10.5 已知但本阶段明确暂缓的缺口

以下能力不能写成“系统已经自动完成”，但它们与正常主链缺陷分开排期：

| 编号 | 暂缓项 | 当前安全行为 | 业务限制 |
|---|---|---|---|
| D-01 | 投递物理动作可能已经开始，但最终结果永久缺失 | 进入 `RESULT_PENDING_RECOVERY`，保留 session 和整机占用，不猜测重量、不建虚假订单 | 已有保守状态投影，但尚无专用现场恢复/最终收口用例；设备仍可能长期不可用 |
| D-02 | 清运再次解锁、主动解锁前结束、`RECOVERY_REQUIRED` 恢复 | 已开始后不直接释放袋和设备占用；小程序提示联系支持 | 后端没有完整的 `END_CLEAN_BEFORE_UNLOCK/RESUME_CLEAN_OPERATION` 业务用例，协议和设备处理器存在不等于端到端完成 |
| D-03 | 清运最终称重失败后的独立皮重重测 | 新袋正常安装，但基准明确记为 `INVALID`；重量参与投递被阻止，清运仍可再次进行 | 没有正式人工/自动重测入口，只能通过另一次完整清运恢复 |
| D-04 | 真实 MCU 屏幕、按钮、门、锁、重量、红外和烟雾的固定帧真机闭环 | 模拟器和软件测试可验证消息及后端事务 | 不能替代当前固定帧协议的真实硬件在环测试；旧 `uart-v1` 审计不是当前生产路径的验收证据 |

固定帧阶段的既有决策是：香橙派执行期重启不自动重放未完成物理作业。投递进入
`DEVICE_ABORTED` 并释放投递占用；清运进入 `ABORTED`、释放新袋预留并建立重启联锁。
这是当前为了避免重复开门形成的保守取舍，不作为本轮新缺陷。

### 10.6 建议解决顺序

1. **先修 S-02 和 S-04**：新增投递命令观察投影器，一次补齐物理开始前安全结束、
   `IN_PROGRESS` 和真实阶段时间。现场安全拒绝是正常会发生的分支，不能让它锁死整机。
2. **再修 S-03**：把可靠任务阻断原因、60 秒授权和业务状态一起判断；先关闭“明确未送达
   且已经过期”的投递/清运，再限制通用恢复按钮的适用条件。证据不确定的情况仍保守保留。
3. **再修 S-01**：为首次皮重冻结专用的可靠恢复语义和迟到结果规则，保证设备身份修复后
   能继续无人值守自动接入，又不伪造 `EDGE_RESTARTED`。
4. D-01～D-04 需要产品负责人再次明确恢复边界或安排真实硬件后再实施，不混入以上主链
   修复，避免为“自动恢复”引入重复开门或错误换袋。

### 10.7 后续每项必须通过的回归场景

- 首次皮重 task 因“设备身份找不到”阻断后，修复身份可以安全继续；不会永久留下
  `PENDING` 测量，也不会同时存在两个活动测量。
- 首次皮重 task 证据超时后旧结果迟到，不覆盖新袋或新代际基准，并能明确归类为迟到/过期
  事实，而不是返回数据库 500。
- 投递在现场烟雾报警、传感器不健康、配置过期、MCU 不支持或本地忙时，于串口写出前拒绝：
  session 进入 `PRE_OPEN_ENDED`，精确整机占用释放，不创建订单。
- 投递 `ACCEPTED → MCU_ACCEPTED → DELIVERY_COMPLETE` 时，session 依次显示排队、执行中、
  已完成；两个阶段时间来自可信设备发生时间，异常设备时间使用明确的后端兜底而不倒序。
- 投递或清运 task 明确未送达且授权过期时自动结束并释放对应资源；证据不确定时不得误释放。
- 平台不能恢复已过期的物理开始 task，也不能把 `DUPLICATE` 误解释为设备再次执行成功。
- 两个真实 MySQL 并发事务扫描同一个已登记空闲袋：恰好一个清运操作和一个袋预留提交，
  另一个稳定返回 `409 CLEAN.BAG_UNAVAILABLE`，没有孤立操作、照片槽或设备占用。
- 设备禁用、机构禁用或新配置发布与已开始投递/清运并发时，先提交的新业务继续按冻结事实
  收敛；先提交的禁用阻止后来的新业务；两种顺序都不丢订单、不回滚真实换袋。
- 清运后当前袋不再是厂家袋时，配置滚动、服务重启和自动激活扫描都接受当前新袋及其有效
  基准，不能再次报告“厂家预装袋不完整”。

### 11.2 首次皮重现在如何自动收敛

自动激活只对“当前仍安装厂家空袋、容量代际仍属于该袋、最新配置已精确
`APPLIED`、尚无有效基准、尚无活动测量”的投口创建新测量。每个“投口 + 当前袋 +
配置版本”最多创建 4 个系统测量代际，上一代技术终止后依次等待 30、60、120 秒
再创建下一代，不会同时存在两个 `PENDING` 测量。

`DEVICE_IDENTITY_UNRESOLVED`（OneNet 找不到设备身份）和
`PERMANENT_TECHNICAL_FAILURE`（传输层明确永久拒绝）不会被系统盲目自动重试。
平台设备详情现在直接展示配置、可靠任务、投递、清运和皮重的技术问题。维修人员
排除原因后，只有同时确认“故障已排除”和“厂家袋仍为空袋”，且平台复核最新测量
身份未变、设备无作业占用、没有清运或待处理投递结果时，才能创建一个独立的平台人工
测量代际。该人工代际不消耗 4 次系统额度，但仍使用全新的测量、命令和可靠任务身份，
不重放旧命令。

### 11.3 可靠任务与业务终态的事务边界

可靠任务现在先投影业务结果，再把任务写为 `BLOCKED`；两步在同一事务中，任何一步
失败都整体回滚，不会再出现“技术任务已结束，业务还在执行”。证据等待到期器同样先投影
不确定结果，再写入 `DEVICE_EVIDENCE_TIMEOUT`。当前补偿扫描只能找出已经 `BLOCKED`、但业务
仍停在活动状态的物理命令；升级前已经因命令证据被写成 `DONE` 的任务不在扫描范围内，
不能据此宣称旧版数据已经全部收口，详见 R-02。

通用“恢复可靠任务”接口已移除投递开门、清运解锁、应用配置和空袋皮重命令。
这些命令会触发物理动作或具有专用代际，必须由对应业务用例创建新身份，不再用旧
`commandUid` 盲目唤醒。

### 11.4 数据库与接口变更

- V47 为 `rec_port_baseline_measurement` 增加 `TECHNICAL_ABORTED` 终态约束和按
  投口、袋、配置、发起方、状态查找测量代际的索引。数据库纪元门禁、H-02 供应脚本和
  部署手册已统一推进到 V47；表数仍为 99，有效权限定义仍为 76。
- 平台新增设备技术问题查询和投口皮重测量发起接口。发起成功返回 HTTP 202，但当前
  `Location` 和响应中的 `statusUrl` 实际指向设备技术问题列表，而不是新可靠任务的查询
  地址；OpenAPI、Web 生成类型已经同步，地址语义仍需按 R-06 修复。
- 技术问题查询的“系统仍会重试”只根据同一投口、同一袋、同一配置的

#### 阶段一：先用失败测试锁定真实组合

1. 为 R-01 增加“2026 年创建、OneNet 已接受、设备无证据”的测试，断言截止时间不能落到

2. 为 R-02 建立升级前数据：command event 已存在、task=`DONE`、delivery 仍为

3. 为 R-03 建立未来 `occurredAt` 后再接收 `DELIVERY_COMPLETE` 的事务测试，先稳定复现

4. 为 R-04/R-05 建立完整序列测试，而不是分别测试纯方法：

5. 为 R-06/R-07 增加控制器响应和 Web 失败展示测试。

#### 阶段二：修复皮重证据期限 R-01

1. 在可靠任务完成服务中增加按命令类型计算证据期限的策略。
2. `MEASURE_EMPTY_BAG_BASELINE` 使用冻结载荷中的 `measurementTimeoutMs`，再加有限的边缘
   处理和北向消息宽限；设置明确最小值和最大值，防止异常载荷形成零等待或多年等待。
3. 不直接把 10 年语义有效期当成结果等待时间：语义有效期回答“命令还能否被设备接受”，

4. 到期后在同一事务中先把测量置为 `TECHNICAL_ABORTED`，再把 task 置为 `BLOCKED`；后续

5. 保持 `TARGET_OFFLINE` 分支不变：OneNet 明确说设备离线时仍是等待上线，不冒充“平台已
   接受但证据丢失”。

#### 阶段三：补齐历史命令证据投影 R-02

1. 新增只读候选查询，按 `dev_device_command_event` 中已经存在的权威阶段，查找仍处于活动
   状态的投递 session；候选不能要求 task 必须为 `BLOCKED`，需要包含旧版 `DONE`。清运原本
   已有实时投影器和 `BLOCKED` 补偿，本轮先只做只读审计；只有审计证明存在同类错位时，才把
   清运纳入同一套历史补偿，避免无证据扩大修复范围。
2. 使用现有投影器幂等推进业务状态，不重新发送 OneNet 命令，也不改变原 task 的历史终态：
   - `ACCEPTED` 只补边缘保存时间；
   - `MCU_ACCEPTED` 补 `IN_PROGRESS` 和首次物理进度；
   - `REJECTED/PRE_START_FAILED` 只在物理未开始时结束业务并释放精确占用；
   - `FAILED` 按结果是否未知进入恢复态，不能直接释放。
3. 每个候选使用独立事务或可靠的逐项隔离，避免一条异常旧数据使整个批次回滚并长期挡住
   其他设备。
4. 部署前在目标库执行只读审计，统计会被补偿的 task、投递 session 和占用，并单独统计清运

#### 阶段四：统一时间和皮重单调语义 R-03～R-05

1. 对命令阶段时间采用统一规则：只有
   `businessCreatedAt <= deviceOccurredAt <= backendReceivedAt` 才使用设备时间，否则回退到
   `backendReceivedAt`。不能接受任何晚于服务器收件时间的“未来开始时间”。
2. 投递 `ACCEPTED/MCU_ACCEPTED/DELIVERY_COMPLETE` 集成测试必须证明时间单调且能完成建单、

3. 皮重技术终止判断接收当前 command 物理状态：
   - `REJECTED/PRE_START_FAILED` 只有在尚未 `PHYSICAL_STARTED` 时才能技术终止；
   - `FAILED` 可以结束已开始但明确失败的测量；
