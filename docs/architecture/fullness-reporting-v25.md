# V25｜设备上报当前袋满溢状态

> 生效日期：2026-08-02
>
> 状态：已实施；覆盖此前“后端建立满溢检测并主动下发 `SAMPLE_FULLNESS`”的设计
>
> 数据库版本：V25

## 1. 业务裁决

投递准入采用“优先允许、明确满溢才阻止”的规则：

- 后端不主动查询、轮询或定时采样设备满溢状态；
- 香橙派在整场投递结束或清运完成后，根据本次真实设备观察在本地计算当前袋状态；
- 只有设备可靠上报当前袋为 `FULL`（已满），后端才阻止该投口开始下一场投递；
- `NOT_FULL`（未满）解除同一当前袋的满溢阻断；
- 没有上报、测量失败、证据不完整、旧袋事件或乱序事件都不新增满溢阻断；
- 已经开始的投递会话不因结束后得到 `FULL` 而被拒绝建单或返现；该结果只影响下一场投递；
- 换入新袋时，后端把新袋初始化为 `NOT_FULL`，但不伪造一条设备测量事件。

这里的“默认 `NOT_FULL`”是投递准入策略，不表示后端凭空证明传感器测得未满。设备故障、门安全锁、清运占用等其他独立安全事实仍按各自规则阻止业务。

## 2. 端到端流程

```text
投递结束或清运完成
  → 后端先提交订单或清运记录，并确认给设备
  → 香橙派使用该作业的最终设备观察计算 FULL / NOT_FULL
  → 仅在本地状态发生 FULL ↔ NOT_FULL 变化时可靠保存并上报 FULLNESS_STATE_CHANGED
  → 后端验证部署、投口、当前袋、来源作业、证据摘要和单调事件序号
  → 当前袋且顺序较新的事件更新容量投影
  → FULL 阻止下一次投递；NOT_FULL 允许下一次投递
```

香橙派离线时事件保存在 SQLite outbox（可靠待发队列）中，恢复网络后重试。重复事件依靠稳定 `eventUid` 幂等；同一事件标识但内容不同会进入冲突处理，而不是覆盖原事实。

## 3. 事件事实

`FULLNESS_STATE_CHANGED` 至少绑定：

- 部署和投口；
- 当前 `bagUid`；
- 来源类型及来源标识：投递订单或清运记录；
- `FULL/NOT_FULL` 新状态；
- 本地单调事件序号和观测时间；
- 判断模式、冻结配置摘要和实际使用的传感器证据；
- 测量是否成功，以及 fixed-frame（固定帧 MCU 协议）兼容时使用的最终缓存观察标签。

只有成功、证据自洽的状态变化才能改变后端投影。`FAILED`、缺字段或摘要不一致只保留技术失败信息，不把未知解释为 `FULL`，也不覆盖已有状态。

## 4. 当前袋与乱序保护

后端只让事件作用于事件所声明的袋，并同时核对投口当前实际绑定袋：

- 事件袋等于当前袋且事件序号更新：应用；
- 同袋重复状态：记录为 `NO_STATE_CHANGE`，不重复产生状态变化；
- 事件属于已取走的旧袋：记录为 `STALE_BAG`，不影响新袋；
- 事件序号不大于当前已应用序号：记录为 `STALE_SEQUENCE`，不回退状态。

投递选项查询和开始投递事务使用同一条事实：只有容量记录中的 `FULL` 与投口当前绑定袋一致时返回 `PORT_FULL`。因此不会再出现“选项显示可投递，开始接口却因过期检测拒绝”的口径分裂。

## 5. 旧主动检测链路的处置

V25 不删除旧检测和样本历史，以保留审计能力；但正常投递、清运完成不再创建新检测或 `SAMPLE_FULLNESS` 任务。迁移会：

- 取消仍处于 `PENDING/BLOCKED` 的旧 `SAMPLE_FULLNESS` 可靠任务；
- 把仍活动的旧检测收敛为 `RETIRED`；
- 将旧的未知、待检测或失败容量 gate 归一为可投递状态；
- 仅保留能与当前袋对应的既有 `FULL` 作为阻断事实。

因此，旧方案中的“过期命令重新签发”和“人工重检后才恢复投递”不再是正常投递链路的前置能力。以后如果需要人工触发设备立即刷新，只能作为独立运维能力设计，不能恢复后端对全量设备主动轮询，也不能让失败或无响应阻止投递。
