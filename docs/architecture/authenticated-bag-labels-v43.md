# V43 平台防伪袋码与标签打印冻结决策

> 状态：**已确认并实施**
>
> 冻结日期：2026-08-09
>
> 影响范围：平台 Web、HTTP/OpenAPI、recycling、device、清运小程序、目标数据库与生产密钥部署
>
> 不影响：香橙派、MCU、OneNet 物模型、设备屏幕协议和机器验收条件

## 1. 为什么需要这次变更

清运员需要拿到可以贴在实体袋上的二维码。只生成普通随机文本虽然简单，但任何人都能
照着格式伪造一个“新袋码”。如果平台先为每张标签创建库存、分配租户和机构，又会把
一个打印需求变成库存生命周期、调拨和回收流程，重新增加已经废弃的部署式复杂度。

本次裁决采用最小模型：**平台只签发可验真的实体标签，不预先创建袋资产。**

## 2. 用户能看到的流程

1. 平台管理员进入独立的“袋码管理”页面，输入 1～100 的数量并生成一批标签。
2. 页面展示本批袋码，可以复制，也可以按 A4 每页 24 张（3 列 × 8 行）打印；浏览器
   打印窗口同时提供“另存为 PDF”。二维码内容就是完整袋码，不是 URL、JSON 或数据库 ID。
3. 厂家登记真实设备时，每个投口必须使用一张平台签发的 EB1 标签作为初始袋码。
4. 机构清运换袋时，小程序扫描新袋标签。后端先验证防伪签名，再检查该袋是否可用。
5. 一个从未使用过但签名有效的袋码，在当前机构第一次发起清运时才创建 `rec_bag`；
   不需要平台先分配租户，也不需要机构先入库或确认。

## 3. 袋码格式和验真

规范格式为：

```text
EB1_<keyId>_<serial>_<tag>
```

- `EB1`：EcoBin 袋码第 1 版。
- `keyId`：签发密钥版本，当前为 `K1`；它不是密钥本身。
- `serial`：16 个安全随机字节编码成 26 位 Crockford Base32，提供不可猜测身份。
- `tag`：HMAC-SHA256 防伪结果的前 12 字节，编码成 20 位 Crockford Base32。
- HMAC 输入域固定为 ASCII `ecobin:bag:EB1:<keyId>:<serial>`。

后端使用常量时间比较校验 `tag`。小程序和 Web 只做严格格式过滤，绝不持有 HMAC 密钥；
因此客户端通过格式检查不等于标签已经验真，业务准入仍以后端结果为准。

跨实现黄金样本：密钥字节依次为 `0x00`～`0x1f`、序列字节依次为 `0x00`～`0x0f` 时，
结果必须为：

```text
EB1_K1_000G40R40M30E209185GR38E1W_GRQ320Z8YDWC8V49M7W0
```

## 4. 数据模型为什么只有两张打印表

- `rec_bag_label_batch`：谁在什么时候生成了多少张、使用哪个密钥版本以及幂等请求摘要。
- `rec_bag_label_item`：本批每一张的序号和完整 EB1 袋码。

这两张表只是**打印和补打历史**，没有 `tenant_id`、`organization_id`、库存状态或分配状态。
真正的袋身份仍只有 `rec_bag`，并在厂家初始袋激活或机构首次换入时按实际业务事实建立。

平台可以物理删除一个打印批次。外键级联删除明细后，页面不能再查看或补打该批次；
已经印出的标签仍能通过 HMAC 验真。删除打印记录不是撤销标签，也不是删除 `rec_bag`。

## 5. 新旧袋码的准入边界

- 新登记设备的厂家初始袋必须通过 EB1 验真。
- 每次清运换入袋必须通过 EB1 验真；签名无效、密钥版本未知、已被占用，或已经固化到
  其他机构的袋都拒绝本次清运，不会开门、不预留袋，也不会创建清运操作。
- 同一机构的 EB1 袋在解除占用后仍可再次使用，每次形成新的绑定历史。
- 升级前已经安装或已由厂家登记的旧格式袋继续随当前设备和历史事实收敛，不批量改码。
  旧袋一旦被取下，不能作为新的换入袋重新安装，因为它无法通过 EB1 验真。

这条兼容边界不恢复旧模型：没有双写、旧签发接口、旧库存表或客户端降级开关。

## 6. 密钥部署和轮换

生产密钥 `K1` 必须以至少 32 个安全随机字节生成，再进行 Base64 编码，持久文件为：

```text
/etc/ecobin/secrets/bag-code-key-k1
```

部署时只读暂存为 `/run/secrets/bagCodeKeyK1`。它不得进入 Git、`runtime.env`、容器环境变量、
日志、审计摘要或 API 响应。缺少密钥、Base64 无效或解码不足 32 字节时后端拒绝启动。

以后轮换到 `K2` 时，配置把 `K2` 设为活动签发密钥，同时保留 `K1` 只用于验证历史标签。
删除旧验证密钥会使仍在流通的对应标签失效，必须作为独立业务决策处理，不能顺手清理。

## 7. HTTP 与权限

平台管理员通过以下同源 Cookie + CSRF 接口工作：

- `GET /api/v1/web/platform/bag-label-batches`：分页查看批次；
- `POST /api/v1/web/platform/bag-label-batches`：使用 UUIDv4 `Idempotency-Key` 生成；
- `GET /api/v1/web/platform/bag-label-batches/{batchUid}`：读取标签明细；
- `DELETE /api/v1/web/platform/bag-label-batches/{batchUid}`：删除打印历史。

页面只对平台管理员展示，租户和机构界面没有袋码生成、分配或部署进度。

## 8. 明确不增加的内容

- 不增加袋码预注册、领用、库存、批次分配、回收或撤销状态机；
- 不把二维码改成网页入口，也不让设备公开码承担袋码身份；
- 不给香橙派、MCU 或 OneNet 增加袋码签发/验真字段；
- 不把标签打印或屏幕显示加入机器验收；
- 不增加 PDF 服务端生成库，A4/PDF 由浏览器标准打印能力完成。
