## 1. 结论与分工

建议升级为 MCU 原生提供真实事实的新版本串口协议；复用已有的帧解析和契约生成基础，
不继续给旧 AA/DD/EE/EF 固定帧补造启动编号、受理回执、稳定性或作业状态。
MCU 的重构是分离职责并逐段验证，不是一次性换掉全部底层驱动或引入操作系统。

| 执行主体 | 负责什么 | 不负责什么 |
|---|---|---|
| MCU（单片机） | 读引脚和称重模块、控制推杆/电磁锁、屏幕交互状态机、测量取值、保留原作业和结果 | 判断秤准确度、云端身份授权、钱包/订单、伪造物理门位 |
| 香橙派业务进程 | 独占正常串口，保存业务及证据、分配 MCU 启动编号、查询与恢复、照片、重量计算、可靠上报 | 根据串口写成功推定 MCU 已接受、根据零值填补缺失重量 |
| 永久管理层 | 动作许可及永久账本、云端通信、更新与业务互斥及串口维护交接 | 用解除账本限制代替查清原业务或机械状态；不代发正常串口命令 |
| 服务器后端 | 发起时登记业务与占用、接收事实、去重、应用订单/袋/基准、按既有规则审核结算 | 指挥每次 MCU 查询重试、根据未上报事实推断现场发生了什么 |
| HMI（串口屏） | 展示状态、发送明确的按钮意图 | 自行认定业务成功、凭跳回首页释放业务、把返回按钮伪装成完成 |

设备的现场动作恢复仍由香橙派本机协调。服务器开始时已知道有清运任务，实际经过只以
收到的报告为准。MCU 清理已交接结果，不等于服务器已完成换袋或设备已可接新单。

## 2. 已确认且不得改回的规则

1. MCU 启动回复分为接受、拒绝；无回复是是否执行未知。接受不是动作完成。
2. 香橙派发出的命令有唯一身份，重复命令不重复动作；失去回复先查原业务，不盲目重发。
3. MCU 重启先停输出，不续跑旧动作。启动编号归零，由香橙派保存并分配新非零编号；
   仅香橙派重启时不更换仍在运行的 MCU 编号，MCU 不为此写 Flash。
4. MCU 保留冻结结果，直到香橙派本地数据库提交成功后的保存确认；查询和补传不重新称重。
5. 业务门状态采用最近有效方向：按 PB6/PB7 顺序，01=关，10=开；实际输出另行记录。
   PB4 未接；PB5 只暂停关门输出，解除后继续仍有效的关门目标，开门忽略 PB5。
   PB5 不证明门位或故障，不单独阻止其他条件满足后的下一次投递开门。
6. MCU 重启且投递必要数据确实丢失：只留问题证据、不建可结算订单，香橙派随后发新的
   关门命令并检查。完整原结果已保存时仍处理原结果，不能因重启将其作废。
7. 清运必要数据丢失：保留原操作，由原清运员完成换袋和人工关门确认，重新核对袋子、
   建立真实新袋基准；旧重量缺失留异常，不因此要求另外的维修人员解锁。
8. 称重目标每 250 ms 读取；最近 5 次新读数最大值减最小值 ≤100 g 时取均值；最多等
   5 s，仍只是波动时取本次合法样本中位数继续业务，不仅因此转异常或禁止接单。
   无响应、损坏报文等真正无可用重量情况不取零或旧值冒充。准确度交人工。
9. 非重启的真正最终称重失败仍可形成系统异常订单、等待人工审核；与重启丢数据的
   问题记录分开。中位数是可用估算值，不冒充已稳定，不仅因使用中位数强制人工审核。

## 4. 协议方案：保留传输基础，替换虚构语义

### 4.1 版本与解析边界

继续使用 `contracts/uart/uart-registry.yaml` 作为唯一机器来源。先逐项判定兼容性，
再按契约版本规则选择版本，不预先命名为“最小事实协议 v2”。不兼容变化不得冒充旧协议，
也不能把规范 UART 版本与当前固定帧自身的 v2 名称混为一谈。

- 复用 `EC42 + 版本 + 类型 + 长度 + 序号 + 数据 + CRC` 的已有帧基础、生成工具和
  C/Python 编解码测试。具体字段布局及最大帧预算在协议细化时重新计算。
- 优先保持当前 256 字节帧上限；不能通过截断结果满足长度。若结果超长，按不可变结果
  身份分段，全部组装验证并落盘后才确认交接；不得按一片的接收确认清理整个结果。
- 一条串口只启用一种解析器。版本或必需能力不匹配时明确拒绝新作业，不自动降级到固定帧。
- 同时处理半帧、粘帧、错误长度、CRC 错误、超时和噪声；缓冲区有界，坏帧可重新找帧头。
- 不直接套用旧 UART 的“最多发送 3 次”：只读查询可重试，机械启动先查原业务；
  完成结果可补传同一份，保存确认可在核对本地原结果后重复发送，启动编号分配不可盲重发。
- 保留配置版本/摘要与固件能力查询。采样参数由明确配置表达，不能只在界面上改值而 MCU
  仍执行旧值；旧设备能力不支持时明确报告，不编造已应用。

### 4.2 必要身份与回复

| 身份/字段 | 用途 |
|---|---|
| MCU 启动编号 | 区分 MCU 的运行轮次；0 仅为未分配 |
| 业务编号及类型 | 对应原投递会话或清运操作，不能因 Pi 重启重新创建 |
| 命令编号及内容摘要 | 命令去重；同编号不同内容明确拒绝，不动作 |
| 查询编号 | 将回复与本次查询关联，拒绝旧查询回复冒充最新事实 |
| MCU 事件/本地动作序号 | 对同业务中的测量、按钮、动作和结果去重；数值相同不是同一事件 |
| 测量身份及阶段 | 区分首次开门前、轮次结束、最终重量、清运换袋后等 |
| 不可变结果身份/摘要 | 对应结果保存确认，防止确认错对象 |

位宽、序号溢出处理、命令去重记录容量和拒旧规则统一在机器契约中落实。特别是结果正文
删除后，也不能因旧命令从缓存淘汰就重新执行它：要保留交接标记或采用经过验证的序号
拒旧规则。查询不到与“从未执行”仍不等价。

### 4.3 最小消息能力

以下是消息职责，不是已冻结的 opcode 或已生成 API：

| 能力 | 发起方与回应 | 是否允许动作 |
|---|---|---|
| 查询当前启动/状态 | Pi 发带查询编号的请求；MCU 返回当前编号及一致状态 | 否 |
| 分配启动编号 | Pi 先保存候选编号，再按本次握手绑定并核实 | 否 |
| 启动投递/清运 | Pi 带原业务和新命令身份；MCU 明确接受或拒绝 | 接受且前置条件满足后 |
| 查询原业务 | Pi 指定原启动/命令/业务；MCU 返回进行中、完成待取、查不到 | 否 |
| 新的投递关门动作 | Pi 因明确业务需要发新命令，MCU 报告目标与输出事实 | 是，不重放旧开门 |
| 恢复清运上下文 | Pi 核对本地原操作后恢复清运交互，明确哪些旧测量缺失 | 本身不自动开锁 |
| 测量/本地阶段事实 | MCU 返回阶段、读数、取值方式、样本和状态 | 不追加动作 |
| 完成结果及保存确认 | MCU 保留原结果；Pi 提交数据库后确认 | 否 |
| 停止/更新控制及结果 | 沿用独立、受权限约束的控制能力 | 按其授权，不冒充正常完成 |

“收到有效帧”“接受命令”“输出已设定”“业务完成”“Pi 已保存”是不同事实。
协议必须能区分，不能用一个 ACK 同时表达全部含义。

### 4.4 启动握手是协议细化的重点验证项

已经接受的 Pi 分配、MCU 归零方向不变。必须补齐以下验证后，才能宣称能可靠识别重启：

1. Pi 使用新查询身份获取 MCU 当前状态；非零且匹配旧运行时继续原业务，不换号。
2. 读到 0 后先核对本地未完业务和已存结果，再持久保存新候选编号并执行当前握手绑定。
3. 绑定回复丢失只查询，不直接重发旧绑定报文；再次确认重启时废弃旧候选，不复用它。
4. 必须验证“MCU 在查询与绑定之间复位”“旧绑定报文延迟到复位后”“Pi 在保存/发送
   之间退出”等组合。单有查询编号不能证明迟到绑定报文不会在新启动中被接受。

具体的会话建立、启动接收状态和旧帧隔离机制尚需设计证明；不能在这里假称已完成。
这属于工程协议问题，不要求用户决定随机种子或报文字节，也不擅自增加 MCU Flash
启动计数、偷偷改成 MCU 自生成正式启动编号，或假设未接的 NRST/BOOT0 已可用。

## 5. MCU 重构方案

### 5.1 模块边界（名称为拟定）

| 模块 | 职责及约束 |
|---|---|
| `runtime_clock` | 连续时间基准；称重、锁通电、界面等待等独立定时 |
| `scale_reader` | USART2/RS485 单请求读取、校验、样本编号、读取故障 |
| `weight_measurement` | 按阶段积累新样本，5 点/100 g 均值，5 s 中位数，冻结测量 |
| `door_control` | 最近有效目标、实际 PB6/PB7、PB5 关门暂停/解除继续，其他停止优先 |
| `clean_lock` | PB8 真实输出和按时间自动断电；不报告物理门扇已关闭 |
| `work_runtime` | 单一业务槽、命令去重、投递/清运阶段、原始结果暂存与交接 |
| `hmi_controller` | 按钮解释、合法阶段检查、显示；界面跳转不是业务事实 |
| `edge_protocol` | 唯一 UART 解析器、真实状态/事件及结果回复，不直接夹带业务推断 |

先提取可纯 C 测试的逻辑，再替换调用点。保留可复用的 GPIO、USART、ADC、更新执行
驱动；核对 Keil 工程实际包含新源文件及生成编解码文件，不能以目录里已有 C 文件视为
固件已经编译它们。测量缓存、结果缓存和收发队列均设容量上限，检查链接后的 Flash/RAM。

### 5.2 投递控制与保护

- 建议启动时用 `targetValid=false` 表示尚无本次运行有效门目标，实际输出 00；不是
  增加运动中间态。新的有效命令建立 OPEN/CLOSE 目标，之后停止不篡改历史目标。
- 另有“该动作仍有效”标记；主动停止、取消、更新停机后 PB5 释放不能复活已取消动作。
- CLOSE 且 PB5 触发：输出 00、保留 CLOSE；PB5 解除且动作仍有效：恢复 01。
- OPEN：不因 PB5 触发阻断 10；由关改开后不得在 PB5 释放时恢复旧关门。
- 保留原业务上下文内的正常继续投递，不每轮重新要求扫码或服务器授权。
  空闲、恢复未核对或更新中，旧屏幕的裸开门字节不能绕过业务状态直接驱动推杆。
- MCU 本地按钮引起的动作有自己的本地动作序号和来源，不伪装为 Pi 下发的新启动命令；
  其去重与阶段约束需验证。永久账本仍按经许可登记、由业务进程下发的指令记账，
  不虚称覆盖所有 MCU 本地动作。

### 5.3 测量与结束

首重、轮次重量、末重和新袋基准使用同一取值算法，分别建立新测量阶段；不能将前一
阶段的缓存当成后一阶段样本。按已确认的 250 ms / 5 点 / 100 g / 5 s 执行。

- 可用状态分为“满足窗口条件的均值”和“纯波动超时的中位数”；取值来源如实保存。
- 无合法读数、持续通信或解析故障另列为无可用值；最少样本数、末次响应时效及断续
  通信判据需在实现细化中给出，不用一个很早的孤立值掩盖后来断线。
- 无效测量保留已有诊断，不把数值改为 0。整数克、负值和取整规则跨 C/Python/Java 一致。
- MCU 形成完成结果后进入待交接状态，禁止新业务覆盖结果；重复查询/完成按钮不重称。
- 仅称重无可用数据时也要能形成明确失败结果，不能像当前 DD/EF 条件不满足时不报告、
  一直占用。真正未执行开门的前置读取失败与用户已经投物后的最终读取失败分开。
- 显示可平滑，不能用平滑后的数据伪造稳定性；不因允许中位数自动修正秤的准确度。

## 6. 香橙派：清理适配层，但保留通信和持久化边界

### 6.1 适配层哪些保留，哪些退出

保留串口单一所有权、有界收发、编解码、队列、日志、超时管理、永久动作许可与账本、
业务状态机之间的清晰边界。它们是正常分层，不应为了“消除适配层”全部塞入 `main.py`。

新版本退出这些固定帧兼容行为：

- 用 Pi 启动身份冒充 MCU 启动身份；
- 在本地合成握手、接受回执、稳定性和采样数量；
- 把 `query_state=[]` 当作 MCU 的空闲或查不到；
- 把只有结果字节的 DD/EF 重新包装成未经 MCU 证实的完整事实。

复用 `uart_link.py` 的可用部分前必须改掉机械命令自动重发和旧握手假设。
切换期间保留旧生产制品用于成对回退；不是在同一个进程内并行识别新旧协议。

### 6.2 本地事务及恢复

以当前 SQLite 为基础，增量保存以下事实，不另造第二套业务数据库：

- MCU 已确认启动身份、尚未确认的分配意图；
- 原业务/命令关系、真实受理和阶段事实、恢复进度；
- 分别有身份的测量、原完成结果及摘要、保存确认发送记录；
- 只供问题记录的失败结果，以及与永久动作账本的明确关联。

关键顺序：先保存命令意图再下发；先提交完成结果再确认 MCU；先核对本地完整结果再
决定数据丢失；业务结束与结果接收使用同一串行化/事务边界，防止同时归档和正常建单。
照片与原会话保持关联，继续直传 COS，不能因恢复把旧照片附到下一用户。

恢复分支：

| 观察到的事实 | Pi 行为 | 新业务 |
|---|---|---|
| 同 MCU 启动、原业务进行中 | 继续跟踪，不重启机械动作 | 暂不开始 |
| 原结果仍在 MCU | 取回、落盘、确认，可靠上报同一份 | 再按业务接单条件检查 |
| 本地已保存完整结果 | 重发必要的保存确认/上报，不作废结果 | 不因一次 Pi 重启额外人工解锁 |
| 无回复 | 保留上下文与占用，继续本机查询，节制报告通信故障 | 不开始 |
| 查不到且证据矛盾 | 核对本地结果/当前启动，不能推定从未执行 | 不因查不到直接放行 |
| 确认 MCU 重启、投递必要数据真丢失 | 形成问题型失败，随后新关门命令与检查 | 条件满足后恢复 |
| 确认 MCU 重启、清运必要数据真丢失 | 恢复原清运交互，原清运员换袋/关门确认并重建基准 | 袋/基准/占用一致后恢复 |

“MCU 已确认 Pi 保存”只解决本地结果所有权，不删除后端袋关系/基准应用确认要求。
清运结果要可靠上报并确认服务器已应用相应袋与基准代次；不在旧袋投影下接受新投递。
网络等待由 Pi 可靠上报机制处理，不转成后端主动指挥串口恢复。

### 6.3 永久动作账本不得绕过

- 新协议仍由业务进程独占正常串口，发动作前通过永久更新器取得许可并登记账本；
  不额外迁移串口所有权，不另开串口路径绕过许可。维护烧录按既有流程交接串口。
- 新命令编码、动作摘要、实际下发和真实结果的关联同步适配 `job_safety` 及更新器本地接口。
- 自动数据丢失处理需要新的明确账本处理路径：记录原动作效果可能未知、数据已丢失及
  问题归档，不伪装原动作成功或机械已安全；恢复关门是另一个受控新动作。
- 不复用要求完整断电、人工检查和 F3 标志的已部署手动隔离操作来假扮自动恢复，也不
  直接把未核对账本条目设为成功。业务取消、物理结果未知、后续恢复完成应分别表达。
- 原手动远程隔离入口及“由操作者确认哪些现场条件”的调整另行评审；本方案不擅自
  放宽已部署检查、打开远程更新或删掉永久管理层。

## 7. 服务器与机器契约修改

后端不参与逐步恢复，但必须能正确接收这三种不同结果：

| 结果 | 保存与业务效果 |
|---|---|
| 正常投递，采用均值或认可的中位数 | 建同一笔订单，保留取值方式；不因中位数额外强制人工。其他审核/金额阈值仍生效 |
| 非重启、真正最终称重失败 | 保存原始证据并建系统异常订单；人工审核前不增加余额或自动提现 |
| MCU 重启丢失投递必要数据 | 问题型记录，不进入正常订单/钱包/自动提现链路，不改写已存在完整结果 |

清运另分为完整结果和“缺失旧重量、换袋事实及新基准已经确认”的恢复结果。后者不能
假填开门前重量，但需要允许真实新袋关系和基准生效；清运从来不产生用户奖励。

修改面包括：

1. UART registry 与生成物：新版本身份、结果保存确认、取值方式、状态快照和查询。
2. OneNet 事件 Schema、wire 映射及生成物模型：表达新结果和测量事实；是否复用事件加
   版本字段或新增事件，在契约细化时统一决定，不能直接改线上旧字段含义。
3. device 可信入站：`TrustedDeliveryCompletionService` 接收均值/中位数与真实失败；
   保持身份、配置、事件唯一性和照片槽校验；不能简单删除全部正常结果校验。
4. recycling：订单计算/异常/自动审核资格、`ApplyCleanCompleteService`、袋和基准
   原子应用；中位数不能被后续旧投影再次认作无效或强制审核。
5. `AbortEdgeRestartedWorkService` 与命令观察：按实际重启主体和新协议能力解释，不
   因 Pi 进程重启中止仍在 MCU 的原任务；新旧设备并存时按可信能力版本分流。
6. operations/integration：可信 inbox、去重、上报结果应用确认、问题展示。自动失败
   记录必须可关联原用户/会话和证据，但不能伪称有已确认物理投物事实。
7. 数据库字段/约束、JSON Schema、Java 类型、Python 校验及生成样例一并检查。需要
   新迁移时另分配版本，部署前核对真实 epoch；不在此草案中假定下一版本一定是 V70。
8. Web/小程序仅做必要显示：数据丢失原因、已有证据、无金额结果、中位数取值方式及
   设备处理中/恢复提示。不新建后端串口恢复控制台或重做整套页面。
9. 厂家热点页面接收真实测量状态，显示每一步取值和方法；不把业务采用中位数的规则
   自动等同于修改厂家参考重量验收标准，不删除现有人工参考测试。

## 9. 分段实施与成对切换

以下是建议顺序，不是本轮授权任务；每段提交和验证后再进入下一段，不要求一次写完上线。

| 阶段 | 交付物 | 验证与进入下一段的条件 |
|---|---|---|
| A. 协议和状态模型 | 最新共识映射、版本/字段/长度预算、启动绑定、防重放、取值判据、结果分类 | 先解决下节关键缺口；跨 C/Python 样例与状态序列可验证 |
| B. MCU 核心逻辑 | 独立时间、方向/保护、称重取值、作业和结果保留的纯 C 模块 | 主机测试、Keil 构建、资源预算；尚不驱动现场设备 |
| C. MCU—Pi 纵向闭环 | 原生新协议、SQLite 恢复、永久账本、同业务查询/结果交接 | 模拟串口断帧/重复/双方进程退出，证明不重复动作或丢结果 |
| D. 云端结果闭环 | Schema/物模型候选、后端/数据库接收、必要界面显示 | 真 MySQL 事务/去重/袋基准/钱包隔离测试；中位数端到端可用 |
| E. 受控真机验收 | 用户刷 MCU、必要 HMI 修改、匹配 Pi 包及已部署云端接收能力 | 新的现场安全确认后测试投递/清运/断电/防夹，逐项留证 |

部署时先准备向后兼容的云端接收面和必要的物模型，再在设备无未完业务及账本状态核对
后进行 MCU/Pi 成对切换。单独刷了 MCU 但 Pi 未切换时，必须保持不接新业务，不自动
“试另一种协议”。上线前检查软件版本认可/允许列表，避免再次卡在设备版本未获认可。

回退同样成对进行，先核对进行中业务、已保存结果和账本；不能在有新协议未交接结果时
只回退其中一端。保留身份与历史数据，不采用重刷 TF 卡、清空数据绕过迁移。若后续需要
制作镜像，必须复用已有受控依赖缓存，仍验证源码/依赖摘要；本轮不构建镜像。

## 10. 验收清单

| 场景 | 必须观察到的结果 |
|---|---|
| 正常接受/明确拒绝/丢接受回复 | 三者区分；丢回复先查询，不重发旧开门 |
| 同命令重复、同编号不同内容、旧编号已清正文 | 不重复动作；冲突拒绝；缓存淘汰不能使旧命令重新有效 |
| Pi 退出，MCU 仍进行中或已完成 | 恢复原业务或取回原结果，不要求重新扫码 |
| 结果保存前退出、保存后确认前退出、确认丢失 | 不丢结果、不提前清 MCU、上报与建单恰好一次 |
| MCU 复位、持续读到 0、绑定消息延迟/丢失 | 准确核对代次，0 不重复算多次重启，不重灌旧编号掩盖重启 |
| 旧查询/旧完成/旧确认延迟到新业务 | 不改变新业务、清错结果或产生二次业务价值 |
| 投递丢数据 | 问题证据保留、无订单结算/余额/自动提现；新关门检查后才恢复 |
| 清运丢旧重量 | 原清运员确认、旧值为空、新袋真实基准可应用；无伪造清运净重 |
| 有完整结果后 MCU 才复位 | 原结果继续处理，不降格为无价值记录 |
| CLOSE 防夹、释放、暂停时改 OPEN | 输出暂停/继续符合最新规则；开门不受 PB5 阻断，无旧关门复活 |
| PB5 因关到底保持触发 | 不单独判故障，不阻止其他条件正常后的下一次开门 |
| 250 ms 采集与屏幕/锁/烟感同时运行 | 无计时串扰；锁保持独立时长；称重等待不阻塞防夹 |
| 5 点跨度恰好 100 g 或 101 g | 前者均值提前结束；后者继续积累或到 5 s 取中位数 |
| 重复读缓存、阶段切换、合法 0/负数、报文错误 | 缓存不凑样本，旧阶段不混入，缺值不变 0，数值语义一致 |
| 5 s 波动中位数、奇偶样本、读取失败 | C/Python/Java 结果一致；中位数可业务采用，真实读取失败分开 |
| 中位数经 OneNet 到后端 | 不被旧 STABLE 校验拒绝、不仅因此触发人工审核、取值方式保留 |
| 新袋结果上报/应用确认丢失 | 原袋/新袋/基准恰好应用一次，不在旧基准下接受下一笔 |
| 旧 HMI 返回/完成/定时跳转、更新中或无业务裸按钮 | 不误完成、不绕过状态驱动机构；页面不等于业务状态 |
| 新旧软件不匹配、失败回退 | 保持停止新业务且可诊断，不双解析、不删除账本或旧数据 |

纯软件测试不代表 PB5 实物覆盖、称重准确度或机械安全已经验收。必须在现场重新确认
安全范围后再做物理动作，不沿用几天前的 SSH 会话或动作授权。
