## 2. 组件和事实所有权

### 2.1 recycling

```text
QueryCleanOptionsUseCase
PrepareCleanOperationUseCase
EndCleanBeforeOpenUseCase
RequestCleanUnlockUseCase
ApplyCleanCompleteUseCase
EditCleanRecordUseCase
QueryBagTraceUseCase
StartFullnessDetectionUseCase
ApplyFullnessSampleUseCase
StartBaselineRemeasurementUseCase
RecoverPendingDeliveryResultUseCase
```

拥有：

- 清运配置/head、操作、记录当前有效业务值、只追加修改留痕和异常；不拥有清运审核决定；
- 袋身份、当前位置和历史；
- 重量基准及重测；
- 容量投影、满溢检测/样本/事件；
- 投递结果待处理的本域 gate。

### 2.2 device

拥有：

- 整机占位和设备命令；
- 投递门真实状态、清运电磁阀通断、独立人工关门确认、称重和传感器物理结果；无门磁时
  清运物理门位保持 `UNKNOWN`；
- 严重设备故障及安全锁；
- 设备级恢复端口。

清运应用用例通过 device 公开端口取得/释放整机占位并保存物理事实，不引用 device Mapper/Entity。

## 3. 清运主体与入口

清运员是当前机构普通用户附加 `CLEAN_OPERATION` 能力后的主体，使用 `aud=miniapp`。工作人员管理小程序的 `aud=miniapp-staff` 不能替代清运员身份。

小程序扫码设备后只做：

1. 查询本机构部署；
2. 选择投口；
3. 扫描准备换入的新袋二维码；
4. 创建清运操作；
5. 观察/恢复自己的原操作。

小程序不提交清运员、租户、机构、旧袋、旧皮重、重量、配置、门或照片等服务端事实。

## 4. 清运选项

查询返回：

```text
deployment/port safe summary
deviceBusy
cleaningAllowed
blockers[]
currentBagQr?
oldBagMissingWarning
recoverableOperations[]  # 只含当前清运员本人
configurationVersion
```

以下本身不阻止一次真实清运：

- `PORT_FULL` 或活动满溢事件；
- 旧袋绑定缺失；
- 旧重量基准缺失；
- 已终结的满溢检测失败；
- 投递结果待处理。

真实换袋可以建立新一代容量事实。

以下仍阻止：

- 清运电磁阀通电/未知、缺少必要人工确认或严重安全锁；
- 存储、称重等已知严重故障；
- 边缘/MCU 离线或协议不兼容；
- 整机有 DELIVERY/CLEAN 占位；
- 目标投口有未终结清运；
- 满溢检测或基准重测当前仍在执行。

## 5. 建立清运操作

请求携带：

```text
deploymentCode
portNo
installedBagQr
Idempotency-Key
```

锁序：

```text
tenant
→ organization
→ current miniapp
→ clean config head
→ organization user / cleaner capability
→ device asset
→ active deployment/deployment/runtime
→ existing clean operation/occupancy（新作业时不存在，由 asset 锁保护空槽）
→ port/port runtime
→ bag identities in stable order
→ bag occupancy/capacity/baseline
```

事务：

1. 验证清运主体、机构、配置、设备安全和冲突；
2. 读取并冻结当前旧袋绑定状态：
   - 存在：`BOUND + oldBagQr`；
   - 缺失：`MISSING`，允许继续且不伪造袋；
3. 只在旧基准与旧袋一致时冻结为可信基准；
4. 规范化新袋码：
   - 本机构首次扫码的全平台新码登记身份；
   - 同机构且当前位置为 `NONE` 的旧袋允许复用；
   - 其他机构/投口/操作占用时拒绝；
5. 旧袋存在时，新旧袋必须不同；
6. 为新袋建立 `CLEAN_RESERVED` 位置；
7. 创建唯一 `PREPARED` 操作，冻结：
   - 旧袋/基准快照；
   - 新袋；
   - 清运配置版本；
   - 默认 30 分钟执行时限；
   - 当前设备配置摘要；
   - 可空的原投口待处理投递 session 快照；
8. 取得整机 `CLEAN` 占位；
9. 创建 `START_CLEAN_OPERATION:<operationUid>` 命令和可靠任务；
10. 写审计。

中心开门前重量此时必须为 `null`，不得读取最近心跳重量。

## 6. 首次解锁与不可逆边界

开始授权在后端事务提交后默认 60 秒失效。

香橙派：

1. 可靠保存完整操作、旧袋/基准、新袋、配置摘要和单调期限；
2. 请求 MCU 取得本操作真正的首次开门前稳定总重量；
3. 把重量和可靠状态提交 SQLite；
4. ACK MCU 前重量事件；
5. 授权仍有效、称重和设备安全时 MCU 才给清运电磁阀通电解锁，门扇随后由机构自动弹出。

重量不稳定、过载、故障、摘要不一致或 SQLite 无法落盘时拒绝解锁并上报明确失败。

```text
第一次 CLEAN_UNLOCK_ACTUATED，或命令已经外调而无法证明未执行
```

是保守的不可逆边界。系统没有清运门门磁，无法知道门扇实际何时打开：

- 之前可以安全结束、释放新袋预留和整机占位；
- 之后不能普通取消、不能恢复旧袋，只能完成原操作或进入原清运员恢复；
- 电磁阀通断只表示锁输出，不能推定物理门位；无门磁时门位保持 `UNKNOWN`，清运员
  关门确认另存独立事实。

60 秒只限制首次开始；期限内开始后按冻结的 30 分钟窗口完成。

## 7. 解锁前结束

当前清运员可以提交解锁前结束请求，必须携 `expectedVersion`。

- 能证明命令从未外调：事务同步推进 `PRE_OPEN_ENDED`；
- 命令可能已经外调：可靠保存停止意图并返回 `202`，保持占位/预留直至物理证据闭合；
- 只有能够证明解锁命令从未外调或可靠拒绝、旧命令不会再执行，才：
  - 删除新袋 `CLEAN_RESERVED` 位置；
  - 追加 `RESERVATION_RELEASED`；
  - 释放整机占位。

不创建清运记录、照片槽、基准或满溢检测。

## 8. 操作内再次解锁

系统无法检测清运门是否意外关闭。最终完成前，清运员发现门已手动关住或需要再次进入时，
MCU 屏幕始终可以提供“再次解锁”，不新增小程序远程开门。

香橙派只在以下条件接受 `CLEAN_UNLOCK_REQUESTED`：

- 原 `operationUid` 仍是本地活动操作；
- 原 30 分钟单调期限未到；
- MCU、电磁阀和称重链无阻断性故障；
- 中心尚未把操作置为 `RECOVERY_REQUIRED`。

每次再次解锁：

- 使用新的本地 `mcuCommandUid` 和事件身份；
- 继续引用原操作、原清运员、旧袋/基准、首次开门前重量和新袋预留；
- 不重新扫码、不创建第二操作/记录；
- 清运员下一次人工确认关门后的候选新皮重覆盖上一候选，但历史观察保留；
- 次数不设业务上限，只受总期限和电磁阀保护限制。

断网时已经可靠授权的活动操作可以在边缘再次解锁并由清运员人工完成；进入
`RECOVERY_REQUIRED` 后必须重新取得中心授权。每次解锁使用新的 `mcuCommandUid`，
命令可能执行但结果未知时不得自动重放。

## 9. 超时与原清运员恢复

30 分钟到期：

| 可证明事实 | 处理 |
|---|---|
| 从未可能执行解锁 | 可以按解锁前结束收敛 |
| 解锁可能已经执行，尚无清运员人工关门确认 | 操作 → `RECOVERY_REQUIRED`；保持整机占位和目标投口阻断，等待原清运员现场恢复 |
| 已有人工关门确认且电磁阀断电，但结果尚未可靠保存 | 保留原操作、目标投口和新袋预留，释放整机占位以允许其他安全投口作业；恢复时重新取得整机占位。继续恢复最终称重/明确故障及上报，不得仅凭断电自动完成 |
| 电磁阀通电/状态未知或设备链故障 | 保持整机占位并锁存故障，整机停止新作业 |

超时不创建清运记录、不交换袋、不释放预留、不采用候选新基准。

P0 只允许原清运员恢复。请求：

```text
operationUid
expectedVersion
Idempotency-Key
```

事务校验原操作、清运员、部署、投口、预留和快照均未改变，然后：

1. 重新取得整机 `CLEAN` 占位；
2. 创建 `RESUME_CLEAN_OPERATION:<operationUid>:<recoveryCount+1>`，只恢复原上下文并允许新的人工再次解锁；
3. 递增版本和恢复次数；
4. 返回 `202`。

设备在新的 60 秒开始授权内加载原上下文后进入 `IN_PROGRESS`，获得一段新的原配置时长窗口；不覆盖首次开门前重量，不建立新操作/记录。

## 10. 人工关门确认与 CLEAN_COMPLETE

清运员手动关住清运门且电磁阀断电后，MCU 等待最后重量稳定并在屏幕展示；若最终确认
无法取得可靠重量，则保存明确终态称重故障。清运员随后明确确认安装及关门完成。系统只
拥有“人工确认 + 电磁阀已断电”这一首期推定，不能声称门磁已经证明真实关门。香橙派
随后可靠保存：

```text
operationUid
firstPreOpenTotalWeightG
finalPostCloseTotalWeightG
deviceRemovedWeightG?
candidateNewBaselineWeightG?
weight reliability/fault codes
installedBagQr
operatorClosedConfirmed
lockPowerState = DEENERGIZED
assumedDoorState = CLOSED
four photo slots
```

克值为带符号整数；失败用 `null + errorCode`，不能用 0。

后端先验证 `installedBagQr` 精确等于预留快照。同身份异内容或袋码不一致进入技术隔离，不能猜测换袋结果。

权威事务先按 D-037 从永久领域锁根进入：

```text
device asset
→ active deployment/deployment/runtime
→ clean operation/occupancy
→ port/port runtime
→ all bags in id order / bag occupancy
→ capacity/baseline/detection
→ 原 dev_edge_event 与唯一 physical result
→ clean record counter
→ 最后更新 operations inbox/attempt/task 与确认任务
```

随后在同一事务：

1. 核对事件摘要、操作、部署、袋快照、人工关门确认和电磁阀断电状态，保存唯一设备物理结果；
2. 复核操作、设备、袋和容量代际；
3. 后端重算取走重量/候选基准并保留设备值；
4. 分配清运记录号和机构序号；
5. 创建唯一清运记录、四个照片槽和必要系统异常；
6. 旧袋存在时：
   - 删除其 `PORT_BOUND`；
   - 追加 `REMOVED_BY_CLEAN`；
7. 旧袋在准备时为缺失：
   - 不创建虚构旧袋/取走事件；
   - 追加 `OLD_BAG_BINDING_MISSING` 系统异常；
8. 把新袋 `CLEAN_RESERVED → PORT_BOUND`，追加 `INSTALLED_BY_CLEAN`；
9. 新袋最终稳定重量可靠、非负且关系一致：
   - 创建 `CLEAN_COMPLETE` 来源的有效新基准；
   - 当前原始净重为 0；
10. 新基准不可靠/矛盾：
    - 保存原值；
    - 当前基准置 `INVALID`；
    - 绝不沿用旧袋基准；
11. 创建清运后 `detectionUid` 和容量 gate；
12. 根据模式创建采样任务，或在 `WEIGHT_ONLY + 无有效基准` 时明确失败；
13. 条件匹配时清除旧投递 session 结果待处理指针；
14. 操作 → `COMPLETED`；
15. 创建边缘业务确认任务。

任一步失败整体回滚，设备继续使用原事件重投。

## 11. 清运记录直接修改、变更留痕与异常统计

清运员属于可信工作人员。满足清运员完成确认、人工关门确认、电磁阀断电，以及最终稳定重量或明确终态称重故障后，`ApplyCleanCompleteUseCase` 在完成事务中创建唯一清运记录。记录不保存 `reviewStatus/currentRevisionNo/reviewRevisionId`，不创建待审任务、审核决定或通过/驳回状态。

`EditCleanRecordUseCase` 只开放 Web，执行顺序固定为：

1. 解析工作人员或平台管理员真实身份、目标租户/机构和 `clean.edit` 作用域；
2. 按公开记录号锁定记录，校验请求幂等摘要和 `expectedVersion`；
3. 校验至少修改一项，当前首批允许设置/清空当前有效取走净重量以及设置/清空记录备注；修改原因必填；
4. 计算修改前后快照，追加唯一 `rec_clean_record_change`；
5. 条件更新记录当前有效字段、来源、版本和更新时间；
6. 同一事务提交后立即返回新版本，列表、详情和统计读取新值。

并发修改同一旧版本最多一个成功。修改当前有效净重量不覆盖设备上报重量、后端复算重量、可靠性、异常、物理结果或照片；设置后以人工值计入已知清运重量统计，清空后从该统计排除。普通记录编辑也不修改清运员、设备/投口、操作、袋关系、完成时间、重量基准、容量 gate、投口阻断或设备安全状态，这些事实只能由对应原子业务操作推进。

异常、安全锁、无效新基准和满溢检测各自按真实事实收敛，不能以修改记录或“审核通过”解除。无论正常、异常或后来修改，都不写用户钱包，不产生积分、返现、审核奖励或其他收益，也不回滚物理换袋、基准、容量、照片或设备事实。

## 12. 袋身份和追溯

袋码是机构内可复用的不可变身份，不保存：

```text
可用
使用中
已清空
已报废
```

当前位置：

```text
NONE
PORT_BOUND
CLEAN_RESERVED
```

`NONE` 只表示没有当前位置，不代表袋已清空或可用于任意机构。

只追加事件至少包括：

```text
REGISTERED
RESERVED_FOR_CLEAN
RESERVATION_RELEASED
INSTALLED_BY_CLEAN
REMOVED_BY_CLEAN
```

约束：

- 一个袋最多一个当前位置；
- 一个投口最多一只当前袋；
- 一个清运操作最多预留一只新袋；
- 清运完成的旧袋移除与新袋安装同事务；
- 实体袋可反复利用，同机构 `NONE` 袋再次扫描后建立新的预留历史。

Web 分别查询袋位置历史、关联清运记录和关联投递订单，不拼成一个伪全局时间线。

## 13. 满溢检测

### 13.1 触发

MCU 不在空闲时间持续采集业务满溢。只在：

```text
DELIVERY_COMPLETE
CLEAN_COMPLETE
MANUAL_RECHECK
```

后端先创建稳定 `detectionUid` 和规则快照，再下发 `SAMPLE_FULLNESS`。

投递/清运首次样本角色为 `INITIAL`；疑似满溢可按配置在默认 10 秒后产生 `CONFIRMATION`。投递后首次等待默认 5 秒。

### 13.2 来源

同一次样本分别返回：

```text
infraredBlocked + infraredHealth
totalWeightG + weightHealth
```

香橙派按冻结模式组合：

| 模式 | FULL | NOT_FULL | 失败 |
|---|---|---|---|
| `INFRARED_ONLY` | 红外可靠且遮挡 | 红外可靠且不遮挡 | 红外失败 |
| `WEIGHT_ONLY` | 重量可靠、有有效基准且达到阈值 | 同条件且低于阈值 | 重量/基准失败 |
| `INFRARED_OR_WEIGHT` | 任一可靠来源满 | 两个来源都可靠且不满 | 一个不满而另一失败，或两者无法可靠判断 |

一个来源失败、另一个不满时不能判未满，必须停止投递。

### 13.3 满溢度

```text
rawNetWeightG = currentTotalWeightG - currentBaselineWeightG
fullnessPercent = max(rawNetWeightG, 0) / configuredFullWeightG × 100%
```

- 展示保留两位；
- 允许超过 100%；
- 原始净重量为负时展示 0%，但完整保存负原值；
- 重量、基准或阈值不可用时显示 `null`，不能显示 0；
- 明确标注检测时间和“上次检测值”，不得称为实时。

### 13.4 检测应用

检测完成事务锁容量并复核：

- 当前袋；
- 按模式可空的当前基准；
- 规则指纹；
- `currentDetectionId`。

全部匹配：

- `FULL`：创建或延续同一活动满溢事件；
- `NOT_FULL`：检测 `APPLIED`，恢复活动满溢事件；
- 来源失败：检测 `FAILED`，保持原满溢事件/阻断。

代际变化时保存 `STALE_IGNORED`，不覆盖新袋、新基准或新规则。

中间垃圾下沉后，后续同一检测的确认样本或一次新的真实重检可以得到可靠 `NOT_FULL` 并恢复告警；系统不靠空闲持续读取自动改写。

## 14. 人工满溢重检

Web `device.detection.execute` 只能发起真实检测：

1. 提交 `expectedCapacityVersion`；
2. 校验没有活动检测/基准重测；
3. 冻结当前袋、基准、规则和配置代际；
4. 创建唯一检测和可靠任务；
5. 返回 `202 + statusUrl`。

不能直接提交 `FULL/NOT_FULL`。终态检测不重开；迟到设备结果只保存证据。

## 15. 空袋基准重测

仅当当前袋基准为 `UNINITIALIZED/INVALID`，且工作人员现场确认袋为空时使用。

事务创建 `measurementUid`，冻结当前袋/配置/容量代际并下发真实测量。

可靠、非负、量程内、代际匹配：

1. 创建来源 `MANUAL_REMEASUREMENT` 的新基准；
2. 当前总重量同值、原始净重为 0；
3. 创建新的 `MANUAL_RECHECK` 检测；
4. 检测可靠结束前仍阻断投递。

失败、负值、过载、不稳定或代际变化只保存失败/过期证据，不沿用旧值、不直接开放投递。

当前投口有投递结果待处理且内容物是否为空不可信时，禁止先做空袋重测；应先真实清运换袋。

## 16. 精确恢复

### 16.1 投递结果待处理

有权限人员必须确认现场袋/内容和门安全，并触发新的真实满溢检测。恢复不：

- 创建、删除、审核或改挂订单；
- 伪造原 session 首末重量；
- 直接填写容量结果；
- 阻止以后可信原结果按旧代际建立订单。

### 16.2 严重安全锁

恢复命令携：

```text
faultUid
expectedRuntimeVersion
现场确认
```

投递门恢复必须有新鲜真实门/传感器健康证据，且旧命令不会再执行。清运门没有门磁，
只能使用原清运员现场确认、电磁阀断电和其他传感器证据，物理门位保持 `UNKNOWN`，
不能宣称门已被机器检测关闭。成功只把精确故障事件置为 `RECOVERED` 并条件解除其安全锁；其他
活动故障、占位、清运、容量、基准、订单和经营开关保持不变。

恢复后只唤醒原协调任务重新判断，不能在恢复事务内直接宣称原作业完成。

## 17. 客户端

### 小程序清运入口

- 扫设备、选投口、扫新袋；
- 显示准备、解锁、人工处理中、恢复、完成；
- 只显示当前清运员自己的操作；
- 再次解锁在设备屏幕，不在小程序；
- `RECOVERY_REQUIRED` 只允许原清运员发起恢复；
- 清运完成即形成已完成记录，但不等于清运后满溢检测已经恢复投递资格；后来修改记录也不改变该检测结论。

### Web

- 清运操作/恢复队列；
- 清运记录、修改留痕、异常与当前有效重量统计查询；
- 具有 `clean.edit` 时直接设置/清空当前有效净重量和记录备注；保存即生效，不进入审核；
- 袋当前位置与历史；
- 容量、最近检测值、活动满溢事件；
- 人工重检、基准重测、待处理结果恢复和精确安全恢复；
- 写能力不自动开放全量读取；
- 工作人员小程序只保留当前机构容量/满溢/告警精简只读。

## 18. 测试矩阵

1. 两个操作并发扫描同一袋只一个预留成功；
2. 旧袋缺失仍可完成，但不虚构旧袋事件；
3. 解锁前结束与首次解锁命令竞争只有一个分支；
4. 前重量未持久 ACK 不给电磁阀通电；
5. 操作内多次再次解锁不创建第二操作/记录；
6. 解锁可能发生后，电磁阀断电也不能绕过人工关门确认自动完成或释放；
7. 只有原清运员能恢复；
8. 完成事件重复/崩溃只一记录、袋交换、基准、检测 gate、确认；
9. 新袋码与预留不一致进入隔离，不改袋；
10. 新基准可靠/负值/故障/不一致各分支；
11. 清运与迟到投递结果竞争按代际不互相覆盖；
12. 清运完成直接形成记录且没有审核/奖励；可靠初始重量进入统计，异常重量保留事实并排除；
13. 清运记录设置/清空有效重量和备注均追加前后值；并发同版本最多一人成功，统计读取已提交当前值；
14. 三种满溢模式的 FULL/NOT_FULL/来源失败矩阵；
15. 满溢检测与换袋/基准/规则并发时旧结果 `STALE_IGNORED`；
16. 基准重测和人工恢复只命中精确版本/故障；
16. 相同袋在本机构多次循环使用形成连续历史。

## 20. 主审否决项

- 扫码后直接创建“已完成清运记录”；
- 清运门首次可能解锁后普通取消或恢复旧袋；
- 旧袋缺失时伪造袋码或从基准反推袋；
- 给袋增加“可用/已清空/已结束”等生命周期状态；
- 新袋预留和整机占位在不同事务后补；
- 前重量使用最近心跳值；
- 再次解锁时创建新操作、重新扫码或由小程序远程解锁；
- 超时伪造完成、交换袋或释放不安全整机；
- 允许其他人员接管 `RECOVERY_REQUIRED`；
- 负重量截断为 0、称重失败用 0；
- 为清运新增审核/驳回/待审队列，绕过 `clean.edit` 和变更留痕直接覆盖记录，覆盖设备原始证据，或因清运修改钱包、积分、返现和奖励；
- 空闲持续传感器数据直接改写业务满溢；
- 一个来源失败、另一个不满时判未满；
- 满溢度限制在 100% 或覆盖负原值；
- 人工按钮直接写未满、皮重或设备正常；
- 安全恢复同时清除其他故障、容量、占位或订单。
- 把电磁阀断电描述成真实门磁证明，或尝试由 MCU/`SAFE_CLOSE` 自动关闭清运门。

## 21. 2026-07-24 / 2026-07-27 修订说明

清运门实际为“电磁阀通电解锁并自动弹开、清运员手动关门”的结构，没有门磁，也没有
可由 MCU 驱动的关门执行器。本章因此用“解锁可能已经发生”替代“实际门已检测打开”
作为不可逆边界，并明确人工关门确认是完成所必需的业务事实。2026-07-27 进一步确认
电磁阀通断不能推定门开关，所有接口、日志和验收都必须保持物理门位 `UNKNOWN`，并将
清运员关门确认作为独立事实。
