## 1. 文档效力与边界

1. 本文描述目标 P0 数据库，不描述当前代码“已经如何运行”。当前结构以 V1～V14、实体和 Mapper 为准。
2. 2026-07-19 的字段草案继续作为历史讨论证据，但其中与冻结需求或业务模型冲突的结论全部失效，不能继续在其字段表上增量拼补。
3. 数据库设计必须承接已经冻结的模块所有权、本地事务、租户/机构隔离、稳定业务身份、不可变资金明细、inbox/outbox 和失败恢复边界。
4. 本阶段先确认总体策略，再依次确认表族、逐表字段、约束/索引、并发锁顺序、迁移和验收；未确认前不修改 Flyway、Entity、Mapper、H2 schema 或真实数据库。
5. 接口 DTO、OneNet/UART 消息字段和 Java 类结构不由本文反向决定；跨端业务身份和数值单位必须保持可无损映射。

## 2. 当前数据库审计

### 2.1 当前最终结构

V1～V14 最终形成 13 张表：

| 当前代码所有者 | 表 |
|---|---|
| system | `sys_tenant`、`sys_admin`、`sys_user` |
| device | `biz_device`、`biz_door`、`biz_device_status`、`biz_door_status`、`biz_device_session` |
| business | `biz_delivery_order`、`biz_clean_order`、`biz_clean_bag`、`biz_withdraw_order` |
| 无代码所有者 | `biz_weight_record` |

当前唯一真实外键是 `biz_door.device_id → biz_device.id ON DELETE CASCADE`。其余用户、设备、订单、会话和资金关系没有数据库外键；所有 `biz_*` 及 `sys_user` 都使用 `tenant_id NOT NULL DEFAULT 1`，但没有机构层级或跨表作用域一致性约束。当前运行配置还启用了 `baseline-on-migrate=true` 和自动建库；这只能作为旧开发环境事实，不能沿用到目标验收/生产数据库。

测试环境关闭 Flyway，使用手工维护的 `schema-h2.sql`。该文件已经从最初的 V1～V3 继续揉入 V14，却仍保留旧说明，已经形成第二套会漂移的 schema，不能作为目标结构依据。

### 2.2 不能通过“加字段”解决的差距

- `sys_tenant` 同时表示企业、经营机构、登录账号、小程序和商户配置；目标模型要求分离租户、机构、工作人员、机构用户及客户端绑定。
- `biz_device` 混合物理设备、机构归属、位置和状态；目标要求物理资产与机构部署实例分离，历史部署不可改挂。
- 当前设备会话允许后来用户覆盖，缺少不可覆盖的稳定投递 session、跨投递/清运统一整机占位及迟到结果的原部署身份；目标不再为 session 内继续开关门建立云端周期。
- 投递订单已有单价字段，但缺少前后原始重量、原始/最终金额、袋码、配置版本以及只追加的审核纠错版本，不能把现有单价列当作完整订单快照。
- 清运仍带有开门预创建记录和分段毛重/皮重更新痕迹。当前记录虽有 `bag_qr + new_bag_qr`，但没有可恢复清运操作、完成事务和约束，不能保证每一对取走袋/换入袋都形成完整不可变历史。
- 钱包余额直接放在 `sys_user`；没有钱包账户与明细、机构出款账户与明细、充值单、双侧冻结、微信转账单和渠道终态证据。
- 当前投口状态已有简单满溢当前值，但没有检测身份、判断来源/配置快照、初检/复检过程和持续事件历史；同时完全没有可靠 inbox/outbox/任务、技术隔离、对账异常或完整操作审计。

另有多处现状错位，例如状态实体继承了数据库不存在的时间列、`delivery_token` 的代码幂等语义与数据库唯一范围不一致，以及已执行 V5 遗留了现已废止的清运审核列、约束和修订表。这些问题说明旧结构只能作为迁移输入，不能作为目标模型骨架；清运历史审核结构必须通过 V20 前向迁移替换为直接修改及变更留痕结构，不能回改 V5。

## 3. 目标表族与所有权

本节只固定表族，不在第一批确认具体表名和字段：

| 所有模块 | 目标表族 |
|---|---|
| identity | 平台管理员、租户、机构、机构 AppID 绑定、工作人员账号与机构授权、机构用户、登录会话 |
| device | 物理设备资产、机构部署实例、投口、配置版本/应用确认、当前健康状态、整机占位、作为唯一作业/结果幂等根的投递会话、设备命令与物理结果 |
| recycling | 投递订单原始事实、异常、照片关联、投递认定/纠错版本；清运操作、记录当前有效值、修改留痕、异常、袋绑定历史、重量基准、满溢检测与持续事件，清运无审核决定或待审状态 |
| funds | 用户钱包及明细、机构出款账户及明细、充值单与支付事实、免确认收款授权及观察、提现单、微信转账单、全平台出款闸门 |
| operations | inbox、唯一可靠执行任务、执行尝试/租约、操作审计、技术隔离、对账异常、聚合告警和只读运营投影 |
| integration | 不拥有业务表，只验证/转换外部协议并通过公开端口写入上述事实 |

每张表只有一个模块拥有写入权。查询投影可以跨表读取，但不得成为第二份可独立修改的业务真相。

## 4. 已由上游冻结、无需重新讨论的数据库原则

1. 一个 MySQL 8.x/InnoDB 是中心业务真相；不为 P0 拆库、分片或引入 Redis 作为余额/锁/作业真相。
2. 同一业务结果的主状态、明细、占位和 outbox 意图在一个本地事务中共同提交。
3. 原始设备结果、投递订单认定版本、钱包/机构资金明细、清运记录修改留痕与袋绑定历史、渠道证据和操作审计只追加，不覆盖旧事实。
4. 当前余额、投递当前认定、清运记录当前有效业务值、当前袋、当前健康、当前任务状态属于可更新投影，但必须能由事实核对并用条件版本更新。清运记录修改保存后立即生效，不经过待审核、通过或驳回状态；原始设备证据始终不被覆盖。
5. 待审核返现来源于待审核正金额订单，不是钱包资金；钱包正式余额只由不可变钱包资金明细解释。
6. 用户钱包与机构出款账户是两个独立账本；提现创建必须同时冻结用户金额和机构额度。
7. 免确认收款授权、提现单与微信转账单相互分离；一笔提现仍只对应一笔微信转账。授权和转账分别以可信回调、查单和不可变观察进入各自幂等归并入口。
8. 物理设备资产不直接改机构；调拨结束旧部署并创建新部署，历史事实永久引用原部署。
9. 投递 session 是云端唯一作业、最终物理结果和订单幂等根；会话内继续开关门、重量、照片和继续意图不上云。唯一 `DELIVERY_COMPLETE` 才原子建立订单、四图、异常和最终满溢 gate。

DD-004 只修订 Java 模块在同线程、同事务内构造跨模块复合外键时的受限协作契约，不把跨模块外键改为公开 UUID 候选外键。目标 DDL 继续使用内部 `BIGINT` 主键、租户/机构复合作用域外键和 D-031～D-035 的约束；2026-07-24 删除原投递周期候选表后，已执行 V1～V10 共 **83 张历史表**。V20 删除已废止的 `rec_clean_revision`，同时新增 `rec_clean_record_change`，因此目标业务表数仍为 **83 张**，其余表所有权不变。接收模块只能用当次强类型引用写自己拥有表的 FK 列，不能因此读取或写入其他模块私表。
