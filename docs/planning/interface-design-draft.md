## 1. 文档效力与边界

1. 本文描述目标 P0 接口，不描述当前代码“已经如何运行”。当前行为仍以代码、测试、现有 OneNet 模型和部署配置为准。
2. `docs/api/api-frontend.md` 和 Postman 集合继续作为旧实现的联调资料，但其中的旧路由、Bearer 登录、角色、状态和 DTO 不能反向决定目标接口。
3. 接口设计必须承接已冻结的可信执行上下文、租户/机构隔离、稳定业务身份、本地事务、inbox/outbox、双账本和设备可靠恢复边界，不能在 DTO 或消息协议中重新打开这些决策。
4. 本基线已经冻结契约语义、路径、字段、状态、错误码及跨端边界；下一阶段只做详细设计与任务拆分，获得明确实施指令前不修改 Controller、前端请求封装、OneNet 模型、UART 协议或业务代码。
5. HTTP、OneNet、微信、UART 和模块公开端口是不同协议面，可以复用同一应用用例和业务身份，但不能共用认证方式、传输应答或入口 DTO。

## 2. 当前接口审计摘要

目标接口不能在当前路径上直接补字段，主要差距如下：

- Web 当前仍使用 `localStorage` Bearer JWT，后端关闭 CSRF；目标已经冻结为同源 Web、`Secure + HttpOnly` Cookie、SPA CSRF 和可立即失效的服务端会话。
- 普通小程序、清运入口和工作人员小程序尚未形成相互隔离的会话受众与入口 DTO；当前 JWT 也缺少目标 `jti`、客户端受众和实时能力复核。
- `/api/iot/**` 当前被整体匿名放行并信任明文设备序列号；生产目标只接受 OneNet 可信链路，保留的设备直连接口必须独立认证且仅限明确的测试/维护环境。
- 多个 Controller 直接收发数据库 Entity，路由权限仍写死旧角色；目标模块只能公开稳定命令、查询、值对象和业务 ID。
- 业务异常可能返回 HTTP 200 加数字业务码，前端需要同时猜测 HTTP 与响应体；目标必须使用真实 HTTP 状态和稳定字符串错误码。
- 开门、提现、充值、审核、纠错等高风险写操作缺少统一客户端幂等身份；OneNet 当前也把消息 ACK、设备受理、物理完成和业务成功混在一起。
- 当前 OneNet JSON、Markdown 与 Python 载荷已经存在字段漂移，旧投递重量还无法表达负数；正式 IoT 契约必须有机器可校验的权威 Schema 和跨语言契约样本。

## 3. 目标契约面

| 契约面 | 调用主体 | 认证与主要边界 |
|---|---|---|
| Web HTTP | 平台管理员、租户主体账号、总部与机构工作人员 | 同源 Cookie、CSRF、实时能力与机构作用域 |
| 普通/清运小程序 HTTP | 机构普通用户、清运员 | 绑定机构 AppID 的 `aud=miniapp` Bearer 会话 |
| 工作人员小程序 HTTP | 已由 Web 绑定的工作人员 | 独立 `aud=miniapp-staff` Bearer 会话，免密进入机构精简管理端 |
| OneNet、COS 与边缘协议 | OneNet、香橙派 | 稳定命令/事件身份、可靠接收、业务确认、受限 COS 凭证和断电恢复 |
| 微信 APIv3 | 微信支付通知与 EcoBin 主动调用 | 精确通知入口、验签解密、不可变渠道单号、查单和幂等归并 |
| UART | 香橙派与 MCU | 规范 `uart-v1` 定义版本/分帧/ACK/物理结果；现有 MCU 以单一显式固定帧模式适配，缺失能力保持未知/不支持 |
| Java 模块公开端口 | 模块化单体内部模块 | `.api` 包中的命令、查询、稳定业务 ID和值对象，不公开 Entity/Mapper；仅 DD-004 允许当前事务内的强类型 FK 构造引用 |

### 5.1 已发现的跨阶段落实项

- I-002 已确认所有客户端可寻址资源不得暴露内部 `BIGINT` 主键。I-009 已为平台管理员、工作人员账号、机构用户和工作人员小程序绑定补充公开 UUID，并同步落实到数据库设计；任职、授权等后续若需要被客户端单独寻址，仍须在对应接口批次继续补充。DD-004 只允许同线程、同事务、指定同步参与端口使用逐关系强类型 FK 构造引用，且不得用于寻址、授权、幂等、日志、载荷或跨事务恢复；该规则不改变内部关系型主键继续使用 `BIGINT` 的原则。
- I-004 的幂等回放只针对已经可靠受理或成功的操作。受理前 `DENIED/FAILED` 不永久缓存为业务结果，重试仍复用原 `operationUid`、生成新 `requestUid` 并重新鉴权和校验当前状态。
- I-020 已确认当前临时 OneNet/UART 协议不能形成配置 `EDGE_SAVED/APPLIED` 证明。I-041～I-050 已补齐配置版本/摘要、防降级、边缘可靠落盘、MCU 子集原子应用及 ACK 语义；I-054 已固定目标 Schema/注册表的机器来源。代码、物模型和固件未落实前，真机部署仍保持不可激活。
- I-022/I-023 已确认一次有效扫码 `sessionUid` 对应整场和一单。开始事务一次性冻结用户、投口、袋、单价、配置与阈值，并用唯一 `START_DELIVERY_SESSION` 授权整场；继续按钮只在设备本地重新开投递门，不上云、不重新授权、不上传中间重量/照片/事件，也不执行普通满溢判断。结束按钮或本地 30 秒窗口届满后才上传唯一 `DELIVERY_COMPLETE`，按首次开门前与最终关门后重量结算并在建单后检测满溢。
- 投递负重量异常阈值由后端配置下发，默认 500 克。设备发现任一轮次减少达到阈值时锁存 `negativeWeightAnomaly=true`；该字段只包含在最终订单载荷中，不单独上报，也不携带中间减少值，订单仍按整场净重量结算。
- I-024/I-025 已确认投递修订和钱包差额同事务生效，待审核正返现仍来源于订单汇总。后续模块公开端口和查询实现必须保留 `expectedRevisionNo`、订单创建水位与可变条件实时筛选的组合语义、修订唯一资金来源、当前负余额停投阈值以及钱包三项和机构流水水位的一致快照，不能用缓存拼接成第二套余额真相。
- I-026～I-030 已确认当前旧清运链不能增量兼容；清运门没有门磁和受控关门执行器，
  MCU 只控制电磁阀通断。通电解锁并自动弹门，人工关门；锁通断不能推定物理门位，
  门位保持 `UNKNOWN`。首次解锁命令可能执行即越过不可逆边界，再次解锁沿用原
  `operationUid` 但使用新 MCU 命令；完成必须同时具备清运员人工关门/完成确认、锁断电，
  以及最终稳定重量或明确终态称重故障。`SAFE_CLOSE` 不适用于清运门，超时/重启保留
  原操作等待原清运员恢复；只有断电且原清运员现场确认门扇关闭后，才可释放整机占位并
  继续锁住原投口/袋预留。
- I-031～I-035 已确认本地资金状态与微信原始状态分离：充值先建本地单再异步取得 Native 二维码，支付成功事实与净额入账分两段恢复；提现先双侧冻结，审核通过后才固定唯一 `outBillNo`，只有微信 `SUCCESS/FAIL/CANCELLED` 可以最终结算。后续运营与契约测试必须继续复用同一观察归并器，不能另建后台“改状态”旁路。
- I-036～I-040 已确认 operations 只提供原任务恢复、脱敏审计、告警确认和受控对账动作，不拥有业务终态。最小概览必须从各模块权威查询端口在专用只读 `REPEATABLE READ` 快照中组装，业务写入仍使用 `READ COMMITTED`；后续 IoT/COS 设计要让业务确认超时、本地写入阻断和隔离消息产生可解释的任务、尝试与告警，但不能增加任意重放入口。
- I-041～I-045 已确认可靠边缘事实使用稳定 `eventUid`、部署内全局 `edgeEventSequence`、强类型 Schema 和规范摘要；OneNet 传输成功、设备受理、物理结果与后端业务完成严格分层。香橙派只有持久化后端业务确认并返回回执后才能清理原事件；COS 凭证只授予原作业精确前缀，照片关联独立于建单。
- I-046～I-050 的 UART 1.0 继续作为规范模型和可选 `uart-v1` 实现：最大 256 字节、
  CRC-16/CCITT-FALSE、启动 HELLO、ACK 后持久化及重启查询边界不变。当前现有 MCU
  通过 F-11 单一显式固定帧适配器接入；无法表达的状态不得伪装为 Registry 能力，
  不允许自动探测、双解析或失败回退。I-054 的单一 Registry 仍固定规范 message type、
  payload、能力位和错误码。
- I-051～I-053 已确认跨模块只导入 `.api`，权威业务用例拥有事务并通过同步端口完成强一致结果；DD-004 的两个受限例外不变。PDD-001 只让 recycling 在开始投递时协调 D-037 逐节点锁序；设备本地继续不进入后端用例，最终完成另按可信入站事务建一单并结束会话。device 仍唯一拥有和写入设备作业事实。
- I-054/I-055 已区分“从首版保存机器契约单一来源”和“首版后再增加自动治理门禁”。详细设计必须规划 OpenAPI、OneNet JSON Schema 和 UART Registry 的落地，但不得把尚未建立的跨端契约 CI/完整自动校验写成首版开工前置。
