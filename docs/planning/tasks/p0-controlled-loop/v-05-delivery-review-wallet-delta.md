# V-05｜投递审核/纠错形成真实钱包差额

## 目标

让有权限人员按冻结规则审核或纠错投递订单，使最终认定、只追加修订和用户钱包差额在一个事务内生效，并让用户看到一致的钱包三项和订单时间线。

## 要构建什么

完成 Web 审核与不限期纠错、只追加 revision、服务端重量/金额计算、funds 钱包差额参与端口、钱包三项视图、负余额规则、提现联动及用户订单时间线。

首次审核和后续纠错由 recycling 开启事务，按冻结锁序调用 funds；revision、订单当前认定和唯一钱包明细必须原子提交。原始设备事实、锁定单价、历史 revision 和既有微信提现终态永远不能覆盖。

## 验收标准

- [ ] 审核只提供“按原数据通过”和“修改最终重量后通过”，没有投递驳回。
- [ ] 审核员只能输入最终重量和可空原因，不能输入或修改最终金额。
- [ ] 最终金额按本单锁定单价和冻结舍入规则由服务端计算。
- [ ] 原始认定基于 session 首次开门前与最终关门后重量；审核界面不展示或要求不存在的云端中间轮次。
- [ ] `negativeWeightAnomaly` 精确来自设备最终载荷，只作为整单审核证据；后端不按整场净重补判，也不能把它解释为具体减少重量或自动处罚。
- [ ] 负金额在审核前不进入钱包、不显示为可提现余额；按原数据通过后才扣减并显示负余额。
- [ ] 首次审核以 revision 1 表达，已通过订单的纠错只追加新 revision，不重开审核状态。
- [ ] revision、订单当前认定和从旧金额到新金额的唯一钱包 delta 在同一事务提交。
- [ ] 两名审核员使用相同 `expectedRevisionNo` 时只有一个成功，失败方不产生钱包明细。
- [ ] 最终金额为 0 时不创建零金额钱包明细，但 revision 能证明认定结果。
- [ ] 钱包一致返回待审核返现、可提现余额和提现处理中金额；待审核返现不是钱包资金。
- [ ] 负向纠错按冻结锁序暂停尚未越过微信边界的提现或记录提交后风险，但不修改既有微信终态。
- [ ] Web 显示原始事实、异常、revision 历史和服务端金额预览；小程序显示自己的当前认定和钱包结果。
- [ ] 真实 MySQL 测试覆盖正、零、负金额，HALF_UP 边界，审核竞争，事务回滚和纠错/提现竞争。

- 自动冻结或处罚负重量用户；
- 自动提现。
