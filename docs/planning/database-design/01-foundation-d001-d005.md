## 5. 第一批已确认数据库决策

### D-001 旧数据与 Flyway 迁移纪元

**已确认：现有数据无需迁移，采用“新数据库干净重建 + 旧版本应用和旧数据库成对保留”，不做 V1～V14 原地改造或旧新双写。**

- 实施前必须列出所有本地、测试、服务器数据库及 Docker volume，并核验各自的 `flyway_schema_history`、表结构、行数、余额、渠道单号和进行中作业；仓库审计不能代替实际实例盘点。
- 实例盘点同时检查孤儿引用和即将新增约束的冲突，包括同一 OpenID 跨机构、袋码重复占用、同用户多笔进行中提现、设备会话与清运并存等；不能让新约束在切换时才首次暴露脏数据。
- 实施前对旧库制作逻辑 dump，记录校验和、表行数、Flyway history 和对应 Git commit/tag，并至少完成一次隔离恢复验证。旧应用制品、配置模板和旧数据库作为同一个可恢复版本保存；新应用不能读取或写入旧库，旧应用也不能连接新库。
- 回退只能以“旧应用 + 旧数据库”整体切换，不能反向执行 Flyway、让旧代码解释新表或把旧库当作新系统的读回退。旧、新两套只有一套可以承接业务入口，禁止同时对外写入。
- 在新库尚未产生任何真实且不可丢弃的业务事实前，可以停止新版本并直接切回旧版本。新库一旦接收真实投递、资金或设备作业，直接切回旧库就不再是无损回退；此时必须先停止新入口、保全新库和外部消息，再选择修复前进，或制定显式的数据迁回/补偿方案，禁止静默丢弃新库事实。
- 在全新的空目标数据库运行一套新的 Flyway V1 基线；旧 V1～V14 从运行迁移目录退出。目标验收/生产关闭 `baseline-on-migrate` 和 `createDatabaseIfNotExist`，新 V1 使用严格 DDL，非空污染或误接旧库必须直接失败。
- 新应用账号不得拥有旧库写权限，部署配置显式使用新数据库名，避免在新旧迁移纪元之间误连。
- 切换窗口先停止旧入口产生新业务，确认所有门安全、结束或隔离进行中作业，并排空能映射的旧 OneNet/微信消息；缺少目标投递会话/清运操作身份的迟到旧事件只进入隔离记录，禁止猜测后挂到新模型。
- 试点租户、两个机构、账号、设备、投口和初始袋绑定通过显式 seed 或白名单导入重建；不迁移旧余额，也不根据当前余额反造资金流水。
- 首次启用真实设备/渠道并写入任何不可丢业务事实之前完成最后一次切库和清库；至少包括真实投递/返现、清运、钱包或机构资金明细、充值单、提现冻结、微信渠道单及 M0 验收证据。此后禁止重新基线或清库，所有已应用迁移永久不可改，只允许前向 `expand → backfill → validate → contract`。
- 本次已确认现有数据不需要迁移。若实施盘点发现与该前提不符，必须暂停当前切换并重新打开本决策，不能把旧链 V15+ 误放进 D-041 的目标新纪元。届时只能另行选择并批准：放弃干净新纪元、继续在旧 V1～V14 之后设计 V15+ 前向改造；或保留目标 V1～V10，设计一套受支持的旧基线到新库的显式导入、映射和逐项对账。两条路径都超出当前已确认方案，未重新设计前不得实施。无法证明历史来源的余额只能在业务负责人确认并留存证据后形成明确的“迁移期初”事实，不能反造虚假的逐笔历史明细。

### D-002 租户与机构作用域键

**已确认：所有机构级目标表显式保存 `tenant_id + organization_id`，两列均非空、无默认租户，并用复合外键保证机构确实属于该租户。**

- `sys_tenant`、平台管理员、物理设备资产、系统商户配置和全平台出款闸门等真正平台级表是明确例外，不伪造 `tenant_id=1`。
- 所有无 `tenant_id` 表必须进入唯一维护的 MyBatis 租户拦截排除清单，并且只能通过对应平台端口访问；新增全局表时数据库清单与拦截器配置必须一起验证。
- 子记录引用钱包、部署实例、订单等机构对象时继续校验同一作用域，不能只凭一个裸主键关联。
- 历史事实创建后禁止修改或级联更新租户/机构；调拨、迁址和换机构通过结束旧对象并新增对象表达。
- 目标业务表不再使用 `tenant_id DEFAULT 1`。MyBatis 租户拦截器是纵深防御，不替代复合约束和机构查询条件。

### D-003 内部主键与跨端业务身份

**已确认：关系型内部主键继续使用 `BIGINT`；跨设备、网络重试和第三方回调的身份使用独立稳定业务 ID，不暴露或复用数据库主键。**

- 投递会话、清运操作等跨 Java 21 与 Python 3.11 的作业身份首期使用双方原生可生成的 UUIDv4；一次投递会话就是云端唯一投递作业和结果幂等根，不再为会话内本地继续开关门生成云端周期身份，也不为 UUIDv7/ULID 增加依赖。
- 充值单、提现单、微信 `out_bill_no` 等使用后端生成、全局唯一且符合渠道字符限制的业务单号。
- 设备二维码、袋码及以后可能公开的随机凭证与表主键分离，不能通过递增 ID 猜测其他对象。
- 每个外部身份同时定义唯一约束和冲突摘要校验；相同 ID、不同内容不能当作普通重复。

### D-004 “唯一进行中”采用当前占位关系

**已确认：对跨多张状态表的互斥规则建立数据库可唯一约束的当前占位关系，不依赖扫描状态或 MySQL 不支持的条件唯一索引。**

- P0 一台物理设备的投递会话和清运操作共用一个“当前物理执行权”槽位；只预留未来扩展类型，不在本阶段定义维护生命周期。
- 清运开门后未完成但门已安全关闭时，清运操作、新袋预留和投口阻断继续存在；满足冻结条件后可以在同一事务释放整机执行槽位。原清运员恢复前必须重新取得该槽位，不能覆盖原操作。
- 袋码没有生命周期状态机，但使用当前绑定/预留关系表达“此刻位于哪个投口或被哪个清运操作预留”。数据库同时保证袋码唯一、每个投口最多一个当前绑定袋、每个清运操作最多一个预留袋，并要求绑定目标与预留目标恰好二选一。
- 同一机构用户最多一笔进行中提现，通过钱包上的当前提现槽位或等价专用占位表保证；历史提现仍保留在提现表。
- 占位创建/释放必须与对应业务状态在同一事务提交；超时任务不能只删除占位而伪造物理作业结束。
- 新增唯一约束前必须先完成 D-001 的冲突盘点、处置和核对报告，不允许通过静默删除重复行让迁移“通过”。

### D-005 数值、账户投影与不可变明细

**已确认：正式资金以带符号整数“分”保存；设备原始称重与业务认定重量分层保存；单价保持每千克 4 位小数。账户采用“锁定更新的当前投影 + 只追加明细”。**

- 用户和机构的正式金额、冻结金额、充值净额、提现金额及手续费使用 `BIGINT` 分，禁止 `FLOAT/DOUBLE`；用户可提现余额允许为负，机构可用/冻结金额不得为负。
- 投递首次开门前、整场最终关门后和设备整场净重等原始称重使用带符号整数克原样保存，任何审核或换算都不能覆盖它们。会话内继续投递的中间开关门重量只留在边缘本地诊断，不进入中心数据库。
- 初始业务重量由原始净重换算为 kg 后按 `HALF_UP` 保留 2 位；审核人员填写的最终认定重量也限定为 0.01 kg 精度并单独保存。单价使用精确定点 `DECIMAL(...,4)` 元/kg，返现金额以最终认定重量乘本单单价后再按 `HALF_UP` 四舍五入一次到分。
- API/页面展示业务重量 2 位和金额 2 位；满溢计算仍可以使用原始克值及克单位阈值，不从已舍入的订单业务重量反推传感器事实。
- 用户钱包表只保存可提现和提现冻结投影；“待审核返现”按订单汇总。机构账户只保存可用和提现冻结投影，总额由两者相加得到。
- 每次入账、扣减、冻结、释放、成功消耗和人工调整都追加唯一幂等资金明细，并与账户投影在同一事务更新；余额不再放在身份用户表中。
- 时间字段统一使用毫秒精度并按 UTC 保存，界面转换为 Asia/Shanghai；具体列名和 MySQL 类型在公共字段批次确认。
