## 8. 第四批已确认：投递、清运、照片与满溢事实

本批把 D-009 已确认的事实所有权展开到字段、状态、唯一约束和事务边界。设备上传的原始物理证据仍由 `dev_physical_result` 唯一拥有；本批只保存 recycling 已经接受的业务快照、人工认定和当前容量投影，不复制 inbox 原文或设备运行健康真相。

### D-016 投递配置与订单事实

**已确认：一个投递 session 只有一个最终设备结果并最多形成一笔订单；订单将不可变来源快照与可变的当前认定投影放在同一聚合，但当前认定只能由追加修订推进。**

| 表 | P0 核心字段与约束 |
|---|---|
| `rec_organization_delivery_config` | `id + tenant_id + organization_id + version_no`、`review_mode`、以分保存且严格 `< 0` 的负余额停投阈值、以克保存的人工认定绝对值上限 `max_review_abs_weight_g`、发布人和发布时间；唯一 `(tenant_id, organization_id, version_no)`，发布后只读。M0 的 `review_mode` 只允许 `ALL_MANUAL`；阈值最高只能为 `-1` 分，不能配置 0 导致新钱包首次投递即被锁存；认定上限允许 `1..1000000` 克且新机构默认 `100000` 克（100.00kg），用于防止误输入和金额溢出；M1 以前向迁移增加仅异常人工和 24/48 小时自动通过，不提前创建自动调度字段。 |
| `rec_organization_delivery_config_head` | 以机构为主键、当前配置 ID/版本号、锁版本及更新时间；复合外键保证当前配置属于同机构且版本一致。它是配置发布、投递选项一致读取和开始投递授权共同使用的可锁根，不能用 `MAX(version_no)` 代替；会话内继续投递不再访问该 head。 |
| `rec_organization_order_counter` | 以机构为主键、非负 `last_visibility_sequence_no` 和锁版本；只作为 recycling 模块在订单提交事务内分配机构级可见序号的锁根，不表达订单总数或经营统计。 |
| `rec_delivery_order` | 全局唯一订单号、作用域、机构内严格递增且唯一的提交可见序号、唯一投递 session、唯一设备物理结果、不可变机构用户、部署/投口、设备与投递配置版本、单价、当时袋 ID/袋码、负重量异常阈值、人工认定绝对值上限快照、设备发生/后端接收时间；保存可空的整场首次开门前/最终关门后带符号克值、整场原始净重克、从最终载荷原样固化的 `negative_weight_anomaly`、按 0.01kg 形成的原始业务重量、可空原始金额分及原始计算可靠性。当前投影保存 `PENDING/APPROVED`、当前修订号/修订 ID、可空最终重量/金额和首次通过时间。 |

- `rec_delivery_order` 通过包含 `tenant_id + organization_id + deployment_id + port_id + session_id` 的复合外键引用 `dev_delivery_session`，并以同作用域强关联目标为该 session 的唯一 `dev_physical_result`；分别对 session 和物理结果建立唯一约束，重复 `DELIVERY_COMPLETE` 只能返回原订单。相同稳定事件 ID 但摘要不同仍进入技术隔离，不能更新订单。
- 机构第一次发布投递配置时，锁定机构根并在同一事务创建版本 1、指向它的 config head 以及初值为 0 的 `rec_organization_order_counter`；后续发布先锁 head，校验 `expectedVersion`，插入下一不可变版本并原子切换指针。普通机构目录创建不提前制造 recycling 状态。缺少 head、配置或计数器时投递授权/建单必须失败并告警，不能在设备结果事务中临时创建一半业务初始化状态。
- 订单机构用户固定来自开始授权时的 session，创建后不可补挂或换人。无法验证既有 session、用户、部署和授权摘要的结果进入隔离，不建立无主恢复订单，也不能把当前占位用户或后来扫码用户猜测为来源。
- 单价使用 session 开始授权时冻结的 `DECIMAL(...,4)` 元/kg；袋使用当时当前绑定的 `bag_id + bag_qr_snapshot`。两者不得在结果到达时读取当前配置或当前袋。原始业务重量的绝对值超过 session 冻结认定上限时保留原始克证据，但业务重量标记为 `INVALID`、追加 `RAW_WEIGHT_OUT_OF_RANGE` 系统异常并强制人工修改后通过。原始金额只有在整场原始净重、范围与价格都可靠时才计算，否则为 `NULL`；`0` 不能代替未知金额，越界原值也不能进入待审核返现。
- 原始克值、原始业务重量、原始金额、用户、部署、投口、配置、单价、袋码和发生时间创建后不可修改。订单上的最终重量/金额、审核状态和当前修订指针是受保护投影，只能由 D-017 的审核/纠错事务更新，普通 Mapper 不提供任意更新入口。
- 待审核返现不另存余额：按“`PENDING`、原始金额可靠且大于 0”的已归属 session 订单汇总。负数、零或原始金额未知的订单在审核前均不进入钱包展示；无法归属会话的结果不会创建订单。
- 订单创建事务锁定机构计数器，把 `last_visibility_sequence_no + 1` 同时写入计数器和订单后才提交；同机构并发订单因此按提交串行取得不回退的可见序号。序号不对客户端裸露，也不能被当作经营订单总数。
- **接口设计落实补充（I-024/I-025）**：小程序订单时间线只按当前机构用户过滤；Web 按目标机构和实时能力过滤。首屏读取机构当前可见序号作为“已创建订单候选全集”的水位，后续页只读取不超过该上限的订单，再按“设备发生时间 + 订单稳定业务号”排序；上限、筛选摘要和末项排序键都封装在防篡改游标中。这样迟到结果在翻页期间新建的旧发生时间订单只会出现在刷新后的新水位。`review_status` 和照片完整度属于每页实时重算的可变投影，不承诺跨请求历史快照：并发审核/补传可以使尚未翻到的旧订单进入或退出后续页，但稳定键不能让已返回订单重复。钱包三项查询中的待审核返现必须与本表按上述口径在一个数据库一致快照中计算，不能保存或缓存成另一份钱包余额。

### D-017 投递异常、审核纠错与照片

**已确认：异常和修订只追加；首次审核与不限期纠错使用同一种版本记录，认定结果和钱包差额在一个事务中只生效一次；照片状态独立于订单审核。**

| 表 | P0 核心字段与约束 |
|---|---|
| `rec_delivery_anomaly` | 订单、`category=USER/SYSTEM`、稳定异常码、来源物理结果、发现时间和可空结构化诊断；唯一 `(delivery_order_id, anomaly_code)`，插入后不可修改或删除。M0 唯一用户异常码为 `NEGATIVE_WEIGHT_ANOMALY`；重量缺失/无效、首末重量与设备整场净重矛盾、session 已进入 `RESULT_PENDING_RECOVERY` 后才到达的结果和价格快照缺失使用系统异常码。正常结束后的异步上报即使曾触发投口待处理指针，也不因该指针单独写“延迟结果”异常。照片缺失不写本表。 |
| `rec_delivery_revision` | 全局唯一修订 UUID、订单、单调 `revision_no`、可空前一修订、`INITIAL_REVIEW/CORRECTION`、`ORIGINAL_APPROVED/MODIFIED_APPROVED`、修改前后最终重量和系统计算金额、金额差额、分型操作人、后端操作时间、可空原因及请求摘要；唯一 `(delivery_order_id, revision_no)` 和修订 UUID，前一修订最多产生一个下一版本，插入后不可修改。初审前值为空，后值必须明确；纠错前值必须精确等于订单当前投影。 |
| `rec_delivery_photo` | 订单、四个固定位置之一、可空且一旦出现不可改的 UUIDv4 `photo_uid`、`UPLOAD_PENDING/AVAILABLE/PERMANENTLY_MISSING`、设备回传的 COS URL、可空 SHA-256/大小/拍摄时间、关联时间或缺失原因；唯一 `(delivery_order_id, position)`，非空 `photo_uid` 在投递照片表内唯一。状态只允许 pending 向 available 或永久缺失前进。 |

- 投递审核只有按原数据通过或修改后通过，不存在驳回。零重量不是异常；后端以“整场最终关门后重量－首次开门前重量”得到原始净重，设备自报整场净重仍保留在物理结果中，两者不一致只追加系统异常。订单的 `negative_weight_anomaly` 精确复制最终 `DELIVERY_COMPLETE` 中的设备锁存布尔值；为真时追加唯一 `NEGATIVE_WEIGHT_ANOMALY`。阈值是严格正整数克，默认 500 克。后端不得因整场首末净重达到负阈值而把 `false` 补判为 `true`，因为该字段只表达“至少一个本地轮次达到阈值”。设备不上传哪一轮触发或该轮减少的具体重量，数据库也不新增中间重量列或单独负重量事件。最终仍只按整场净重量认定和结算；负数、零数在审核前不进入待审核返现或钱包。
- **已确认的金额输入边界**：审核/纠错人员只输入 0.01kg 精度的最终重量，系统始终使用本单锁定单价按 `HALF_UP` 自动计算最终金额分；金额字段保存并只读展示，不允许脱离重量与单价独立覆盖。这样“修改最终重量/金额”由一次重量认定和一次确定性金额计算完成；价格快照确实无法恢复时只能将最终重量和金额认定为 `0kg/0分`。若以后要允许人工覆盖金额，必须修订 D-005，并在修订表增加覆盖模式、金额及原因。
- 无论按原数据通过还是修改后通过，最终认定重量都必须满足订单冻结的 `-max_review_abs_weight_g <= final_weight_g <= max_review_abs_weight_g`；越界原始重量不能选择 `ORIGINAL_APPROVED`。人工输入金额计算全程使用精确定点数，并在写入前验证重量、乘积、舍入结果和差额都能安全落入目标整数列；任一越界整体拒绝，不能截断、环绕或部分更新。后续修改机构上限不追溯改变旧订单的初审或不限期纠错边界。
- 初审与每次纠错先锁订单并校验预期修订号，再插入一条修订、更新订单当前投影；有归属用户且本次金额差额非 0 时，同一数据库事务调用 funds 创建以修订 ID 唯一幂等的钱包明细并更新钱包。初审的资金变化从 0 到首次最终金额，纠错只使用新旧最终金额差额；差额为 0 时由修订本身记录“已认定但无钱包变化”，不制造零增量资金明细。订单已提现也不修改既有微信终态。
- 如果该事务使实际可提现余额小于 0，按已冻结架构同时暂停尚未越过微信提交边界的原进行中提现并保持双侧冻结；已经进入微信提交阶段的单据只追加风险标记并等待真实渠道终态，不能本地暂停或伪造结果。后续任意可信正向钱包变动使余额恢复到 `>= 0` 时，同一钱包事务解除原暂停并继续原提现，不创建新单或重复冻结。事务任一步失败则修订、订单投影、钱包和提现联动全部回滚。平台管理员或本机构有审核权限的工作人员均使用分型操作者字段，允许审核自己的业务记录；操作审计另存请求上下文，但不能代替修订事实。
- 订单创建时只为整场四个标准位置各建立一行：首次开门前 `BEFORE_INNER/BEFORE_OUTER`、用户结束或 30 秒超时后的最终关门 `AFTER_INNER/AFTER_OUTER`。会话内中间开关门不创建照片槽，也不上报照片。完成事件已有 URL 就置为 available；设备仍在补传时为 pending；确定没有照片或 72 小时放弃补传时记录永久缺失及原因。后端保存并校验设备回传 URL，不自行推导 COS 对象 key。
- 照片补传按“订单 + 位置”幂等更新；已 available 的同位置收到相同 URL/摘要返回成功，收到冲突对象进入隔离而不覆盖。缺图不创建用户/订单异常，不阻断订单、审核、返现或自动审核扩展。
- **接口设计落实补充（I-044/I-045，2026-07-24 路径修订）**：`AVAILABLE` 必须同时具备 `photo_uid/url/sha256/size_bytes`；`UPLOAD_PENDING` 可以先保留可空照片身份，`PERMANENTLY_MISSING` 必须有稳定缺失原因。URL 只接受配置 COS HTTPS host 及 `ecobin/{deploymentCode}/delivery-session/{sessionUid}/{slot}/{photoUid}.jpg` 精确规范路径，原样保存且不带查询凭证。乱序先到的独立照片事件在原订单尚未建立时保持原 inbox 可重试，不能临时创建空订单或把照片挂到当前用户；订单建立后同一处理器按原 session 和槽位归并。对应可靠事件只有在槽位已关联或永久缺失事实已提交后才取得业务确认。
- **接口设计落实补充（I-024）**：初审请求的 `expectedRevisionNo` 固定为 0，成功建立修订号 1；纠错必须提交当前修订号并只追加下一版本。`ORIGINAL_APPROVED` 不接收最终重量，`MODIFIED_APPROVED` 只接收两位小数的带符号千克值，金额仍由本单锁定价格确定性计算。HTTP 幂等操作号与修订 UUID 各自稳定：同一操作重试返回原修订，两名操作者竞争同一预期版本最多一人成功。`review.execute` 只执行初审，`delivery.correct` 只执行已通过订单纠错，两者不能互相替代。

### D-018 清运操作、记录直接修改、异常与照片

**已确认：清运配置通过当前 head 线性化；清运操作负责开门前准备和失败恢复，清运员完成确认直接形成记录，一次操作最多一条记录；系统缺少旧袋绑定不阻止普通清运。记录允许有权限人员直接修改并留痕，但不审核、不产生通过/驳回决定，也不产生钱包、积分、返现或奖励。**

| 表 | P0 核心字段与约束 |
|---|---|
| `rec_organization_clean_config`（新增） | `id + tenant_id + organization_id + version_no`、清运操作总时限秒数、发布人和发布时间；唯一 `(tenant_id, organization_id, version_no)`，发布后只读。M0 总时限默认 1800 秒；不保存审核模式。 |
| `rec_organization_clean_config_head`（新增） | 以机构为主键，强引用本机构当前 `config_id + version_no`，保存切换时间和锁版本；当前配置版本只能通过发布事务原子切换，清运准备锁 head 后读取，不使用 `MAX(version_no)` 猜当前。 |
| `rec_organization_clean_record_counter`（新增） | 以机构为主键，保存最后一个已提交清运记录可见序号；分配、记录插入和完整清运完成事务共同提交，回滚不消耗序号。 |
| `rec_clean_operation` | 全局唯一 UUID、作用域、部署/投口、清运员机构用户、设备/清运配置版本及时限快照、`old_bag_binding_state=BOUND/MISSING`、按准备时事实锁定且可空的旧袋/袋码、`old_baseline_state=TRUSTED/UNTRUSTED/MISSING` 及可空旧基准快照、可空旧皮重/开门前重量、必填预留新袋/袋码、可空待处理投递 session 快照、状态、固定开始授权到期时间、首次边缘落盘、首次可能成功通电解锁、电磁阀断电、清运员人工确认完成、当前执行期限、解锁前结束请求、待受理恢复请求、重开与恢复次数、结束时间/原因和锁版本。`CHECK` 保证 `BOUND` 时旧袋必填、`MISSING` 时旧袋为空；旧基准只有在绑定存在且基准袋与旧袋一致时才可标记 `TRUSTED`。状态闭集为 `PREPARED/EDGE_SAVED/IN_PROGRESS/RECOVERY_REQUIRED/PRE_UNLOCK_ENDED/COMPLETED`；只有能证明命令从未进入可能通电边界时才可进入 `PRE_UNLOCK_ENDED`，越过该边界后的超时或重启只能进入非终态 `RECOVERY_REQUIRED` 并沿原操作恢复。 |
| `rec_clean_record` | 唯一清运记录号、机构内唯一提交可见序号、唯一操作、唯一设备物理结果、作用域/配置/清运员快照、旧袋绑定/旧基准状态、可空旧袋 ID/二维码快照、必填新袋 ID/二维码快照；开门前重量、旧皮重、设备报告净重、后端复算净重以及关门后最终稳定总重量（候选新皮重）均保存为不可覆盖的可空带符号克值，并分别保存来源可靠性，缺失/无效时禁止用 `0` 代替。另保存可空 `effective_removed_net_weight_g`、当前有效重量来源 `DEVICE_RECALCULATED/MANUAL_SET/MANUAL_CLEARED`、可空记录备注、`NORMAL/SYSTEM_ANOMALY`、完成时间、修改版本和更新时间；不保存审核状态、审核指针或审核决定。初建时只有可靠且关系一致的后端复算值成为当前有效重量，否则为空。 |
| `rec_clean_record_change`（V19 新增） | 全局唯一 `change_uid`、作用域和清运记录、记录版本从 `from_version` 到 `to_version`、修改前后当前有效重量/来源/备注、必填修改原因、分型平台管理员或工作人员操作者、修改时间、UUIDv4 幂等键和规范请求摘要；唯一 `(clean_record_id, to_version)` 与作用域内幂等身份，插入后只读。它只证明谁直接修改了什么，不保存待审、通过、驳回或审核意见。 |

| `rec_fullness_sample` | 检测、`INITIAL/CONFIRMATION/MANUAL_RECHECK`、唯一设备物理结果、红外状态/遮挡值、称重状态/可空带符号稳定总重量、可空基准/阈值、可空带符号原始净重量、可空满溢度、红外/重量分别判满结果、综合 `NOT_FULL/FULL/SOURCE_FAILED`、可空原因 `INFRARED/WEIGHT/BOTH`、设备发生及后端接收时间；`INFRARED_ONLY` 不得因缺少重量或基准伪造零值；唯一 `(detection_id, sample_role)`，插入后只读。 |
| `rec_fullness_event` | 全局唯一事件 UUID、作用域/投口、`ACTIVE/RECOVERED`、首次发现检测/时间、确认检测/时间及确认快照、当前原因、最近检测/最近满溢检测、检测次数、恢复检测/时间；active-slot 保证每个投口最多一条持续满溢事件。 |

- 自动检测只由整场投递最终 `DELIVERY_COMPLETE` 或清运完成触发：订单/清运记录与唯一检测在同一事务创建；存在可贡献真实结论的来源时再共同创建可靠设备任务。投递 session 的本地中间关门不会创建检测、采样或 gate，中间重量/红外也不上云，因而中间过程既不结束本 session，也不参与判断用户能否继续投递；最终检测只影响后续新作业。`WEIGHT_ONLY` 清运后新基准无效时直接以 `WEIGHT_BASELINE_UNAVAILABLE/SOURCE_FAILED` 收敛失败 gate；`INFRARED_OR_WEIGHT` 仍采集红外，红外可靠判满可以进入正常疑似/确认复检链，红外不满或失败则因重量来源不可用进入 `SOURCE_FAILED`。其余自动初检可靠不满即结束；初检为满进入疑似并等待配置间隔，确认复检仍满才创建/延续事件，复检不满则取消疑似且不创建事件。人工重新检测按已确认需求只采样一次，可靠不满即可恢复事件，不在后台持续轮询。
- `FAILED` 通常必须强回指产生失败结论的终态 sample；唯一例外是创建事务已经能从权威新基准状态确定的 `WEIGHT_BASELINE_UNAVAILABLE`，此时不下发采样命令，初始/终态 sample 均为空且失败码必须精确匹配。不能把任意技术异常借该例外闭合为无证据失败。
- 普通 `MANUAL_RECHECK` 在存在非空投递结果待处理指针、未终结检测或活动基准重测时拒绝；I-030 的专门恢复事务必须先为当前袋/基准/规则建立新的 `MANUAL_RECHECK` 和容量 `PENDING` gate，再条件清除精确匹配指针。若重量模式需要的基准同时无效，只能先完成真实清运换袋，不能在内容物未知时重置基准或强清指针。
- 判断模式冻结为 `INFRARED_ONLY/WEIGHT_ONLY/INFRARED_OR_WEIGHT`。任一参与来源可靠判满即可判满；所需来源全部可靠且均不满才判不满；没有来源判满但任一所需来源失败（包括清运后新基准无效）时为 `SOURCE_FAILED` 并阻断投递。设备已经上报但不属于当前模式的传感器值仍保存用于诊断，不参与本次业务结论，其硬件健康可由 device 独立阻断。
- 原始净重量等于稳定总重量减有效基准，允许为负；展示满溢度使用 `max(raw_net_g, 0) / threshold_g * 100`，精确到两位且不限制 100%。重量、基准或阈值不可用时满溢度为 `NULL`，不能显示 0%。红外只参与判断，不参与百分比。
- 每次检测终结时先锁容量状态，并核对当前袋绑定、按模式可空的当前基准 ID、满溢规则指纹和 `capacity.current_detection_id` 均与检测快照一致。全部一致才以 `APPLIED` 在同一事务写入最终 sample/detection、更新容量，并创建、延续或恢复当前 `rec_fullness_event`；`INFRARED_ONLY` 下“两侧基准均为空”是合法一致，不得因此把可靠红外结论判为陈旧。任一实际不一致则以 `STALE_IGNORED` 保存样本和检测历史，但不能覆盖当前容量或事件。满溢模式或阈值变更使旧 `READY` 结论失效并阻断投递，须由后台显式发起一次新的人工重检；仅展示名称等不改变规则指纹的配置修改不使结论失效。
- 重复仍满只更新事件当前原因、最近检测和次数；原因历史由 detection/sample 还原，不另建重复告警。检测失败时已有满溢事件保持 active，没有事件时容量进入 failed；只有适用于当前袋、基准和规则的可靠不满结果可以恢复。`COMPLETED/FAILED` 都是不可回退终态；终态后到达的物理结果只保留在 `dev_physical_result` 作为迟到设备证据，不再补写样本、推进原检测或改变容量/事件，需要重新判断时新建 `MANUAL_RECHECK`。
- 24/48 小时从首次确认满溢时间计算，重复检测、原因变化和告警已查看都不重置。M0 只保存足以计算的时间和事件；通知升级属于 M1 的 `ops_alert` 能力，不在本批增加重复计时字段。
- `dev_physical_result` 拥有原始规范化传感器证据，`dev_port_runtime_state` 拥有硬件健康，`dev_port_config_snapshot` 拥有配置，recycling 拥有检测判断和容量事实，`ops_alert` 只拥有展示/通知/已查看投影；任一层都不能替代另一层解除满溢。
- **接口设计落实补充（I-029/I-030）**：袋历史、关联清运记录和关联投递订单使用独立游标，不在 SQL 中拼成一条伪全局时间线。容量、检测、事件和基准重测均使用公开 UID/版本；工作人员小程序只读取当前机构安全摘要。严重安全锁恢复由 device 的故障事件和运行投影拥有，recycling 端点只能通过真实检测/重测推进本域 gate，不能替 device 直接写健康。
