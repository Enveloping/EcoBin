## 12. 第八批已确认：跨聚合事务、全局锁序与并发恢复验收

### D-036 事务协调器、隔离级别与重试纪律

**已确认：P0 所有中心侧写用例显式使用 MySQL `READ COMMITTED`；一个业务命令只有一个最外层事务协调器，正确性依靠永久锁根、显式行锁、条件更新、唯一约束和稳定幂等身份，不依赖可重复读快照或缺失行间隙锁。**

1. 所有业务模块共享同一个 DataSource 和事务管理器。主用例的 public 应用服务开启最外层事务，跨模块只能通过公开领域端口加入同一个 Spring `REQUIRED` 事务；各模块仍只写自己拥有的表。
2. 禁止跨模块直接调用 Mapper/Entity、在强一致主链中异步拆事务、通过 `REQUIRES_NEW` 提前提交原子结果的一部分，或先修改投影再另行补写流水、审计和可靠任务。业务事务彻底结束以后，为记录一次已经失败的技术尝试而开启的新短事务不属于提前提交，具体边界见 D-039。
3. 事务开始前允许普通读取不可变关联来解析后续锁根，例如由转账单解析钱包和提现单 ID；所有决定业务结果的状态、作用域、版本、余额、占位和闸门都必须在事务中按 D-037/D-038 的顺序加锁后重新读取并校验，不能使用事务外快照作最终决定。
4. 先锁永久存在的聚合根和全部可变父行，再插入修订、明细、事件、占位、审计或可靠任务。同类多行统一按数据库主键升序取得锁；业务键用于定位和幂等，不另造一套不稳定排序。
5. 在 `READ COMMITTED` 下，`SELECT ... FOR UPDATE` 未查到一行不能被当作可靠的“空槽锁”。整机占位由设备资产行保护，袋占位由投口和袋行保护，活动提现由钱包行保护，微信转账单缺失由提现单保护；先锁永久父行、再检查和插入槽位，唯一约束只作为并发兜底。
6. `FOR UPDATE SKIP LOCKED` 仅用于 D-027 的可靠任务领取，不能用来跳过钱包、机构账户、设备作业、容量或业务状态冲突。
7. OneNet、微信、COS、MQ ACK 等外部业务动作永远发生在本地事务提交后。事务只固化不可变请求、稳定外部 ID、调用边界和唯一可靠任务；提交后的内存通知只降低延迟，数据库任务才是重启恢复真相。I-012 的 AppSecret 已改为本地 IAM 表字段，和 AppID、版本在一个短事务中提交，不再存在先写外部秘密设施的存储例外；渠道和设备动作仍不得借用本地配置写入绕过可靠任务。
8. MySQL `1213` 死锁和 `1205` 锁等待超时都按整个本地事务失败处理。应用必须明确回滚整个事务，以同一个 `operation_uid`、业务 UUID、任务键及外部单号最多重试 3 次，并加入短随机退避；禁止在 Mapper 内只重试失败 SQL。超过次数后，同步请求返回可重试错误，后台任务按原任务退避并形成可观测失败。
9. 若 `1205` 所在 MySQL 配置只回滚当前语句，应用仍必须把当前 Spring 事务标记为 rollback-only，不能在已经执行了一部分写入的事务上继续运行。
10. 一旦已经记录“外部调用可能开始”，不得用普通业务命令重放外部动作；只能由原可靠任务使用原设备命令 ID、`out_trade_no` 或 `out_bill_no` 查单、收敛或幂等续办。

I-040 引入一个不改变上述写入纪律的窄例外：最小运营概览的最外层协调器显式开启只读 `REPEATABLE READ` 事务，首次一致性读建立快照，各模块公开查询端口以 `REQUIRED` 加入同一事务。该事务严禁写入、`SELECT ... FOR UPDATE`、外部调用或复用到业务命令；所有中心侧写用例继续使用 `READ COMMITTED`。

### D-037 设备作业、投递、清运与容量事务

**已确认：凡事务会取得、释放或恢复整机执行权，物理设备资产都是设备域支配性锁根；所有路径使用同一方向，满溢结果固定先锁容量再锁检测。投递和清运新作业分别具有“租户 → 机构 → 当前机构小程序 → 对应配置 head → 机构用户 → 钱包或清运能力”的跨域前缀，但取得设备资产锁后不得反向申请任一前缀。**

涉及的节点允许按用例跳过，但不得反向：

```text
dev_device_asset
→ dev_asset_active_deployment（涉及当前部署时）
→ dev_device_deployment
→ dev_deployment_runtime_state
→ 已存在的 dev_delivery_session，或 rec_clean_operation
→ 已存在的 dev_device_occupancy
→ dev_port（多个投口按 id 升序）
→ dev_port_runtime_state（按对应投口 id 升序）
→ rec_bag（所有涉及袋按 id 升序）
→ rec_bag_current_occupancy
→ rec_port_capacity_state
→ rec_port_baseline_measurement（存在或新建时）
→ rec_fullness_detection
→ rec_fullness_event
→ 不可变领域事实 / dev_device_command / 已存在的 dev_edge_event
→ operations 支撑记录
```

- I-017 的受控直接部署先锁定 `dev_device_asset`，再检查当前部署槽缺失，并在同一事务建立 `COMMISSIONING` 部署、当前部署槽、全部投口、初始运行投影、资产 `IN_USE` 状态和审计。任何一步失败都整体回滚；相同资产的并发部署由资产锁串行化，当前槽唯一约束只作兜底，不能留下半套部署。
- 新作业尚无 session、operation 或 occupancy 行时，先锁设备资产及相关永久父行，确认当前槽位缺失并完成开门资格校验，再创建作业根和整机占位；不能试图“锁住不存在的占位行”。
- 新投递除了检查整机占位，还必须在同一设备锁序内锁定并检查所选投口是否存在未终结 `rec_clean_operation`、未终结 `rec_port_baseline_measurement` 或非空 `pending_delivery_result_session_id`。`RECOVERY_REQUIRED` 清运、活动基准重测和投递结果待处理都可以没有整机占位，但仍阻断原投口；该投口不得建立投递会话，其他投口是否可用继续由整机安全、占位和各自投口条件共同决定。
- 只做初始装袋等不涉及整机执行权的操作，可以从“投口 → 全部相关袋按 ID 升序 → 袋占位 → 容量”开始。D-019 的“旧袋和新袋”在实现层统一细化为所有涉及袋按主键升序，不能按业务角色先旧后新，否则两个投口交叉扫描对方袋码时会形成反向锁。
- 只有“开始投递”是中心复合授权事务。recycling 应用用例开启事务，并通过 identity、funds、device 各自的公开参与端口逐段取得所属模块的锁；各端口只操作本模块表并加入同一事务。进入设备锁序前，固定按 `iam_tenant → iam_organization → iam_organization_miniapp → rec_organization_delivery_config_head → iam_organization_user → fund_user_wallet` 取得并持有跨域锁，再进入 `dev_device_asset` 及其下游。这里 identity 的锁被 recycling 配置 head 分为前后两段，不能误写成按模块一次性锁完 identity，也不得由 device 反向调用 recycling 或 funds。device 仍唯一拥有并写入 session、occupancy、device command 和 physical fact。锁内复核全部资格并冻结配置版本/摘要、单价、袋、负余额开门阈值、认定上限、正整数负重量异常阈值及 30 秒本地结束等待；随后共同建立唯一 session、整机占位、以 `session_uid` 为目标的开始命令和可靠任务。任一步失败均不得留下活动 session、占位或可执行意图。
- 禁用、配置发布或钱包闸变更与开始授权共享上述锁前缀，以提交顺序形成唯一线性化边界：变化先提交时新 session 必须看见并拒绝；授权先提交时该 session 已经是使用冻结快照的在途作业。中心不再有阶段 B、周期授权或继续授权，因此这些后续变化只阻止下一次新 session，不能介入当前 session 内的本地继续动作。取得配置 head、用户/钱包或 device asset 后禁止反向申请任何更早前缀。
- 香橙派可靠保存 session 和冻结配置后，在首次开门前保存第一次稳定重量和开门前内外照片。此后每个中间开关门、重量、照片及“继续”选择只在边缘本地发生；不建云端周期、事件、物理结果、pending 或解析任务，也不因前一轮重量、红外、满溢、订单确认或中心资格变化重新授权。每次关门后本地等待最多 30 秒；用户结束或等待超时后，以最后一次关门稳定重量和最终关门内外照片保存唯一 `DELIVERY_COMPLETE`。硬件安全故障仍可在本地阻止动作，但不能被编码为另一轮中心业务授权。
- 开始授权到期和中心结果恢复超时统一按 `asset → session → occupancy → port runtime` 收敛。能证明命令从未外调或可信 `PRE_OPEN_FAILED` 从未开门时，可把 session 推进 `PRE_OPEN_ENDED` 并释放占位而不写待处理指针；只要已有设备受理或更后物理进展、最终业务结果尚未共同成立，结果期限届满就把 session 推进 `RESULT_PENDING_RECOVERY`。释放 DELIVERY 占位前必须先条件写入 `pending_delivery_result_session_id`；投递门或旧授权仍不明确时继续保留占位/安全锁。后到结果始终只归并原 session，不能挂到后来用户或创建第二个作业。
- 最终 `DELIVERY_COMPLETE` 按资产锁根进入原 session，锁定收件事务已经建立的 `dev_edge_event`，幂等保存该 session 唯一 `dev_physical_result`，并在创建订单前锁定本机构 `rec_organization_order_counter` 分配唯一提交可见序号；随后在一个事务中形成唯一订单、四个最终照片槽、负重量与其他异常、唯一投递后满溢检测 gate 及需要的可靠任务，推进 session 为 `BUSINESS_CONFIRMED`，把对应 inbox 标为已处理，并创建唯一 `CONFIRM_EDGE_EVENT:<event_uid>` 任务及不可变确认快照。`negativeWeightAnomaly` 是该最终载荷内的布尔值，不是独立事件；recycling 原样固化它，不得用整场首末净重补判。整场首末净重仍单独用于结算和重量一致性校验，但不改变该本地轮次标志。
- 若 session 正是投口运行态锁存的待处理 session，只有订单和最终满溢 gate 都成立后才在同一事务清除匹配指针；检测 gate 随后阻断下一次新 session 直至可靠闭合。指针不匹配、结果不能建单或任一步失败都不得被其他 session 清除；若指针已由后续独立人工安全恢复清除，迟到结果仍可形成原订单，但容量派生必须服从 D-020 的代际/过期规则。同机构其他设备的完成事务只能按相同“asset → 机构订单计数器”方向取得锁，禁止从计数器反向取得设备锁。失败时全部回滚，设备继续使用原 session 和事件 ID 重投；OneNet/MQ ACK 或确认发送 attempt 都不能补交缺失的业务事务。
- 清运准备在进入设备锁序前按 `iam_tenant → iam_organization → iam_organization_miniapp → rec_organization_clean_config_head → iam_organization_user → iam_organization_user_capability` 取得并持有跨域前缀，再按同一资产锁根依次锁定投口、全部相关既有袋（按 ID 升序）、袋占位和容量，并确认当前没有未终结满溢检测或基准重测；清运不取消或改写它们。全平台新袋码的首次插入由 binary 唯一键线性化，冲突方整体回滚。随后共同建立清运操作、旧袋/旧基准及可空投递待处理 session 快照、新袋预留、整机占位、固定 60 秒开始授权、设备命令和可靠任务；操作的开门前重量保持空，必须由香橙派可靠保存上下文后从 MCU 取得本次现场稳定值再补入。旧袋缺失继续沿 D-018 已确认的降级路径，不能临时伪造旧袋。禁用/能力撤销/配置发布共享相同身份前缀，先提交者决定新操作是否成立。
- 解锁前结束、开始授权过期、第一次可能成功给电磁阀通电和设备拒绝在同一 `asset → operation → command` 锁序竞争。清运门无门磁，只有任务从未外调或设备可信证明通电命令未执行且无在途动作时，才能共同推进 `PRE_UNLOCK_ENDED`、释放新袋预留和整机占位。命令一旦可能已成功通电即越过不可逆边界，普通取消永远失败；不能等待“实际开门”观察来回退。`SAFE_CLOSE` 不适用于清运门。
- 清运恢复、超时、操作内再次通电和完成同样先锁资产，不能采用“新清运先 asset、恢复或完成先 operation”的反向顺序。越过可能解锁边界后的超时或任一端重启只能进入/保留 `RECOVERY_REQUIRED`，不能自动完成。电磁阀断电只证明停止解锁，物理门位仍为 `UNKNOWN`；没有原清运员现场关门确认时继续保持整机保护。只有断电且已经现场确认门扇关闭、但最终结果仍待恢复时，才可释放整机占位并保留活动投口槽和袋预留。通电或状态未知时同样保持整机保护。原清运员恢复沿用原操作并按需要重新取得整机占位。完成事务除锁定原事件和唯一物理结果外，还必须验证电磁阀已断电及清运员人工关门/完成确认，然后分配清运记录序号、创建记录、交换袋、建立/清空新基准、更新容量、创建满溢 gate/任务、结束操作并共同提交 inbox 与确认任务；不得由断电、超时或 `SAFE_CLOSE` 自动触发完成。
- 清运完成若携带的操作快照指向仍匹配的 `pending_delivery_result_session_id`，只能在新袋绑定和 `CLEAN_COMPLETE` 检测 gate 已同时成立后条件清除；迟到投递完成先接管时清运事务按当前空指针继续，清运先接管时迟到投递容量派生按旧袋代际保存为过期。解锁前结束、未完成或超时恢复态都不得清该指针。
- 满溢归并固定为：

```text
rec_port_capacity_state
→ rec_fullness_detection
→ sample / rec_fullness_event
```

  锁内容量快照、当前袋、基准和规则全部匹配才更新当前投影；换袋、基准或规则已经变化时只保存 `STALE_IGNORED` 历史，绝不能覆盖新事实。取得容量锁以后不得反向申请部署、投口或袋锁。

- 普通人工满溢重检在资产/投口/容量锁下要求无作业、无未终结清运、门安全、没有活动检测、活动基准重测和投递待处理 session 指针，随后共同创建唯一 `MANUAL_RECHECK`、容量 `PENDING` gate 和可靠任务。专门的投递结果安全恢复则精确锁定运行态指针和容量，确认没有可直接重试的可信完成结果后，必须先创建同一新 gate，再条件清除匹配指针；事务顺序禁止出现既无指针又无 gate 的空窗。
- 空袋基准重测按资产/投口/容量锁序创建唯一 `rec_port_baseline_measurement` 和设备任务；活动 measurement 自身阻断新作业，不改容量当前检测指针。结果事务只在袋、配置、容量代际及当前 measurement 全部匹配时创建 `MANUAL_REMEASUREMENT` 基准，并在同一事务创建后续 `MANUAL_RECHECK` gate；失败保持原阻断，代际变化保存 `STALE_IGNORED`。有投递待处理且内容物未知时禁止基准重测，需先真实清运换袋。
- 严重安全恢复由 device 事务锁资产/runtime/精确 `dev_device_fault_event`；只有没有仍执行物理动作的命令、旧命令不会执行、新鲜设备健康证据晚于故障最后发现且人工现场确认同时成立时，才恢复该故障并条件清对应锁。具备门磁的投递门还要求可靠门关；清运门只校验电磁阀断电与独立人工关门确认并显式保留物理门位 `UNKNOWN`，不能伪造门磁或调用 `SAFE_CLOSE`。因该故障安全停住的原作业/占位可以保留，恢复事务只在提交后唤醒其协调任务；它不在持有 runtime 锁时反向申请 recycling 容量锁，也不顺带修改任何容量、订单、占位或作业事实。

### D-038 投递修订、充值与提现资金事务矩阵

**已确认：D-025 的资金域局部顺序不重开，并精确冻结为“活动槽位在提现单之前”；所有入口即使从渠道单或提现单开始定位，也必须先普通读取不可变关联，再从正确锁根重新进入。**

创建充值、发布提现配置、创建提现和提交微信在进入下述资金锁根前，按用例取得 `iam_tenant → iam_organization → iam_organization_miniapp → iam_organization_user（涉及收款用户时）` 的身份前缀并复核当前有效性；商户绑定验证/禁用至少锁到对应机构小程序。身份禁用与新资金意图以提交顺序线性化：禁用先提交则不得新建充值/提现或提交微信，资金意图先提交则已经越过的真实渠道事实仍继续收敛。取得任何资金锁后禁止反向申请该身份前缀。

```text
fund_payout_gate（仅涉及创建、提交或 NOT_ENOUGH 时）
→ fund_organization_withdraw_config_head（仅发布或创建提现时）
→ fund_miniapp_merchant_binding（仅涉及渠道就绪时）
→ fund_user_wallet
→ fund_organization_wallet_entry_counter（仅产生用户钱包明细时）
→ fund_active_withdrawal
→ fund_withdrawal_order
→ fund_organization_payout_account
→ fund_wechat_transfer
→ 资金明细 / 渠道观察 / 闸门事件
→ 审计、告警与可靠任务
```

允许跳过不涉及的节点，但不得反向：

| 用例 | 锁序与同一事务结果 |
|---|---|
| 投递初审/纠错 | 外层 recycling 协调器先锁 `rec_organization_delivery_config_head` 取得资金变动线性化时的当前停投阈值，再锁 `rec_delivery_order` 并计算确定性差额；差额非 0 时按 `wallet → organization wallet-entry counter → active withdrawal → withdrawal order` 进入资金链，把当前阈值作为受信参数传给 funds，分配钱包内及机构可见序号、追加唯一钱包明细、更新余额，并在新余额达到该当前阈值时锁存 `MANUAL_RECOVERY_REQUIRED` 及阈值快照，同时完成负余额提现暂停/风险或恢复联动。订单冻结阈值只保留历史解释，不参与本次锁存判定；funds 无需也不得反向读取 recycling。普通正向明细不能清除已经锁存的停投闸。差额为 0 时只追加修订和更新订单当前认定，不取得资金锁、不消耗任一序号、不制造资金明细。已经锁住钱包后不得再取得平台闸门或配置 head。 |
| 创建提现 | `gate → withdrawal config head → miniapp-merchant binding → wallet → organization wallet-entry counter → organization account`；锁 head 后固化当前配置并复核渠道就绪，钱包锁保护活动槽缺失，同一事务创建提现单、活动槽和双方 `FREEZE` 明细并更新双方投影。若外键要求先插入提现单再插入槽位，这是钱包根保护下的合法构造顺序，不允许其他路径绕过“已有槽位先于提现单”的读取锁序。 |
| 审核或渠道前终止 | 先普通读取不可变钱包/账户 ID，再按 `wallet → organization wallet-entry counter（仅释放时） → active slot → withdrawal order → organization account` 加锁。审核通过不产生钱包明细，因此跳过计数器，只追加决定、推进 `READY_TO_SUBMIT` 并建立唯一任务；驳回和严格渠道前终止原子分配序号、释放双方冻结并删除槽位。新流程不提供用户取消。 |
| 提交微信 | `gate → miniapp-merchant binding → wallet → active slot → withdrawal order → organization account → transfer`；该步不产生钱包明细，跳过配置 head 和机构钱包计数器，使用提现既有快照并复核当前渠道关系；短事务只固化唯一 `out_bill_no`、请求快照和不可本地取消的渠道边界，提交后才调用微信。 |
| 微信终态归并 | 普通读取转账单的不可变关联后，从 `wallet → organization wallet-entry counter` 开始按主链加锁；同一事务追加观察、更新渠道投影、写双方唯一 `FINAL` 明细、更新账户投影、推进提现终态并删除活动槽。 |
| `NOT_ENOUGH` | 必须先锁 gate，再按完整主链归并当前观察和暂停事件；不释放当前或其他提现的任何冻结，不修改其他机构账本。 |
| 充值成功第一段 | `recharge order → wechat payment`；保存可信支付观察、推进 `PAID_PENDING_POST` 并建立唯一净额入账任务，不修改机构额度。 |
| 充值净额入账第二段 | `recharge order → wechat payment → organization account`；复核成功事实和唯一明细缺失，追加 `RECHARGE_POSTED`、增加净额投影并推进 `POSTED`。 |

- 平台出款闸门暂停与 D-024 的负余额暂停是两种不同条件：负余额暂停期间仍禁止审核通过；平台闸门暂停时拒绝创建新手动提现，也禁止任何尚未提交的提现调用微信，但暂停前已经存在且没有负余额暂停的 `PENDING_REVIEW` 提现仍可审核通过并进入 `READY_TO_SUBMIT`，可靠任务等待闸门恢复后再提交。审核驳回照常允许；用户端没有取消能力。
- 任意余额恢复事务已经取得钱包锁时，只解除原负余额暂停，并在最后经 operations 公开端口精确锁定本提现的提交任务；空闲任务推进运行时间和唤醒版本，租约中任务只推进唤醒版本，其他派发等待保持原原因，阻断/终态任务保持原状态。funds 不得直接更新可靠任务表，也不能反向取得 gate；后续提交执行器必须重新从 gate 开始完整复核。
- 人工钱包调整由外层受控协调用例按 `rec_organization_delivery_config_head → wallet → organization wallet-entry counter → active withdrawal → withdrawal order` 进入；先取得当前阈值受信快照，再调用 funds 原子调整。这样遵守 Maven 依赖方向，funds 不反向读取 recycling，且调整恢复后下一次投递仍会按新 head 再检查。
- 提现配置发布只锁 `fund_organization_withdraw_config_head` 及新版本；创建提现从 gate 进入后锁同一 head，再进入钱包主链。提交微信使用提现已经固化的配置和收款快照，不反向读取或锁当前配置 head。配置发布与提现创建以 head 的提交顺序决定新单使用哪个版本，既有提现不受影响。
- 充值创建先锁 `fund_miniapp_merchant_binding` 再建立充值/支付请求；绑定验证或禁用也从该行线性化。禁用先提交时新充值和新转账提交失败；已经可靠越过外部调用边界的原支付/转账继续按原身份归并，禁用不能把真实成功改写为失败。下单是否可能外调不明的既有充值继续原单查单，只有证明从未外调时才允许本地关闭。
- 审核、严格渠道前终止、提交和渠道终态并发时，先按统一锁序取得根并满足条件者生效；后来者返回已存在结果或明确状态冲突，不能覆盖先发生的决定。
- 禁止单侧冻结、单侧释放、单侧结算，以及对账发现缺一侧后只补另一侧；禁止修改提现金额、换 `out_bill_no`、把 API 错误码当微信终态，或在资金事务中调用微信。

### D-039 inbox 与可靠任务的分段执行和崩溃恢复

**已确认：可信收件、任务领取、领域处理、外部调用和结果归并是五个明确阶段；任务租约只授予当前执行权，不能证明业务或外部动作尚未发生。**

1. **收件事务**：完成来源认证、验签/解密和基本格式校验后，插入或命中唯一 inbox，并确保唯一 `PROCESS_INBOX` 任务同时存在；合法 OneNet 事件还必须在同一事务插入或命中唯一 `dev_edge_event`，用 `eventUid` 作为外部身份并用 `(deployment_id, edge_event_sequence)` 做跨类型冲突约束。事务提交后才 ACK OneNet 或微信。相同稳定身份但摘要冲突、同部署序号复用或同一 inbox 形成第二事件头进入隔离，不能覆盖原证据。
2. **领取事务**：只锁 `ops_reliable_task`，设置新租约并插入唯一 attempt，立即提交。该短事务可以使用 `SKIP LOCKED`，但提交后不能继续持有 task 锁申请任何领域锁。
3. **业务处理事务**：解析和不影响决策的准备可以在事务外完成；进入事务后按 D-037/D-038 从领域锁根开始，锁定原公共事件头，写唯一强类型子事实、业务事实、投影及派生任务，最后条件更新 inbox、当前 attempt 和 task。对 `RELIABLE_FACT`，业务事实、`PROCESSED`、本次成功结果和唯一业务确认任务必须共同提交；照片/满溢等事件只等待本事件直接目标事实，不等待后续人工审核或另一个异步业务终态。
4. **外部调用**：执行器先用一个只涉及任务/尝试及不可变请求的短事务，一次性记录 `external_call_may_have_started_at`，提交后才调用外部系统。该技术尝试标记不替代 D-037/D-038 的领域前置事务；例如微信提交必须已经按完整资金锁序创建唯一转账单、固化请求并把提现推进到渠道边界。
5. **结果归并事务**：外部响应、回调、查单或设备迟到事件先按领域锁序进入同一个幂等归并器，保存真实观察并收敛领域状态，最后再条件更新 attempt/task；禁止先锁 task 后反向申请钱包、账户、设备或容量锁。

崩溃和失败统一按以下边界恢复：

- inbox 已提交但 ACK 前崩溃：来源重投命中原 inbox 和原任务，提交事实存在后可以 ACK。
- 领取后、处理前崩溃：租约到期后新 worker 接管；原 attempt 不被伪造成失败。
- “可能调用”提交后崩溃：只允许使用原稳定外部 ID 查单或幂等续办。
- 外部响应返回但结果事务提交前崩溃：后续回调、查询或原任务重试再次进入同一归并器。
- 旧 worker 在租约被接管后迟到：仍可一次性保存自己的真实技术结果并调用幂等领域归并器，但不能覆盖新租约决定；可信新证据按 D-027 的 wake-version 规则触发复检。
- 业务处理抛错时，所有业务变化、`PROCESSED` 和成功结果一起回滚。最外层业务事务结束以后，执行器再开启一个仅操作 task/attempt 的短事务记录技术失败和退避；该记录不能伪造业务异常或领域终态。
- 自动重试耗尽时，只把原任务置为 `BLOCKED` 并产生聚合告警；`PROCESS_INBOX` 对应 inbox 保持 `RECEIVED`。人工恢复必须复用原任务、原业务身份和原外部单号，不能创建第二条可执行真相，也不能顺带把订单或提现改成失败。
- I-036 的平台恢复事务锁定原任务并校验 `expectedVersion`、`BLOCKED`、无有效租约和原因排除确认；只递增 `wake_version`、恢复为可立即领取的 `PENDING` 并写审计，任务稳定身份和领域事实都不变。隔离确认是另一条仅更新 `OPEN -> ACKNOWLEDGED` 的条件事务，不创建或唤醒任务。
- I-019/I-020 的配置下发遵守同一边界：技术重试耗尽只阻断原可靠任务，配置应用保留最后一条可信设备状态。只有设备明确 NACK、边缘持久化失败或 MCU 同步失败才允许应用进入 `FAILED`；发布更高期望版本只使旧应用派生为非当前，并把仍可执行的旧 `PENDING/BLOCKED` 任务安全取消，已有任务终态不回退，不能伪造设备失败。重同步只能唤醒当前最高版本的原任务并复用原应用/命令身份。
- I-041～I-045 的业务确认遵守同一分段：业务事务提交后 `CONFIRM_EDGE_EVENT` 可以任意重试但始终复用原确认身份；OneNet `code=0` 不结束任务。可信 `BUSINESS_CONFIRMATION_RECEIPT` 作为新的 inbox/公共事件头进入处理器，锁定原确认任务并证明设备已持久化后才把它置为 `DONE`；该回执处理只标记自身 inbox `PROCESSED`，不得再创建确认任务。重复确认/回执幂等命中，确认任务与回执之间不形成无限循环。

### D-040 真实 MySQL 并发与故障恢复验收门槛

**已确认：数据库设计只有在目标 MySQL 8 小版本、写用例显式 `READ COMMITTED`、I-040 只读概览显式 `REPEATABLE READ`，并使用独立物理连接通过确定性交错、崩溃注入与不变量查询后才算可实施；H2 结果不能替代。**

测试必须用屏障/锁点精确控制交错，不能依赖 `sleep` 碰运气。最低验收矩阵如下：

| # | 并发或崩溃场景 | 唯一可接受结果 |
|---|---|---|
| 1 | 同一资产同时发起投递与清运，包括选择不同投口 | 只有一方取得整机占位并产生命令/任务；失败方没有残留会话、清运操作或袋预留。 |
| 2 | 同一投口两次清运准备，两个投口扫描同一新袋，或交叉扫描对方旧袋 | 最多一个合法作业和一个袋预留；另一方明确冲突，无孤儿占位，袋按 ID 排序后不得形成不可恢复死锁。 |
| 3 | 同一投递完成或清运完成事件并发重投，并分别在提交前、提交后崩溃 | 业务事实、订单/清运记录、袋交换、基准、容量、检测和任务各最多一次；提交前全部回滚，提交后重试为幂等 no-op。 |
| 4 | 旧满溢检测与换袋、基准变化或规则变化并发 | 旧检测要么先应用后被新状态取代，要么保存为 `STALE_IGNORED`；绝不能覆盖新袋、新基准、新规则或新检测。 |

| 10 | 微信 `SUCCESS` 与 `FAIL/CANCELLED`，或提交、回调、查单、对账乱序竞争 | 第一个可信终态最多结算一次，只产生一对双方 `FINAL` 和一次槽位删除；相反证据只建立冲突 issue，不覆盖或再次调账。 |
| 11 | `NOT_ENOUGH` 与真实终态、人工恢复、新提现或新提交竞争 | 每段资金不足期只有一个暂停事件；暂停期间无新提现和新提交，原单仍按真实终态结算；恢复只产生一个恢复事件并复用原 `out_bill_no`。 |

| 13 | 任务租约过期接管、旧 worker 迟到，以及“可能调用”前后崩溃 | 一个任务、多个唯一 attempt、一个稳定外部 ID；旧 worker 不覆盖新租约，迟到证据进入领域归并和 wake-version 复检，业务效果最多一次。 |
| 14 | 人工制造 `1213/1205` 并在每个关键写点注入回滚 | 最多整体成功一次且稳定业务/外部 ID 不变；不得出现单侧资金、状态无占位、占位无状态、终态无指针或业务结果无可靠任务。 |
| 15 | 多 worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务 | 同一租约不能被两个 worker 同时持有，较后任务不能永久饥饿；任何领取事务都不携 task 锁进入领域处理。 |
| 16 | 平台闸门暂停和负余额暂停分别作用于待审核提现 | 仅平台闸门暂停时，既有且无负余额暂停的单可审核进入 `READY_TO_SUBMIT` 但不得提交；存在负余额暂停时不得审核通过；两种情况下合法驳回或取消均可原子释放。 |
| 17 | 同一库存资产被两个机构并发直接部署，或部署事务在创建投口/运行投影之间失败 | 最多一个完整当前部署；失败方无部署、投口、运行投影或资产状态残留，资产与当前槽始终一致。 |

- 每个系统商户最多一个当前暂停事件；闸门恢复事件精确引用原暂停且不改变任何机构账户；
- 每个已确认隔离项最多一个成功确认审计且始终没有由该确认直接派生的 inbox、任务或领域事实；每次人工任务恢复只改变原任务的调度代际，不改变其稳定身份；
- 告警确认投影与来源恢复状态正交；对账人工 action 只追加且不能单独把 issue 改成 `RESOLVED`；
- 每个投递 session 最多一个最终物理结果、一笔订单、一组四图槽和一个最终 `DELIVERY_COMPLETE` 满溢 gate；不存在云端周期、继续 pending、解析任务或中间重量/照片事实。订单负重量异常标志精确等于设备最终载荷布尔值，后端不得按整场首末净重补判，数据库不保存本地触发轮次减少值；
- 同一业务来源最多一笔订单、清运记录、资金阶段明细或可靠任务。
- 每机构订单可见序号唯一且计数器等于当前最大已提交序号；带快照上限的订单游标不读入更高序号。

普通 CI 中每个确定性交错至少运行 20 轮；发布前在目标 MySQL 环境至少运行 200 轮压力验收，并保留关键 SQL、事务时序、故障点和不变量查询结果。次数以后可以上调，但不能因 H2、单线程或正常路径测试通过而降低或跳过这一门槛。
