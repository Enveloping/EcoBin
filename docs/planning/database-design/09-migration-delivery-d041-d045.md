## 13. 第九批已确认：迁移纪元、目标建库、账号与切换

### D-041 新迁移纪元与新旧数据库物理隔离

**已确认：旧 V1～V14 作为一个不可拆分的旧迁移纪元冻结；目标应用只扫描独立的新迁移目录，并在一套新的 MySQL 数据库中从目标 V1 开始建库。过渡及回退保留期内，新旧应用分别使用独立 MySQL 容器/实例、账号和数据卷，不在同一实例内只靠两个 schema 模拟隔离。**

1. 旧版本恢复单元必须同时保存旧 Git tag/commit、可运行应用制品、配置模板、旧 V1～V14、数据库逻辑 dump、校验和、Flyway history、行数清单和隔离恢复记录。不得从旧链中挑选部分脚本放入新纪元。
2. 新应用的 Flyway location 与旧 `db/migration` 完全分离；构建和部署检查必须证明新应用不会发现或执行旧 V1～V14，旧应用也不得发现目标 V1～V10。
3. 过渡期推荐使用两套独立 Docker Compose MySQL 服务或等价独立实例，各自具有明确容器名、数据库名、账号和持久卷。应用到数据库的网络和授权也按版本成对隔离：旧应用不能连接新库，新应用不能连接旧库。这只是迁移期的版本隔离，不是双主、HA 或长期业务分库；任一时刻仍只有一套应用/数据库承载中心业务真相。
4. P0 目标运行版本固定为 MySQL 8.4 LTS；实现时锁定完整镜像版本及不可变 digest，开发集成、自动化测试、M0 联调和目标部署使用同一数据库版本。D-033 的 MySQL 8.0.16 仅保留为 CHECK 能力来源说明，不再代表本项目实际目标版本；D-033 原定的真实 8.0.16 非法值负测由本决策统一收口为在目标 8.4 上执行。
5. 目标 V1 在 `flyway_schema_history` 中使用唯一且固定的版本、description 和 checksum 作为新纪元标记。运行应用启动时只读校验该标记存在且成功，并确认 schema 至少完整到 V10；遇到空库、旧纪元、错误 V1、失败迁移或低于 V10 时立即拒绝承接业务入口。
6. 该启动校验不是自动迁移。目标环境关闭 `baseline-on-migrate`、`createDatabaseIfNotExist` 和应用启动时 Flyway migrate，数据库必须由 D-044 的一次性迁移步骤预先创建并升级。
7. `PREPARED` 阶段旧栈仍是生产所有者，旧库继续随旧应用正常写入。进入 `QUIESCED`、旧栈停止写入并完成最终备份以后，旧应用不得在 `ACTIVATED` 观察期重新连接旧库写入；旧库和数据卷以离线或只读恢复材料保留，不因新库安装成功而删除。任何删除、清理或释放旧恢复材料都必须另行列出精确对象并获得明确的破坏性操作批准。

### D-042 首个目标版本的 V1～V10 建库批次

**已确认：首个可承接业务的目标 schema 由十个职责单一、顺序固定的版本化迁移组成，不使用一个巨型 V1；V1～V10 全部成功前，应用不得开放任何业务入口。**

| 版本与建议文件名 | 唯一职责 |
|---|---|
| `V1__p0_epoch_and_iam_core.sql` | 建立目标纪元标记语义以及租户、机构、工作人员、权限授权、机构小程序配置等 IAM 核心结构；不导入环境账号或试点业务数据。 |
| `V2__device_inventory_and_configuration.sql` | 建立物理资产、部署、投口、配置版本/快照、配置应用和基础运行投影。 |
| `V3__organization_users_and_sessions.sql` | 建立机构用户、管理绑定、用户能力以及平台/Web/小程序登录会话。 |
| `V4__device_operations_and_evidence.sql` | 建立设备整机占位、作为唯一作业/结果幂等根的投递会话、命令、公共边缘事件头、命令事件、物理结果和设备故障等作业证据骨架；不建立投递周期表。 |
| `V5__recycling.sql` | 建立投递、审核修订、清运配置 head/记录计数器/操作与记录、袋追溯、重量基准及真实重测、满溢检测与照片事实。 |
| `V6__funds.sql` | 建立提现配置及当前 head、用户钱包、机构账户、双侧明细、充值、提现、微信支付/转账观察和平台出款闸门。 |
| `V7__operations.sql` | 建立可信 inbox、隔离记录、唯一可靠任务、执行尝试、操作审计、聚合告警与对账事实。 |
| `V8__cross_module_foreign_keys.sql` | 在所有端点表存在后，补齐模块内循环指针和跨模块强类型外键。 |
| `V9__immutability_triggers.sql` | 仅建立 D-035 已确认的少量身份不可变触发器。 |
| `V10__permission_reference_data.sql` | 仅写入权限目录和与环境无关、非秘密、可版本化的静态参考数据。 |

每个版本已经应用后永久不可修改；修正只能新增后续版本。上述文件名在实现时作为默认正式名称，若因构建约束必须调整 description，必须同时更新纪元校验、部署清单和测试，不能只改其中一处。

V1～V10 完整安装后的目标清单为 **83 张表**：identity 14 张、device 16 张、recycling 24 张、funds 20 张、operations 9 张。该数量与 D-007～D-010 及 D-035 逐表登记一致；旧设计中的第 84 张投递周期候选表不得出现在 V4、V8 或任何后续补丁迁移中。

MySQL DDL 会隐式提交，Flyway 迁移失败不能被理解为整个文件已原子回滚。因此：

- 首次向全新目标空库安装 V1～V10 时，只要任一版本中途失败，就停止应用和迁移器，保存错误证据，丢弃这套尚无真实事实的目标数据库并从新的空库重装；不得对半成品空库盲目执行 `repair` 后继续。
- `repair` 只能在人工证明 schema 与脚本事实完全一致、记录了原因且经过专项批准时用于修复 Flyway 元数据，不能用来掩盖部分 DDL 或 checksum 漂移。
- 一旦目标库越过 D-045 的真实入口闩锁或存在不可丢业务事实，就不得丢库重装，只允许新增前向迁移并按 D-001 保全事实。

### D-043 严格 DDL、循环关系闭合与静态数据边界

**已确认：V1～V7 在依赖已存在时立即建立完整约束，V8 只负责无法提前建立的循环/跨模块外键；所有迁移始终开启外键检查，拒绝用宽松 DDL 或 baseline 隐藏污染。**

1. 每张表在所属版本中一次性定义列、主键、D-031 候选唯一键、D-032 当前唯一机制、D-033 命名 CHECK、D-034 查询/外键索引，以及当时已具备父表的外键。所有约束和索引使用全 schema 唯一且可审计的显式名称。
2. 迁移脚本禁止使用 `IF NOT EXISTS`、`FOREIGN_KEY_CHECKS=0`、忽略错误、自动猜测旧表或 baseline 非空污染库。目标库中出现意外对象、重复名称或约束冲突必须让迁移失败。
3. V8 至少闭合以下已确认关系；D-031 的逐表登记仍是完整清单，实施时须用外键矩阵证明没有遗漏：
   - 投递 session 到其唯一物理结果，投递订单到同一 session/物理结果及 current revision；
   - 清运 operation 与 completion record、清运 record 与唯一 review revision；
   - 基准重测与其唯一物理结果/结果基准，以及清运操作可空的投递待处理 session 快照；
   - 满溢 detection、initial/terminal sample、capacity state、current event，以及出款闸门 current pause event；
   - 设备整机占位到 recycling 清运操作，设备命令/物理结果到投递、清运和满溢目标；
   - 公共边缘事件头到 operations inbox，命令事件/物理结果到公共事件头，资金渠道 observation 到 inbox/attempt；
   - 钱包人工调整、提现审核等敏感事实到对应 operations 审计证据。
4. MySQL 不支持延迟外键。合法循环统一按“先插入允许空当前指针的父行 → 插入子事实 → 在同一业务事务回填父指针并推进状态”构造；完成态 CHECK 要求指针非空，任何中间提交都不能伪装成完成态。
5. V9 不实现通用业务状态机，只创建 D-035 已确认的两类纵深防御：机构小程序的 `activated_at` 只允许从 `NULL` 补写一次，写入后不可变，AppID/作用域在激活后不可变；机构用户的 `registered_at`、`registered_via_deployment_id`、AppID/OpenID/作用域不可变。触发器使用预先存在的稳定 `ecobin_trigger_definer`，运行账号没有 `TRIGGER` 权限。
6. V10 只维护 `iam_permission_definition` 和真正环境无关的静态参考数据。租户、机构、人员、密码、AppID、商户号、设备、投口、袋、余额、订单和任何密钥都不得写进普通 Flyway。
7. I-014 已冻结的身份目录权限码由 V10 建立；`organization-manager.manage` 仅建立 `TENANT` 作用域定义，不能以普通 `permission.manage` 或机构级同名授权替代。I-018～I-020 新增的 `device.read`、`device.manage`、`device.configuration.manage`，I-024/I-025 新增的 `delivery.read`、`review.execute`、`delivery.correct`、`wallet.read`，I-026～I-030 新增的 `clean.read`、`device.detection.execute`、`device.recovery.execute`，I-031～I-035 新增的 `wallet.adjust`、`fund.read`、`recharge.create`、`withdrawal.configuration.manage`、`withdrawal.read`、`withdrawal.handle`，以及 I-036～I-040 新增的 `audit.read`、`alert.read`、`alert.acknowledge`、`reconciliation.read`、`reconciliation.handle`、`statistics.read`，均建立 `TENANT` 与 `ORGANIZATION` 两种作用域定义。`review.execute` 是投递、清运和提现共用的初审能力，不能按业务类型拆成同义权限码；读取、调整、充值、配置、运营查询和处置能力互不隐含。平台任务恢复、隔离确认、平台对账运行和出款闸门恢复是平台域固定用例，不伪装成租户权限码；工作人员小程序只把当前机构 `alert.read` 与 `statistics.read` 加入客户端白名单。V10 一旦在任何持久环境应用，后来新增权限只能用新的前向迁移，不能修改已应用文件。

### D-044 数据库身份、一次性迁移与试点初始化

**已确认：数据库实例初始化、schema 迁移、触发器定义、应用运行和备份分别使用独立身份；应用进程不持有 schema owner 凭证，也不在启动时自动迁移。试点业务对象通过受控的一次性 bootstrap/seed 命令创建。**

| 身份 | 使用边界 |
|---|---|
| 实例初始化/恢复管理员 | 只用于创建数据库、账号、初始授权及灾难恢复；不进入应用配置或日常 Flyway。 |
| `ecobin_schema_owner` | 只由一次性迁移作业运行 Flyway，拥有目标 schema 所需 DDL/引用能力以及 D-035 已确认的受控授权能力；不进入后端运行容器。 |
| `ecobin_trigger_definer` | 禁止交互登录、长期保留，只拥有触发器执行所需最小权限；在 V9 前完成创建和授权。 |
| `ecobin_app` | 后端唯一日常数据库身份，严格执行 D-035 的表/列级 DML 矩阵，无 DDL、GRANT、TRIGGER、全库 UPDATE/DELETE 或旧库权限；只读访问目标 Flyway history 供纪元校验。 |
| `ecobin_backup` | 只用于备份读取及目标工具必需的最小元数据/锁权限，无业务 DML、DDL 或授权能力。 |

1. 数据库、账号、角色、密码和环境 GRANT 属于环境供应，不写入普通 schema Flyway。授权完成后保存脱敏的 `SHOW GRANTS` 结果，并通过正向用例和“应用账号执行 DDL、改不可变列、删事实表必须失败”的负向测试验收。
2. 迁移器是一个显式、可重复部署但一次只运行一个实例的作业：注入 `ecobin_schema_owner`，从空库执行 V1～V10，完成校验后销毁该凭证上下文。后端容器只获得 `ecobin_app`，启动时执行 D-041 的只读纪元/版本守卫。
3. 试点租户、两个机构、租户主体/工作人员、投递/清运/提现初始配置、设备、部署、投口、初始袋及其投口绑定和必要的初始重量基准，由受控 bootstrap/seed 命令调用正式应用用例创建，不由通用 Flyway 插入。投递初始配置使用已冻结的 `ALL_MANUAL`、机构负余额阈值和默认 100.00kg 人工认定绝对值上限；清运初始配置使用 `ALL_MANUAL + 1800秒`；提现初始配置使用 `hardLimit=200.00/manualMinimum=0.10/manualMaximum=200.00/reviewFreeThreshold=0.00`。三类配置都必须共同建立当前 head，订单/清运记录/钱包明细等机构计数器从 0 初始化或由首笔正式用例幂等建立，不能靠查询当前最大值。该命令在 V10 完成后使用 `ecobin_app` 数据源及同一份最小 DML 权限矩阵运行，不借用 schema owner 或实例管理员扩大写权限。初始重量基准必须来自袋安装后的可信实际称重并通过 D-019 的有效性校验，禁止用固定 0 或默认值伪造物理事实；尚未取得可靠基准时，对应投口保持阻断。密码从外部安全输入或一次性生成后强制妥善交付，不存在固定默认弱密码。
4. seed 使用稳定输入键和幂等检查：目标对象不存在则创建；已存在且 seed 清单控制的声明字段完全相同则视为成功，数据库生成的 ID、创建时间和密码哈希不参与逐值相等比较；同一稳定键对应任何声明字段冲突时立即失败并要求人工处理，禁止覆盖。重跑不得重置已有账号密码；外部安全输入无法验证已有密码哈希时也必须失败并转人工处置。
5. 不导入旧余额、订单、资金流水或进行中作业，也不为当前余额反造历史。机构用户由首次 `wx.login` 在目标机构重新注册；其来源设备和注册时间继续遵守 D-013。
6. 所有目标环境显式使用 UTC、业务写事务默认 `READ COMMITTED`、严格 SQL mode，并关闭自动建库、baseline 和应用启动自动迁移；I-040 最小概览由应用在该专用只读事务上显式覆盖为 `REPEATABLE READ`。字符集、排序规则及其他 MySQL 参数在 DDL 实施清单中固定并由临时真实 MySQL 验证。
7. H2 只保留给不依赖 MySQL 方言、锁和约束的快速测试；正式迁移、Mapper、触发器、权限负测及 D-040 并发恢复测试全部使用从空库执行 V1～V10 的临时 MySQL 8.4。

### D-045 成对切换、保守闩锁与回退验收

**已确认：新旧版本按“应用 + 数据库”成对管理，切换采用 `PREPARED → QUIESCED → ACTIVATED` 三态；“允许新栈接收真实入口或使用真实渠道”本身就是保守的不可逆闩锁。闩锁前可整对回退，闩锁后不得假设新事实为空而直接切回旧库。**

三态都是完成相应门槛后记录的稳定检查点，不把排空过程误作已完成状态。从 `PREPARED` 进入 `QUIESCED` 的操作窗口先停止旧入口，再允许已经开始的旧事务和可证明的外部动作按规则收敛；全部检查通过并完成最终备份后才记录 `QUIESCED`。一旦记录该状态，旧库不再有生产写者。

| 阶段 | 必须成立的状态 |
|---|---|
| `PREPARED` | 旧栈仍是唯一生产所有者；新库已从空库完成 V1～V10、权限验收和受控 seed，新栈只连接 Fake/Stub 或被网络/凭证硬阻断的外部适配器。会写入合成订单、资金或设备事实的演练使用一次性演练库；待激活目标库除受控 seed 外不得残留测试业务事实。 |
| `QUIESCED` | 旧栈已经停止接收新业务、停止 OneNet/MQ 消费和后台执行；在途 HTTP/数据库事务及可证明的外部动作已经收敛，旧业务表、日志、消息积压和外部渠道证据已盘点，资金渠道单已终结，投递门/清运门安全，进行中设备作业已结束或隔离，最终旧库备份已经完成并验证；此时不存在生产写者。 |
| `ACTIVATED` | 明确切换 Web/API 流量、OneNet 消费者、可靠任务执行器和真实微信/OneNet/COS 凭证到新栈；记录版本、数据库、时间和操作者。全系统任何时刻只能有一套栈拥有这些入口和执行权。 |

回退和闩锁规则如下：

1. 在真实入口闩锁前，可以停止新栈并把“旧应用 + 旧数据库”整体恢复为唯一所有者，前提是自动检查确认新栈从未取得真实入口/渠道能力且没有不可丢事实。用于演练的新库仍保留供诊断，不反向写入旧库。
2. 第一次开放真实 API/OneNet 消费、设备下行、真实微信/COS 凭证，或允许生产可靠任务 worker 连接目标任务库并具备真实外部副作用能力中的任意一项时，即记录闩锁已经越过；不等待“数据库中已经找到第一笔订单”才判断不可逆。只连接一次性演练库和 Fake/Stub 的合成 worker 不触发闩锁。
3. 越过闩锁后只允许保护新库并修复前进，或停止全部入口后制定显式的数据迁回/补偿方案；禁止直接让旧应用重新接管而丢弃新库、MQ、设备或渠道事实。
4. 即使尚未开放真实入口，只要已经发布与旧栈不兼容的小程序、香橙派或 MCU 协议/配置，也视为失去直接回退条件；必须先恢复端到端兼容性或采用显式升级/回迁方案。
5. 切换脚本和运行手册必须把 Nginx/API、OneNet 消费、任务 worker、设备下行和真实渠道凭证列成同一张所有权清单，逐项证明旧栈已停、新栈才启，不能只切 HTTP 流量。
6. 进入 `QUIESCED` 前必须逐笔检查旧栈能够提供的非终态业务单、设备会话/作业、任务或调用日志、MQ/OneNet 积压和微信渠道记录。目标旧审计已确认 V1～V14 没有 D-039 的可靠 task/attempt，因此不得把“表不存在”当作没有在途调用；缺少本地调用边界时，要结合结构化/容器日志、固定外部单号、OneNet 命令与消息状态、微信查单或商户记录证明动作从未开始或已经收敛。凡已有 `external_call_may_have_started_at` 或等价证据的动作，必须以原外部身份归并或形成明确的隔离/接管方案；无法证明的未终结资金单、待执行设备命令、状态不明的门或其他不安全物理作业一律阻断激活。
7. 切换后到达的旧 OneNet/微信消息只有在其稳定外部身份能无歧义映射到目标事实时才进入既有幂等收敛入口；目标 OneNet 入口要求可信 `eventUid`、原作业/部署和规范摘要，旧 OneNet/MQ 消息 ID 不能回退成为业务身份。缺少目标投递 session、清运操作、提现/充值或部署身份的迟到消息只保存到隔离记录，禁止按时间、设备或用户猜测挂接；旧周期身份或中间开关门数据不能用来临时创建目标周期表。
8. 最终旧库备份完成后，项目负责人必须再次确认 D-001 的“旧数据无需迁移”前提仍成立；若 PREPARED 期间新增了必须保留的事实，立即停止激活并按 D-001 重新设计迁移，不能临时复制余额、订单或设备状态。

首次激活前的硬性门槛：

- 旧 dump、校验和、Flyway history、应用制品已在隔离环境完成整对恢复；
- 新空库可以一次完成 V1～V10，目标纪元/最低版本守卫能拒绝旧库、空库和半成品库；
- `ecobin_app` 权限正向用例通过，DDL、不可变列、事实 UPDATE/DELETE 等负向用例全部被数据库拒绝；
- D-040 当前完整的真实 MySQL 并发与故障恢复验收矩阵、每轮不变量查询及规定轮次全部通过；不得在这里复制一个会随场景新增而失真的固定数量；
- 权威 OneNet 物模型、事件/命令 Schema、Java 21/Python 3.11 摘要黄金样本、后端消费者及香橙派版本形成同一兼容矩阵；试点设备已经持久化新 `deploymentCode` 和部署内全局事件序号起点，旧未确认事件已经收敛或显式隔离，禁止在同一部署自动重置序号；
- F-10 规范机器注册表、Python 3.11/通用 C11 编解码器和黄金样本已通过；所选 MCU
  模式的真机测试必须通过。`uart-v1` 用 HELLO/CRC/ACK/重启证据证明兼容；当前
  `fixed-frame` 则由 H-03 验证定长帧、活动作业绑定、投递唯一最终结果、清运电磁阀
  自动断电和人工确认，缺失能力保持未知/不支持。旧 D1、自动双解析及 gross/tare 清运
  路径不在生产构建中；
- 受限 COS 临时授权只能写入原作业前缀，业务确认/回执、重复/乱序事件和边缘断电恢复的非真实渠道演练已经通过；当前旧 `deliveryComplete/cleanGross/cleanTare` 和匿名设备写入口不在激活后的生产写路径；
- 使用一次性演练数据库和非真实渠道完成至少一次 `PREPARED → QUIESCED → ACTIVATED` 切换演练和闩锁前整对回退演练，并保存步骤、时间、结果和故障处置证据；目标待激活数据库若曾写入 seed 以外的合成业务事实，必须在闩锁前丢弃并从空库重建、重新验收和 seed；
- 激活清单明确唯一入口所有者、真实凭证注入点、设备/客户端协议兼容性和旧栈停止证明。

本决策要求的是本次版本切换可恢复性和临时备份证据：它是允许新迁移纪元首次激活的一次性操作门槛，不是新增的 M0 产品场景或通用完成条件，也不代表已经具备生产灾备能力。正式 PITR、RPO/RTO、长期备份治理和灾难恢复演练仍属于 M1。旧栈、旧卷和恢复材料持续保留，直到另一次明确评审和破坏性删除批准。
