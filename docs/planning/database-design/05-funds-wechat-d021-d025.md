## 9. 第五批已确认：钱包、机构额度、充值、提现与微信渠道

本批只落实 M0 的手动提现和真实微信收付闭环；投递后自动提现继续按 D-010 留到 M1 前向迁移。本批中的“状态”分为 EcoBin 业务状态、微信原始渠道状态和技术任务结果，三者不得共用一个枚举或互相冒充终态。

### D-021 提现配置、用户钱包与人工调整

**已确认：机构提现配置使用不可变版本；用户钱包只保存可用余额和提现冻结投影，待审核返现继续从订单汇总；人工调整输入有符号差额而不是覆盖目标余额。**

| 表 | M0 核心字段与约束 |
|---|---|
| `fund_organization_wallet_entry_counter` | 以机构为主键、非负 `last_visibility_sequence_no` 和锁版本；只负责在机构内为真实用户钱包明细分配提交可见序号，不表达资金余额、流水总数或经营统计。机构首次创建机构用户及其钱包时在同一事务确保该行以 0 初始化；同机构并发首次注册由机构锁和唯一键串行化。 |
| `fund_organization_withdraw_config` | `id + tenant_id + organization_id`、机构内单调 `version_no`、单次硬上限、手动最低/最高金额、手动免审阈值、发布人和发布时间；唯一 `(organization_id, version_no)`，插入后只读。M0 不预建自动提现字段。 |
| `fund_organization_withdraw_config_head` | 以机构为主键，强引用本机构当前 `config_id + version_no`，保存切换时间和锁版本；发布事务插入新配置并原子切换，提现创建锁 head 后读取，不使用 `MAX(version_no)` 推导当前。 |
| `fund_user_wallet` | `id + tenant_id + organization_id + organization_user_id`、带符号 `available_balance_cent`、非负 `frozen_withdrawal_cent`、非负 `last_entry_sequence_no`、`OPEN/MANUAL_RECOVERY_REQUIRED` 投递闸状态、可空停投阈值快照/触发明细/锁存时间、锁版本及时间列；机构用户复合唯一，钱包与机构用户同事务创建且余额、冻结和末序号初值均为 0、投递闸初值为 `OPEN`。 |
| `fund_user_wallet_entry` | 全局唯一明细 UUID、钱包内从 1 开始严格递增的 `entry_sequence_no`、机构内严格递增的 `visibility_sequence_no`、事件类型、可用/冻结的有符号增量及两项变动前后值、投递认定版本/提现单/人工调整三选一的强类型来源、发生时间；只追加。唯一 `(wallet_id, entry_sequence_no)` 和 `(organization_id, visibility_sequence_no)`；投递认定版本唯一，提现按 `(withdrawal_order_id, fund_phase)` 唯一。 |
| `fund_wallet_adjustment` | 全局唯一调整 UUID、钱包、有符号调整差额、调整前后可用余额、分型操作人、可空原因和发生时间；插入后只读，只能改变可用余额，不能改变提现冻结。唯一钱包明细只从 `fund_user_wallet_entry.adjustment_id` 引用并反查，调整表不反向持有明细外键，避免 MySQL 无延迟外键时形成插入死结。 |

- 金额统一使用 `BIGINT` 分。配置必须满足 `10 <= manual_min_cent <= manual_max_cent <= hard_limit_cent <= 20000`、`0 <= manual_review_free_threshold_cent <= manual_max_cent`；阈值为 0 表示全部人工审核。新机构默认依次为 10、20000、20000、0 分，配置只影响之后创建的提现，提现单继续固化完整快照。
- 钱包行不是资金事实本身。每次真实变动必须按“钱包 → 机构钱包明细计数器”取得锁，把钱包 `last_entry_sequence_no` 和机构 `last_visibility_sequence_no` 分别加一，以两个新值追加唯一明细并更新余额投影；持有机构计数器直到事务提交，使其序号成为机构级提交可见水位。数据库 `CHECK` 保证 `before + delta = after` 和冻结前后均不小于 0。差额为 0 且不形成资金明细时不得消耗任一序号。禁止 Controller、Mapper 或管理员直接覆盖余额列、末序号或机构计数器。
- 钱包明细的提现阶段固定为 `FREEZE/FINAL`：创建提现时可用 `-X`、冻结 `+X`；失败释放时可用 `+X`、冻结 `-X`；成功时可用不变、冻结 `-X`。同一提现在钱包中只能有一次冻结和一次最终处理，最终处理只能是释放或成功消耗之一。
- 对外钱包流水的稳定事件类型固定区分 `DELIVERY_INITIAL_REVIEW`、`DELIVERY_CORRECTION`、`WITHDRAWAL_FREEZE`、`WITHDRAWAL_SUCCEEDED`、`WITHDRAWAL_RELEASED` 和 `MANUAL_ADJUSTMENT`；提现仍同时使用 `fund_phase=FREEZE/FINAL` 保证每单阶段唯一。数据库可以使用受约束字符串或代码表保存这些值，但不得把不同业务效果压成前端无法解释的单一“余额变化”。
- “待审核返现”不写入钱包表，继续由已归属用户、待审核、原始金额可靠且大于 0 的投递订单汇总。待审核负金额、零金额和金额未知订单均不进入钱包三项展示。
- 人工调整采用“输入有符号差额，系统在钱包锁内计算并保存前后值”的方式。这样没有绕过明细直接设置余额的通道；页面若以后希望输入目标余额，也必须在行锁内换算成差额后执行同一用例。
- 负余额停投是锁存闸门，不是只看当前余额的瞬时派生值。任一可信业务命令使调整后可用余额达到或低于该资金变动线性化时由外层协调器锁定并传入的当前机构停投阈值时，同一事务把投递闸置为 `MANUAL_RECOVERY_REQUIRED` 并保存触发明细和该当前阈值快照。投递订单中的开门阈值快照只解释“该 session 开始时为何曾被允许”，不能用于后来审核或纠错决定是否锁存，也不能在 session 内本地继续投递时重新授权；投递审核/纠错和人工调整都必须先锁 recycling 的当前 config head，再调用 funds 完成钱包事务，funds 本身不反向读取 recycling。之后自动正返现、正向纠错或阈值变化都不能清闸。只有一笔非零 `MANUAL_ADJUSTMENT` 使调整后余额严格高于钱包锁存的阈值快照时，才能在同一事务恢复 `OPEN`；下一次新 session 仍按当前 config head 复核，更严格的新阈值可以再次锁存。该人工调整明细和操作审计就是恢复依据，不另造无金额恢复事件。
- funds 不反向依赖 recycling。以后定义人工调整接口时，由允许依赖双方的外层受控协调用例先锁当前投递 config head，再把受信阈值快照传给 funds 命令；funds 在同一数据库事务中锁钱包并验证调整/恢复。提现创建不会让可用余额低于 0，而投递阈值严格小于 0，因此普通提现资金阶段不需要读取 recycling 配置。
- 负余额联动统一为钱包不变量，而不只绑定某一种投递纠错：任何可信钱包明细生效后，只要实际可用余额 `< 0`，尚未越过微信调用边界的活动提现就增加暂停标记并保持双侧冻结；已经越界的只增加风险标记。之后可信明细使余额恢复到 `>= 0` 时自动解除渠道前暂停并继续原单。达到机构停投下限仍只是开门规则，不是数据库金额下界，也不得钳制实际负余额。
- **接口设计落实补充（I-025）**：普通小程序按当前机构用户读取自己的三项视图和明细；Web 通过 `organization_user_uid` 定位目标钱包或使用机构级筛选入口，并要求独立 `wallet.read` 能力，`user.read` 或 `delivery.read` 不隐含取得。三项汇总必须由一个 SQL 语句或等价同一快照同时读取待审核正返现、`available_balance_cent` 和 `frozen_withdrawal_cent`；待审核订单不得提前写入 `fund_user_wallet_entry`。个人明细按钱包内 `entry_sequence_no` 形成稳定游标；机构明细首屏冻结机构计数器水位，后续页只读取 `visibility_sequence_no <= snapshot`，再按发生时间、机构用户和钱包内序号排序。水位、末项排序键及筛选摘要封入防篡改游标。两类入口都只返回实际改变钱包投影的追加事实。

### D-022 机构出款账户与不可变明细

**已确认：每个机构只有一个独立本地出款账户；账户只保存可用和冻结投影，所有累计数从不可变明细汇总，不提供任何人工调账事件。**

| 表 | M0 核心字段与约束 |
|---|---|
| `fund_organization_payout_account` | 以 `tenant_id + organization_id` 一对一建账，`available_payout_cent`、`frozen_withdrawal_cent`、锁版本及时间列；两个金额均非负，新机构初值均为 0。 |
| `fund_organization_payout_entry` | 全局唯一明细 UUID、账户、事件类型、可用/冻结有符号增量及两项变动前后值、充值单或提现单二选一的强类型来源、充值适用的毛额/手续费/净额快照、发生时间；只追加。充值单唯一，提现按 `(withdrawal_order_id, fund_phase)` 唯一。 |

- 当前机构资金总额只按 `available_payout_cent + frozen_withdrawal_cent` 计算；累计充值毛额、累计手续费、累计净入账和累计成功出款从明细汇总或构建只读报表投影，不在账户行维护另一套可能漂移的累计余额。
- 明细的确定性变化固定为：充值入账时可用 `+净额`；创建提现时可用 `-X`、冻结 `+X`；驳回、本地取消、渠道前终止、微信 `FAIL/CANCELLED` 时可用 `+X`、冻结 `-X`；微信 `SUCCESS` 时可用不变、冻结 `-X`。数据库同样检查前值、增量和后值等式。
- 机构额度只由上述业务事件驱动，不存在人工调整类型、跨机构调拨或退款入口。平台管理员也只能查看、查单、处置渠道流程和对账异常，不能直接修改账户或补写一条无来源额度。
- 本地机构额度表达 EcoBin 对该机构可继续出款的账本额度，不等于公司微信运营账户真实余额。P0 不读取微信余额来重算、冻结或清零机构账户；公共运营账户不足由 D-025 的平台闸门单独表达。

### D-023 机构充值、Native 支付与净额入账

**已确认：充值单与微信 Native 支付单一对一；微信支付成功事实和机构净额入账分成两个可恢复事务，30 分钟到期必须经查单/关单验证，不能由本地定时器直接宣告失败。**

| 表 | M0 核心字段与约束 |
|---|---|
| `fund_recharge_order` | 全局唯一充值单号、作用域、创建工作人员、毛额、`fee_rate_ppm=6000`、`CEILING_TO_CENT`、手续费、净额、30 分钟业务到期时间、`PENDING_PAYMENT/PAID_PENDING_POST/POSTED/CLOSED/EXPIRED`、支付/入账/关闭时间和锁版本；机构、金额及费用快照创建后不可改。 |
| `fund_wechat_payment` | 与充值单一对一，系统商户及机构 AppID 快照、商户内唯一 `out_trade_no`、请求金额/币种/描述/到期时间/通知地址摘要、完整请求摘要、可空 `code_url`、可空唯一微信支付单号、当前微信原始状态、最后 API 错误码和渠道时间；渠道状态使用可扩展字符串，不使用数据库 ENUM。 |
| `fund_wechat_payment_observation` | 支付单、`CREATE_RESPONSE/CALLBACK/QUERY/CLOSE_RESPONSE/STATEMENT`、来源 inbox 或任务尝试二选一、原始状态/API 错误码、微信支付单号、总金额/付款者实付金额、可空付款 OpenID、渠道时间和内容摘要；一个可信来源最多形成一条只读观察。 |

- 充值毛额限制为 `100～20000000` 分。手续费只按已冻结公式 `ceil(gross_cent × 6000 / 1000000)` 计算，净额等于毛额减手续费；不调用微信费率作为计算依据。全部值在建单时固化并用整数运算，1 元示例得到手续费 1 分、净入账 99 分。
- Native 下单使用该机构已经与系统商户绑定的 AppID。二维码可以由任意微信付款人扫码，付款 OpenID 只作为渠道证据，永远不能决定或改写充值机构；机构只来自创建充值单时的不可变作用域。
- Native 下单同时把微信 `time_expire` 设为业务创建时间后 30 分钟。到期任务先查单：若已成功则按成功处理；仍未支付时请求关单，并在关单成功或随后查得 `CLOSED` 后才将业务单置为 `EXPIRED`。主动提前关闭则使用 `CLOSED`。在确认关闭前到达的有效 `SUCCESS` 优先；已经存在相反渠道终态时停止自动变更并创建对账异常。
- 验签解密后的成功回调、主动查单或对账都先核对商户号、AppID、`out_trade_no`、总金额和币种，再在第一个短事务中追加观察、把支付及充值推进为 `PAID_PENDING_POST`，并创建唯一净额入账任务。第二个事务锁充值单和机构账户，追加唯一 `RECHARGE_POSTED` 明细、增加机构可用额度并改为 `POSTED`。因此即使入账事务失败，也能明确保存“微信已收款但本地待补账”，重复消息最多补齐一次。
- 支付成功后禁止 EcoBin 发起退款。若微信后来出现 `REFUND`、金额矛盾或相反终态，只保留观察并建立对账异常，不自动冲减机构额度，也不能把钱改挂其他机构。
- **接口设计落实补充（I-032）**：创建充值的本地事务同时建立支付请求快照和唯一 Native 下单任务，接口返回 `202`；`code_url` 在可信创建响应前保持空，Web 通过原充值单轮询。结果不明只原 `out_trade_no` 续办。30 分钟到期仍须先查单、再关单并确认渠道关闭；本地计时和二维码失效不能直接推进终态。

### D-024 手动提现、审核、双侧冻结与活动占位

**已确认：提现申请、两侧冻结、两侧明细和每钱包唯一活动占位在一个事务共同成立；审核、业务生命周期与渠道状态分离，30 分钟未结算只做正交标记。**

| 表 | M0 核心字段与约束 |
|---|---|
| `fund_withdrawal_order` | 全局唯一提现单号、作用域、钱包/机构出款账户/机构用户、正金额、配置版本及范围快照、商户/AppID/OpenID 收款身份快照、`PENDING_REVIEW/READY_TO_SUBMIT/CHANNEL_PROCESSING/SUCCEEDED/REJECTED/LOCAL_CANCELLED/LOCAL_ABORTED_BEFORE_CHANNEL/CHANNEL_FAILED/CHANNEL_CANCELLED` 业务状态、负余额暂停/提交后风险、渠道前阻断原因、长时间未结算时间、各阶段时间和锁版本。M0 不预建自动提现来源字段。 |
| `fund_withdrawal_review` | 全局唯一审核动作 UUID、提现单、`APPROVED/REJECTED`、分型审核人员、可空备注和发生时间；一笔提现最多一个有效审核决定，只追加且不能修改金额。 |
| `fund_active_withdrawal` | 以钱包 ID 为主键、提现单唯一，保存作用域和创建时间；创建提现时物理插入，任一业务资金终态结算时物理删除。历史只看提现单，不对当前槽位做软删除。 |

- 创建前必须验证手机号已绑定、用户及机构可用、钱包当前非负且可用余额充足、配置及金额合法、没有活动提现、机构可用额度充足、机构 AppID/系统商户绑定可用且 D-025 平台闸门开放。额度不足、闸门暂停或其他前置条件不成立时直接拒绝，不建立失败提现单也不改变余额。
- 创建事务按固定锁序串行检查，随后建立提现单和活动槽位，并分别追加用户与机构 `FREEZE` 明细、把双方可用转为冻结。任一行、明细、槽位或可靠任务失败都整体回滚，不允许只冻结一侧。
- M0 免审阈值固定为 0，因此新单进入 `PENDING_REVIEW`。没有负余额暂停时，审核通过只推进 `READY_TO_SUBMIT` 并创建唯一可靠提交任务；暂停期间禁止通过，但仍可审核驳回或由用户按原边界取消。审核驳回在同一事务释放两侧冻结并删除活动槽位。允许审核自己的业务记录。用户仅能在 `PENDING_REVIEW` 且尚无渠道单时取消手动提现，取消同样原子释放两侧冻结。
- 提交执行器先按 D-038 锁定租户/机构/小程序/机构用户身份前缀，再在短事务内依次锁平台闸门、AppID/系统商户绑定、钱包、活动槽位、提现单和机构账户，复核闸门开放、没有负余额暂停且收款绑定仍可用；提交阶段使用提现已经固化的配置快照，不反向读取或锁当前配置 head。随后创建唯一微信转账单和固定 `out_bill_no`、把提现改为 `CHANNEL_PROCESSING` 并越过“不可本地取消的领域渠道边界”；事务提交后，执行器还必须按 D-039 在独立技术短事务中记录 `external_call_may_have_started_at`，再调用微信，绝不持有数据库锁发网络请求。崩溃或超时只能用该原单号及原请求续办。
- 为避免审核通过但从未触达微信的内部故障永久占住用户，已确认保留严格的 `LOCAL_ABORTED_BEFORE_CHANNEL` 恢复终态：系统强制“先提交微信转账单和渠道边界、后调用网络”，因此只有提现仍为 `READY_TO_SUBMIT` 且不存在 `fund_wechat_transfer` 时，有权限客服才可执行并原子释放两侧冻结；操作写审计。只要转账单已经存在，就按“可能已经调用”处理，只能使用其中的原 `out_bill_no` 查单、重试或请求微信撤销，不能人工伪造失败。
- 任意可信钱包明细使可用余额 `< 0` 时，若尚未记录渠道调用边界，则活动提现只增加暂停标记并保持双侧冻结，待余额恢复至 `>= 0` 自动解除；如果已经越过边界，只增加风险标记并等待真实终态。纠错、人工调账和提交执行器都必须锁同一钱包及活动提现，防止已要求暂停的旧任务继续穿透。
- `long_unsettled_at` 在进入渠道处理 30 分钟仍无终态时写一次，只用于查询、告警和客服查单；它不改变业务状态，不释放槽位/冻结，不自动撤销、退款、换单或创建新单。

### D-025 微信转账、商户绑定与平台出款闸门

**已确认：微信转账单保存固定请求和原始渠道投影，所有响应进入追加观察；只有微信 `SUCCESS/FAIL/CANCELLED` 能驱动渠道后的双侧资金终态，`NOT_ENOUGH` 只关闭共用商户的平台出款闸门。**

| 表 | M0 核心字段与约束 |
|---|---|
| `fund_wechat_merchant_profile` | 平台级普通商户号、启停状态、已获批“二手回收”场景 ID、固定报备类型/内容、普通确认页样式及非敏感配置引用；商户号唯一。私钥、APIv3 密钥、证书私钥和真实凭证不入库。 |
| `fund_miniapp_merchant_binding` | 作用域、机构小程序、已验证 AppID、核查时小程序版本、系统商户、`VERIFIED/DISABLED`、验证人/时间、失效时间和锁版本；AppID 唯一，作为该机构 AppID 确已与该商户建立渠道关系的资金域事实。核查时版本用于并发保护，之后只有 AppID 与快照不一致才使旧验证失效；AppSecret/展示资料变化不影响绑定。平台核查事务不能接受客户端自报 AppID 或商户号。 |
| `fund_wechat_transfer` | 与已经越过提交边界的提现单一对一，系统商户、全平台唯一且最长 32 位字母数字 `out_bill_no`、可空唯一 `transfer_bill_no`，金额、AppID、OpenID、场景 ID、报备信息、备注、确认页样式、通知地址和请求摘要不可变快照，原始渠道状态、内部终态分类、`package_info`、最后 API 错误码、终态失败原因、提交/更新时间/终态时间、状态冲突标记和锁版本。 |
| `fund_wechat_transfer_observation` | 转账单、`SUBMIT_RESPONSE/CALLBACK/QUERY/CANCEL_RESPONSE/STATEMENT`、来源 inbox 或任务尝试二选一、原始渠道状态/API 错误码/终态失败原因、双单号、`package_info`、金额/OpenID/渠道时间和内容摘要；一个可信来源最多形成一条只读观察。 |
| `fund_payout_gate` | 以系统商户为主键，`OPEN/PAUSED_NOT_ENOUGH`、可空当前暂停事件、暂停时间和锁版本；P0 全部机构共享公司商户，因此共享这一行闸门，但不共享机构账本。 |
| `fund_payout_gate_event` | 全局唯一事件 UUID、系统商户、`PAUSED/RESTORED`；暂停事件引用首次触发的转账观察，恢复事件唯一引用原暂停事件并保存平台管理员、恢复时间和可空备注；只追加。重复 `NOT_ENOUGH` 只增加渠道观察和聚合告警发现次数，不重复制造暂停事件。 |

- 微信原始状态列使用字符串而不是数据库 ENUM。已知非终态为 `ACCEPTED/PROCESSING/WAIT_USER_CONFIRM/TRANSFERING/CANCELING`，已知终态为 `SUCCESS/FAIL/CANCELLED`；必须保留微信官方拼写 `TRANSFERING`。未知新状态保存原值、停止自动资金归并并产生对账异常，不能因为应用暂不认识就当失败。
- `SUCCESS` 的唯一结算事务把用户冻结 `-X`、机构冻结 `-X` 并分别追加成功消耗明细，机构资金总额相应减少；`FAIL/CANCELLED` 的唯一结算事务把双方冻结各 `-X`、可用各 `+X` 并追加释放明细。二者都删除活动槽位并推进提现终态。双方 `FINAL` 唯一键、条件状态更新和行锁共同保证重复回调/查单/对账只结算一次；已经存在相反终态时不覆盖、不调账，只创建对账异常。
- 回调、主动查单、人工查单和每日对账统一经过同一渠道状态归并器；先验签/解密，再按该来源实际返回的字段核对不可变快照：回调至少核对商户号、双单号、金额和 OpenID，查单还核对 AppID 等完整字段。缺少某个返回字段不能靠猜测补齐，矛盾也不能推进。小程序前端返回永远不能证明到账。查单只有 30 天窗口，长期终态证据必须保存在本地并由后续资金账单对账。
- `WAIT_USER_CONFIRM` 才能向原用户在原 AppID 下提供 `package_info`。24 小时确认提示和 30 分钟长时间未结算都不是微信终态；`CANCELING` 也只表示撤销处理中，仍可能竞态进入 `TRANSFERING/SUCCESS`，因此只有最终 `CANCELLED` 才释放资金。
- P0 固定使用“二手回收”场景；报备类型为“回收商品名称”、内容为“混合可回收物”，普通确认页，备注按 `EcoBin回收款 + 提现单短标识` 生成并限制在微信允许长度内。当前单笔硬上限 200 元，P0 不传 `user_name`；如果渠道规则变化导致提交前已确定缺少实名信息，则保存阻断原因并提示联系客服，尚无转账单时可走 D-024 的渠道前终止，已经建立转账单时仍只能按真实渠道结果处理。
- HTTP 非成功、超时、`SYSTEM_ERROR`、限频、`ALREADY_EXISTS`、未知错误和 `NOT_ENOUGH` 都不是渠道终态；分别保存在任务尝试及渠道观察中，必须使用原 `out_bill_no` 和完全相同的请求摘要查单或幂等续办，禁止换号创建第二张转账单。`last_api_error_code`、原始 `channel_state` 和终态 `fail_reason` 分列，不能把 API 错误码伪装成微信单据状态。
- 第一次收到 `NOT_ENOUGH` 的事务只追加当前转账观察；若当前单仍非终态则保持提现及双侧冻结，同时插入一个 `PAUSED` 事件、把商户闸门改为暂停并创建/触发同一聚合告警。若并发终态已经先完成结算，迟到的 `NOT_ENOUGH` 仍可证明平台曾发生流动性不足并暂停闸门，但不得回退该单或重新冻结。两种情况都不冻结、清零或怀疑其他机构未占用额度。暂停后拒绝新手动提现且不建单；尚未提交的新单不能调用微信；已经在微信处理中的其他单继续接收回调和查单。
- 公司补足公共运营账户后，由平台管理员人工确认恢复：同一事务追加唯一 `RESTORED` 事件、打开闸门并记录操作者/时间。原资金不足单恢复后复用原 `out_bill_no` 和原请求续办；新提现也可继续。数据库不读取微信运营账户余额来重算机构额度，运营账户专用于 EcoBin 出款这一外部管理制度由验收和审计保证，不能伪装成数据库约束。
- **接口设计落实补充（I-031～I-035）**：钱包人工调整使用钱包锁版本且只接受非零差额；机构资金明细/充值、提现和调整使用各自稳定公开号。M0 提现配置发布切换独立 head，免审阈值固定 0，自动提现字段不进入 DTO。渠道前终止只允许不存在转账行；查单/撤销均创建或唤醒原单可靠任务。机构 AppID 与系统商户绑定的本地 `VERIFIED` 事实只能由平台核查用例建立，租户不能自报。

#### 统一锁序与提交边界

```text
资金入口先按用例取得：租户 → 机构 → 小程序 → 机构用户身份前缀
→ 平台出款闸门（创建提现、提交微信或 NOT_ENOUGH）
→ 提现配置 head（发布配置或创建提现）
→ AppID/系统商户绑定（充值创建、提现创建或提交微信）
→ 用户钱包
→ 活动提现槽位 / 提现单
→ 机构出款账户
→ 微信转账当前投影
→ 追加明细、观察和可靠任务
```

- 允许跳过当前用例不涉及的节点，但不得反向。投递审核/纠错在投递聚合锁之后按“钱包 → 活动提现/提现单”进入资金锁序；充值入账只使用“充值单/支付单 → 机构出款账户”。任何事务一旦取得资金锁，禁止再反向申请身份前缀；一旦取得钱包或提现锁，也禁止反向申请平台闸门、配置 head 或商户绑定。
- 外部网络调用永远发生在本地事务提交之后。需要调用微信时，短事务先固化请求、原单号、业务状态和可靠执行身份；进程在提交后崩溃也只能领取同一任务、使用同一单号恢复，不能用持锁等待网络来换取虚假的确定性。
- 创建提现、两侧最终结算、充值入账、负余额联动、`NOT_ENOUGH` 暂停和闸门恢复都必须以真实 MySQL 并发测试验证重复、乱序、死锁重试及事务回滚；H2 单线程测试不能证明资金正确性。
