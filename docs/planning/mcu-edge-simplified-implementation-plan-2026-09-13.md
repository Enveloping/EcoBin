# MCU与香橙派精简业务实施计划

日期：2026-09-13。状态：核心共识已收敛，进入新方案计划与本地实施；S0基线核查进行中。

依据：[D01-D15逐项决定](../architecture/mcu-edge-simplified-recovery-discussion-2026-09-13.md)。
用户已确认称重恢复只接受新业务，原已上报失败保持失败，并允许无其他核心分歧时进入计划实现。
经代码和既有决定核查，没有必须另行决策才能开始的核心阻断；技术细节由实现与测试确定，不继续扩大业务问卷。
本计划取代旧计划中不符合新共识的恢复目标，旧计划及候选证据保留，不整库回退、不删除用户已有工作。

## 1. 目标与范围

先让正常投递、连续投递、清运换袋在完整主入口跑通，再验证少量明确的失败出口。
MCU负责本地按钮、门控制、防夹、称重、业务结束；Pi负责发起、必要记录/照片、结果保存和云端上报。
不恢复Pi逐动作证明或跨重启多代关门机制，不把所有故障都展开成可恢复的机械流程。

只做本地代码、契约和测试。部署后端、变更线上数据库、烧录MCU/HMI、写TF卡及驱动真实机构另行取得操作授权。
复用现有Python 3.11、Java 21、工具链及依赖缓存；不为每批变更重新下载环境。

## 2. 冻结业务边界

| 场景 | 目标处理 |
| --- | --- |
| 正常业务 | MCU本地完成，Pi可靠保存完整结果后确认；保留原业务/用户归属、必要首末重量、重复处理保护 |
| MCU重启 | 放弃旧未完成执行，自行设置关门/锁定控制；Pi已有可靠完整结果优先，否则保留问题记录，不据过程记录重建成功 |
| Pi单独重启 | 找回同一业务，查询/接收原结果，不重发开门、不因自身重启直接判失败 |
| 控制通信故障 | 当前未完成业务失败/问题记录，拒绝新业务并交人工；不猜测机械位置 |
| 称重始终不可读 | 本次上报失败；新有效读数到来前停接单并提示人工，恢复后只允许新业务，不改原失败 |
| 烟感/测距/相机采集故障及烟雾报警 | 真实记录和页面提示，不因它们单独阻断；正常时继续采集，不把缺测伪造成正常 |
| 仅断网，MCU及存储正常 | 原业务完成保存待补报，不接新业务；连续离线超过10分钟释放用户/设备使用占用，保留原结果和归属 |
| 必要存储损坏 | 停接单、人工处理，不做多库备用重建，不承诺保存或上报一定成功 |
| 清运中断且袋状态不明 | 人工确认当前袋，必要时重新换袋/空袋称重；不恢复旧机械过程，不虚构清运重量 |

PB5仅在关门时防夹，触发暂停、解除继续；PB4不承担门位检测。门关闭是控制状态，不是实测到位。
称重250毫秒目标、单次最长5秒、既定稳定均值/超时中位数规则及清运前重减后重保持。
现有设备启用、授权、单业务互斥和已知满溢规则不因模块容错取消。

### 沿用而不重新裁决的资金边界

- 真正非重启的最终称重失败：沿用既有设计的系统异常订单，人工审核前不产生资金效果；
  设备原失败事实不改，人工审核认定独立记录，不等于称重恢复后自动恢复旧业务。
- MCU重启缺最终包以及已经问题归档的业务：只供排查，不产生正常结算、余额或自动提现；后到结果只补证。
- 仅断网待补报不等于问题归档；10分钟释放占用不使原完整结果失效或转为零价值。
- 不修改既有审核/提现配置，不在此任务中增加任何新的自动资金路径。

## 4. 实施顺序及完成条件

每批必须改到实际调用路径并有针对性测试；不以新增一个脱离入口的框架或局部测试很多来宣称整套完成。

### S0：冻结新范围并核实保留能力

- 更新决定、入口文档及本计划，旧方案明确被替代而非继续自动推进。
- 保存工作区现状及基线证据；任何实质裁剪前先完成保留/停用文件清单和可恢复备份，不执行整库reset/clean。
- 运行既有最终结果持久化、Pi单独重启查询和称重失败报告的有限基线测试；结果仅证明保留组件，不证明新方案已接通。
- 完成标准：新旧目标不混用，已有缺口明确，第一批的文件/测试边界可核对。

### S1：接通最小的正常投递与完整结果

- 先确定开始/受理、当前业务查询、完整最终结果/已保存确认、必要故障和采集配合的数据清单。
  复用现有字段和编码工具；不要求Pi接收每次按键或引脚变化，完整最终包自身携带必要首末重量和结束原因。
- 同步 `contracts/uart/uart-registry.yaml`、生成器/守卫与实际MCU执行器、结果保留接口，生成文件只用既有生成器更新。
- 从 `mcu_delivery_execution.c` 等真实路径解除过程保存确认对本地执行的阻塞；Pi结果接收不再依赖独立过程/动作证明。
- 将正常投递接入MCU主入口/工程和Pi主入口，不通过旧恢复专用入口假称业务已接通。
- 完成标准：一次正常投递/继续投递可到最终结果可靠保存；中间诊断消息不影响本地执行，结果重复交接不重复处理，Pi重启不重发开门。

### S2：清运、最低运行条件和失败出口

- 清运本地重开锁/结束、最终首末重量和人工完成语义接通，正常结果使用前重减后重并更新袋/皮重。
- 对齐MCU/Pi的必要通信、称重、存储/联网准入；烟感、测距、照片与烟雾报警只提示，不漏掉其他真正阻断原因。
- 称重失败形成失败结果；持续按受控读取取得新读数后恢复新业务准入，原失败不被改写，不增加修复旧业务阶段。
- 通信故障按既有明确超时配置失败收尾；仅查询健康，不自动重放机械启动。其他故障人工恢复复用现有运维入口，并只检查最低运行条件。
- 照片采集失败使用已有缺失状态；必要存储无法保存不能被当作普通相机故障放行。
- 完成标准：每个已确认故障场景仅走明确出口；正常清运、异常清运人工袋确认和下一笔投递不串袋，不要求非必需模块全部健康才接单。

### S3：后端失败处理、10分钟释放与补报

- 接通现有设计的最终称重失败异常订单入口；目前Pi可生成该结果，但后端正常完成校验仍拒绝缺测，这是实现缺口，不是新业务决定。
- 基于后台确认的连续离线计时，超过600秒释放原用户/设备占用；重复离线事件不刷新本次起点，计时不从业务开始算。
- 明确表示占用已释放而结果仍可补报，同步活跃用户查询、设备占用、原结果接收和重复处理，不只删除占用行。
- Pi保留原身份及待上报结果；重连优先完成旧结果上报/收尾再允许本设备的新业务，用户在其他在线设备的使用不继续被阻断。
- 完成标准：10分钟后用户可使用其他正常设备；原设备离线仍拒单；补报归原用户、不误删新占用、不覆盖新袋，不把离线补报与问题归档混淆。
- 数据库修改使用新前向迁移，不改已部署迁移；Java多模块集成测试前先按项目规则install，真实MySQL验证不以H2替代。

### S4：页面、热点验收、完整构建与现场交付

- 复用已有故障和缺照片显示，体现“可继续/停接单/已失败/结果待补报”，不新增不必要的监控大页面。
- 复用现有HMI页面，不自动更改布局。完成/返回同为05时先核对原脚本语义；若确需区分，提供最小修改表，由用户操作上位机。
- 热点验收接新硬件接口，保留手填克数和实测数据；运行时容错不擅自放宽厂家验收标准。
- 完整MCU工程验证ROM/RAM/栈/时序；历史核心探针不算完整固件。核验真实RS485读数及250毫秒目标，不做自动校准。
- 完成相关契约/Python/Java/前端检查、发布清单与本地数据库版本对齐后，再申请具体部署/烧录/现场动作授权。
- 完成标准：成对软件有可交付制品、正常与已确认异常用例证据、真实现场验证和回退说明；未过这些条件不称为完成上线。

## 5. 协作与防止复杂度再次膨胀

主代理负责契约边界、整合和最终审查。可并行分工互不覆盖的后端占用/补报、MCU执行和界面测试；
共享协议先统一再改消费者，子代理不自行扩展未确认业务规则，不部署或操作硬件。

新增状态、表、协议消息或恢复阶段之前，先说明其保护的已确认需求；现有简单终态/记录能表达就不另建机制。
不能用“所有罕见故障都自动恢复成功”替代本计划。真正需要改变资金、业务含义、硬件接线或现场操作时才再询问用户。
