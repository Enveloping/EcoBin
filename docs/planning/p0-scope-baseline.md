## 1. 文档效力与范围原则

1. `requirements-baseline.md` 继续描述完整目标需求；本文只决定近期里程碑的交付范围，不删除或否定被延期的需求。
2. 一周 P0 的目标是完成**公司自用、受控环境下的真实端到端闭环**，不是宣布系统已经达到无人值守的大规模生产上线标准。
3. P0 可以缩小启用人数、机构和设备数量，但不得用硬编码破坏多租户、机构隔离、资金一致性和设备安全边界。
4. 任何涉及真实资金、用户归属或物理开关门的安全要求，不得以时间紧张为理由省略。
5. 本阶段只确认业务范围、验收结果和外部依赖；不在本文决定数据库表、类、接口 URL、消息字段或具体技术实现。

本文中：

- **P0** 是一周内承诺交付和验收的业务范围；
- **M0** 是 P0 全部通过验收后达到的里程碑；
- **M1** 是 M0 之后、公司自用正式上线前的下一产品里程碑；
- “范围冻结后进入业务建模”描述开发流程阶段，“M0 通过后进入 M1”描述产品里程碑，两者不是同一时间轴。

## 2. 近期里程碑定义

### 2.1 M0：一周 P0 受控闭环

M0 至少使用一个真实租户、两个机构配置、一个真实机构小程序、一台部署在试点机构的真实设备、两名可验证设备独占的机构用户，以及覆盖平台管理、机构审核和清运职责的测试账号，完成真实小额资金和物理设备的受控联调。允许同一自然人在业务规则允许时承担多个工作人员职责，但业务账号和作用域仍须独立留痕。

为验证隔离边界，应额外建立第二机构的配置及测试数据；没有第二台真实设备时，可以使用模拟设备或纯业务数据验证越权与资金隔离，不要求为 M0 额外采购设备。

M0 完成表示核心链路能够在受监督条件下正确运行，不表示已经满足全部公司自用生产要求。

M0 只有在以下条件**同时满足**时才成立：

```text
P0-0～P0-7 全部满足
+ 第 4 节全部不可削减质量边界验证通过
+ 第 6 节 12 个验收场景全部通过
+ 第 7 节标记为“强制真实”的外部依赖全部通过
= M0 完成
```

任一强制真实依赖缺失时，最多只能记录为“软件模拟闭环”，不能以其他测试项通过抵消。

### 2.2 M1：公司自用上线准备

M1 在 M0 之后补齐公司真实日常运营所需的权限自助配置、设备生命周期、告警通知、运维能力、自动化规则、完整对账与上线保障，达到可以让普通用户持续使用的上线门槛。

### 2.3 M2：后续扩展

M2 才考虑外部企业正式商用、平台收付通或二级商户、完整经营分析以及其他当前明确排除的能力。

## 3. 一周 P0 承诺范围

P0 按端到端业务结果拆成八个纵向切片。每个切片必须可以独立说明输入、业务结果、失败结果和验收证据。

### P0-0 外部渠道与真实环境就绪

- 公司系统微信商户号已开通所需的扫码支付和新版商家转账能力。
- 已取得“二手回收”转账场景 ID，试点机构 AppID 已与系统商户号绑定。
- 微信 APIv3 凭证、微信支付公钥、接口安全 IP、公网 HTTPS 回调地址及运营账户资金已经就绪。
- 试点机构充值所需的 Web 扫码支付能力能够产生真实支付二维码，并可通过回调和查单确认支付结果。
- OneNet 上下行、COS 临时凭证与设备照片上传使用真实配置完成联调。
- MCU 与香橙派具备 P0 所需的投递门状态、清运门电磁阀通断、稳定重量、按钮事件、
  故障码和幂等命令能力；清运门没有门磁，物理门位保持 `UNKNOWN`，最终完成依赖
  清运员现场确认。
- 微信渠道已经实际验证 `NOT_ENOUGH` 等资金不足结果只能使用原 `out_bill_no` 和原参数续办；该验证可以使用官方文档、受控测试或微信技术支持结论，不通过故意耗尽生产运营账户完成。

该切片是联调前置条件；任一关键外部条件缺失时，只能完成模拟链路，不能宣称真实闭环完成。

### P0-1 试点机构、身份与基础配置

- 使用一个公司自用租户和至少一个试点机构完成真实业务配置，并建立第二机构用于隔离验证。
- 小程序根据 AppID 唯一确定机构；用户完成微信登录和手机号绑定后才能投递或提现。
- 用户、钱包、订单、设备、价格、清运和机构资金均按机构隔离。
- 完成试点设备、投口展示名称、通用回收单价、投递审核方式、负余额下限、单轮负重量异常阈值（默认 500 克）、满溢阈值及提现参数配置。
- 试点投口在首次业务使用前通过初始化流程绑定当前空袋二维码并取得有效空袋/空箱重量基准；初始化不创建清运订单。
- 试点阶段由租户主体账号、机构负责人和少量明确授权的审核/客服/清运人员操作；P0 必须校验操作权限和机构作用域并记录关键日志。
- 新机构在启用投递前必须显式完成必要业务配置；M0 不依赖尚未确认的系统默认审核模式或默认负余额下限。

### P0-2 用户投递闭环

- 用户扫码设备、选择投口，系统完成全部开门前置校验并建立不可覆盖的设备作业会话。
- 一次有效扫码投递会话最多形成一笔订单；会话开始时冻结用户、投口、单价、袋码和配置，整场沿用这些快照。
- 设备取得首次开门前稳定重量和前两张标准照片，允许用户完成一次或多次本地开关门轮次，再在用户结束或选择窗口超时后取得最终稳定重量和后两张标准照片。
- 中间轮次不建立云端投递周期、不建单、不上传重量/照片/过程事件，不执行普通满溢判断或云端继续授权；硬件安全故障仍阻断再次开门。
- M0 必须至少成功完成一笔四张照片均经真实 COS 链路上传并关联订单的正常投递；单笔订单仍允许因相机或网络故障缺图，但必须保存缺失原因且不得影响订单和返现。
- 用户结束后，设备只通过 OneNet 上报唯一 `DELIVERY_COMPLETE`；后端业务事务成功后返回确认，重复或延迟事件不得重复建单或返现。
- M0 真机链路必须证明稳定设备事件 ID、部署内全局持久序号、后端业务确认及设备确认回执可以在重复、乱序和断电恢复后收敛；不得用 OneNet `code=0` 或 MQ ACK 代替。
- 事件必须永久关联原用户、原机构设备实例、原投口、会话单价和袋码快照；不能归属后来用户。
- 任一本地轮次减少达到会话冻结阈值时锁存 `negativeWeightAnomaly=true`；该布尔值仅包含在最终完成载荷和订单中，不单独上报、不携带中间减少值，订单仍只按整场首末重量结算。
- 零重量、正重量、负重量异常标记、照片缺失、称重失败、断网补传和上报超时均按需求基线产生明确结果。
- 仅在整场投递会话结束后执行满溢检测；确认满溢或关键传感器失败时停止该投口的下一次会话，不反向影响当前会话。

### P0-3 投递审核、钱包与纠错

- M0 试点机构采用“全部人工审核”，以降低真实资金联调期间的误返现风险。
- 审核人员可以按原数据通过，或修改最终重量后由系统使用锁定单价重新计算金额再通过；金额不可脱离重量独立覆盖，原始设备数据永久保留。
- 正金额审核后进入可提现余额，审核前显示待审核返现。
- `negativeWeightAnomaly=true` 的订单必须人工审核；整场最终金额为负时，审核前不进入钱包，人工确认后才按最终负金额扣减余额。
- 钱包正确展示待审核返现、可提现余额和提现处理中金额，并允许可提现余额为负。
- 已完成订单可以再次纠错，系统只按差额幂等调整钱包，并保留操作日志。
- 任意可信钱包变动使可提现余额实际小于 0 时，暂停尚未越过微信提交边界的进行中提现并保持双侧冻结；恢复非负后继续原单。
- P0 必须验证重复审核、重复回调或事务重试不会重复入账或扣款。

### P0-4 清运换袋闭环

- 清运员扫描设备、选择投口并扫描换入袋，系统创建可恢复的清运操作而不是提前创建完成订单。
- 清运操作创建时锁定原清运员、投口、旧袋及旧皮重和新袋预留；香橙派可靠保存上下文后，必须在第一次可能解锁前现场取得并保存本次稳定总重量，不能使用旧心跳值冒充。
- 设备通过电磁阀通电解锁且门自动弹开，由清运员手动关门；再次解锁仍属于原操作。
  首期无门磁，电磁阀通断不能推定物理门位，最终完成必须由清运员现场确认。
- 第一次可能成功通电解锁即越过不可逆边界；解锁后超时或任一端重启都保留原操作等待人工恢复，`SAFE_CLOSE` 不适用于清运门。
- 设备完成解锁、换袋、意外关门后的原单再次解锁、最终人工关门、新袋稳定称重和最终确认。
- `cleanComplete` 重复上报只能事务性完成一次清运订单、一次投口换袋和一次重量基准更新。
- 清运记录永久保存取走袋、换入袋、原始重量、旧皮重、新皮重和最终净重量；袋码可以在不同时期重复使用。
- 清运异常仍创建可审核记录，但不能伪造重量或覆盖原始数据；新重量基准无效时，使用重量参与满溢判断的投口保持不可用，`INFRARED_ONLY` 只有在称重硬件仍健康且可靠红外检测不阻断时才可继续投递，满溢度保持未知。
- 清运完成后重新执行满溢检测，不能仅因换袋自动清除传感器故障。

### P0-5 机构充值与本地资金账本

- 有权限的机构人员在 Web 创建 1 元至 20 万元的充值订单，并使用该机构已绑定系统商户号的小程序 AppID 获得微信 Native 支付二维码。
- 微信明确支付成功后，先持久化成功事实和唯一入账任务，再按固定 0.6% 且向上取整到分的手续费规则以独立事务幂等增加机构净出款额度。
- 未支付、关闭、过期和重复通知不得增加额度；充值成功后不退款、不调拨、不允许人工修改额度。
- 充值、提现冻结、释放和成功消耗都产生不可修改的机构资金明细。
- 机构可用额度、冻结额度和总额始终满足账本等式且不得为负，不同机构之间完全隔离。

M0 至少按以下等式验收机构账本：

```text
机构当前资金总额 = 机构可用出款额度 + 机构提现冻结额度

创建提现：可用额度减少 X，冻结额度增加 X，总额不变
提现失败/驳回/撤销：冻结额度减少 X，可用额度增加 X，总额不变
提现成功：冻结额度减少 X，累计成功出款增加 X，当前资金总额减少 X
```

### P0-6 手动提现与真实微信零钱到账

- M0 承诺手动提现主流程；试点机构的手动提现免审阈值设为 0，即全部人工审核。
- 提现申请原子冻结用户余额和机构额度；机构额度不足时不创建失败提现单。
- 审核员只能通过或驳回，不能修改金额；驳回后同时释放两侧冻结金额。
- 审核通过后使用固化的机构 AppID、OpenID、“二手回收”场景和固定报备信息发起微信商家转账。
- 审核通过后若仍卡在渠道调用之前，只有提现仍待提交且不存在微信转账单时，客服才能受审计地终止并释放双侧冻结；转账单一旦存在即禁止本地终止。
- 一笔本地提现只对应一个固定 `out_bill_no`；超时、系统错误、频率限制或状态不明时只能原单查单或幂等续办。
- 小程序能够调起用户确认收款页；只有微信 `SUCCESS` 才确认成功，`FAIL` 或 `CANCELLED` 才释放冻结金额。
- 回调、主动查单和前端查询使用同一套幂等状态结算逻辑。
- `NOT_ENOUGH` 时暂停作用域是共用系统商户号下的**全平台新出款提交**，不是只暂停当前机构；已经提交微信的其他在途单继续根据各自渠道状态收敛，不自动撤销、不换单，也不提前释放资金。
- 当前资金不足单继续保持双侧冻结。公司补足平台运营账户后，由平台管理员依据已完成的公司公户充值操作人工确认恢复，记录操作人和时间；重复执行恢复操作必须幂等，系统随后使用原单续办。
- 长期未补资时不自动释放当前单；微信最终返回 `FAIL` 或 `CANCELLED` 后按终态释放。客服确需提前处置时只能调用微信允许的撤销能力，并等待明确 `CANCELLED`，不能直接修改本地终态。

### P0-7 最小运营处置、对账与验收

- Web 能查看并筛选试点机构的投递订单、清运记录、钱包流水、提现单、充值单和机构资金明细。
- 有权限人员能够处理投递/清运审核、以有符号差额执行并完整留痕的用户余额人工调整、用户冻结和长时间未结算提现查单。
- 平台管理员能够查看平台资金不足告警并执行受审计的“恢复出款”；M0 不依赖微信运营账户余额自动查询来解除暂停。
- 超过 30 分钟未终结的提现只标记长时间未结算，不自动退款或换单。
- 至少提供每日交易级核对任务，能够发现充值成功未入账、提现终态未结算等遗漏并幂等补账。
- 严重门故障、称重不可用、本地数据无法写入、平台资金不足等 P0 阻断事件能够停止对应业务并在 Web 中被发现。
- 完成第 6 节定义的全部验收场景并保存订单、渠道单号、操作日志和资金明细作为证据。

## 4. P0 不可削减的质量边界

### 4.1 数据归属与权限

- 所有业务写入必须从可信上下文确定租户和机构，不接受客户端任意指定后直接信任。
- 至少验证机构人员不能读取或操作其他机构数据，普通用户不能读取他人订单或钱包。
- 平台代操作、敏感配置、余额调整和资金处置必须记录操作者与前后值。

### 4.2 资金一致性

- 用户钱包、机构额度、业务订单和微信渠道订单之间必须有稳定业务标识和幂等边界。
- 任何状态不明确的渠道调用都不得被本地直接判断为成功或失败。
- 同一次本地业务动作中的提现单创建、用户余额冻结和机构额度冻结必须原子完成，任一失败时本地变更整体回滚。
- 本地数据库事务不能与微信渠道调用形成单一原子事务；渠道结果不明确时保持处理中，通过原单查单、回调和对账最终收敛，不能用本地回滚假装微信没有受理。
- 回调、查单、重复消息和进程重启不得造成重复入账、重复退款或重复出款。

### 4.3 设备与人身安全

- 投递门状态未知或无法关闭时停止设备，不允许仅释放用户会话后继续使用。
- 投递门开关命令必须可识别、可确认并幂等；MCU 必须能在香橙派或网络异常时独立超时关闭投递门。
- 设备在断网或重启后必须恢复进行中作业及未确认事件，不能把旧事件归给新用户。
- 清运门只有电磁阀解锁、没有门磁或自动关门执行器；系统不得把阀断电当作真实门扇证明，不得对清运门使用 `SAFE_CLOSE`，解锁后的超时/重启只能由原清运员现场恢复并确认。

### 4.4 凭证与隐私

- 商户私钥、APIv3 密钥、OneNet 密钥、设备密钥和 COS 临时凭证不得进入版本库、日志或前端响应。机构 AppSecret 仍不得进入版本库或普通业务响应，但已有当前机构小程序配置权限的 Web 操作者可以在配置详情中取得当前完整值，不要求独立回显步骤、额外角色或再次输入密码；配置更新响应只返回版本和脱敏摘要，以保持幂等结果可重放。
- 完整 AppSecret 不进入日志、告警、审计摘要或导出；这些位置只允许记录统一脱敏值。其他日志、告警和导出内容也不得泄露完整敏感凭证或不必要的用户身份信息。

## 5. 一周 P0 明确不承诺的内容

以下能力仍是完整需求的一部分，但不作为 M0 完成条件：

- 投递订单 24/48 小时自动审核、仅异常订单人工审核等自动化模式；M0 固定全部人工审核。
- 投递后自动提现和微信免确认收款授权；M0 只承诺手动提现和用户确认收款。
- 面向普通员工的完整自助权限配置界面、总部及机构在小程序中的经营数据查看。
- 完整投诉工单、用户小程序申诉、经营统计、排行榜和复杂报表。
- 完整设备资产分配、调拨、迁址、替换、报废、维修和人员接管流程。
- 香橙派远程升级、自动回滚、远程日志、完整告警通知升级和短信/电话通知。
- 满溢 24/48 小时升级通知和不阻断核心投递的精细化设备健康运营能力。
- 自动核对微信基本账户或运营账户真实余额、完整财务导出和长期归档策略。
- 自动判断平台运营账户已经补足并自动恢复出款；M0 采用平台管理员人工确认恢复。
- 10 租户、每租户 50 台设备及 8,000 用户规模的性能压测。
- 外部企业正式商用、平台收付通、二级商户、机构间资金调拨和充值退款。

P0 不承诺完整功能，不代表允许删去可靠上报、物理关门安全、租户/机构隔离或资金幂等。

## 6. M0 端到端验收场景

以下场景全部通过，才能宣称一周 P0 闭环完成：

本节定义业务验收结果，不代替后续详细设计中的测试参数。重量稳定窗口、门控超时、命令重试次数、告警发现时限和证据格式必须在实现前的详细设计/测试方案中明确，并在执行 M0 验收时记录实际配置版本和判定依据。“长期保存”和“不可修改”在 M0 中至少要求业务界面及正常接口不提供物理删除或覆盖历史事实的能力，正式保留年限在 M1 上线治理中确定。

1. **机构与身份**：试点 AppID 正确进入试点机构，完成微信登录和手机号绑定；第二机构的账号、钱包和数据不能互访。
2. **机构充值**：真实扫码支付一笔小额充值，验证手续费向上取整、净额入账、重复回调不重复增加额度。
3. **正常投递**：真实设备完成扫码、冻结快照、首次开门前称重/前两图、投递、最终关门后称重/后两图和唯一完成事件上报；只创建一笔订单，人工审核后钱包只入账一次。
4. **连续投递**：同一用户无需重新扫码完成至少两个本地开关门轮次；验证中间轮次不上云、不建周期/订单、不上传重量或照片、不做普通满溢判断或云端再授权，整场最终只产生一笔归属正确的订单。
5. **负重量异常与纠错**：在某个本地轮次构造达到配置阈值的重量减少，验证只在最终完成载荷及订单中得到 `negativeWeightAnomaly=true`、没有独立异常事件或中间减少值；整场仍按首末重量结算，审核前负金额不扣款、审核后才扣款，再次纠错只按差额调整。
6. **断网与重复事件**：在设备完成前后模拟断网、重启和重复上报，验证门安全、原作业恢复、订单不重复且不归属后来用户。
7. **清运换袋**：完成扫码新袋、电磁阀通电解锁、意外关闭后在原操作再次解锁、换袋、人工关门、稳定称重、清运员最终确认和订单创建；验证无门磁推定边界、`SAFE_CLOSE` 不作用于清运门、解锁后重启需人工恢复，以及旧袋、新袋与新皮重可追溯。
8. **手动提现成功**：用户申请小额提现、人工审核、调起微信确认收款并真实到账；用户钱包、机构额度和微信单号一致。
9. **渠道异常**：通过可控模拟验证超时、重复回调、`FAIL`、`CANCELLED` 和状态乱序不会重复释放或消耗资金。
10. **平台资金不足**：通过渠道适配器模拟 `NOT_ENOUGH`，验证暂停新出款、当前资金保持冻结以及补资后使用原单号续办。
11. **安全故障**：模拟门无法关闭、称重不可用或本地数据无法写入，验证设备或投口停止服务且后台可以发现。
12. **重启恢复**：在充值入账、投递完成、清运完成和提现结算的关键边界重启相关进程，验证业务结果保持幂等一致。

真实资金验收使用事先批准的小额金额和指定账号；不得通过故意耗尽生产运营账户来验证 `NOT_ENOUGH`。

## 7. 外部依赖与一周风险

以下条件不由编写业务代码即可保证，应在范围确认后立即逐项核验：

| 外部依赖 | M0 门槛 | 允许模拟的范围 | 缺失影响 |
|---|---|---|---|
| 微信扫码支付 | 强制真实：创建真实充值二维码，并验证至少一次真实成功支付、回调和查单 | 超时、重复通知和失败码可模拟 | 无法完成机构充值与本地额度闭环 |
| 微信商家转账 | 强制真实：产品权限、二手回收场景、运营账户和安全 IP 就绪，并完成至少一次真实成功到账 | `FAIL`、`CANCELLED`、乱序和 `NOT_ENOUGH` 可通过渠道适配器模拟；原单续办规则仍须有官方依据 | 无法完成真实微信零钱到账 |
| 机构小程序 | 强制真实：AppID 体验版或正式版可用、绑定商户号，并能调起真实用户确认收款页 | 前端失败提示可模拟 | 无法验证机构身份与用户确认收款 |
| HTTPS 域名 | 强制真实：微信能够访问合法回调地址，并成功验签解密至少一笔真实通知 | 丢回调、重复回调可模拟 | 只能查单兜底，不能完成正式回调验收 |
| OneNet | 强制真实：真实设备完成至少一次服务下行、北向上行和后端业务确认 | 断网、延迟和重复事件可故障注入 | 无法完成真实设备闭环 |
| COS | 强制真实：至少一笔正常投递的四张照片成功上传并关联订单 | 单笔相机/网络故障导致的照片缺失可模拟且不得阻断订单 | 无法证明正常照片链路可用 |

| 真实试点资源 | 强制真实：具备第 2.1 节所列机构、设备、用户、工作人员和小额资金 | 第二台设备不是必需，可用第二机构测试数据验证隔离 | 只能完成模拟验证，不能宣称 M0 完成 |

如果外部审批或 MCU 能力在一周内无法就绪，应如实把结果标记为“软件模拟闭环”，不得与“真实闭环”混用。

## 8. M1 优先范围

M0 通过后，M1 按以下顺序推进：

1. 投递审核自动化模式和投递后自动提现；
2. 可配置权限的完整员工管理与小程序运营查看；
3. 设备现场安装验收、资产/实例生命周期和调拨；
4. 告警通知升级、远程诊断、受控升级和维护恢复；
5. 满溢长期运营、经营统计、资金导出和对账运营；
6. 公司自用上线检查、备份恢复、监控和试运行方案。

## 9. 已确认的范围决策

以下五项已经由项目负责人全部确认，后续不得在设计阶段自行扩大 M0 范围：

1. 一周 M0 是“单设备、少量指定用户、受监督的真实闭环”，不是正式生产上线。
2. M0 投递订单全部人工审核，手动提现免审阈值为 0；自动审核模式在 M1 开放。
3. M0 承诺手动提现，并在 `NOT_ENOUGH` 补资后由平台管理员人工确认恢复；投递后自动提现、免确认授权和自动余额恢复进入 M1。
4. 完整设备生命周期、远程升级、精细告警和完整权限配置进入 M1，但 P0 的门安全、可靠上报、机构隔离和资金幂等不能延期。
5. 外部能力缺失时只能标记为模拟闭环；只有真实设备、真实充值和真实微信零钱到账全部通过才算 M0 完成。
