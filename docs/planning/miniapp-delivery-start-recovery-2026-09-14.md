# 小程序投递启动状态恢复修正

## 问题事实

- 小程序首页当前只读取本地 `pendingDeviceEntry`，并不查询服务端是否仍有活跃投递会话。
- 本地记录只要含有投递会话或启动请求的幂等键，首页就统一显示“投递请求处理中”。幂等键用于标识同一次提交，避免网络重试重复触发设备动作。
- 本次请求第一次在旧投递尚未结束时收到 HTTP 409；该结果可能是同一请求仍待确认，所以小程序保留幂等键是合理的。
- 旧投递结束后，小程序用同一幂等键重试，目标设备已经离线，服务端明确返回 HTTP 422，且没有创建新投递会话。
- 当前客户端仅在第一次尝试收到 400、401、403、404 或 422 时释放幂等键。第二次及以后的明确拒绝不会清理，因此无效记录最长保留 24 小时，并被首页误认为正在处理。

## 修正规则

1. 只要服务端明确返回 400、401、403、404 或 422，就清理与该次请求完全匹配的设备、投口、幂等键和尝试次数，不再限制必须是第一次尝试。
2. 清理时仍核对当前缓存中的入口编号、投口、幂等键和尝试次数。旧请求较晚返回时不能清掉用户随后发起的新请求。
3. HTTP 409、网络中断、请求超时和服务端 5xx 继续保留原幂等键，以便用同一个请求标识核对结果，避免重复执行物理动作。
4. 首页区分两种状态：服务端已经受理时显示“投递进行中”；只有本地请求标识、结果尚未确认时显示“投递结果待确认”，避免把客户端恢复记录说成服务端正在处理。
5. 手机号验证属于服务端明确拒绝当前启动请求的情形。释放原请求后，用户完成验证时重新准备请求；用户取消验证时可以安全退出该入口。

## 验证场景

- 第二次请求收到 422 后，匹配的本地幂等键被释放，返回首页不再显示处理中卡片。
- 较早请求的错误响应不能清理较新的本地请求。
- 409、网络错误和 5xx 后仍保留原请求标识。
- 首页针对已受理会话和结果未知请求显示不同文案。
