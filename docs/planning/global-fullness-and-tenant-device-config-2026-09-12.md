# 全局满溢设置与租户设备配置权限

日期：2026-09-12。状态：已提交 `2d6c6c938e1c`，并部署为 `20260912094429-2d6c6c938e1c`；数据库 V70 和完整授权验证通过。

## 已确认目标

- 在「配置管理 → 满溢设置」增加平台统一设置：仅重量、仅红外、重量或红外任一满足；重量参与判断时设置满溢净重，单位千克，三位小数。
- 所有租户、机构、设备和投口采用同一套规则，不增加设备或投口覆盖项。空袋重量是每个投口实际测量的事实，仍分别保存。
- 租户负责人能够管理本租户各机构的设备日常参数。普通工作人员继续按实际授予的权限和机构范围操作。
- 页面默认只展示规则、必要状态和操作；说明放在控件旁的帮助提示。发布前显示影响范围和正在进行的业务如何处理。

## 现状核对

1. Web 只有平台和租户两个登录入口，没有独立的机构账号或机构密码。工作人员和租户负责人共用租户入口。
2. 创建机构只建立机构资料。机构管理员的操作步骤是：工作人员 → 创建工作人员（登录名、初始密码）→ 授权机构并设为机构管理员；用该工作人员账号从租户入口登录。
3. 后端 DeviceScopeAuthorizationService 已允许租户负责人对本租户所有机构执行设备配置管理；DeviceAssetDrawer 的 canConfigure 却排除了 tenant 视角，这是界面遗漏。修复时必须使用当前设备的 organizationCode，不能使用列表上另一个已选机构。
4. 已核对菜单、机构/人员/用户目录、投递与清运查询、资金与钱包、提现和审核配置的授权入口：租户负责人拥有本租户管理范围，未发现相同的机构高于租户限制。机构停用、业务占用和资金规则仍需遵守，权限更高不代表绕过业务条件。
5. 进一步追踪确认另一处界面遗漏：OrganizationUserStaffBindingPanel 只列出 STAFF，排除了租户负责人；但后端 TargetOrganizationUserBindingService.hasManagementPath 明确允许租户负责人绑定机构微信用户。本批移除该前端过滤，在候选列表标识租户负责人。之前将此项判断为账号限制不准确，已更正。
6. 租户负责人不能被普通工作人员授权页面降权、停用或重置密码，这是对主体账号的保护。绑定微信并不自动赋予现场清运身份；清运资格仍由机构用户的实际资格记录决定。
7. 目前满溢值来自投口配置；初始默认值是 50.000 千克、红外或重量任一满足，没有可编辑的统一设置。默认配置只影响新设备，不能当作全局同步。

## 实施设计

- 新增数据库全局策略和配置来源版本；保留旧配置与历史满溢事实，不回写历史。
- 初始统一规则采用现有默认值 50.000 千克、红外或重量任一满足。迁移为已有合格设备排队生成新配置，正式部署前可在迁移记录中审查该影响。
- 平台发布一次设置，系统按批次为已分配、验收通过且未停用/报废的设备生成完整新配置并交给现有可靠下发任务。离线设备等待联网；后来启用/分配的设备补齐当前策略。
- 初始配置、日常价格修改、平台修复和自动补偿都合并当前全局满溢规则。旧客户端携带投口旧值不能覆盖全局规则。
- 全局设置发布使用版本冲突检查、幂等提交和操作审计。进度区分等待下发、设备已保存、设备已应用、失败和阻塞，不能将配置生成完毕标为全部设备已生效。
- 已有投递/清运继续使用原业务固定的配置；新配置用于后续业务。修改规则不凭旧重量伪造新的满溢结论，已有满溢状态等待设备真实检测/清运后的报告更新。
- 设备详情移除单投口满溢编辑；保留名称、启停和价格编辑。租户与机构工作人员共用同一机构设备接口，后端继续校验账号、租户和目标机构。
- 修复上一批 DeviceAsset.listStatus 的响应契约必填可空声明，避免合同校验失败。

## 部署约束

1. 新后端需要先完成 V70 前向迁移与运行账号授权收敛，不能把需要 V70 的后端直接启动在 V69 上。应先备份并执行完整升级核对。
2. 初始统一值为 50.000 千克、红外或重量任一满足。新后端启动后会为已有合格设备生成对应配置，覆盖它们之前不同的投口满溢设置；需要在部署记录中明确这一实际影响。
3. 设置已应用不代表旧满溢结果已经重新检测。历史结果按原事实保留，后续真实设备报告决定是否解除已有满溢阻断。
4. 回退应用不能撤销设备已应用的配置；恢复旧判断规则应发布更高配置版本。数据库不以删除新表或改写历史配置作为回退方式。
