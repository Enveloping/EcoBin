## 本章统一边界

1. 目标后端仍是一个 Spring Boot 进程和一个 MySQL 主库。模块公开端口用于建立事实所有权、依赖方向和可测试边界，不把系统拆成微服务，也不引入进程内 RPC。
2. Java 模块端口、HTTP DTO、OneNet JSON 和 UART payload 是四种不同契约：可以表达同一业务身份和数值语义，但不能直接复用同一个类或让传输框架类型进入领域端口。
3. 强一致业务结果优先由同一数据库事务中的显式同步调用完成；外部系统和跨事务长流程继续使用已冻结的 inbox、唯一可靠任务、稳定业务身份和状态机。
4. 机器可读契约负责消除手写字段、枚举和数值单位漂移。它不替代需求、业务模型和人工可读接口设计；业务语义仍以本接口基线及其上游文档为准。
5. 当前先完成首个共同可运行版本。机器契约要从一开始保存，但跨语言契约 CI、完整自动契约门禁和自动 HIL 发布门禁不作为首版开发前置条件，具体节奏见 I-055。

## I-051 Java 模块公开 API

**修订后确认：其他业务模块只能导入目标模块的 `.api` 包；普通公开内容限于不可变命令、查询、结果、稳定业务身份、必要值对象和端口，不公开数据库或实现细节。为保留已冻结的内部 `BIGINT` 复合外键，唯一例外是本章 2.1 节定义的同线程、同事务强类型 FK 构造引用。**

### 1. 目标包边界

目标业务模块统一使用以下结构：

```text
org.enveloping.ecobin.<module>
├─ api/              # 唯一跨模块公开面
├─ application/      # 本模块用例、事务边界和协调器
├─ domain/           # 本模块业务规则与内部值对象
├─ infrastructure/   # Entity、Mapper、XML、仓储和技术实现
└─ web/              # 本模块 Web/小程序 HTTP 适配（如有）
```

跨模块允许导入：

- `.api.command`：写用例输入；
- `.api.query`：只读用例输入；
- `.api.result`：用例输出和只读投影；
- `.api.id` 或 `.api.value`：稳定业务 ID、金额、重量、版本等必要值对象；
- `.api.persistence`：仅放 2.1 节逐关系定义的受限 FK 构造引用，不作为普通业务 API；
- `.api.port`：由本模块拥有并提供给其他模块调用的能力，或本模块消费的外部能力抽象。

跨模块禁止导入：

- Entity、Mapper、Mapper XML、仓储实现和裸数据库主键；2.1 节的受限引用不得扩大为通用主键传递；
- `application`/`domain`/`infrastructure`/`web` 中的类；
- 内部 Service 实现、可变聚合和延迟加载对象；
- Spring MVC、Spring Security、MyBatis-Plus、OneNet、微信、COS 或 UART SDK 类型；
- HTTP `Result<T>`、HTTP Header、Cookie、状态码或 Controller DTO。

P0 不增加成对的 `*-api`/`*-impl` Maven 工程，也不使用 JPMS。物理隔离先依靠 Maven 依赖方向、包约定和代码审查；首版稳定后再按 I-055 引入自动包边界检查。

### 2. 公开类型规则

1. Java 21 公开命令、查询和值结果优先使用不可变 `record`；集合在构造时复制为只读快照，不能把内部可变集合返回给调用方。
2. 客户端可寻址资源和跨模块业务关联使用已经冻结的公开 UUID、业务编号或强类型包装，不能暴露内部 `BIGINT` 主键，也不能用登录名、手机号、设备 SN 或当前时间替代稳定身份。
3. 容易混淆的基础量必须在类型或字段名中带单位：分、克、万分之一元/千克、UTC `Instant`、版本号和摘要不得使用含义不明的 `long`/`String` 裸值传播。
4. 模块查询分页使用与 HTTP 无关的稳定查询结果，例如“条目 + 下一游标”；HTTP 适配器负责映射为 I-001 的响应封套。模块 API 不返回 Controller 专用 `Result`/`PageResult`。
5. 可预期业务拒绝使用稳定业务错误码并由 HTTP/任务适配层翻译；模块 API 不抛出或返回第三方 SDK 异常。未知技术失败保留原因果链，统一由框架层记录和映射。
6. 同一模块化单体内的 Java API 随一个仓库、一个版本共同发布，不为内部端口单独建立网络式版本号；不兼容修改必须在同一变更中更新所有调用方。

### 2.1 受限 FK 构造引用（DD-004）

目标数据库继续使用内部 `BIGINT` 主键和带租户/机构作用域的复合外键。DD-004 不把这些键提升为业务身份，而是为同库原子写入增加唯一的数据库身份例外：

1. 事实所有模块只能在同一进程、同一线程和一个已经开启的数据库事务内，创建按主体或关系强类型定义的 FK 构造引用。引用只携带构造目标复合外键必需的键分量，禁止退化为裸 `Long`、任意 `Map` 或可承载任何表主键的通用容器。
2. 该引用只能进入设计中明确点名的同步参与端口，使接收模块在当前调用栈中把键分量写入自己拥有表的 FK 列。引用对象本身不得持久化，也不得跨事务、跨线程或跨进程复用。
3. 公开 UID/业务号仍是寻址、授权、幂等、审计目标和跨事务恢复的唯一业务身份。FK 构造引用不得参与这些判断，也不能代替公开身份。
4. 引用不得进入 HTTP、OneNet、UART、微信、MQ、可靠任务 payload、缓存、会话、日志、审计正文、异常详情或异步闭包。该类型不适用上节“公开类型优先使用 `record`”的普通规则，应使用不可继承的关系专用类型，并避免 Jackson 可见属性或构造入口；不得实现 Java `Serializable`，其 `toString()` 固定脱敏且不得输出内部键值。
5. 该例外不允许接收模块查询事实所有模块的私有表、Mapper、Entity 或 Repository。新事务或异步处理必须先用公开业务身份进入事实所有模块的受控端口，并在新事务内重新取得当次引用。
6. 初版先以专用包、明确调用点、代码审查和测试限制使用范围；共同首版形成后再按 I-055 增加 ArchUnit/CI 自动检查。不得因自动门禁尚未建立而扩大例外。

该引用是实现期的受限协作契约，不是客户端可见资源，也不改变任何表的事实所有权。

### 3. 可信作用域

- 登录请求、OneNet 事件、微信通知和后台任务先由对应入口建立已认证的可信执行上下文；业务模块从框架提供的只读上下文访问主体、客户端受众、租户、机构和特权执行信息。
- 命令可以携带“要操作的机构/资源”作为业务目标，但不能让调用方传入任意 `tenantId`、角色或权限集合来构造可信上下文。
- 平台跨租户、租户跨机构和后台恢复必须分别走已经冻结的显式用例；不能通过传 `null tenantId`、关闭拦截器或伪造系统用户复用普通入口。
- 异步处理器从已持久化的受信来源和业务目标重建上下文，不能沿用早已结束的 HTTP ThreadLocal，也不能把原客户端提交的作用域字段直接当作授权事实。

## I-052 事务所有权与模块协调

**已确认：产生权威业务结果的模块应用用例负责开启事务，并在同一线程中通过下游模块公开端口完成必须原子成立的结果；强一致主链不使用异步进程内事件、`REQUIRES_NEW` 或隐式 Spring self-invocation 切断事务。**

### 1. 事务所有者

| 结果类型 | 主用例所有者 | 可同步调用的公开能力 |
|---|---|---|
| 租户、机构、工作人员、机构用户和授权 | identity | framework 的可信上下文、审计技术端口 |
| 独立设备管理、设备状态/物理观察归并及设备安全恢复 | device | identity 作用域能力、可靠任务技术端口 |
| 开始投递的唯一复合授权：跨域资格与 session/occupancy/frozen snapshot/command 原子成立 | recycling | identity、funds、device 的公开参与端口及技术端口 |
| 最终投递结果建一单及其审核纠错、清运记录及直接修改留痕、袋、基准和满溢 | recycling | identity、device、funds 的公开端口及技术端口 |
| 钱包、充值、提现、微信转账业务状态和平台出款闸门 | funds | identity 能力、可靠任务与审计技术端口 |
| 技术处置、对账、告警和一致只读概览 | operations | 各业务模块公开查询/受控恢复端口 |

主用例的 public 应用服务使用同一个 `DataSource` 和 `PlatformTransactionManager` 开启边界；被调用模块以默认加入现有事务的方式执行自己的规则和持久化。某个模块参与同一事务，不代表主用例可以直接访问该模块的 Mapper 或表。

PDD-001 修订后只覆盖**开始投递**：recycling 的 public 应用用例按 D-037 开启一次复合事务，锁定跨域资格并原子建立整场冻结快照、投递会话、整机占位和唯一 `START_DELIVERY_SESSION` 命令。recycling 只直接写自己的配置与订单业务表；identity、funds、device 分别通过自身 `.api` 参与端口锁定并写入本模块事实。device 唯一拥有并写入 session、occupancy、device command 和 physical fact；目标模型没有会话内云端分段作业。

设备屏幕“继续投递”是香橙派/MCU 本地动作，不存在后端继续处理用例、云端继续任务或第二次复合授权。最终唯一 `DELIVERY_COMPLETE` 属于另一条可信入站完成事务：recycling 以开始时冻结快照创建唯一订单和结束后满溢检测，并同步调用 device 参与端口验证/结束原会话、释放匹配占位和保存设备结果；资金模块在订单审核前不参与建单。该完成事务不是 PDD-001 的再次授权，也不得重新检查后来价格、袋、普通满溢或钱包来否定原整场结果。

### 2. 强一致调用规则

1. 订单审核/纠错与钱包差额、提现双侧冻结、清运完成与换袋/基准/检测 gate、设备结果与订单/业务确认意图等已冻结组合，必须通过显式同步端口在一个本地事务内完成。
2. 需要原子生效的下游调用不得改成 `@Async`、内存事件总线、提交后监听器或“先返回成功再补写”。这些机制只能承载不影响已承诺业务结果的派生通知。
3. 主链内禁止使用 `REQUIRES_NEW` 把审计、明细、占位、inbox 完成或 outbox 意图提前提交。技术尝试和外部调用结果可以在主事务之外使用独立短事务，但不能伪造或越过业务终态。
4. 数据库死锁、锁等待和可重试并发冲突按 D-036～D-040 重试整个短事务；不能只重放其中一个模块调用。
5. 对同一聚合的所有写入继续遵循数据库设计冻结的全局锁序。公开端口不能隐藏一条与主用例相反的加锁路径。
6. 开始投递必须保留 D-037 的逐节点锁序：identity 的 tenant/organization/miniapp → recycling 的 delivery config head → identity 的 organization user → funds 的 wallet → device asset 及下游。identity 的锁被配置 head 分成前后两段，不能粗化成“先锁完整 identity 模块”，也不能由 device 反向调用 recycling 或 funds。设备本地继续不进入该锁序；最终完成按 D-037 已冻结的结果归并锁序处理原会话、订单、容量和确认意图。

### 3. 可信入站的事务闭环

OneNet 和微信入站保持以下两个事务边界：

```text
integration 验证/解密/规范化
  → operations 可靠写入 inbox
  → 返回传输层 ACK

可靠处理器领取原 inbox
  → 调用权威业务模块公开用例
  → 业务事实 + inbox 完成 + 必要可靠任务/业务确认意图同事务提交
```

- `integration` 不在写 inbox 前直接改订单、清运、钱包或机构资金。
- 第二段由权威业务用例控制业务事务；它通过 framework 中的稳定技术端口，把 inbox 完成、审计和唯一可靠意图加入当前事务。实现这些端口的 operations 代码必须参加调用方事务。
- 若业务事务回滚，inbox 保持可重试且不得标记完成；若业务已完成但传输响应丢失，同一稳定身份再次到达时只重放已有结果。
- 同一 JVM 内不额外复制一条“领域事件总线”作为强一致真相。确需跨事务传播的事实使用已冻结的唯一可靠任务及稳定业务键。

### 4. 查询协调

- 单模块页面由事实所有模块的公开查询端口提供。
- operations 的最小运营概览可以在专用只读 `REPEATABLE READ` 事务内同步调用各模块查询端口，形成同一数据库快照；它不能导入其他模块 Mapper，也不保存第二套可修改统计真相。
- 普通业务查询仍使用冻结的 `READ COMMITTED`、稳定游标和创建水位规则，不能为了方便返回内部实体或跨模块拼装可写对象。

## I-053 技术端口、外部端口与组装

**修订后确认：审计、可信上下文、inbox 完成和可靠任务登记等跨域技术能力通过 framework 中的最小稳定端口提供；OneNet、微信和 COS 等外部能力端口由需要该能力的业务模块定义、由 integration 实现，第三方协议类型只留在 integration。唯一的业务端口归属例外是 DD-004 定义的首次机构用户原子创建参与扩展。**

### 1. 端口归属

| 端口类别 | 接口由谁定义 | 实现由谁提供 | 例子 |
|---|---|---|---|
| 跨模块业务端口 | 拥有业务事实的模块 | 同一业务模块 | 钱包差额、设备占位、机构授权、订单查询 |
| 源聚合原子创建参与扩展 | 创建源聚合的模块 | 依赖该模块的下游事实模块 | identity 定义 `OrganizationUserRegistrationParticipant`，funds 实现空钱包初始化 |
| 稳定技术端口 | framework | operations 或 framework 基础设施 | 读取可信上下文、追加审计、完成 inbox、登记唯一可靠动作 |
| 外部能力端口 | 消费该能力的业务模块 | integration | 微信登录、Native 支付、商家转账、OneNet 下行、COS 临时授权 |
| 外部入站适配 | integration | integration | OneNet/Pulsar 消费、微信通知验签解密、外部结果规范化 |

端口放置遵循“业务规则决定需要什么，适配器决定如何调用第三方”，不能因为某个 SDK 先被引入就让 integration 反向定义业务状态机。

PDD-001 的复合事务协调者不因此取得其他模块端口的定义权。identity 定义并实现作用域与机构用户锁定能力，funds 定义并实现钱包资格锁定能力，device 定义并实现 session/occupancy/command/frozen snapshot 的开始事务参与能力；recycling 只按 D-037 协调调用。最终结果另使用 device 定义的会话验证/完成参与端口。所有参与端口以 `REQUIRED` 语义加入当前事务，不开启新事务、不返回 Entity/Mapper，也不在 framework 建立通用业务协调器。

### 1.1 首次机构用户原子创建参与扩展（DD-004）

为了同时保持 `funds → identity` 的 Maven 依赖方向和“机构用户与空钱包同事务”，DD-004 确认以下唯一扩展：

```text
identity 开启首次注册事务
  → 写入新的机构用户和不可变注册归因
  → 调用 identity.api.port.OrganizationUserRegistrationParticipant
  → funds 实现加入原事务，使用当次强类型 FK 构造引用创建唯一零余额钱包
  → identity 创建会话
  → 共同提交
```

- 只在首次实际创建机构用户时调用一次；重复 `wx.login` 不再次调用，也不把该扩展用于补写、修复或更新现有用户。
- 参与者是目标组装中的单一必需 Bean，不按 `List` 注入，不提供动态注册表，不允许演变为通用事件总线或 `afterCreate` 插件链。
- funds 实现不得回查 identity 私表；参与命令只包含公开业务身份、创建钱包所需的受信事实和 2.1 节限定的当次 FK 构造引用。
- 参与失败时机构用户、钱包和会话整体回滚；不得异步补建钱包，也不得使用 `REQUIRES_NEW` 或提交后监听器。
- identity 只依赖自己声明的接口，funds 依赖 identity 并提供实现，bootstrap 只负责装配，因此既有 Maven DAG 不增加反向边。

除这个已点名场景外，跨模块业务端口仍遵循“事实所有模块定义并实现”。新增其他源聚合参与扩展必须重新形成明确设计决策，不能类推 DD-004。

### 2. 技术端口限制

1. framework 只保存跨业务域稳定且确有多个调用方的技术抽象，不保存订单、清运、钱包或提现专用接口。
2. 审计、inbox 完成和可靠动作登记必须能加入调用方现有事务；端口实现不得偷偷异步、吞错或开启新事务。
3. 审计端口接收已经结构化、已脱敏的动作和目标，不接收任意 Entity、整份请求对象或秘密正文。
4. 可靠动作端口只登记稳定动作类型、业务键、请求摘要和必要快照；执行 attempt、退避和租约由 operations 管理，业务模块不自行再建第二份重试表。

### 3. 外部端口限制

1. 外部端口返回 EcoBin 规范化结果，明确区分“已受理、处理中、明确终态、结果未知、可重试失败和永久失败”；禁止只返回一个容易误用的 `boolean success`。
2. 微信 `transaction_id/out_bill_no`、OneNet 请求证据、COS 对象信息等确需保留的渠道标识转换为项目值对象；SDK 请求、响应、异常和证书对象不得穿过端口。
3. 入站消费者与出站客户端是独立适配器。OneNet 消费者只负责可信收件，不能同时注入业务内部 Service；微信通知入口也不能绕过 inbox 直接结算资金。
4. integration 可以读取外部调用所需的秘密引用，但永久密钥、设备 Key、AppSecret、APIv3 密钥和临时凭证不能进入稳定业务快照、普通日志或模块 API 结果。
5. Fake/Stub 只能在开发和测试组装中提供；真实验收和生产缺少真实适配器配置时必须失败启动或保持对应能力不可用，不能回退为占位成功。

### 4. Spring 组装边界

- 各模块显式导出自己的配置和公开实现，bootstrap 负责最终装配；任何模块不得依赖 bootstrap。
- integration/operations 对 framework 或业务外部端口的实现通过构造器注入，不使用全局 Service Locator，也不以 Bean 名字符串进行业务路由。
- 目标依赖 DAG 仍以系统架构 A-006～A-010 为准；本章不增加反向依赖。需要外层实现而内层调用的能力通过内层定义的端口反转依赖。
- identity 注入自己声明的单一注册参与接口、funds 提供实现 Bean 属于上一节的受限依赖反转；它不允许 identity 导入 funds，也不允许 bootstrap 承担业务协调。

## I-054 机器契约的单一来源与生成物

**已确认：HTTP 使用 OpenAPI 3.1，OneNet 使用强类型 JSON Schema，UART 使用单一机器注册表；实现阶段从这些来源生成或自动校验代码模型、平台物模型和人类文档，避免各端各写一套字段与枚举。**

### 1. 计划中的契约目录

详细设计阶段按以下逻辑建立仓库内 `contracts/`，具体拆文件方式可随大小调整，但每个协议面只能有一个权威机器来源：

```text
contracts/
├─ http/
│  ├─ openapi.yaml
│  └─ schemas/
├─ onenet/
│  ├─ envelope.schema.json
│  ├─ events/
│  ├─ commands/
│  └─ thing-model.mapping.yaml
├─ uart/
│  └─ uart-registry.yaml
└─ examples/
   ├─ http/
   ├─ onenet/
   └─ uart/
```

该目录尚未在本阶段创建；创建、生成器选型和现有文件迁移进入详细设计与任务拆分。

### 2. HTTP：OpenAPI 3.1

- OpenAPI 是 HTTP 方法、路径、参数、请求/响应 DTO、状态码和稳定字符串错误码的机器来源，覆盖 Web、普通/清运小程序、工作人员小程序以及精确外部通知入口。
- 安全方案分别声明 Web Cookie + CSRF、小程序 Bearer 和外部签名入口，不能用一个全局 Bearer 模型掩盖差异。
- OpenAPI 只描述传输 DTO。可以生成客户端类型、Mock 或做实现校验，但不从 OpenAPI 生成领域聚合、Mapper、模块 `.api` 命令或数据库 Entity。
- 已冻结的公开 UID、金额/重量单位、UTC 时间、游标和异步状态必须在 Schema 中有明确格式、范围和示例；示例不得包含真实 OpenID、手机号、密钥或商户数据。

### 3. OneNet：强类型 JSON Schema

- 使用 JSON Schema Draft 2020-12 表达规范事件头、规范命令头以及每种事件/命令专属 payload；禁止通用任意 Map 或嵌套 JSON 字符串。
- `eventUid`、`commandUid`、作业 UID、部署内序号、Schema 版本、整数克、摘要和照片槽位等规则必须同时进入 Schema 约束和人工文档。
- 当前 `docs/iot/onenet-thing-model.json` 和 Markdown 是旧运行协议。正式实现时从目标 Schema 生成或校验 OneNet 控制台物模型、Java 规范模型、Python 3.11 模型和文档；切换时整体替换旧写协议，不保留生产双写。
- OneNet 外层传输字段与 EcoBin 规范业务字段分层保存。平台消息 ID、MQTT Packet ID 或 Pulsar 元数据不进入业务 Schema 的稳定身份。

### 4. UART：单一消息注册表

- `uart-registry.yaml` 固定 I-046～I-050 的帧版本、message type 数值、flags、能力位、错误码、payload 字段顺序/宽度/符号/单位/范围和配置分段规则。
- MCU C 与香橙派 Python 3.11 的枚举、常量和编解码器由注册表生成，或由同一注册表自动校验；两端不能各自维护一份手写编号表。
- CRC 参数、big-endian、最大帧长、负重量、定点单价、ACK/NACK、HELLO 和状态快照必须有机器样例。生成物注明来源版本与摘要，便于 MCU 和香橙派在进度不一致时确认自己实现的契约版本。
- Java 后端不直接解析 UART，但 OneNet/中心模型对作业 UID、重量单位、故障和配置摘要的无损映射必须能够由共享样例核对。

### 5. 生成物和人工文档

1. 权威机器源由人工评审修改；生成文件带“不要直接编辑”标记和源摘要。确需手写实现时，必须提供本地校验命令证明其与机器源一致。
2. 为支持 MCU、香橙派、后端和前端错峰开发，首版允许把必要生成物提交到仓库；各端不必在构建时安装另一端工具链。
3. 人工接口章节解释业务原因、状态机和失败恢复；机器 Schema 解释可校验结构。两者冲突时先停止实现并修订同一决策，不能默默选择更容易编码的一份。
4. Schema 版本、规范化和摘要算法必须有明确输入范围；临时凭证、传输 attempt、日志字段和动态 URL 查询参数不得混入稳定业务摘要。

## I-055 首版契约治理节奏

**调整后确认：首个共同可运行版本形成前，不强制增加跨端契约 CI、完整自动契约检查或自动 HIL 发布门禁；待首版跑通并形成共同基线后，再在后续升级中逐步加入黄金样本、自动契约检查和发布门禁。**

### 1. 首版形成前

- HTTP、OneNet 和 UART 机器契约仍按 I-054 保存为单一来源，但允许后端、香橙派和 MCU 依据实际进度分批实现。
- 契约变更通过同一仓库文档、Schema 版本/摘要和人工联调记录协调；不要求每次提交都等待所有端完成，也不要求首版前先跑通完整自动契约套件。
- 不把跨语言黄金样本全集、契约 CI、ArchUnit CI 或自动 HIL 套件设为“开始写首版代码之前必须完成”的条件。
- 在首版尚未对真实使用者开放时，可以协调修改尚未发布的 1.0 草案并同步所有已实现端，不为开发中的旧草案建立兼容层。

### 2. 仍不可延期的验证

“不设置自动门禁”不等于可以跳过真实资金和物理安全验证：

1. 某条纵向切片进入真实联调前，相关端至少完成本地编译、必要单元/集成测试和人工协议样例核对。
2. 真机投递门开关/超时关门、投递多轮本地继续与最终一次上报、清运电磁阀通断/人工确认、重启恢复、称重和 UART CRC/重试必须在实际启用前人工验证并保留结果；清运锁断电不得当作门磁验收。
3. 真实机构充值、微信通知验签、商家转账和渠道终态必须按 P0/M0 已冻结场景小额验收；不能用“尚未建 CI”降低资金边界。
4. 任何已知契约不一致都不能在生产中以默认值、旧协议回退、伪成功或跳过校验临时掩盖。

这些属于业务验收和安全底线，不是本章暂缓的自动契约 CI/HIL 治理。

### 3. 首版共同基线形成后

后续升级再按风险逐步引入：

1. 建立 Java 21、Python 3.11 和 MCU C 共享的最小黄金样本，先覆盖变更频繁或风险最高的 UART、OneNet 身份/摘要和金额/重量边界。
2. 在 CI 中只对受影响的协议面运行 Schema、生成物漂移、模块包边界和跨语言样本检查，再逐步扩大覆盖面。
3. MCU 与香橙派都完成共同 1.0 基线后，把关键真机冒烟和 HIL 套件提升为发布门禁，而不是要求当前单边进度等待尚不存在的完整平台。
4. 共同基线发布后，破坏性变化提升 major；向后兼容的可选新增提升 minor；不改变线格式的说明或样例修正提升 patch。未协商兼容版本的端保持不可激活，不做生产协议猜测。

何时宣布“首版共同基线形成”、CI 使用何种平台、黄金样本清单和 HIL 设备池属于后续详细设计/版本治理事项，本章不提前锁定。

## 本章明确不设计

- 每个 Java 接口、record、Bean 或包的最终类名；
- 具体 OpenAPI/JSON Schema/UART Registry 生成器及脚本语言；
- CI 平台、分支保护、自动契约检查范围或评审人数；
- MCU HIL 台架、电路注入设备和自动化控制软件；
- 把模块公开端口部署为 RPC、消息服务或微服务；
- 为首版开发中的旧草案建立生产兼容层；
- 以机器 Schema 反向修改已经冻结的业务需求、事实所有权或资金/安全不变量。
