## 5. 现场验收顺序

### 5.1 先确认 OneNet 模型

导入文件必须是：

`contracts/onenet/generated/onenet-thing-model.candidate.json`

其 SHA-256 必须为
`39e793b1a72f64ed70a3e8a202d4cf8e38369d3cd98b5c3f944cac45fab030a5`，大小为
173777 字节。导入后人工确认 0 个属性、17 个同步服务、21 个事件；尤其确认下面四项存在：

- 开始业务程序更新；
- 取消业务程序更新；
- 业务程序更新进度；
- 业务程序更新取消结果。

控制台导入结果无法从 Git 或后端数据库推断。没有项目负责人确认时，不开启下发。

### 5.2 写卡、回读和基础业务

1. 用户明确确认 Windows 磁盘 1 后，运行固定写卡脚本；
2. 脚本重新核对 USB 类型、非系统盘、容量、序列号和源镜像摘要；
3. 写入后必须对前 2571108352 字节做完整回读并得到相同 SHA-256；
4. 设备冷启动，完成热点网页接入、厂家验收和封存；
5. 先完成一次普通投递和一次普通清运，证明新镜像没有破坏基线业务。

写卡属于不可逆覆盖操作，不能在用户睡眠或未确认目标磁盘时执行。

### 5.3 设备只读门禁

把仓库中的设备预检脚本传到香橙派后执行：

```bash
sudo bash audit-v30-device-remote-business-readiness.sh
```

脚本只有在以下事实全部成立时输出 `v30-device-remote-readiness=PASS`：

- 硬件运行时、永久通信代理和永久更新器均为 v30 对应版本；
- 永久通信代理和更新器正在运行，出厂和旧直连服务没有运行；
- 两个永久服务都真正启用了远程业务更新；
- 通信代理已经连接 OneNet，且只把业务更新命令交给更新器；
- 业务程序通过本机代理工作，永久作业闸门为打开状态；
- 没有活动投递、清运、MCU 更新、业务更新、维护锁或未确认物理动作；
- 正式公钥摘要正确，私有 COS 域名可以解析，存储空间足够；
- 下载和解包暂存目录为空。

任何一项失败都先修原因，不能为了继续测试跳过检查。

### 5.4 生产只读门禁

部署本轮后端/Web 修复后，在服务器执行：

```bash
sudo /usr/local/sbin/ecobin-business-remote-readiness \
  '<当前应用 Release ID>' '<当前应用完整 Git commit>'
```

它要求 V66/131 张领域表、v30 已认可、v29 已移除、`0.3.0-rc.3` 精确可用、没有未结束计划，
并确认真实下发仍是关闭状态。

### 5.5 开启受控单设备窗口

只有 5.1～5.4 全部通过时才执行：

```bash
sudo /usr/local/sbin/ecobin-business-release-dispatch \
  enable --controlled-single-device-test
```

脚本会先拒绝任何未结束计划，再备份配置、重新暂存秘密、执行生产预检、通过 systemd 重载应用
并等待两个容器健康。失败会自动恢复旧配置。

必须在开关开启以后创建测试计划，因为每条计划都会保存“创建时是否允许真实下发”的快照。
先前在关闭状态下建立的计划不能通过后来开开关获得下发权。

每个测试计划只填写一台“先验证的设备”，把“后续参与灰度的设备”留空。这样计划只会影响
这一台设备，也不会进入尚未实现的后续批次。单设备成功后计划应自动显示“更新计划已完成”，
不会再停留在“等待人工放行”。

## 6. 建议的真实场景顺序

先执行不会改变已安装版本的场景，最后才做成功更新和故意失败回滚：

| 顺序 | 场景 | 谁在什么情况下发起 | 必须看到的结果 |
|---:|---|---|---|
| 1 | 设备暂时离线 | 在创建并启动单设备计划前暂时断开设备云连接，随后恢复 | 后端沿用原命令和更新编号重试；恢复连接后设备只受理一次 |
| 2 | 工作中等待并安全取消 | 设备已有一笔投递或清运时启动更新；候选包准备好后由管理员点“安全取消” | 旧业务先完成；取消在快照前生效，计划停止，设备重新允许新业务 |
| 3 | 下载授权失效与续期 | 用受控限速让下载连接保持有进展但无法在 30 分钟期限内完成；不要用立即拒绝连接的断网方式 | 更新器到期后删除不完整文件并报告需要新授权；后端沿用更新编号，生成更高授权序号和新的临时 URL |
| 4 | 正常更新和重启恢复 | 使用健康发布启动新计划；在观察期内重启永久更新器 | 更新器从持久账本继续同一观察窗口，不重复快照或切换；最终安装 rc.3 |
| 5 | 后端暂时收不到事实 | 候选已完整下载后短时断开云连接，让设备本地继续 | 后端保持业务暂停、不猜测成功；重连后按序收齐进度和实际安装事实 |
| 6 | 故意不健康发布 | rc.3 成功后，创建并批准一个发布顺序大于 3、启动必然失败的受控测试发布 | 新程序健康检查失败，自动恢复数据库和 rc.3；计划显示验证失败，不开放错误版本 |

重复消息由第 1、3 场景中的可靠重试自然产生，也可在 OneNet 调试窗口重发同一个命令编号。
设备必须返回原受理/终态，不得重新下载已验证包、重新建快照或再次切换。不要修改命令编号、
更新编号、包摘要或发布编号来伪造“重复”；那是新的或冲突的命令。

下载授权失效测试按已确认的 30 分钟生产参数执行，本身必然超过 30 分钟。立即断网会在三次
临时失败后提前请求新授权，能够验证失败重试，但不能证明旧 URL 到期；所以第 3 项必须使用
受控限速，并保证每次网络读取不超过设备端 30 秒读取超时。正常成功更新还需要完整 30 分钟
观察。监控时每次查询都有短超时并输出当前中文阶段，不能把一次长睡眠当成测试。

## 7. 故意失败发布的准备

不要预先创建、批准或下发故意失败发布。完成 rc.3 正常更新后再按下面顺序操作：

1. 在平台页面新建草稿，取得后端生成的发布编号和发布顺序；
2. 使用版本名如 `0.3.0-rollback-test.1`，确认发布顺序大于 3；
3. 在正式离线签名环境运行：

```bash
sudo bash build-v30-intentionally-unhealthy-release.sh \
  '<后端生成的发布编号>' '0.3.0-rollback-test.1' '<发布顺序>' \
  --intentional-unhealthy
```

4. 脚本核对固定源码 bundle、正式私钥权限和公钥指纹，构建 Linux ARM64/Python 3.11 包，
   签名并在导出前再次验签；
5. 通过平台页面把归档和 64 字节签名上传到后端自动生成的私有 COS 路径；
6. 依次点击“开始校验”和“批准”，再建立只有当前设备的计划；
7. 回滚完成后，把故意失败发布归档，不能作为普通候选继续保留。

该测试允许恢复更新前数据库快照，可能丢失观察窗口内尚未上传的一笔本地业务数据。这是已经
确认的“设备可恢复性优先”取舍。测试前不得存在真实未完成投递或清运。

## 8. 每个场景的完成判据

一次场景只有同时满足以下四层事实才算完成：

1. 设备更新器记录到明确终态，且没有活动更新、维护锁或未确认物理动作；
2. 永久通信代理把进度和实际安装事实交付到 OneNet，发件箱没有遗留；
3. 后端部署记录、实际安装事实和兼容性投影一致；
4. 后端业务准入恢复允许后，再完成一次普通投递和清运。

“后台命令发送成功”“OneNet 返回成功”“页面出现更新成功”任意一项都不能单独代替这四层
事实。故意失败场景还必须看到 `databaseRestored=true`，并确认当前版本仍是 rc.3。

## 9. 关闭测试窗口

所有已经开始的设备更新必须先到达成功、已取消、已恢复上一版、已推迟、已拒绝或安全锁定等
明确终态。随后执行：

```bash
sudo /usr/local/sbin/ecobin-business-release-dispatch \
  disable --controlled-single-device-test
sudo /usr/local/sbin/ecobin-business-release-dispatch verify-disabled
```

关闭脚本发现未结束计划时会拒绝修改，避免后台停止调度而设备仍在半途中。关闭以后再做生产
只读核验，并保留脱敏的发布编号、计划编号、设备终态、实际版本和测试时间；不记录设备密钥、
临时 URL 查询参数、COS 凭据或签名私钥。

## 10. 本轮明确不做

- 不向后续设备批量推广，不实现或验收后续灰度批次；
- 不在线更新永久通信代理或永久更新器；
- 不设计签名密钥轮换和泄露处置；
- 不允许业务发布包修改 systemd、操作系统、设备密钥或永久信任根；
- 不支持跨 EdgeStore 数据结构版本的破坏性迁移；第一版继续要求新旧结构版本相同。

这些是已确认的首版边界，不是本轮遗漏。
